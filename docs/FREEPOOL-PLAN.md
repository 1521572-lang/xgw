# XGW Free Pool: план реализации

Основа — ТЗ «XGW Free Pool» v1.1 (28.10.2026, требования R01–R56, этапы F01–F16, сценарии
FP01–FP55). Ниже — как оно ложится на нынешний код (ветка `freepool` от `tspu2`, а не `d327aa4`,
под который ТЗ написано) и решения заказчика, которые меняют ТЗ.

## Решения заказчика (28.10.2026)

1. Бесплатный режим — **альтернативный режим работы**, переключаемый, «приложение внутри
   приложения». После испытаний — замена подписки примерно на 90 %.
2. **Подписка остаётся несущим каналом управления**: списки серверов на закрытых сайтах
   (VPN Gate, VPNBook), профили и учётные данные качаются через неё. Трафик пользователей в
   бесплатном режиме идёт только через бесплатные серверы.
3. Делать всё по ТЗ, включая OpenVPN (OpenVPN отменён решением 9).
4. **VPNJantit убран** (по отчёту вехи М1): учётку он выдаёт только формой на сайте, на 7 дней;
   без неё ни одного рабочего сервера («фактически платный»). Вместе с ним убрано поле
   «Выданные ссылки» в панели.
5. **Списки серверов с GitHub** (после отчёта М2а): «добавь списки с GitHub, экономия трафика для
   этих серверов не нужна»; исправления М2а и списки — одним ТЗ. Из названных заказчиком
   barry-far отключён GitHub, Epodonios удалён; взяты `igareck/vpn-configs-for-russia`
   (проверенные в России «чёрные списки») и `mahdibland/V2RayAggregator` (Eternity.txt).
   Источники пула — списки GitHub, VPN Gate и VPNBook.
6. **Суточный предел подключений OpenVPN — 96, а не 60 из R29** (29.10.2026, по отчёту М2а.3):
   серверы защищает предел «2 в час на источник», а 60 останавливали наблюдение на 9 часов в
   сутки (ASSUMPTIONS п. 261).
7. **Трафик через пул — сначала одно устройство** (29.10.2026, план М2б): в панели у
   выбранного устройства — «через бесплатные серверы», остальной дом идёт через подписку;
   весь дом одним переключателем — следующим шагом.
8. **OpenVPN для трафика — отдельным шагом** после серверов списков (29.10.2026): из четырёх
   туннелей М2а.4 данные прошли у одного, а постоянным туннелям нужны тёплый резерв и плавная
   смена.
9. **OpenVPN убран из XGW, у VPN Gate — SSTP** (29.10.2026, веха М2в): «можно убрать из сборки
   openvpn как неэффективный в условиях тспу», «отказаться от openvpn в пользу более
   эффективных протоколов». Из протоколов VPN Gate взят MS-SSTP (TLS по TCP — для DPI это
   HTTPS); L2TP/IPsec не взят — режется так же, как OpenVPN; родной протокол SoftEther —
   запасной шаг, если SSTP не оправдается.

## Архитектура

```
устройства LAN, сама машина, Docker, tailnet
  → перехват XGW (TPROXY/TUN, как сейчас)
  → Xray: балансировщик бесплатного пула (участники и запасные — бесплатные серверы)
      ├─ VLESS, Trojan, VMess, Shadowsocks (списки GitHub, ключи Outline у VPNBook) — обычные
      │  outbound'ы Xray; Hysteria2 и TUIC (списки GitHub) — через sing-box, как сейчас
      └─ SSTP (VPN Gate; до М2в — OpenVPN) — SOCKS-мост к изолированному работнику:
           пространство имён службы xgw-fp@<gen> ← veth → хост (NAT, ACL: только адрес:порт)
             sstpc (TCP от root, затем xgw-vpn) ↔ pppd (root, /etc/ppp пуст) → PPP fpt0
             SOCKS-работник (Xray, свой пользователь) → только через fpt0
  Xray: серверы подписки (несущий канал) ← http-in на 127.0.0.1
      ← демон: каталоги, профили, учётки (никакой трафик пользователей сюда не маршрутизируется)
```

## Бэкенд OpenVPN (веха М2а; с М2в туннель — SSTP, раздел «Веха М2в»)

Веха М2 делится на два шага. **М2а** — настоящая проверка серверов OpenVPN в изолированном
пространстве имён, пока в режиме наблюдения: трафик по-прежнему идёт через подписку. ТСПУ
распознаёт и режет сам протокол OpenVPN, поэтому сначала нужно увидеть на машине заказчика,
сколько серверов вообще подключаются. **М2б** — трафик через пул по переключателю (выбор,
поколения, резерв, пустой пул — закрыто с предложением вернуть подписку).

Поведение OpenVPN здесь не проверяется: пакет openvpn не ставится ни в WSL, ни в контейнер
(решение заказчика 28.10.2026). Конфиг пишется по руководству OpenVPN 2.6, агент — с юнит-тестами
на подставных работниках. До решения о минимуме проверок у разработчика ядро Linux
(пространство имён службы, veth, TUN-устройство с владельцем, правила nftables, самопроверка
охраны) один раз проверено стендом в WSL с подставным OpenVPN; дальше всё это — в ТЗ М2а на
машине заказчика («живое поколение», см. «Как проверяется»).

```
служба xgw-fp@<gen> (root, PrivateNetwork=yes — своё пространство имён, PrivateTmp; возможности
CAP_NET_ADMIN, CAP_SETUID, CAP_SETGID, CAP_CHOWN, CAP_KILL; NoNewPrivileges; /run — только
чтение, кроме /run/xgw/fp/<gen>) — агент `xgw pool agent <gen>` (freepool/agent.py):
  1. охрана nftables (inet xgwfp): всё закрыто; на выходе — отказ со счётчиком по отправителю
     (refused_ovpn, refused_socks, refused_other — ответы ядра); служебный IPv6 ядра —
     тихий сброс (dropped_v6): IPv6 внутри не нужен никому (М2а.2, по отчёту М2а.1);
  2. постоянный TUN fpt0 с владельцем xgw-ovpn; маршрута по умолчанию нет; фаза «guarded»;
  3. ждёт veth от демона: fpi<idx> 10.250.<idx>.2/30, маршрут только к адресу сервера /32;
  4. самопроверка охраны (R46): от пользователей работников — к серверу без туннеля, наружу, к
     хосту, к интерфейсу управления; закрыто = «нет маршрута» или отказ с ростом счётчика;
  5. OpenVPN от xgw-ovpn: конфиг собран заново из разобранного профиля (ifconfig-noexec,
     route-noexec, disable-dco, pull-filter для маршрутов и DNS, auth-retry none); конфиг и
     учётка — в /tmp службы (у каждого поколения свой), root:<группа работника>, 0640
     (memfd не годится: Xray читает конфиг только по пути, проверено);
  6. управление OpenVPN — 127.0.0.1 внутри своего пространства имён: CONNECTED — адрес на fpt0
     и маршрут по умолчанию в fpt0; RECONNECTING/EXITING — маршрут убран (закрыто);
  7. при первом CONNECTED (М2а.1, по отчёту М2а) — проверка изнутри от пользователя SOCKS: TCP к
     Cloudflare:443, DNS сервера (dhcp-option из PUSH_REPLY) и Cloudflare — итог в журнал и
     состояние, без адресов; затем SOCKS-работник — Xray от xgw-fps (socks 10.250.<idx>.2:1080,
     пароль, UDP; выход — только fpt0, ForceIPv4: без системного резолвера (М2а.3); DNS —
     ответивший первым, затем 1.1.1.1 и 8.8.8.8);
     готов — когда порт слушается (/proc/net/tcp), без подключения к нему (М2а.2);
  8. пока туннель поднят — счётчики fpt0 и охраны в состоянии раз в 2 с; при остановке или
     отказе — итог туннеля одной строкой (пакеты в туннель и из него, канал к серверу после
     подъёма — счётчики fpi, предупреждения OpenVPN, ошибки канала данных,
     отбитое охраной после подъёма по отправителю), в состоянии — раньше фазы failed: демон
     пишет туннель и вид изнутри в запись и при отказе работника. Отказ до подъёма: вырос
     refused_ovpn — GUARD_BLOCKED (дефект шлюза; код по журналу OpenVPN — рядом), нет —
     код OpenVPN (HOST_UNREACHABLE — ICMP с пути, не дефект).
демон (хост, CAP_NET_ADMIN, freepool/backend.py): задание /run/xgw/fp/<gen>/manifest.json
(0600); адрес сервера — в набор fp_peers таблицы ip xgw (адрес . протокол . порт) и в
/run/xgw/fp/peers.json; veth fpv<idx> ↔ fpi<idx> (внутренний конец — в пространство имён агента
по PID, только после фазы «guarded»: PID службы известен раньше, чем systemd создаёт
пространство имён); 10.250.<idx>.1/30. В ip xgw: из fpv* в WAN — только к fp_peers, ответы —
обратно, маскарадинг 10.250.0.0/16 (только при free_pool.mode не off).
проверка: временный Xray (http-inbound → socks к 10.250.<idx>.2:1080) — загрузка и страна выхода;
трафик — по счётчикам fpv<idx> (внешние байты вместе с рукопожатием); поколение — убрать всегда.
пределы (R26, R29): туннель — один за шаг, 12 подключений в час, 96 в сутки (в R29 — 60;
решение заказчика, М2а.4), 2 в час на источник; профиль VPNBook — через несущий канал, раз в сутки.
```

Бэкенд не годится (нет OpenVPN, пользователей, службы, пересылки IPv4 — шлюз без сети LAN,
или набора fp_peers — перехват не загружен) — серверы OpenVPN проверяются как в М1, только
доступностью адреса; причина видна в карточке, `xgw pool` и `xgw diag` («Бесплатный пул»).
ufw: при включённом — правило `route allow in on fpv+ out on <wan>` (с подтверждения при
установке; «+» в имени интерфейса ufw принимает — проверено по его исходнику); точные адреса
и порты задаёт таблица XGW.

**Отчёт М2а** (`docs/TEST-REPORT-REAL-MACHINE-0.2.0-freepool-m2a-2026-10-28.md`): изоляция,
охрана, пределы, секреты и повторная установка — без замечаний; 4 туннеля VPNBook поднялись, но
через них не прошло ни одного запроса (наибольший трафик проверки — 0,0 МБ, за 16 попыток 114
пакетов к серверам — только рукопожатия). По отчёту не отличить блокировку OpenVPN после
подключения (автор списков igareck пишет, что OpenVPN в России «не работает уже давно») от
обрыва в шлюзе — отсюда проверка изнутри и итог туннеля (шаги 7–8). «No route to host» к двум
серверам VPN Gate — тот же ответ, что даёт отказ охраны (admin-prohibited), но порт и протокол в
конфиге и в правиле охраны одни: вероятнее ICMP с пути; теперь их различает счётчик охраны.

## Веха М2в: SSTP вместо OpenVPN

Решение 9. Всё вокруг туннеля — пространство имён службы, охрана, veth, самопроверка, проверка
изнутри, SOCKS-работник, счётчики, пределы подключений — остаётся из М2а (проверено отчётами
М2а–М2а.4); меняются клиент туннеля и источник серверов.

```
источник VPN Gate: страница www.vpngate.net/en/ (через несущий канал, раз в 15 мин)
  → таблица с «DDNS hostname», строки по 10 ячеек; берутся серверы с SSTP:
    имя *.opengw.net, IPv4, порт («SSTP Hostname : имя[:порт]», 443 не пишется), страна по флагу
  29.10.2026: 100 серверов, SSTP — у 72, SSL-VPN — у 94, L2TP — у 17; Япония 42, Корея 25,
  Россия 10, Евросоюз 2 → при регионе EU к трафику годятся единицы
служба xgw-fp@<gen> (как в М2а, плюс TemporaryFileSystem=/etc/ppp:ro /run/sstpc,
DeviceAllow /dev/ppp, /dev/ptmx, char-pts):
  1. охрана: к адресу и порту сервера — только root (TCP-сокет sstpc создан до сброса прав),
     xgw-vpn — никуда; SOCKS — только в fpt0; отбитое — refused_vpn, refused_socks, …
  2. veth, маршрут /32 к серверу; самопроверка (SOCKS и xgw-vpn — к серверу, хосту, наружу);
  3. sstpc --log-stderr --log-level 2 --ca-path /etc/ssl/certs --host <имя> --user vpn
     --password vpn --priv-user xgw-vpn --priv-group xgw-vpn --ipparam <gen> <адрес>:<порт>
     file /tmp/xgw-vpn/ppp.options — SNI нет (без --tls-ext), цепочка сертификата — по
     системным, pppd: ifname fpt0, nodetach, logfd 2, noauth, noipdefault, nodefaultroute,
     noipv6, require-mschap-v2 (прочая проверка подлинности — refuse-*), без сжатия, эхо LCP
     10 с × 3;
  4. адрес на fpt0 — туннель поднят: маршрут по умолчанию в fpt0, проверка изнутри (DNS —
     другой конец PPP и Cloudflare), SOCKS-работник; адрес пропал — LINK_LOST (без
     переподключения);
  5. отказ — код по выводу sstpc и pppd (AUTH_FAILED, CERT_VERIFY_FAILED, SSTP_REFUSED,
     PPP_TIMEOUT, CONNECT_*, HOST_UNREACHABLE…) и строка-улика без адресов.
установка: пакет sstp-client (тянет ppp), пользователи xgw-vpn и xgw-fps.
убрано: разбор и сборка профилей OpenVPN, страница OpenVPN VPNBook и её учётка, профили и
итоги проверок OpenVPN на диске (удаляются при запуске пула).
```

**Проверка М2в.1** (`docs/TEST-PLAN-REAL-MACHINE-0.2.0-freepool-m2v1.md`) — наблюдение, трафик
через подписку: установка ставит sstp-client и xgw-vpn; живое поколение (свойства службы,
пустой /etc/ppp, /dev/ppp, сброс прав sstpc, охрана); сколько подключений SSTP поднимают туннель,
проходит ли проверка сертификата без SNI, передаёт ли туннель данные, страны пригодных;
остатки OpenVPN убраны; секреты; выключение без следов. По итогам — регион для VPN Gate и
переход к М2б.3 (туннели SSTP постоянными выходами) или к родному SoftEther.

**Отчёт М2в.1** — главный вопрос не решён: агент передавал sstpc несуществующий ключ
`--ca-dir`, клиент завершался при разборе строки, все 18 подключений — UNKNOWN. **М2в.2**
(ASSUMPTIONS п. 264): ключ `--ca-path` (сверено с исходником sstp-client 1.0.18 и 1.0.20), код
SSTPC_ARGS для отказа самого клиента, подключения туннелей за сутки — журналом, а не по
вариантам текущих снимков. Проверка — тот же вопрос, что у М2в.1:
`docs/TEST-PLAN-REAL-MACHINE-0.2.0-freepool-m2v2.md`.

## Веха М2б: трафик через бесплатный пул

Итог М2а (отчёт М2а.4): изоляция и охрана OpenVPN доказаны, шлюз доводит ответы сервера до
туннеля; из списков GitHub в каждом прогоне работают 25–28 серверов EU. Трафик через пул
вводится в три шага (решения 7 и 8), каждый — со своим ТЗ:

| Шаг | Что | Подписка |
|---|---|---|
| **М2б.1** | Одно (или несколько) устройство — через серверы списков и ключи Outline | Остальной дом, сама машина и каналы демона — как сейчас |
| **М2б.2** | Весь дом одним переключателем | Только несущий канал: каталоги, профили, обновления |
| **М2б.3** | Туннели SSTP (VPN Gate; до решения 9 — OpenVPN) как постоянные выходы пула | Как в М2б.2 |

### М2б.1 — устройство через бесплатные серверы

```
устройство с выбором «Бесплатные серверы» в панели (managed.routes[адрес] = "pool")
  → перехват XGW (как сейчас) → Xray, правила по порядку:
      DNS, частные сети, direct_* (российские домены .ru/.su/.рф — напрямую, как у всех)
      source [адрес] → балансировщик «pool»            ← новое
          участники и запасные — допущенные серверы пула (outbound'ы Xray; Hysteria2/TUIC —
          мостом sing-box, как у подписки); теги pool-<страна>-<отпечаток>
      пул пуст → source [адрес] → block (закрыто)      ← R05: прямого WAN нет никогда
  остальные устройства, сама машина, http-in/socks-in демона → «auto» (подписка), как сейчас
```

- **Допуск** (часть R30): свежая проверка шлюзом — OK или SLOW не старше 3 часов (серверы
  списков перепроверяются раз в 2 часа); страна по фактическому выходу — в регионе пула
  (strict: только он); ядро — Xray или sing-box; Xray его принимает (`xray run -test` сборки,
  как у подписки); **адрес — IPv4 в ссылке**: сервер добавляется в работающий Xray через API, а
  закрепление имени (dns.hosts) вступает в силу только перезапуском (ASSUMPTIONS п. 262).
  OpenVPN в М2б.1 не участвует (решение 8). Никаких показателей из каталога или имени
  сервера.
- **Выбор и смена** — движком XGW, как у основного балансировщика: пробы ядра
  (burstObservatory) отсеивают мёртвых для новых соединений; закреплённый основной — самый
  быстрый живой участник (0.1.9), смена — когда он умер или по правилам скорости без прыжков
  (xgw-speed-policy); запасные повышаются как у подписки. Скорость серверов пула замеряется
  обычным замером (экономия их трафика не нужна — решение 5). Существующие соединения при
  смене доживают на старом сервере (R06).
- **Состав «pool»** — до 8 допущенных (OK раньше SLOW, затем скорость проверки), сначала уже
  применённые; все — в балансировщике, живых выбирают пробы ядра, закреплён один (умер —
  сразу закрепляется другой живой). Пересборка — раз в минуту демон сверяет допущенных с
  применёнными: у устройства закрыто при допущенных — не чаще раза в 3 минуты, сервер выпал из
  допущенных или есть место — не чаще раза в 10 минут. Смена состава — через API ядра
  (outbounds pool-* и routing), без перезапуска Xray; пробы ядра для пула включаются по
  наличию устройств, а не серверов.
- **Пул пуст** — у устройства закрыты зарубежные сайты; в карточке и в списке устройств —
  предупреждение и кнопка «Вернуть на подписку» (сам шлюз не переключает).
- **DNS устройства** в М2б.1 идёт прежним путём (DoT через «auto»): DNS — не выход для
  пользовательского трафика, а его смена задела бы весь дом. В М2б.2 — через пул.
- **Свой сервер устройства (Ф4)** и «Бесплатные серверы» — один выбор: у устройства либо
  сервер подписки, либо пул.
- **Панель**: в выборе сервера устройства — пункт «Бесплатные серверы» (только при
  включённом наблюдении: пул должен проверять серверы). При выборе — предупреждение один раз:
  владельцы бесплатных серверов неизвестны и видят, к каким сайтам идёт устройство; содержимое
  сайтов с https защищено, без https — нет; российские домены идут напрямую. В карточке
  «Бесплатные серверы» — устройства через пул, текущий сервер (страна, скорость, задержка),
  участники и запасные, последняя смена и её причина. События (Ф2): устройство переведено,
  сервер пула сменён, пул пуст — устройство закрыто, пул снова есть.
- **`xgw pool`** и **`xgw diag`** («Бесплатный пул»): устройства через пул, участники
  «pool», закрыто ли, совпадает ли применённый конфиг с желаемым.

### М2б.2 — весь дом

Режим `free_pool.mode = "on"` (переключатель в карточке с подтверждением; обратный — «Вернуть
режим подписок», подписки не удаляются — R02): «auto» собирается из пула, а серверы подписки
уходят в отдельный балансировщик «carrier» только для http-in/socks-in демона (каталоги,
профили VPNBook, подписки, обновления ядер) — пользовательский трафик через него не идёт.
DNS — через пул. Свои серверы устройств (Ф4) из подписки на время режима не действуют.
Сама машина и Docker — как все устройства. Пул пуст — закрыто для всех, кроме прямых
российских адресов, с предупреждением и кнопкой.

### М2б.3 — SSTP постоянными туннелями (до решения 9 — OpenVPN)

Поколение xgw-fp@ живёт, пока его сервер в «pool» (R31: PREPARED → READY → ACTIVE →
DRAINING → RETIRED); участник Xray — SOCKS к его работнику 10.250.<idx>.2:1080, как у пробы.
Активный + тёплый запасной (R36), всего поколений не больше `max_instances` (4, R38);
снятый сервер сливается: новые соединения — уже нет, старые доживают до 10 минут, через 30 —
принудительно (R38). Туннель упал — участник мёртв для проб ядра, работает запасной.
Предупреждения М2а.4 об OpenVPN (проверка сертификата, пароль управления, права учётки) с М2в
не нужны: сертификат проверяет sstpc по системным, управления и файла учётки нет.

### Что остаётся на М3

Формула рейтинга R32 и правила смены по качеству R35 (если испытания покажут нужду), эпохи
WAN R39, полный набор команд R50, восстановление (истёкшие учётки, холодный старт), сутки
наблюдения.

### Проверка М2б.1

- **Здесь:** юнит-тесты сборки (балансировщик «pool», правило по адресу, закрыто при пустом
  пуле, «auto» без серверов пула), допуска и состава пула, выбора в панели; `xray run -test`
  собранного конфига настоящим Xray 26.10.21 (факт, без которого не обойтись); ruff.
- **ТЗ на машине:** заказчик выбирает тестовое устройство; трафик этого устройства — только
  через участников «pool» (счётчики Xray по выходам), остальных — как прежде; российские
  домены напрямую; ни одного пакета устройства в WAN мимо Xray; смена закреплённого при его
  смерти; закрыто при пустом пуле (регион без пригодных серверов) с предупреждением и
  кнопкой; возврат на подписку; «auto» и подписка не задеты; секреты; выключение без следов.
  Заказчик пользуется устройством 1–2 часа и говорит, что открывалось и как.

## Как проверяется

Решение заказчика: проверок у разработчика — минимум, на машине заказчика — максимум.

- **Здесь:** юнит-тесты затронутых модулей (один прогон в конце правки), ruff и извлечение
  помощника из ТЗ с подсчётом его суммы. Стендов, полных прогонов и опытов здесь нет, кроме
  проверки факта, без которого код не написать.
- **На машине — ТЗ вехи** (`docs/TEST-PLAN-REAL-MACHINE-0.2.0-freepool-*.md`) с помощником,
  который только читает: установка и повторная установка (пакет, пользователи, шаблон службы,
  ufw), правила (fp_peers, форвардинг, отпечаток), **живое поколение** (свойства службы,
  возможности и пространство имён агента и работников, интерфейсы и маршрут внутри до и после
  подъёма туннеля, права файлов в /tmp службы, секреты в состоянии, veth и элемент fp_peers на
  хосте — по `/proc` и `systemctl show`, без входа в пространство имён), самопроверка охраны,
  подключения и их пределы, коды отказов, сброс в форвардинге, трафик проверок, секреты в
  журналах, оценка `systemd-analyze security`, панель, `xgw pool`, `xgw diag`, выключение без
  следов.
