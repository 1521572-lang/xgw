## 2. Как установить процесс записи без установки кандидата

Наблюдаем `/etc/xgw/xray/config.json`. Штатная запись в `paths.atomic_write_bytes` заканчивается `os.replace`. Следим за родительским каталогом, фильтруем конечное имя. Помощник использует inotify ядра, начинает слушать перед первым снимком, сравнивает inode, байты и содержимое JSON, сверяется с файлом раз в секунду. Если подписка недоступна, в отчёте будет `poll`. Для изменившихся секций в памяти строится unified diff с сортировкой ключей объектов и сохранением порядка массивов. В JSONL выходят названия секций и число групп изменений, секретные значения остаются в процессе. Отдельно видны перезапись идентичного содержимого и изменение одного лишь форматирования. [Наблюдатель](../helpers/xray_writer_observe.py) · [Семантика inotify](https://man7.org/linux/man-pages/man7/inotify.7.html)

Диагностический эквивалент при уже установленном inotify-tools — `timeout 185 inotifywait -m -q -e moved_to,close_write,delete,moved_from --format '%e %f' /etc/xgw/xray`. Для ТЗ достаточно помощника. Несколько событий между чтениями, смена каталога, очередь с переполнением либо polling ограничивают вывод о промежуточных версиях. Пустое окно off/off не закрывает вопрос про Selective.

**Лестница доказательств.**

1. Найти в приватном `watch.jsonl` событие целевого имени, относительное время, изменение inode/байтов и непустые секции. Различать количество событий ФС и количество наблюдавшихся версий.
2. В приватном `audit` искать успешный `SYSCALL` вместе с `PATH` назначения в том же audit serial. Для замены подтвердить целевой каталог и конечное имя, для записи на месте — операцию и объект. Сверить время с окном, PID, UID, exe, тип syscall и экземпляр службы. Открытие файла для записи само по себе слабее успешной замены с совпавшим наблюдением. Совпали несколько кандидатов — оставить источник открытым. Фильтр `ausearch -f` может пропустить относительные PATH. При известном ключе уже действующего правила искать по ключу в том же интервале и собрать CWD + PATH. Отсутствие audit-событий означает недостаток покрытия. [Формат запроса ausearch](https://man7.org/linux/man-pages/man8/ausearch.8.html)
3. По `unix` сопоставить с приватными `xgw.journal`, `xgw-xray.journal` и `events` из `state.db` в пределах ±2 с с учётом границ выгрузки. В базе читать `events(ts,kind)` через SQLite `mode=ro`; при необходимости локально посмотреть `detail` одной строки. Проверить boot и PID службы, фазы/возраст из `/run/xgw/watchdog-step.json`. Период измерить по меткам; ориентир — 20 с. Временное совпадение с `apply` даёт гипотезу о причине, известный PID Python ещё не различает pending, rebuild и обновление маршрута. По 200 строк на службу и 512 последних событий базы — предел покрытия.
4. Если исходное окно удаётся восстановить из пары `*-route-before.json` и `*-route-after.json` прежнего прогона, повторить чтение существующих журналов по их `unix`, сверив boot/epoch. Без audit-записи того времени ретроспективная атрибуция остаётся ограниченной. Если нужен новый audit watch, это отдельный **Mutating** на amd64 при доступном изменяемом audit и свободном ключе: ограниченное окно, transient guard до добавления, точный парный `auditctl -a always,exit -F arch=b64 -F dir=/etc/xgw/xray -F perm=wa -k xgw_writer_trial` / `auditctl -d always,exit -F arch=b64 -F dir=/etc/xgw/xray -F perm=wa -k xgw_writer_trial`, затем сверка `auditctl -l`. В этом варианте явно учитывать 32-битные процессы как пробел покрытия. В ближайшем Read-Only действуют только уже существующие правила.

**Три объяснения с проверкой.** (1) Тест версии подменяет `binary.installed_version`; при пустой версии каждая публикация статуса может повторить чтение, включая checkpoint и финал одного tick. Проверять смену inode бинарника, кеш успешного чтения и повтор после ошибки. (2) Прежняя заглушка отмены возвращала сам Event в `_scan`, а код читал `result.bytes_read`. Объяснение проверено для теста отмены. Для остальных требуются собственные сообщения и место отказа в паре JUnit. Кроме того, неразобранный `poke` и асинхронная сборка способны изменить момент видимости applied/scanned. (3) Рабочая полная сборка начинает с VPN и может пересоздать probe-inbound/outbound перед возвратом правила. Проверять связку секций и журнал реального применения при том же epoch. Проверить также путь pending и внешнего писателя. Счётчик теста версии не является измерением ни одной из этих записей.

**Короткий ретроспективный запрос.** В приватном каталоге именно прогона CDN r2 выбери пару одного плеера. Для переменной `BEFORE` укажи его файл `*-route-before.json`. Команда сверяет epoch, три секции, длительность и правила на границах, затем возвращает последние записи демона за исходное окно. Сопоставлять только внутри подтверждённой загрузки машины. Если журнал уже ротирован, отметь пробел. Содержимое журнала остаётся в терминале стенда.

```bash
historical_writer() {
  local bounds begin end
  bounds=$(python3 -I - "$BEFORE" "${BEFORE%-route-before.json}-route-after.json" <<'PY'
import json, math, sys
from pathlib import Path
a,b = (json.loads(Path(p).read_bytes()) for p in sys.argv[1:])
assert a["xray_epoch"] == b["xray_epoch"]
assert a["client_zapret2_rule"] and b["client_zapret2_rule"]
x,y = a["config_sections_sha256"], b["config_sections_sha256"]
assert {k for k in x.keys() | y.keys() if x.get(k) != y.get(k)} == {"routing","inbounds","outbounds"}
assert 0 < b["unix"] - a["unix"] <= 300
print(math.floor(a["unix"]), math.ceil(b["unix"])+1)
PY
  ) || return
  read -r begin end <<<"$bounds"
  timeout 10 sudo -n journalctl --quiet --no-pager -u xgw.service --since="@$begin" \
    --until="@$end" -n 100 -o short-unix
}
historical_writer
```

## 3. Допуск изменений и лечение test_daemon

Выбор — строгие проверки контракта плюс полное сравнение остальных тестов с базой в том же окружении. Обе копии на кандидате, в контрольной копии восстановлены ровно три поставляемых файла из `3a00777`. Одинаковые pytest, права, фикстуры и относительное имя basetemp. Любой новый отказ, смена содержательной диагностики, потеря теста, новый skip или повреждённый JUnit блокирует Deploy. Пассивное чтение установленного шлюза идёт независимо. [Команды двух прогонов](XRAY-CONFIG-WRITES-2026-11-20.md) · [Сравниватель](../helpers/acceptance_test_gate.py)

- **(а) Починка всех 17 одним PR** объединяет причины разной природы и задерживает наблюдение. Разобрать владельцами отдельных групп — отмена/таймеры, ротация, восстановление перехвата. Для ротации записывать решения, очередь сборок, следующий tick и итоговый состав. Для fail-closed проверить фактический результат правил и число повторных загрузок. Ни один совпавший отказ не считать закрытым.
- **(б) Contract/legacy** использовать как разделение ответственности. В r3 оба набора уже обязательны. Для временно известных отказов учитывать exact nodeid, сигнатуру и место проверки, базовый SHA, владельца Codex, условие снятия и пересмотр при следующем релизе. Выносить в отдельный список лишь после повторения на ThinkCentre. Для ежедневной эксплуатации проверки перехвата, VPN fallback и маршрута обязаны пройти положительный и отрицательный контроль.
- **(в) Уточнение gate** — сохранять приватно тип исключения, тестовую функцию и нормализованную строку assert, публиковать только класс причины. Всплывший после AttributeError новый assert — `NEEDS_TRIAGE`. Критерий допуска — исправленная общая фикстура с повторным парным прогоном, либо подтверждённая починка на кандидате. Не игнорировать AssertionError целиком. Подкрепить тестами сравнивателя: разные численные результаты блокируют, смена типа блокирует, идентичные причины совпадают, падение→успех допускается, неполный сбор блокирует. `aedb68c` уже убрал адреса объектов из критичных сообщений и исправил заглушки. Полный r3 на ThinkCentre ожидается.

## 4. Короткая серия для скорости и разных CDN

Общий предел **600 с**, каждый запрос имеет таймаут. До старта взять свежий приватный формат 720p для маршрута, проверить остаток срока, itag, кодек и допустимые байты. Использовать один видеоряд и начальное смещение. Записывать HTTP-код, Content-Range, фактический протокол, TLS, TTFB, байты по 5-секундным корзинам, скорость после первых 5 с, буфер и stalls. Размеры указывать в байтах, скорость — Б/с, битрейт медиа — бит/с. Контроль для вывода о запасе — скорость / (битрейт / 8). `speed_download` по всему запросу и медиана чтения mpv измеряют разные величины. Исторические 200 КБ/с сами по себе не устанавливают лимит CDN или провайдера. [Отчёт плеера](../reports/2026-11-20T043221Z_headless-playback.md)

Определять ASN по актуальному префиксу, а не по первому октету. Для проверки TTL-зависимости в отдельном Deploy менять только один из уже принятых профилей воркера с тем же peer. Одна разница RTT или TTL не доказывает эффект fake_md5 |

Итого 580 с, 20 с резерв. Если при дешёвой пробе выбран новый узел, исходное сравнение закончить как несопоставимое. Пример штатной команды — `python3 -m docs.helpers.headless_playback "$FORMAT" probe --bytes 65536`; потребовать ровно 206/65536. Для curl хранить signed URL в приватном config, шаблон `curl -q --config "$URL_CFG" --http2 --range 0-8388607 --max-filesize 8388608 --max-time 25 -so /dev/null -w '%{http_version} %{response_code} %{size_download} %{time_appconnect} %{time_total}\n'`. Для профиля скорости брать интервальные байты сокета или клиента. Опыт согласовать с остатком квоты каждого маршрута, задать общий предел объёма до первого запроса; нехватку квоты отмечать SKIP. Плеер и извлечение входят в бюджет. Две смены режима сюда не входят; измерять на уже допущенном маршруте либо заранее проверенном служебном входе. Если второй путь недоступен, межмаршрутный вывод открыт.

**Устойчивость без ручного IP.** Использовать TTL DNS и срок подписи, привязывать успешный 206 к hostname, конкретному peer, профилю, ревизии политики и тестируемому пути. Кешировать только до меньшего срока. При промахе, TLS timeout или исчерпании бюджета — существующий VPN fallback. Очередь допуска максимум на два свежих peer, одна проба одновременно, отрицательная запись с backoff; вторую пробу оплачивать из `daily_probe_mb`. Переключение по ASN отложить: текущая клиентская маршрутизация Xray доменная, один CDN-host может вернуть несколько IP. Для peer-specific fallback сначала доказать совпадение адреса пробы с адресом нового медиапотока; иначе применять действующий доменный fallback. Ранжирование профилей по классу peer — будущий изолированный опыт, только после повторяемого выигрыша на двух назначениях и проверки квоты.

## 6. Приёмка и совместимость

Предлагаемые пороги для текущего 720p и этого стенда. Устойчивость считается по прогонам с известным маршрутом. Результат одного проверенного peer остаётся действительным только для его окна.

| Измеряемый допуск | Требование к отчёту |
|---|---|
| Воспроизведение | На двух свежих CDN peer минимум по одному старту 900 с и seek ещё 300 с. 720p ≥99% пригодного времени, прогресс ≥98%, stalls ≤1%, ни одного непрерывного stall >5 с. Связать хотя бы один медиапоток каждого нового старта с ожидаемой группой, подсчитать несопоставленные |
| Fallback и возврат | 3 из 3 контролируемых отказов — новый медиазапрос по VPN с 206/65536 за ≤20 с. После возвращения годного peer — свежий active и корректный новый поток за retry_seconds + 2 фактических интервала watchdog, без ручного выбора IP |
| Записи Xray | В трёх стабильных 120-секундных окнах без изменения политики — 0 необъяснённых семантических перезаписей и 0 необъяснённых смен маршрута. Переход/ротация — объяснить каждую смену по секциям и источнику, повторить испорченное окно. Фиксировать знаменатель и полноту наблюдения |
| Квота | За 24 ч расход штатных проб ≤ настроенного daily_probe_mb × 1048576 Б; нет проб при исчерпании лимита. Отдельно учесть диагностические Range-загрузки и медиатрафик; таймаут/повтор тоже имеет цену |
| Целостность | До, в активном режиме и после восстановления `xgw diag` с FAIL=0; обычный HTTPS через VPN доступен во всех контрольных точках. По окончании исходные SHA и режим, число воркеров, guard и контроль VPN сходятся. IPv6 WAN на данном стенде отсутствует |

| Ф4, свой сервер устройства | В `generator/builder.py` правила source идут после прямых исключений и до обычного медиапути. `zapret2.patch` вставляет Selective перед медиабалансировщиком/общим правилом.
