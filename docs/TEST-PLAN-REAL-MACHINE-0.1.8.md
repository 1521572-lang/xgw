# Программа испытаний XGW 0.1.8 на реальной машине

Задание для модели-тестировщика. Машина та же, что в прошлых отчётах: ThinkCentre, Ubuntu
24.04.5 LTS, Docker запущен, роутер HUAWEI AX2 — точка доступа с адресом от `xgw-dhcp`. На ней
стоит XGW 0.1.5 (отчёт `docs/TEST-REPORT-REAL-MACHINE-0.1.5-2026-10-15.md`) либо 0.1.7, если
программа `docs/TEST-PLAN-REAL-MACHINE-0.1.7.md` уже выполнена и её отчёт есть в `docs/`.
Задача — поставить 0.1.8 поверх и проверить:

- **0.1.6 — Xray 26.10.10** и восстановление TUN после запуска Xray: кейсы REAL-26…REAL-29
  программы 0.1.7, без изменений. Если отчёт 0.1.7 уже есть и эти кейсы в нём пройдены —
  не повторять;
- **0.1.8 — лимиты подписок, множители и резервный выход** (REAL-40…REAL-46). Они заменяют
  кейсы приоритета 0.1.7 (REAL-30…REAL-38): в 0.1.8 приоритет работает вместе со стоимостью
  серверов, и прежние ожидания на машине с подписками с лимитом уже неверны;
- **0.1.8 — уведомления только когда нужно действие** (REAL-47);
- короткую регрессию и тесты (REAL-48).

Итог — отчёт в том же формате, что и прошлые (раздел 7).

Читать до начала работы: ASSUMPTIONS пп. 181 (Xray 26.10.10), 182 (приоритет), 183 (лимиты,
множители, резервный выход), 184 (уведомления); README — разделы «Приоритет серверов»,
«Проверки серверов», «Уведомления и страница статуса», «Панель управления», «Разработка и
тесты».

## 0. Правила работы

Те же, что в программе 0.1.7 (§0 там), коротко:

1. **Сеть меняется только командами XGW** (`xgw install`, `enable`, `disable`, `net up`,
   `apply`, `update-xray`, `uninstall`), действиями в панели и правкой `/etc/xgw/config.toml`.
   Никаких `nft flush ruleset`, ручных правок чужих таблиц nftables, правил ufw и Docker,
   ручных `ip addr`/`ip route`/`ip link`, блокировки адресов серверов.
2. **Аварийный выход**: `sudo xgw disable`. Интернет пропал больше чем на 2 минуты, и кейс
   этого не ждёт — `disable`, время, `sudo xgw status`, `sudo xgw diag`,
   `sudo journalctl -u xgw -u xgw-xray -u xgw-net --since -15min`, дефект в отчёт.
3. **Секреты в отчёт не попадают**: адреса подписок, UUID, пароли, ключи, токены, в том числе
   токен панели. Имена серверов и отпечатки (8 hex) — не секрет. Перед коммитом отчёта —
   `grep` на `vless://`, `vmess://`, `trojan://`, `ss://`, `token=`. Исключение — ссылка
   ненастоящего сервера F (REAL-43): она придумана для теста и ничего не открывает.
4. **Код XGW не чинить.** Найденное — дефект в отчёте. Обход — только если без него дальше не
   пройти, и он описывается.
5. **Только фейковые данные.** Новых подписок не добавлять. Единственный добавляемый сервер —
   ненастоящий F из REAL-43.
6. **Квота заказчика.** В REAL-43 весь трафик машины и сети идёт через лимитированный сервер
   и тратит квоту подписки заказчика. Не дольше 15 минут; качать большие файлы в это время
   нельзя.
7. **Команды — те, что в программе.** Нужна команда, которой здесь нет, — только читающая
   (`cat`, `ls`, `ip … show`, `nft list …`, `systemctl status`, `journalctl`, `curl` к
   127.0.0.1). Ключи команд XGW не угадывать: `xgw --help`, `xgw <команда> --help`.
8. **Записывать точно.** Для каждого шага — время (`date +%T`), команда, вывод (существенная
   часть дословно), сравнение с ожиданием. Ожидание не совпало — дефект, и дальше, если
   следующий шаг от этого не зависит.
9. Telegram с настоящим токеном не проверяется.

### Как действовать в панели

Панель — `http://127.0.0.1:8781/` (ярлык «XGW» в меню приложений). Без графического сеанса —
запросами к панели с самой машины (токен в отчёт не записывать):

```bash
mkdir -p ~/xgw-0.1.8-test && cd ~/xgw-0.1.8-test
J=~/xgw-0.1.8-test/panel.jar
curl -s -o /dev/null -c $J "http://127.0.0.1:8781/?token=$(sudo cat /var/lib/xgw/panel-token)"
P() { curl -s -b $J -H 'X-XGW-Panel: 1' -H 'Content-Type: application/json' -d "$2" "http://127.0.0.1:8781/api/$1"; echo; }
S() { curl -s -b $J http://127.0.0.1:8781/api/state | python3 -m json.tool > ~/xgw-0.1.8-test/state.json; }
```

Действия: добавить ссылку — `P add '{"text":"<ссылка>"}'`; убрать ссылку —
`P link/remove '{"id":"<id из state.json, раздел links>"}'`; отключить или включить серверы —
`P servers '{"fingerprints":[…],"mode":"disabled"}'` (`"enabled"` — включить); приоритет —
`P priority '{"fingerprints":["<отпечаток>"],"level":"high"}'`; проверить запасные —
`P scan '{}'`; обновить подписки — `P refresh '{}'`. В отчёте указать, чем пользовались.

Где видны уведомления: каждое отправленное уведомление демон пишет в журнал с уровнем
WARNING, а событие без уведомления — с уровнем INFO. Отправленные за время кейса:

```bash
sudo journalctl -u xgw --since "<время начала кейса>" -p warning --no-pager
```

## 1. Что изменилось в 0.1.8

| Что сделано | Кейс |
|---|---|
| Подписка с лимитом трафика — та, что сообщает `total` больше нуля в заголовке `subscription-userinfo`; без заголовка или с `total = 0` — безлимитная. Ручные ссылки — безлимитные | REAL-41 |
| Множитель расхода — по имени сервера: `x10`, `х10` (кириллица), `×2`, `x0.5`; без отметки — x1. Шаблон — `filters.multiplier_regex`. У сервера безлимитной подписки стоимость 0 при любом множителе | REAL-41 |
| Порядок: безлимитные → лимитированные x1 → x10 → x100; ручной приоритет важнее стоимости. В балансировщике — только серверы одного (лучшего) класса | REAL-41, REAL-45 |
| Резервный выход: лимитированный сервер с наименьшим множителем — `fallbackTag` балансировщика. Ядро его не пробует. Все участники мертвы — Xray сам ведёт трафик через него (состояние `RESERVE`), участник ожил — сам возвращается | REAL-42, REAL-43 |
| Лимитированные запасные проверяются коротким запросом (`probe.trace_url`) и редко: кандидаты в резервный — раз в 6 ч и сразу, если трафик не идёт совсем. Плановый скан их не трогает | REAL-42 |
| Расход трафика проверок считается по подпискам с множителями: доля квоты, предупреждение «больше 10 % остатка» | REAL-42 |
| Уведомления — только когда нужно действие: «часть серверов недоступна», замены серверов, смена уровня и резервного — события в журнале без уведомления | REAL-47 |
| Панель: у серверов подписок с лимитом — метка множителя, у резервного — «резервный»; у подписки — «осталось N ГБ» или «Безлимитная»; в `RESERVE` — «Работает резервный сервер». `xgw status`/`servers`: «[x10]», «← резервный выход», строка «Резервный выход: …», «безлимитная» у квоты | REAL-41, REAL-43 |

## 3. Кейсы 0.1.8: лимиты, множители, резервный выход

### REAL-40. Подписки заказчика: какие с лимитом, какие нет

Через минуту после обновления:

1. `sudo xgw status` — для каждой подписки строка квоты:
   - «Квота «…»: израсходовано X ГБ из Y ГБ, осталось Z ГБ» — **подписка с лимитом**;
   - «Квота «…»: израсходовано X ГБ, лимита нет — безлимитная» или «Подписка «…»: безлимитная
     (лимит трафика не сообщает)» — **безлимитная**.
2. Панель, раздел «Подписки»: у подписки с лимитом — «Израсходовано … из …, осталось …» с
   полосой; у безлимитной — «Безлимитная …». Совпадает с п. 1.
3. Записать таблицу: подписка → с лимитом или нет → сколько серверов. От этого зависит
   **вариант** дальше:
   - **A1** — есть подписка с лимитом, у неё есть живые серверы (в `sudo xgw servers` у её
     запасных хоть одна проверка `OK`, или её серверы в работе), **и** есть безлимитная
     подписка с живыми серверами;
   - **A2** — подписки с лимитом есть, безлимитных нет;
   - **B** — все подписки безлимитные.

### REAL-41. Множители и классы на настоящих именах

1. `sudo xgw servers` — у серверов подписок с лимитом отметка «[xN]», у безлимитных — нет.
   Выписать 5–10 имён серверов подписки с лимитом и что показал XGW: имя → отметка. Отметка
   должна совпадать с числом после `x`/`х`/`×` в имени, без отметки в имени — `[x1]`.
   Расхождение — дефект: имя дословно, ожидание, что показано.
2. Кто в работе:
   - A1 → **все участники — безлимитные**, даже если их меньше `max_members`; ни одного
     «[xN]» среди участников;
   - A2 → участники — лимитированные **одного** множителя, наименьшего из тех, у кого есть
     живые (обычно x1);
   - B → всё как раньше: участников до `max_members`, отметок нет.
3. Резервный выход (A1, A2): в `sudo xgw servers` у одного запасного — «← резервный
   выход», внизу — строка «Резервный выход: spare-… «имя» (xN) — через него идёт трафик,
   только когда все участники не отвечают; ядро его не пробует». Ожидается сервер класса
   хуже участников с наименьшим множителем (при безлимитных участниках — лимитированный с
   наименьшим множителем). В панели у него метки «резервный» и «xN», подпись «резервный:
   через него пойдёт трафик…». Вариант B — строки «Резервный выход» нет (если приоритетов нет).
4. В конфиге Xray то же самое: резервный — это `fallbackTag`, и его нет среди проб ядра:

   ```bash
   sudo python3 -c 'import json; c=json.load(open("/etc/xgw/xray/config.json")); b=c["routing"]["balancers"][0]; print(b["fallbackTag"], b["selector"], c["burstObservatory"]["subjectSelector"])'
   curl -s http://127.0.0.1:10086/debug/vars | python3 -c 'import json,sys; print(sorted((json.load(sys.stdin).get("observatory") or {}).keys()))'
   ```

   Ожидается: `fallbackTag` = тег резервного (`spare-…`), `selector` и `subjectSelector` —
   `['proxy-']`; во втором выводе — только теги `proxy-…`, тега резервного нет. (Путь к
   конфигу Xray — тот, что показывает `sudo xgw diag`, если он другой.)

### REAL-42. Лимитированные проверяются редко и коротко; расход с множителями

Варианты A1 и A2. Наблюдение — 70 минут (можно параллельно с REAL-47, п. 1).

1. В начале — запомнить у запасных подписки с лимитом время последней проверки (`sudo xgw
   servers`, в скобках). Сразу после запуска демона их проверяли один раз — это перепроверка
   резервного (до 4 серверов); их вердикт — `OK`/`SLOW` с размером в сотни байт (короткий
   запрос), а не ~57 600 байт.
2. Через 70 минут (это больше `scan_spares_minutes = 60`): у безлимитных запасных время
   проверки **обновилось** (плановый скан), у лимитированных запасных класса хуже участников —
   **нет**. Исключение — если безлимитных участников нет: тогда запасные того же множителя,
   что участники, сканируются по расписанию, но тоже коротким запросом (сотни байт).
3. `sudo xgw status` — строки «Трафик проверок…» и «за месяц это ~N % квоты подписки «…»
   (~M МБ квоты в сутки с множителями)». В A1 доля квоты подписки с лимитом — **меньше 1 %**
   (её тратят только редкие короткие проверки). В A2 участников пробует ядро, и доля
   заметная: проба 57 КБ через сервер x10 уносит 576 КБ квоты; записать цифру и сверить с
   оценкой: участников × 57 620 Б × 2880 × множитель в сутки плюс сквозная проверка. Панель: «За месяц это
   меньше 1 % трафика подписки «…» (с учётом множителей серверов)». `sudo xgw diag`, строка
   «Трафик проверок» — то же, с пометкой «(с множителями серверов)».

### REAL-43. Резервный выход в работе

**Ожидаемая картина**: участник балансировщика — единственный безлимитный сервер, и он
ненастоящий (F), поэтому трафик сразу идёт через резервный лимитированный. Интернет при этом
**не пропадает** (короткий перерыв до 30 с при переключении конфига — допустимо). Длительность
кейса — не больше 15 минут (§0, п. 6).

Ненастоящий сервер F (адрес из TEST-NET-1, RFC 5737 — не маршрутизируется, гарантированно не
отвечает; ручная ссылка — значит, безлимитный):

```
vless://00000000-0000-4000-8000-0000000000f1@192.0.2.10:443?encryption=none&type=tcp#XGW-TEST-DEAD
```

**Вариант A1.**

Порядок важен: класс участников берётся от нынешних участников, поэтому F добавляется, пока
безлимитные включены (он попадает в их класс), и только потом безлимитные отключаются.

1. Во втором терминале — `ping -D 1.1.1.1 | tee ~/xgw-0.1.8-test/ping-43.txt`.
2. Добавить F в панели (поле «Вставьте адрес подписки… или ссылку сервера») или
   `P add '{"text":"<ссылка F>"}'`. Через минуту: F в `sudo xgw servers` — запасной или
   участник рядом с безлимитными (без «[xN]»); состояние `HEALTHY` или `DEGRADED` (если F
   стал участником — он не отвечает), но не `ALL_DEAD`. Засечь время.
3. Отключить все серверы безлимитных подписок, **кроме F** (F — ручная ссылка, у неё своя
   группа «Отдельные ссылки», её не трогать): в панели у каждой безлимитной подписки
   «Отключить все» (или `S`, затем отпечатки серверов этой подписки со статусом
   `member`/`spare`/`waiting` из `state.json` → `P servers '{"fingerprints":[…],"mode":"disabled"}'`).
   **Список отключённых отпечатков сохранить** в `~/xgw-0.1.8-test/disabled-43.json` — по
   нему включать обратно. Засечь время. Ожидается, в течение 2 минут:
   - `sudo xgw servers` — участник **один**: F (`proxy-xx-…`, «XGW-TEST-DEAD»), не живой;
     лимитированные — запасные; у одного из них «← резервный выход» (наименьший множитель);
   - состояние `RESERVE`: «серверы в работе не отвечают — трафик идёт через резервный сервер
     «имя» (xN); Xray вернётся к ним сам…». В панели — отметка «Работает резервный сервер» и
     плашка с тем же смыслом; кнопка питания остаётся зелёной;
   - интернет есть: `curl -s https://api.ipify.org` на машине — адрес выхода резервного
     сервера (записать; сравнить с адресами «до»); контейнер
     (`docker run --rm alpine wget -T 10 -qO- https://api.ipify.org`) и устройства за
     роутером — через VPN; `nslookup example.com` отвечает; адреса провайдера — ни разу;
   - тега резервного по-прежнему нет в `observatory` (команда из REAL-41, п. 4) — ядро его не
     пробует, хотя трафик идёт через него; тег F — есть.
4. **Лимитированных в балансировщик не берут.** 10 минут ничего не трогать, каждые 2 минуты —
   `sudo xgw servers`: участник всё время один — F; состояние `RESERVE`. Записать.
5. **Уведомления.** В первые 5 минут `RESERVE` — уведомлений нет. Через 5–6 минут — ровно
   одно: «XGW: резервный сервер» — «уже 5 мин трафик идёт через резервный сервер «…» (xN):
   серверы в работе не отвечают…» (на рабочем столе, если сеанс есть; в журнале — уровень
   WARNING, см. §0). Других уведомлений за кейс быть не должно.
6. Убрать F (панель — убрать ссылку `XGW-TEST-DEAD`, или `P link/remove`). Засечь время.
   В течение 2 минут: участники — лимитированные наименьшего множителя, состояние `HEALTHY`;
   событие и уведомление «серверы в работе снова отвечают — Xray вернул на них трафик с
   резервного «…» (xN)».
7. Включить обратно серверы из `disabled-43.json` (`"mode":"enabled"`, или «Включить все» в
   панели у тех подписок). Засечь время. В течение 6 минут: участники — снова безлимитные,
   событие (без уведомления) «снова отвечают серверы лучшего класса — в работе безлимитные
   серверы (были — лимитированные серверы x1)» (множитель — тот, что был у участников).
   Записать, через сколько секунд.
8. Остановить `ping`. Записать перерывы по `ping-43.txt` (все, дольше 5 с) и сопоставить с
   шагами.

**Вариант A2** (безлимитных подписок нет). Сделать участников мёртвыми, не трогая настоящие
серверы, нельзя: ненастоящий F (безлимитный) классом лучше нынешних участников, а класс
меняется на лучший только по удачной проверке — F её не пройдёт. Кейс пропустить и написать
об этом; переход на резервный проверяет стенд (REAL-44).

**Вариант B** (все подписки безлимитные — переход через резервный при приоритете, та же
последовательность, что в REAL-31…REAL-34 программы 0.1.7):

1. `ping` — как в п. 1 варианта A1. **B** — безлимитный запасной с последней проверкой `OK`.
2. `sudo xgw priority <тег B> high`. В течение 5 минут участник один — B (`[высокий]`);
   строка «Резервный выход: … (безлимит)» — сервер среднего уровня.
3. Добавить F, затем `sudo xgw priority XGW-TEST-DEAD high`. В течение минуты участники —
   B и F, оба `[высокий]`; F не живой; состояние `HEALTHY` или `DEGRADED`, уведомлений нет.
4. `sudo xgw priority <тег B> medium`. Засечь время. Ожидается: участник один — F; трафик
   сразу несёт резервный (средний уровень), состояние `RESERVE` (может мелькнуть между шагами
   watchdog); затем событие «на уровне «высокий» живых серверов нет — в работе серверы уровня
   «средний» (были — «высокий»)», участники — средние, `HEALTHY`. **Интернет не пропадает.**
   Записать время от команды до каждого события и перерывы по `ping`. Сравнить с REAL-34
   программы 0.1.7: там здесь был `ALL_DEAD` с перерывом до 2 минут.
5. Уведомлений за кейс быть не должно (§0, команда `journalctl -p warning`).
6. Уборка: `sudo xgw priority XGW-TEST-DEAD medium`, убрать ссылку F.

### REAL-45. Приоритет важнее стоимости

Только вариант A1.

1. Выбрать лимитированный запасной сервер **H** с наибольшим множителем, у которого последняя
   проверка `OK` (если таких нет — с любым множителем больше 1). Записать имя, тег, множитель.
2. `sudo xgw priority <тег H> high`. В течение 5 минут: участник один — H (`[высокий] [xN]`);
   событие (без уведомления) о смене класса; резервный — безлимитный сервер среднего уровня
   («(безлимит)» в строке «Резервный выход»); интернет — через H (`curl -s
   https://api.ipify.org`).
3. Через 3 минуты — `sudo xgw priority <тег H> medium`. Ожидается: сразу после сборки
   участниками могут стать лимитированные того же множителя, что у H (класс берётся от
   нынешнего участника), затем, после проверки безлимитных запасных, — снова безлимитные (в
   течение 5 минут); резервный — снова лимитированный с наименьшим множителем. Записать, кто
   был участником между этими шагами и сколько.
4. Записать времена. Кейс тратит квоту через H с множителем — не дольше 10 минут.
