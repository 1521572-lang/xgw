## Основание

Рабочая схема ThinkCentre/XGW→роутер→устройства, HEALTHY/on. У Flash доступен только
ThinkCentre. Потеря входящего интернета дольше минуты лишает модель возможности выполнить
следующую команду. Нужен заранее работающий локальный возврат on, не ручной rescue.
Свойства клиентов за LAN остаются отдельным вопросом; отсутствие клиента не означает
неисправность уже работающей раздачи.

Результаты U/V не обосновали продуктовый patch. Их принятие описано в
[review V](REVIEW-REAL-MACHINE-0.2.0-wave3v.md). Не продолжать серию одинаковых чтений
кэша/журнала ради получения общего PASS.

## Почему нельзя переиспользовать старую страховку

У [старого prepare](https://github.com/1521572-lang/xgw/blob/351fb54e074f4a7b497a8a4244fc74c6088788d7/tests/stand/wave3_safety.py#L51-L94)
явная предпосылка off. Его
[restore](https://github.com/1521572-lang/xgw/blob/351fb54e074f4a7b497a8a4244fc74c6088788d7/tests/stand/wave3_safety.py#L97-L137)
останавливает писателей, загружает off.nft и оставляет демон остановленным.
Результат always_off противоречит исходной рабочей схеме. Старые prepare/watch/window/
launch/restore не применять к on, не менять их исторические байты ради нового опыта.

Простой вызов xgw enable также недостаточен как независимая страховка:
[enable берёт net.lock и входит в _load](https://github.com/1521572-lang/xgw/blob/351fb54e074f4a7b497a8a4244fc74c6088788d7/src/xgw/net/capture.py#L749-L768),
[net.lock допускает ожидание30с](https://github.com/1521572-lang/xgw/blob/351fb54e074f4a7b497a8a4244fc74c6088788d7/src/xgw/net/capture.py#L240-L241).
Это часть устанавливаемого Python-кода и живого состояния; зависший писатель/неполная
установка могут сделать такой путь непригодным для бюджета восстановления.

## Решение: узкий scope и проверяемая цепочка

Первая будущая живая операция ограничена потерей **одной принадлежащей XGW capture-таблицы**.
Guard, RPDB, конфигурации, binaries/units, WAN/LAN/NM/sysctl/Tailscale/pin/pool и процессы
VPN остаются вне fault scope. Нельзя считать этот механизм готовым для D1-on установки,
сбоев ядра, guard deletion, глобального flush ruleset, TUN или reboot.

Цепочка допуска:

1. REC-A: чистый контракт и синтетические сценарии. Сейчас реализован только этот слой.
2. REC-B: приватный snapshot и read-only qualification на неизменном рабочем on.
3. REC-C: согласованный writer fence для всех писателей затрагиваемого поколения.
4. REC-D: независимый локальный driver, сначала без сетевых действий.
5. REC-E: конкретный ограниченный реальный fault/recovery-протокол после доказательств B–D.

Проверка A не подразумевает B–E. Состояние реальных предпосылок по умолчанию false;
неизвестное, missing, строка "true" и подтверждение только моделью не заменяют evidence.

### Контракт состояния

ARMED → FAULT_RUNNING → RECOVERY_DUE → RESTORING → VERIFYING → RESTORED_ON.
Раннее окончание job также ведёт к RECOVERY_DUE. Отсутствие job до истечения срока даёт
EXPIRED_UNUSED, после чего запуск fault запрещён. Отказ предусловий — REFUSED.
Ошибка snapshot/транзакции/проверки или истечение восстановления — FAILED, не RESTORED_ON.
В модели нет состояния RESTORED_OFF и нет операции продления срока через heartbeat.

Предлагаемый бюджет от вооружения: fault window15с, restore≤20с, verify≤5с,
hard deadline≤45с. Это требование и модель, а не измеренная гарантия Linux/systemd.
Clock монотонный; NaN/inf/отрицательные сроки/обратный ход невалидны. Перед живым опытом
необходимо подтвердить бюджет реальным driver, включая запуск, ожидания и таймауты.
Без гарантии исполнения при зависшем ядре/питании нельзя обещать возврат: такие сбои
исключаются из scope и не тестируются через единственный канал управления.

### Snapshot и гонки писателей

Снимок содержит только нужные для узкого scope данные: подтверждённый исходный on,
семантическую идентичность capture+guard/RPDB, поколение конфигураций и process/boot,
точную принадлежность таблиц и байты проверенной транзакции восстановления.
Только root0700/0600, обычные файлы без symlink, EXCL manifest, ограниченные размеры,
полный digest каждого входа. Все реальные адреса/правила/config остаются локальными.

Nft-транзакция должна восстанавливать свою capture-таблицу при её наличии И отсутствии,
сохраняя guard и чужие таблицы. Не использовать flush ruleset. Проверка nft -c сама по себе
не подтверждает пакетную работу и не разрешает переход к fault.

Слепой replay старого on при работающем демоне опасен: конфигурации, bridge endpoints,
Tailscale-маркеры и FreePool-поколения могли измениться. Однократная проверка digest перед
записью не закрывает гонку между проверкой и записью. Нужен writer fence с проверяемым
поколением, понятным владельцем и ограниченным временем жизни. Lease без интеграции всех
затрагиваемых writers не является fence. Нельзя удалять чужой lock или убивать демон ради
обхода этой задачи. Пока REC-C не решён, active fault gate остаётся закрытым.

### Независимость driver

Будущий driver запускается до fault отдельным локальным процессом/контуром, переживающим
выход terminal/controller. Его код заморожен, не импортирует меняемый XGW, не требует DNS,
удалённого API, связи модели, кэша подписок или работающего UI. Конкретный способ запуска
и зависимости служб должны быть отдельно реализованы и проверены на systemd255.
Не копировать сюда непроверенный systemd-run шаблон и не заявлять автономность по Popen.

Driver имеет только именованный scope; не восстанавливает WAN, не перезапускает NM,
не возвращает глобальный ruleset и не открывает прямой fallback. При сетевой ошибке
не делает off и не удаляет guard. Если возврат не подтверждён, результат FAILED/UNKNOWN.
Нельзя скрывать его успешным exit-кодом контроллера.

## Доставка и ограничения нынешнего W

REC-A находится в tests/stand/wave3_on_recovery_model.py: только stdlib, синтетические
bool/clock, без чтения/записи файлов, subprocess/socket/XGW imports. CLI только simulate.
Положительные proof flags существуют в явно названной synthetic fixture. Они не должны
переходить в будущий сборщик реальных предпосылок по умолчанию.

W переносит25 сценариев на реальную ThinkCentre, не вооружая driver и не создавая таймер.
Сохранение результата контроллером W — обычный пользовательский файл с синтетическими
данными. Результат runtime_recovery_implemented=false остаётся false даже при25/25.
Продуктовый runtime pin неизменен. WAN/LAN/Tailscale/службы/правила не меняются.
Подробные задания REC-B–E и критерии остановки — в
[PR spec](PR-SPEC-WAVE3-ON-RECOVERY.md).
