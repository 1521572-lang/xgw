# Сравнение двух исполнителей Flash на ThinkCentre

Цель — выбрать исполнителя для технической приёмки XGW. Оба получают одинаковый код, права, время, вопросы и инструменты. Модель самостоятельно запускает команды, интерпретирует наблюдения и оформляет отчёт. Код шлюза и тестов пишет разработчик. Участие в сравнении не меняет статус продуктовой приёмки.

## Условия пары

Координатор случайно назначает модели меткам A и B, записывает соответствие и точные версии моделей приватно до старта. Случайно выбирает, кто начинает. Выдать каждой только её карточку в **новом чате** с одинаковым доступом к терминалу, GitHub и клону. Запускать последовательно в одной сессии пользователя на ThinkCentre с Ubuntu 24.04 LTS, с одинаковыми путями к Python и Xray. Дать каждой до 25 минут активной работы и одинаковый лимит инструментов. Ожидание предоставления доступа и GitHub записывать отдельно. Подсказки, количество вмешательств и время фиксировать. Название модели, чужие сообщения, отчёты и журналы второго слота в задание не передаются. До сдачи разрешено читать свою карточку, этот протокол, собственные исходные данные и свои логи. Предыдущие отчёты с ответами и отчёт другого слота открывать после фиксации оценок. Изоляция чатов организационная, обе модели используют один аккаунт шлюза.

## Выполнение и отчёт

1. Запросить доступ при отсутствии терминала. В полном клоне XGW запустить блок своей карточки. Параллельный запуск получит `BUSY`. Выполнить его после окончания первого. Параметры `XGW_TEST_PYTHON` (интерпретатор с pytest) и `XGW_TEST_XRAY` (исполняемый файл) можно задать до запуска, если владелец установил их в другом месте. Установку пакетов, sudo, перезапуск сервисов и переключение VPN/WAN задание не предусматривает.
2. Стенд сверяет бандл SHA-256 и его Git-базу, запускает одни и те же два теста кандидата на исходниках двух ревизий, отдельный Xray на loopback и четыре HTTP-запроса к локальному серверу. Идентификатор сессии, начальный байт и порядок четырёх ответов создаются заново. Штатные службы читаются до и после. Время тестов и версия ядра Xray могут отличаться от предыдущих отчётов.
3. Сохранить обезличенный Markdown со своим анализом как `report.md` в приватном каталоге прогона. Начать со слота, round, UTC начала/конца, SHA карточки по ссылке из чата, SHA кандидата/контроля, версий ОС, Python, pytest и Xray. Указать предоставленную помощь (либо 0), повторы, их причины и затраченное время. При ошибке сверить свой приватный журнал, записать первый сбой и продолжить доступные части. Один технический повтор после устранимого сбоя среды допускается той же командой в новом каталоге. Включить evidence обоих запусков и причину. Функциональное расхождение на одной ревизии само по себе не требует повтора.
4. Ответить по таблице ниже. Для каждого вывода сослаться на строку своих измерений. В заключении указать, пригоден ли **кандидат для следующей проверки служебного маршрута**, с какой границей доказательства и какое *одно* следующее наблюдение могло бы расширить эту границу. Не оценивать собственную модель баллами.
5. В конце отчёта вставить полный `evidence.txt` одним текстовым блоком с сохранением строк и указать отдельно напечатанный SHA-256 **этого файла**. Это разрешённые к публикации измерения. Если выполнение остановилось до файла, указать этап, короткую причину и `NOT_RUN` для зависимых проверок. Сырые журналы, имена пользователя и машины, пути, PID, IP и настройки шлюза остаются на машине. Отчёт публикуется самим исполнителем даже при частичном результате.

| Вопрос | Что должно быть в ответе |
|---|---|
| Что изменилось между ревизиями? | Для каждой ревизии привести оба node ID (можно общим списком), исход и rc. Для первого расхождения открыть соответствующий лог, привести проверенное условие и написать, какое поведение оно различает. Отличить падение assertion от ошибки сбора, отсутствия зависимости и таймаута. |
| Что доказал отдельный Xray? | Для каждого из трёх этапов привести увиденную метку либо причину отсутствия. Объяснить, где измерялся трафик, что сохранилось в SQLite, что показала сводка и что значит ответ второго источника для планировщика. Отдельно дать статус публичному видео, рабочему WAN и суткам M3. |
| Доставлен ли диапазон? | Четыре строки H1–H4. Для каждой привести запрос, HTTP, Content-Range, фактические байты, совпадение тела и свой вердикт с причиной. «Получен ответ» и «получен весь запрошенный диапазон» — разные наблюдения. |
| Сохранился ли шлюз? | Привести `HOST_FIELDS` и назвать три сравниваемых поля пяти юнитов. При DRIFT указать предел вывода о причине, при UNKNOWN — какой замер отсутствовал. |
| Где заканчивается доказательство? | Отделить контракт, loopback и наблюдение штатных служб. Пропущенный пункт имеет причину и статус. |

## Автопубликация одного отчёта слота

В том же терминале должны остаться `REPO`, `D`, `SLOT` и `ROUND` из карточки. При блокере до старта создать свой каталог командой `umask 077; D=$(mktemp -d)`, выставить свой слот, номер раунда и путь к полному клону XGW. После записи своего `report.md` выполнить блок. Он использует временный Git-индекс, публикует один файл, сохраняет рабочую ветку. Повтор возможен при гонке с другим отчётом. При отсутствии права push запросить доступ, сохранить тот же отчёт и сообщить владельцу приватный путь до публикации.

```bash
(
set -euo pipefail
umask 077
[[ $SLOT == A || $SLOT == B ]]
[[ $ROUND == 1 || $ROUND == 2 ]]
test -s "$D/report.md"
ref=refs/heads/docs/flash-proton-ui-manifest
file="docs/reports/flash-pair-v1/r$ROUND-$SLOT.md"
export GIT_INDEX_FILE="$D/publish.index"
blob=$(git -C "$REPO" hash-object -w -- "$D/report.md")
local_ref="refs/xgw-flash-pair/$(basename "$D")-$SLOT"
trap 'git -C "$REPO" update-ref -d "$local_ref"' EXIT
for attempt in 1 2 3; do
    git -C "$REPO" fetch --quiet --no-tags --no-write-fetch-head origin "$ref:$local_ref"
    tip=$(git -C "$REPO" rev-parse "$local_ref")
    if old=$(git -C "$REPO" rev-parse --verify "$tip:$file" 2>/dev/null); then
        [[ $old == "$blob" ]] || { echo 'Слот уже содержит другой отчёт'; exit 1; }
        echo "Отчёт уже опубликован $tip $file"
        exit 0
    fi
    git -C "$REPO" read-tree "$tip"
    git -C "$REPO" update-index --add --cacheinfo "100644,$blob,$file"
    tree=$(git -C "$REPO" write-tree)
    commit=$(git -C "$REPO" -c user.name='XGW acceptance' -c user.email='1521572-lang@users.noreply.github.com' commit-tree "$tree" -p "$tip" -m "docs: Flash pair r$ROUND slot $SLOT")
    if git -C "$REPO" push origin "$commit:$ref"; then
        echo "Опубликовано $commit $file"
        exit 0
    fi
done
exit 1
)
```
