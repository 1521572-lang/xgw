## 4. Кейсы REAL-01…REAL-06 (блок А и блок Б)

### REAL-01. Предохранитель D1 для режима TUN — пройден

Порядок: установка без подписок → `capture.method = "tun"` → добавление подписки → включение
перехвата вне окна 04:00–05:00.

1. **Отказ до применения конфига.** `xgw enable` при работающем Xray, в применённом конфиге
   которого нет `tun-in`:

   ```
   ошибка: перехват пока не включён: в применённом конфиге Xray нет inbound tun-in
   для интерфейса xgwtun0 — правила отправили бы трафик в никуда. Трафик идёт напрямую;
   перехват включится сам, когда Xray перезапустится с новым конфигом
   применить сейчас: sudo xgw apply --now
   ```

   Код возврата 1, правил TPROXY в nft — 0, интернет остался прямым (внешний адрес
   46.242.12.248 — адрес провайдера), `xgw status`: «Перехват: НЕ ВКЛЮЧЁН (ожидание
   применения inbound в Xray) — в применённом конфиге Xray нет inbound tun-in для
   интерфейса xgwtun0; трафик идёт напрямую…».

2. **Немедленный перезапуск вне окна.** `xgw apply --now`:

   ```
   применено с перезапуском Xray: restart (срочное применение: основные inbounds,
   изменение inbound перехвата)
   ```

   `MainPID` Xray 1425 (запуск 19:15:11) → 19663 (19:39:17) — перезапуск сразу, а не в окне
   04:00–05:00. В применённом конфиге появился `inbound tag='tun-in' protocol='tun'`,
   интерфейс `xgwtun0` создан, в журнале Xray пошли записи `[tun-in -> proxy-nl-88d6]`,
   `xgw status`: «Перехват: включён — сеть enp4s0 и эта машина **через TUN**».

3. **Искусственное удаление `tun-in`.** Из применённого `/etc/xgw/xray/config.json` удалён
   inbound `tun-in`, Xray перезапущен, затем `xgw enable`:

   ```
   ошибка: перехват пока не включён: в применённом конфиге Xray нет inbound tun-in
   для интерфейса xgwtun0 — правила отправили бы трафик в никуда.
   ```

   Код возврата 1, `nft` — 0 правил TPROXY, интернет прямой (46.242.12.248),
   `capture.json` сохранил `{"enabled": true}` (выбор запомнен).

4. **Самовосстановление.** После запуска демона он за 13–15 с сам применил конфиг и включил
   перехват:

   ```
   19:43:37 ERROR xgw.net: перехват не включён: … нет inbound tun-in …
   19:43:50 INFO  xgw.daemon: apply: обновление подписки: применено с перезапуском Xray:
                  restart (срочное применение: основные inbounds, изменение inbound перехвата)
   19:43:51 WARNING xgw.daemon: capture: Xray перезапущен с inbound'ом перехвата — перехват включён
   ```

   Интернет вернулся через VPN. Итог: обе половины критерия REAL-01 выполнены.

Возврат `capture.method = "tproxy"` прошёл бесшовно. Остаётся интерфейс `xgwtun0`
(без адресов и маршрутов: `ip route show table 101` пусто, правила на таблицу 101 нет) —
косметический след, на трафик не влияет.

### REAL-03. Новый `probe.url` (D3) и недоступный адрес (D4) — пройден частично

**D3 — новый адрес по умолчанию.** Взято значение из `config.example.toml`:
`https://cdn.jsdelivr.net/npm/material-design-icons@3.0.1/iconfont/MaterialIcons-Regular.woff`.

| Запрос | Код | Получено | Content-Encoding |
|---|---|---|---|
| с браузерным User-Agent | 200 | 57 620 Б | нет |
| без User-Agent (`xgw/0.1`) | 200 | 57 620 Б | нет |
| с `Accept-Encoding: gzip` | 200 | 57 620 Б | нет |

Файл несжимаемый: и без браузерного UA, и с gzip ответ тот же по размеру — то есть проба
не «усохнет» ниже порога заморозки. 403, из-за которого D3 и появился, нет.

Наблюдение за журналом Xray при этом адресе (5 минут):

```
ошибок проб Xray за 5 мин: 13
     12  read/write on closed pipe
      1  timeout
по узлам:
  proxy-eu-0498   МЁРТВ   read/write on closed pipe×12
  proxy-lc-0b98   жив     timeout×1
```

Строк с HTTP 403 — 0. Все «closed pipe» приходятся на участника, который в это время
действительно мёртв, то есть на живых узлах обещанных ошибок нет.

**D4 — недоступный адрес пробы.** `probe.url = https://127.0.0.1:9999/bad`:

* демон распознал подмену: `19:51:43 WARNING xgw.daemon: Внимание: все пробы падают
  с одинаковой ошибкой — вероятно, недоступен сам probe.url (обрыв соединения; через VPN
  другие адреса открываются, а probe.url — нет; напрямую — нет ответа)`;
* `xgw status` печатает это предупреждение отдельной строкой;
* веб-панель отдаёт его в `/api/state` полем `probe_target` — проверено запросом к панели
  с её cookie;
* `xgw diag`: `FAIL probe.url: Внимание: все пробы падают…` и совет сменить адрес;
* замена участников не началась: за 6 минут наблюдения в `xgw status` — «0 событий ротации»,
  состав участников не изменился.

То есть заявленные в D4 меры работают. Но при этом найдены дефекты **F1**, **F2**, **F3**
(§5) — и один из них привёл к аварии на живой машине (см. F1).

### REAL-05. Физическое устройство в LAN на `enp4s0` (блок Б) — пройден частично

Устройство — роутер `10:71:00:ce:58:48` со статическим адресом 192.168.137.2 и собственным
NAT, за ним клиенты (телефон/ноутбук по Wi-Fi). Чтобы его WAN-порт заработал, на `enp4s0`
добавлен адрес 192.168.137.1/24 (после испытаний удаляется).

| Проверка ТЗ | Результат |
|---|---|
| Получение адреса по DHCP в 192.168.60.x, шлюза 192.168.60.1 и DNS | **не проверено**: устройство DHCP-запросов не отправляет (в `/var/lib/misc/dnsmasq.leases` пусто), оно NAT-ит своих клиентов. Сама служба при этом настроена: dnsmasq слушает только `enp4s0`, диапазон 192.168.60.100–192.168.60.200, `dhcp-option router/dns-server = 192.168.60.1` |
| Совпадение внешнего IP на устройстве с IP активного VPN-узла | **подтверждено** (заказчик проверил вручную: устройство показывает адрес VPN-узла, не провайдерский). Со шлюза тот же путь давал 195.123.208.149 (LV) и 2a01:ecc0:200:1037::2 (DE), провайдерский — 46.242.12.248 |
| Перехват DNS (запросы к принудительно прописанному серверу) | **подтверждено**: устройство шлёт DNS на 8.8.8.8, в журнале Xray — `from 192.168.137.2:… accepted udp:8.8.8.8:53 [tproxy-in -> dns-out]` |
| Поведение при `xgw disable` | **подтверждено**: за 20 с после снятия перехвата — 0 обращений устройства через Xray; на WAN появились настоящие адреса сайтов устройства (64.233.164.100:443, 172.217.118.4:443, 172.217.112.4:443) с источником 192.168.50.24, то есть выход напрямую через NAT провайдера |
| Поведение при `xgw enable` | **подтверждено**: адреса сайтов устройства с WAN исчезли (0 строк), снова видны только адреса узлов (138.249.18.115:443 и другие), кабель не трогали |
| Автоматическое переключение при «заморозке» во время скачивания | не воспроизводилось, см. §6 |

Что видно было на шлюзе при включённом перехвате (журнал Xray, 3 минуты наблюдения, 41
обращение устройства):

from 192.168.137.2:39099 accepted udp:172.217.116.4:443     [tproxy-in -> proxy-lv-12ef]
```

Сниффер на WAN за 25 с при включённом перехвате (1575 пакетов, 95 потоков) не показал
ни одного адреса сайтов устройства — только адреса узлов (`154.193.152.x:8443`,
`138.249.18.115:443`, `201.10.72.171:443` и другие). Утечки нет.

Форвардинг ICMP из LAN: правило `iifname "enp4s0" … meta l4proto icmp … accept` в таблице
`ip xgw` на месте, но счётчик за всё наблюдение — 0 пакетов, проверить не удалось.

### REAL-06. Соседство с Docker — пройден

```
$ systemctl enable --now docker && docker --version
Docker version 29.1.3
$ nft list tables
table ip nat / table ip filter / table ip6 nat / table ip6 filter     ← Docker (iptables-nft)
table ip xgw / table ip6 xgw6                                         ← XGW
$ iptables -S FORWARD

  изменился, профиль `xgw-lan` активен.
* После запуска Docker перехват и трафик устройства за роутером продолжают работать
  (`[tproxy-in -> proxy-lv-12ef]` в журнале Xray), `xgw diag`: «Файрвол: ufw и Docker
  перехвату не мешают», «Итог: OK — 19, WARN — 1, FAIL — 0».

$ docker run --rm alpine wget -qO- https://ifconfig.me

## 5. Найденные дефекты
### F1 (высокий). Состояние LEAK перекрывает PROBE_TARGET_UNREACHABLE, и защита от круговой замены участников не включается

`watch/states.py` разбирает состояния по порядку (`XRAY_DOWN` → `WAN_DOWN` → `LEAK` →
`PROBE_TARGET_UNREACHABLE` → …), а `daemon.py` включает защиту по имени состояния:
`probing = state is not State.PROBE_TARGET_UNREACHABLE`. Пока в состоянии стоит `LEAK`,
недоступность `probe.url` не видна, сканы и замена участников идут полным ходом.

Хронология на живой машине (14.10.2026):

| Время | Событие |
|---|---|
| 19:45:04 | `LEAK: HEALTHY → LEAK` (балансировщик выбрал узел, выходящий в RU) |
| 19:51:43 | демон уже видит «все пробы падают одинаковой ошибкой…» — предупреждение в журнале и статусе |
| 20:06:53 | `PROBE_TARGET_UNREACHABLE: LEAK → PROBE_TARGET_UNREACHABLE` — только теперь защита включилась |
| 20:08:12 | `ALL_DEAD: PROBE_TARGET_UNREACHABLE → ALL_DEAD: живых серверов нет — обновление подписки напрямую, скан запасных, замена` |
| 20:09:21 | `rotation: замена участников: proxy-ru-d309 → «Латвия», proxy-eu-0498 → «Франция»` |
| 20:08 | заказчик снял перехват (`xgw disable`) — интернет не работал |

Пятнадцать минут состояние LEAK держало защиту выключенной, после чего XGW ушёл в ALL_DEAD
и начал менять живые серверы, потому что пробы всех участников падали на недоступном адресе
пробы. На реальной машине это выглядит как пропавший интернет — что и произошло.

Что предлагается:

* оценивать признак «не отвечает адрес пробы» независимо от LEAK (например, `probe_target`
  проверять до разбора состояния либо вводить отдельный флаг, гасящий замену участников и
  сканы, а не только имя состояния);
* в состоянии LEAK не переводить шаг в ALL_DEAD, пока контрольные запросы не подтвердили,
  что живы сами серверы;
* в `xgw status` показывать одновременно и утечку, и недоступность адреса пробы — сейчас
  в первой строке видно только одно состояние.

### F2 (средний). Предупреждение `xgw probe --all` о недоступном `probe.url` практически не появляется

`cli.py` печатает предупреждение, только если `target.uniform()` нашёл **одну и ту же** ошибку
у всех узлов. На реальной подписке вердикты почти всегда разные: в прогоне с недоступным
адресом пробы из 67 узлов получено 64 `CONNECT_FAIL` и 3 `TIMEOUT` — предупреждения нет,
хотя недоступен именно адрес пробы. Та же хрупкость у диагностики демона: достаточно одного
узла с другой ошибкой в выборке, чтобы признак пропал.

Что предлагается: считать признаком не строгое равенство подписи, а долю одинаковых ошибок
(например, ≥ 80 % узлов с одним классом сбоя и ни одного успешного), и упоминать это в тексте.

### F3 (мелкий). Оценка трафика проверок при недоступном `probe.url` даёт ложное предупреждение

Пока адрес пробы не отвечает, размер пробы неизвестен, `diag` считает его по запасной оценке
65 536 Б и выдаёт:

```
WARN  Трафик проверок: трафик проверок ~1041 МБ/сут больше лимита 1024 МБ — уменьшите
      max_members или увеличьте interval. … (проба 65536 Б, по оценке)
```

Измеренный размер того же адреса — 57 620–58 116 Б, то есть в бюджет укладывается. Совет
менять `max_members`/`interval` в этот момент вреден.

### F4 (средний). Трафик контейнеров Docker идёт мимо VPN

```
$ docker run --rm alpine wget -qO- https://ifconfig.me
ip=46.242.12.248            (адрес провайдера)
$ # сама машина в этот момент
ip=195.123.208.149 (LV)
```

XGW перехватывает исходящий трафик самой машины (цепочка `output`) и то, что приходит с
`enp4s0`; форвардинг из `docker0` не перехватывается, при этом в `xgw status` он не значится
и в списке «мимо VPN» (`capture.bypass`) его нет. Для шлюза, за которым стоят контейнеры,
это неочевидная утечка.

Что предлагается: добавить в `xgw diag`/`status` строку о том, что трафик мостов Docker
(`docker0` и прочие) идёт напрямую, и, если это нежелательно, — шаг установки, перехватывающий
и его (`iifname "docker0"` в тех же цепочках), либо явное предупреждение в README.

### F5 (мелкий). `xgw status` не сообщает, что демон (watchdog) не работает

После остановки `xgw.service` (проверка REAL-01, часть А) `xgw status` продолжает печатать
состояние из хранилища:

```
Состояние: DEGRADED с 14.10 19:38 — часть серверов недоступна — замена на запасные
Xray 26.3.27: отвечает
Перехват: включён — сеть enp4s0 и эта машина
```

Ни слова о том, что наблюдение остановлено, и код возврата 0. Ошибку видит только `xgw diag`
(«FAIL Службы: не работают: xgw.service»). На шлюзе это значит, что о проблемах никто
не узнает: события, ротация и уведомления не работают.

Что предлагается: печатать в первой строке `xgw status` пометку, что служба `xgw.service`
не активна, и возвращать ненулевой код.

### F6 (мелкий). Устойчивое состояние LEAK засоряет события и переприменяет правила каждые 20 с

`daemon.py`: `if state is State.LEAK: self._handle_leak()` — на каждом шаге watchdog (20 с)
заново загружаются правила перехвата и в хранилище пишется событие `leak: выход в RU при
включённом перехвате`. За 6 минут наблюдения список «Последние события» в `xgw status`
целиком состоял из таких записей; правила перехвата переприменялись ~180 раз в час.
Причина устойчивого LEAK — выбранный балансировщиком узел, выходящий в домашнюю страну:
у заказчика на 186 мс оказался российский узел, он и был выбран как самый быстрый.

Что предлагается: держать признак «утечка уже обработана» до смены выхода (или ограничить
частоту переприменения правил), а в балансировщике учитывать `routing.home_country` —
сейчас нет ни фильтра по стране, ни предупреждения, что выбран узел своей страны
(спасает только ручное `xgw pin`).

### F7 (мелкий). Ключ `probe.url_fallback` есть в конфиге, но не используется

`config.example.toml` содержит `url_fallback = ""`, значение читается в `config.py`
и больше нигде не применяется (`ASSUMPTIONS`, п. 157 — там это признано). Пользователь,
вписавший резервный адрес, не получит ничего.

### F8 (косметика). Остатки после возврата с TUN на TPROXY

После `capture.method = "tproxy"` интерфейс `xgwtun0` остаётся (адрес `169.254.10.1/32`,
маршрутов в таблице 101 нет, правила `ip rule` на неё нет). Безвредно, но `xgw diag`
про него молчит, а `ip link` показывает лишний интерфейс.

### F9 (средний). Стенд «одноразовой машины» не работает с относительным путём в `XGW_XRAY_BIN`

Команда из программы испытаний и из докстринга самого теста
(`sudo -E XGW_XRAY_BIN=tools/xray/xray pytest tests/stand/test_machine.py -q`) даёт
22 падения из 23:

```
RuntimeError: bash -c mkdir -p /opt/xgw/xray && cp tools/xray/* /opt/xgw/xray/ …
cp: cannot stat 'tools/xray/*': No such file or directory
```

Причина: в `test_machine.py` путь берётся как `Path(XRAY_BIN).parent` и копируется
**относительным** путём внутри контейнера, а рабочий каталог там — `/` (проверено:
`box.sh("pwd")` → `/`), хотя каталог репозитория в контейнере виден по своему пути.

Что предлагается: в тесте разрешать путь до абсолютного (`Path(XRAY_BIN).resolve()`)
или копировать из `REPO / XRAY_BIN`; и упомянуть в докстринге, что путь должен быть
абсолютным.

### F10 (средний). Копирование Xray в контейнер поверх работающего процесса

Если в контейнере Xray уже запущен (предыдущая проверка поставила XGW), то повторное
копирование из `_put_config`/хелперов падает:

```
cp: cannot create regular file '/opt/xgw/xray/xray': Text file busy
```

и уносит за собой `test_tun_method_on_the_installed_system`. Что предлагается: перед
копированием останавливать службу (`systemctl stop xgw-xray`) либо копировать во временный
файл и переименовывать (`cp` во временный + `mv`, `mv` поверх работающего файла проходит).

### F11 (мелкий). Проверки стенда привязаны к Ubuntu 26.04 и к чистоте хоста

* `assert "Итог: OK"` (в `test_install`, `test_second_install_...`) падает на Ubuntu 24.04:
  `xgw diag` честно предупреждает «Система: Ubuntu 24.04.5 LTS … XGW проверялся только на
  Ubuntu 26.04», а тест WARN не допускает. На целевой системе предупреждения не будет,
  но на 24.04 (а это как раз стенд заказчика) прогон красный.
* Сравнение профилей NetworkManager ломается от `docker0`: в контейнере профиль получает
  новый UUID, и снимок «до/после» не совпадает (`test_machine_only_mode_...`).
* Отключённый XGW IPv6 на WAN хоста наследуется сетевым пространством контейнера, и
  проверка IPv6 падает на `ip addr replace … : IPv6 is disabled on this device`.

Что предлагается: в проверках первого запуска не требовать отсутствия WARN про версию
системы (или сравнивать только FAIL), исключать профиль `docker0` из снимка, а в
подготовке контейнера явно включать IPv6 на его `wan0`/`lan0`.

## 6. REAL-08. Реальная аппаратная перезагрузка

## 8. Отличия фактического стенда от описанного в программе

1. LAN-клиент — **роутер** со статическим адресом 192.168.137.2 и собственным NAT, а не
   ноутбук/точка доступа. Чтобы его WAN заработал, на `enp4s0` временно добавлен адрес
   192.168.137.1/24 (после испытаний удаляется). Штатный сценарий ТЗ (устройство получает
   адрес по DHCP от XGW) в такой топологии не воспроизводится: клиент сидит за NAT роутера,
   и шлюз видит только сам роутер. Перехват, DNS и DNS-подмена проверены на его трафике.
2. `capture.method` в ходе испытаний менялся на `tun` (REAL-01) и обратно на `tproxy`;
   на момент сдачи отчёта на машине `tproxy`, перехват включён.
3. Docker установлен на хост в ходе испытаний (REAL-06) и оставлен запущенным.

## 9. Приложение: как воспроизводилось

* REAL-01: полный бэкап `/etc/xgw/config.toml`; `xgw disable`; конфиг без блока
  `[[subscriptions]]`; `xgw install --yes`; `method = "tun"`; `xgw enable` (отказ);
  `xgw apply --now`; удаление inbound `tun-in` из применённого `/etc/xgw/xray/config.json`
  и `systemctl restart xgw-xray`; снова `xgw enable`; запуск демона и наблюдение
  самовосстановления; возврат конфига и `xgw install --yes`
* REAL-02: подмена `lan_address`/`dhcp_range`, `xgw diag`, `xgw install --yes [--force]`
* REAL-03: правка `probe.url` в `/etc/xgw/config.toml`, `xgw apply --now`, наблюдение
  `journalctl -u xgw-xray`, `xgw status`, `/api/state` панели
* REAL-05: сниффер на `enp3s0f0` и `enp4s0` (свой, на `AF_PACKET`), журнал Xray,
  `xgw disable` / `xgw enable`
* REAL-06: `systemctl enable --now docker`, `docker run --rm alpine wget -qO- https://ifconfig.me`,
  `nft list tables`, `iptables -S FORWARD`
