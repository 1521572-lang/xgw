# Отчёт об испытаниях XGW 0.1.10 на реальной машине

Прогон по `docs/TEST-PLAN-REAL-MACHINE-0.1.10.md`. Машина — ThinkCentre, Ubuntu 24.04.5 LTS, ядро 7.0.0-38-generic; WAN `enp3s0f0`, LAN `enp4s0`, Docker и HUAWEI AX2 за шлюзом. На момент начала работы стояла XGW **0.1.9** в боевом режиме.

## Краткий итог

XGW 0.1.10 установлен поверх 0.1.9 обычной установкой, без `--force`. Четыре службы активны, `diag` — FAIL 0. Основные новые функции 0.1.10 проверены: ручной выбор сервера работает, включая автопереключение при отказе выбранного и уведомления; лимитированные серверы участвуют в работе, когда безлимитные недоступны; `xgw update-xray` не меняет версию Xray. Стендовые тесты 0.1.10 — 8 passed.

**Важное замечание REAL-61/D2**: синтетическая проверка в отдельной службе показывает, что WARNING теперь пишется в journald с `PRIORITY=4`, однако основной демон `xgw.service` продолжает сохранять свои WARNING-сообщения с `PRIORITY=6`. Таким образом, `journalctl -u xgw -p warning` по-прежнему не находит предупреждения демона. Это регрессия/недоделка D2.

**REAL-60**: сбой 17.10 объясняется сочетанием кратковременных потерь связи с провайдером (`WAN_DOWN`) и недоступностью безлимитных серверов conn-liberty. Пользователь подтвердил, что безлимитная подписка работает в Happ через мобильный интернет и активна в личном кабинете. На момент испытаний безлимитные серверы conn-liberty в панели были отключены (статус `disabled`), поэтому шлюз работал через лимитированные узлы libhub.

Проверяемый код: коммит `2c5330d3fbb0aa488d4852b87c0f9e4e71b73744`. Установка: `sudo sh packaging/install.sh --yes`, 17.10.2026 14:52:47 MSK, код 0.

## 4. REAL-62. Лимитированные серверы

### 4.1 Текущее состояние после снятия приоритета

После установки 0.1.10 и снятия временного высокого приоритета шлюз самостоятельно сформировал состав из лимитированных x1:

| Роль | Серверы |
|---|---|
| Участники (5) | proxy-ro-fddc, proxy-us-e475, proxy-il-4b86, proxy-lv-12ef, proxy-pl-7e92 — все x1, libhub |
| Основной | proxy-us-e475 (выбран по задержке) |
| Резервный выход | spare-pl-0377 x10 |

Это подтверждает, что 0.1.10 допускает лимитированные x1 в работу, когда безлимитные недоступны. Сервера x10 и дороже остались запасными/резервом.

### 4.2 Чистый переход не смоделирован

Программа предполагает вариант А (безлимитные мертвы, `RESERVE`) или вариант Б (безлимитные работают, смоделировать отказ). На момент испытаний безлимитные серверы conn-liberty были отключены в панели, поэтому:
- вариант А требовал бы дождаться, пока шлюз сам уйдёт в `RESERVE`, что непредсказуемо;
- вариант Б требовал бы включать безлимитные, добавлять фейковый F, отключать безлимитные — вмешательство в боевую конфигурацию без гарантии восстановления.

В журнале за 17.10 видны события такого перехода, произошедшие до начала наших действий: `priority: снова отвечают серверы лучшего класса — в работе лимитированные серверы x1 (были — лимитированные серверы x10)` в 15:30.

- REAL-67: два `pin:` WARNING о XGW-TEST-DEAD — ожидаемые уведомления.
- Telegram: `ERROR` доставки `WAN_DOWN` — сеть.
- `WAN_DOWN`: WARNING перехода в `WAN_DOWN` в 15:49.

### 5.3 Замечание D2

**Дефект**: основной процесс `xgw.service` не использует исправленный обработчик journald. Все его WARNING (`pin:`, `WAN_DOWN:`, пропуски узлов) сохраняются systemd с `PRIORITY=6`, поэтому предписанный фильтр `journalctl -p warning` их не находит. Синтетический `xgw-d2-check` проходит, реальный демон — нет.

## 7. Дефекты

**D1 — journald priority для основного демона (REAL-61/REAL-65).**

- Как повторить: выполнить любое действие, которое порождает WARNING в `xgw.service` (например, REAL-67 п. 4), затем `journalctl -u xgw -p warning --no-pager`.
- Ожидалось: сообщение видно.
- Получилось: 0 строк; сообщение есть только в `journalctl -u xgw --no-pager -o cat` с текстом `WARNING`, а structured `PRIORITY=6`.
- Причина: исправление D2 применено только к `log.setup()` в синтетических вызовах, но не к стартовой конфигурации основного демона.

**D2 — текст статуса показывает «уровень приоритета «высокий»» после полной очистки `panel.json`.**

- Как повторить: очистить `/etc/xgw/panel.json` → `"priority": {}`, перезапустить `xgw`; `sudo xgw status`.
- Ожидалось: строка участников без указания уровня приоритета (автоматический).
- Получилось: строка «Участники балансировщика (5), уровень приоритета «высокий»».
- Примечание: API `/api/state` возвращает `priority: None`, `tier: high`; текстовый формат, вероятно, использует `tier` вместо фактических приоритетов.
