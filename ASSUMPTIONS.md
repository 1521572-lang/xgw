# ASSUMPTIONS.md — допущения и результаты проверок

Обновляется по мере прохождения этапов. Нумерация сквозная.

## Среда разработки (этап 1)

1. **Только Ubuntu 24.04 и 26.04.** Юнит-тесты, ruff, `xray run -test` и стенды
   (loopback, netns, «одноразовая машина») выполняются на Ubuntu 26.04 под root;
   настоящая машина заказчика — Ubuntu 24.04.5 (отчёты в `docs/`). Всё, что требует
   root (nftables, network namespaces), помечено ниже по этапам.
2. **Python 3.11+** (в ТЗ — 3.14). Используется только стандартная библиотека,
   доступная с 3.11 (`tomllib`); проверено на 3.12 (Ubuntu 24.04) и 3.14 (26.04).
3. **pytest и ruff — только для разработки**, ставятся в venv; на целевой машине
   зависимостей нет (PEP 668 учтён).

## Xray (проверено фактически)

4. **Xray 26.3.27** (официальный релиз GitHub, linux/amd64) — выше требуемой
   25.7.23. SHA-256 сверен с `.dgst`.
   Golden-конфиг из фикстур проходит `xray run -test` → `Configuration OK`.
5. **Предупреждения Xray 26.3.27, не влияющие на работу:**
   - `wsSettings.headers.Host` объявлен устаревшим («will be removed soon»).
     Генератор пишет отдельное поле `wsSettings.host` (см. п. 43): версия Xray
     по умолчанию — `latest`, и после удаления старой записи все ws-серверы
     перестали бы проходить `xray run -test`.
   - VMess помечен устаревшим — поддержку сохраняем (панели до сих пор его
     отдают), предупреждение Xray игнорируется.
6. **`burstObservatory.pingConfig.httpMethod: "GET"`** — Xray 26.3.27
   принимает конфиг без ошибок (поле есть начиная с v25.7.23 по разделу 4 ТЗ).
7. **hysteria2/hy2 и wireguard**: поля соответствующих outbound не описаны ни
   в разделе 4 ТЗ, ни в официальной документации — до 0.1.12 узлы пропускались с
   предупреждением. **Проверено** на Xray 26.10.10 (0.1.12): hysteria2, TUIC и AnyTLS
   в нём нет («unknown config id»), WireGuard требует ключи. Эти серверы теперь ведёт
   второе ядро — sing-box (п. 197).
8. **`sockopt.domainStrategy: "UseIPv4"`** у proxy-outbounds — из раздела 6.4
   ТЗ; Xray 26.3.27 конфиг принимает. Требуется `sockopt.mark` + CAP_NET_ADMIN
   на Linux — проверяется на стенде (этап 3).
9. **Inbound `tunnel`** (бывший dokodemo-door) с `allowedNetwork`/
   `followRedirect` — по разделу 4 ТЗ; Xray 26.3.27 принимает.

## Парсеры ссылок (этап 1)

10. **Транспорт kcp**: seed берётся из `path` (как в v2rayN), либо из
    параметра `seed`, если он задан явно.
11. **vmess JSON**: для grpc serviceName хранится в поле `path` (поведение
    v2rayN) — учитывается при разборе.
12. **trojan**: если `security` не задан — по умолчанию `tls` (trojan почти
    всегда поверх TLS; v2rayN-панели обычно задают явно).
13. **ss**: плагины SIP003 (`simple-obfs`, `v2ray-plugin`) Xray-core не
    поддерживает — у shadowsocks-outbound нет полей для плагина, а неизвестные
    поля ядро молча игнорирует. Узел с `plugin=` **пропускается с
    предупреждением** (прежняя запись про поля `plugin`/`pluginOpts` была
    ошибкой: таких полей в Xray нет). Старый формат ss:// (весь userinfo+host
    в base64) и percent-encoded userinfo шифров 2022-blake3 поддерживаются.
14. **socks://**: userinfo может быть base64("user:pass") или plain —
    поддерживаются оба варианта.
15. **Метаданные подписки**: строки `#key: value` распознаются только с
    ASCII-ключами (реальные панели используют `# expire: …`, `# трафик: …`
    может не распознаться — уходит в «ссылок не найдено» только если ссылок
    действительно нет).
16. **User-Agent по умолчанию** — `xgw/0.1`. Панели выбирают формат ответа по
    UA; если панель отдаёт не то — пользователь задаёт `user_agent` в
    конфиге (пример в README, «Частые проблемы»).
17. **Редиректы подписок** (301/302/303/307/308) обрабатываются до 4 подряд.
18. **JSON-подписки**: звенья цепочек `sockopt.dialerProxy` получают
    собственные теги `chain-<хеш содержимого>`, ссылки `dialerProxy`
    переписываются на них. Исходные теги сохранять нельзя: у разных конфигов
    одной подписки они совпадают при разном содержимом, а тег вида `proxy-…`
    попал бы под селектор балансировщика. Звено — freedom с fragment/noises —
    переносится как часть цепочки; узел, чья цепочка недоступна (нет такого
    тега, blackhole/dns/loopback, цикл), пропускается с предупреждением.
    Звенья получают `sockopt.mark`, в балансировщик и пробы не попадают.
    Имя узла берётся из поля `remarks` конфига (основной outbound там обычно
    зовётся просто `proxy`). Плоская запись `settings.address/port` распознаётся
    наравне с `vnext`/`servers`.
19. **Порядок узлов канонический** — сортировка по отпечатку: теги и порядок
    выходного конфига не меняются при перемешивании входных ссылок
    (требование раздела 9). Состав участников при этом «липкий»: участники
    применённого конфига остаются участниками (`select_nodes(prefer=…)`),
    свободные места заполняются по каноническому порядку.

## Xray API (этап 2 — проверено фактически на живом процессе 26.3.27)

23. **Порядок аргументов `xray api`**: флаги подкоманды (`-s`, `-t`, `-append`,
    `-b`, `-r`) обязаны идти ДО позиционных аргументов, иначе парсер их
    игнорирует и молча стучится на 127.0.0.1:8080. Рабочая форма:
    `xray api bi -s 127.0.0.1:10085 -t 10 auto`.
24. **Живые интеграционные тесты** (`tests/test_api_integration.py`,
    запуск `XGW_XRAY_BIN=<путь> pytest tests/test_api_integration.py`):
    ado/adi → lso/lsi видят добавленное, rmo/rmi удаляют, adrules заменяет
    правила и балансировщик остаётся жив, bi отдаёт состояние. Открыты также
    команды lso/lsi/lsrules — используются для проверки операций.
25. **`lsrules` отдаёт теги правил** (ruleTag), а не содержимое: при проверке
    замены правил сверяемся по явному `ruleTag` (Xray назначает его сам,
    если не задан). Генератор поле ruleTag не задаёт — теги назначает ядро.
26. **Формат observatory в /debug/vars** (проверено на живом процессе):
    у живого узла `alive: true, delay: <мс>`; у мёртвого поля `alive` нет
    вовсе (это False), в `health_ping` только `all`/`fail`;
    `health_ping.average` — наносекунды. Парсер `metrics.parse_observatory`
    написан ровно под этот формат.
27. **adrules и `routing.domainStrategy`**: замена правил проверена живым
    тестом; меняет ли adrules domainStrategy без перезапуска — проверяется
    на стенде (этап 2/3), XGW на это не полагается.

## Продуктовые решения

20. **Выбор участников**: текущие участники сохраняются, замену «мёртвого»
    выбирает `apply/rotation.py` по последнему скану. Ранжирование всех узлов
    по метрикам при первой сборке не делается — данных ещё нет.
21. **Один случайный пароль** на все probe-inbound (секция 6.6 ТЗ говорит о
    «случайном пароле» в единственном числе; пароль не покидает конфиг 0640).
    Генерируется один раз и дальше берётся из применённого конфига
    (`builder.probe_state`): у работающего Xray действует именно он.
22. **fail_mode/open, bypass, ICMP, сон, ufw** — этапы 3–4; в коде этапов 1–2
    сеть хоста не трогается вообще.
28. **Замена участника идёт через пересборку конфига и diff** (раздел 6.7
    прямо описывает это как ado+adrules+rmo): тег содержит роль, поэтому
    ротация — это удаление тега spare-* и добавление proxy-*; соединения
    через мёртвый узел всё равно уже нет. Цепочка вызовов: `plan_rotation` →
    `preferred_members` → `select_nodes(prefer=…)` → `build` → `Applier.apply`.
29. **Сквозная проверка и сканы** читают тело ответа с детектором тишины 5 с
    (`watch/checks.py`); https через probe/http-inbound открывается
    CONNECT-туннелем — так «заморозка» видна и на TLS-трафике. Успех — только
    ответ 2xx с телом, дочитанным до Content-Length; `downloaded` считает байты
    тела без заголовков; на всю загрузку отведено 60 с (защита от сервера,
    который «капает» по байту). Проверено тестами на локальном TLS-сервере.

## Решения, принятые при исправлении ошибок (ревью этапов 1–2)

30. **Повторы запросов** — первая попытка и до трёх повторов с паузами 2, 4 и
    8 с (раздел 6.5). Повторяются только временные сбои: сетевые ошибки и
    ответы 429/5xx; неверный URL, недоверенный сертификат и отказ прокси — нет.
31. **Ответ подписки не 200 или без серверов — сбой**, а не «пустая подписка»:
    берётся последняя удачная версия из `/var/lib/xgw/cache` (файлы 0600), кэш
    не перезаписывается. Серверами не считаются служебные адреса (0.0.0.0,
    loopback, порт вне диапазона) — так провайдеры отдают заглушку вместо
    списка («Приложение не поддерживается!»). Квота (`subscription-userinfo` из
    заголовка или из строки `#subscription-userinfo:` в теле) сохраняется в
    SQLite (`meta.quota`).
32. **Прямые запросы и DNS**: при запросе напрямую (метка `mark_bypass`) имя
    хоста разрешают резолверы `dns.bootstrap` сокетами с той же меткой, а не
    системный резолвер — тот ходит через перехват и при упавшем Xray не
    отвечает. Без прав на SO_MARK (запуск не от root) XGW работает без метки и
    системным резолвером, предупреждая об этом.
33. **«Здоровый Xray» для запроса подписки** в `xgw generate` — это открытый
    порт http-in (`127.0.0.1:<http_port>`): запрос идёт через него с одним
    повтором, при неудаче — напрямую. Точнее состояние знает демон (этап 2).
34. **`xgw generate` не пишет в рабочий конфиг**: без `--out` результат — в
    `config.generated.json`. Иначе `Applier` увидел бы новый конфиг уже
    «применённым» и ядро осталось бы на старом.
35. **dns.hosts перезапуска не требует** (раздел 6.4: домен нового сервера
    попадает в hosts при следующем перезапуске). Остальные изменения секции
    dns — требуют. Адреса в hosts сортируются: DNS-ротация не должна менять конфиг.
36. **Изменившийся outbound/probe-inbound с прежним тегом** заменяется через
    API (rmo+ado, rmi+adi). Изменение каркаса — `direct`, `block`, `dns-out` —
    требует перезапуска: через них идёт служебный трафик ядра.
37. **Порты probe-inbounds закреплены за тегом**: существующие берутся из
    применённого конфига, новые получают первый свободный от `probe_port_base`
    (служебные порты пропускаются). Суффикс тега `<страна>-<fp>` общий для
    proxy-/spare-/probe-, коллизия считается по суффиксу; длина (4→6→8 hex)
    выбирается сразу для всей группы совпавших узлов и не зависит от порядка.
38. **Ошибка вызова API** — перезапуск по общим правилам (сразу при
    ALL_DEAD/XRAY_DOWN и `--now`, иначе в окне), как требует раздел 6.7. До
    перезапуска ядро считается изменённым частично (метка `/run/xgw/api-dirty`),
    и через API больше ничего не применяется: повторный `ado` поверх половины
    изменений упал бы на «existing tag».
39. **Готовность Xray после перезапуска** проверяется вызовом `bi auto`:
    `bi` без тега балансировщика отвечает ошибкой `app/router: cannot find tag`
    (проверено на живом 26.3.27). Прежний код вызывал `bi` без тега — после
    каждого перезапуска он ждал 15 с и откатывал рабочий конфиг на last-good.
40. **Конфиг без проверки не применяется**: если `xray` не найден, `Applier`
    отвечает `rejected`. Установленный Xray старше 25.7.23 — отказ ещё до
    `xray run -test`: такой бинарник конфиг примет, а `httpMethod` проигнорирует.
41. **Сервер, который Xray не принимает** (снятый транспорт, неизвестный шифр),
    находится проверкой каждого outbound отдельным минимальным конфигом и
    отбрасывается; остальная подписка применяется.
42. **Состояние участника «неизвестно»**: тега нет в observatory, пока ядро не
    завершило по нему ни одной пробы. Такие участники не считаются мёртвыми
    (иначе каждый перезапуск Xray давал бы ложный ALL_DEAD).
43. **`wsSettings.host`** вместо `headers.Host`: на живом 26.3.27 конфиг с
    отдельным полем проходит `xray run -test`, предупреждение об устаревшей
    записи пропадает.
44. **Маскирование в логах** выполняет форматтер обработчика: фильтр логгера
    `xgw` к записям дочерних логгеров (`xgw.generate`, …) не применяется.
    Ссылки серверов маскируются целиком (`trojan://***`), пароли и ключи из
    разобранных узлов регистрируются для точной замены.
45. **Тесты на машине разработчика**: если локальный HTTP-фильтр (веб-защита
    антивируса) буферизует неполные ответы на loopback, сценарии «тишина
    посреди тела» по открытому HTTP пропускаются и проверяются по TLS.
46. **Проверено на живом Xray 26.3.27 при ревью** (`tests/test_apply_live.py`,
    запуск с `XGW_XRAY_BIN`): повторный `ado` существующего тега — ошибка
    `existing tag found`; `rmo` отсутствующего тега — успех, `rmi` — ошибка;
    транспорт `h2` и шифр `rc4-md5` отвергаются при `xray run -test`; поля
    `plugin`/`pluginOpts` у shadowsocks молча игнорируются; плоская запись
    `settings.address/port/id` у vless и freedom+fragment в роли `dialerProxy`
    принимаются; замена outbound с прежним тегом (rmo+ado) доходит до ядра.

## Этап 2: демон, команды и стенд

47. **Стенд в двух режимах.** Проверки этапа 2 (переключение, применение без
    разрыва, замена участника) не требуют перехвата трафика, поэтому идут и в
    режиме loopback: все процессы на 127.0.0.1, без root. Тот же набор в
    пространствах имён (`tests/stand/netns.py`) включается на Linux под root.
    Оба режима прогнаны на Ubuntu 26.04.1 под root (ядро 6.18.40,
    Python 3.14.4): 8 проверок из 8, после прогона в корневом пространстве
    имён не остаётся ни интерфейсов, ни процессов. Это не штатное ядро
    Ubuntu: перед этапом 3 там же нужно было проверить nftables/TPROXY
    (`nft_tproxy` собран модулем, `nft_socket` в конфиге этого ядра нет).
48. **Проверено на стенде с живым Xray 26.3.27**: на «замороженном»
    узле GET-проба падает с `context deadline exceeded (… while reading body)`,
    узел получает `alive = false`, балансировщик уходит с него за 6–16 с в
    режиме loopback и за 7–16 с в netns — по шесть заморозок в
    разные моменты цикла; `interval = 10s`, `sampling = 1`, `timeout = 3s`.
    С `httpMethod: HEAD` тот же узел остаётся живым и выбранным.
    Домен сервера, добавленного через API, ядро разрешает через свои DNS-серверы.
49. **leastPing на равных узлах «прыгает»**: при близких задержках выбор меняется
    от пробы к пробе и без всякой заморозки. Поэтому реле стенда умеет
    добавлять задержку (`latency=МС`) — проверяемый узел делается заведомо
    самым быстрым, и «`bi` показывает другой узел» становится однозначным.
50. **Вердикт FROZEN на живом Xray** получен на Linux: `xgw probe` замороженного
    узла (`freeze_after=16384`) показывает `FROZEN 16208 Б за 5.0 с — тишина 5 с
    после 16208 байт тела` (остальное из 16384 — заголовки HTTP и VLESS).
51. **`capture.lan = false` и `capture.local = false`** — XGW только управляет
    Xray: TPROXY-inbound и правило порта 53 в конфиг не попадают (без root
    inbound и не открылся бы). Так настроен стенд этапа 2.
52. **DNS-серверы с портом** (`"адрес:порт"` в `dns.proxy_servers` /
    `direct_servers`, `udp://адрес:порт` в `bootstrap`): в конфиг Xray идут
    объектом `{"address", "port"}` — проверено `xray run -test` и стендом.
53. **`XGW_XRAY_SERVICE=process`** — Xray как обычный процесс с pid-файлом
    `/run/xgw/xray.pid` и выводом в `/run/xgw/xray.log`. Нужен там, где нет
    юнита `xgw-xray.service` (стенд до этапа 4). По умолчанию — systemd.
54. **Демон однопоточный**, за шаг применяет не больше одного изменения конфига.
    Скан запасных идёт порциями (до 8 с за шаг), чтобы watchdog не замирал на
    время обхода длинного списка.
55. **XRAY_DOWN** — когда недоступны и метрики, и API. «После двух неудач» —
    это две проверки watchdog подряд; откат на last-good выполняется один раз
    на инцидент и только если last-good отличается от текущего конфига.
56. **ALL_DEAD**: обновление подписки напрямую и скан запасных повторяются не
    чаще раза в 5 минут; замена участников идёт сразу, без ожидания
    `rotate_after_min`. Отложенный перезапуск в этом состоянии и в XRAY_DOWN
    выполняется немедленно (раздел 6.7).
57. **«Последний скан»** для замены участника — результат не старше двух
    периодов `scan_spares_minutes`. Если менять пора, а свежих результатов
    нет, демон сначала запускает внеочередной скан (не чаще раза в минуту).
58. **Неполный опрос подписок не применяется**: если хотя бы одна подписка не
    дала серверов даже из кэша, рабочий конфиг не меняется — иначе её серверы
    пропали бы из ядра. Исключение — первый запуск, когда конфига ещё нет.
59. **Проверка утечки (LEAK) работает только при включённом перехвате**: без
    него обычный сокет идёт напрямую, и выход в `home_country` — не утечка.
    С этапа 3 признак «перехват включён» демон берёт из режима перехвата (п. 78).
60. **Уведомления** на этапе 2 — запись в журнале уровня WARNING и событие в
    SQLite, не чаще `min_interval_min` на тип события (тип — состояние:
    уведомление об ALL_DEAD не придерживается из-за недавнего DEGRADED).
    Рабочий стол и Telegram — этап 4, подключаются как получатели `Notifier`.
61. **Трафик проверок** в статусе считается по формуле раздела 6.8 (пробы
    участников плюс сканы); с ней и сравнивается `max_daily_probe_mb`.
    Сквозная проверка watchdog (загрузка `probe.url` каждые `interval_s`, при
    значениях по умолчанию ещё ~280 МБ/сут) показана отдельной строкой: в
    формулу ТЗ она не входит, но трафик настоящий.
62. **Закрепление (`xgw pin`)**: срок хранится в SQLite, снимает его демон
    (`bo -r`). adrules и перезапуск сбрасывают закрепление в ядре — пока срок
    не вышел, оно выставляется заново; если узел перестал быть участником,
    закрепление снимается. Без запущенного демона срок никто не отслеживает —
    `xgw pin` об этом предупреждает.
63. **`xgw status` без демона** показывает разовый снимок (применённый конфиг,
    метрики, `xray api bi`) без состояния: машину состояний ведёт только демон.
    Статус демона считается свежим, если он не старше трёх шагов watchdog (но
    не менее 3 минут — в WAN_DOWN шаг равен 60 с).
64. **Вывод `xray api bi`** — текстовая таблица (`Selecting Override` /
    `Selects`), не JSON; разбор — `xraycore.api.parse_balancer_info`.
65. **Процесс-зомби живым не считается** (`pid_alive`). Xray, запущенный одной
    командой XGW и остановленный другой, остаётся в таблице процессов, пока
    родитель его не снимет, и `kill(pid, 0)` для него проходит. Состояние
    читается из `/proc/<pid>/stat`; без этого остановка ждала весь `grace`
    (5 с лишнего простоя). Найдено первым прогоном на Linux — как и п. 66.
66. **Реле стенда закрывает соединения через `shutdown()`.** В Linux `close()`
    сокета, на котором соседний поток ждёт в `recv()`, не отправляет FIN, пока
    тот не выйдет из вызова: клиент за реле не видел, что сервер закрыл
    соединение.

## Этап 3: перехват трафика

Проверено на стенде в netns: Ubuntu 26.04.1 (ядро 6.18.40), nftables 1.1.6,
dnsmasq 2.92, Xray 26.3.27.

67. **UDP у inbound `tunnel` включает поле `network`, а не `allowedNetwork`.**
    Раздел 4 ТЗ называет поля `allowedNetwork`, `rewriteAddress`, `rewritePort`,
    но Xray 26.3.27 их не знает (строк нет в бинарнике) и молча игнорирует: с
    одним `allowedNetwork` открывается только TCP, и обычный DNS и QUIC устройств
    терялись бы. Генератор пишет `network: "tcp,udp"`; `allowedNetwork` оставлено
    рядом на случай версии, где поле переименовано. Найдено на стенде.
68. **«Проверить на месте» из раздела 4.** Модули `nft_tproxy`, `nf_tproxy_ipv4`,
    `nft_fib_ipv4`, `nft_ct` загружаются сами при загрузке правил. В таблице `ip`
    принимаются и `tproxy to 127.0.0.1:порт`, и `tproxy ip to …`; используется
    первое. TPROXY-трафик принимает inbound с `listen: "127.0.0.1"` — и TCP, и
    UDP; из LAN этот порт не виден (соединение отклоняется), запасной вариант с
    `0.0.0.0` не нужен.
69. **Порядок правил prerouting** — уточнения к разделу 6.3. На `lo`
    перехватывается только то, что пометила цепочка output (`meta mark`): прочий
    трафик машины к самой себе в Xray не идёт. Адреса самого шлюза исключены
    правилом `fib daddr type local` — иначе при «белом» адресе WAN обращение к
    нему ушло бы через VPN. Порт 53 перехватывается всегда, включая адрес шлюза
    в LAN: его устройства получают как DNS-сервер по DHCP.
70. **Заглушка systemd-resolved (127.0.0.53) не перехватывается**: цепочка output
    пропускает всё, что адресовано самой машине. Запросы приложений идут в
    resolved как обычно, а запросы resolved к вышестоящему DNS (в том числе по
    частному адресу роутера провайдера) перехватываются и уходят в Xray.
71. **forward: политика drop действует только на LAN.** Первое правило цепочки
    пропускает всё, что идёт не через LAN-интерфейс: у нескольких цепочек одного
    хука пакет должен пройти все, и без этого XGW отбрасывал бы форвардинг
    Docker и libvirt.
72. **WAN в правилах.** При пустом `wan_if` форвардинг и маскарадинг записаны
    как «любой интерфейс, кроме LAN»: правила загружаются до сети, когда
    маршрута по умолчанию ещё нет, и определить по нему WAN нельзя.
73. **DNS мимо Xray — цепочка `dns_direct`.** dnsmasq DNS не обслуживает
    (`port=0`), а по DHCP устройства получают DNS-сервером адрес шлюза. Чтобы
    устройства из `bypass_hosts`, а после `xgw disable` и вся сеть, не
    оставались без имён, запрос к шлюзу на порт 53 переадресуется (DNAT) на
    первый из `dns.direct_servers`, записанный адресом. В ТЗ этого нет.
74. **Служба времени.** В правила идут uid тех из `_chrony` и `systemd-timesync`,
    что есть в системе (nft не загрузит правило с неизвестным именем): UDP 123
    и TCP 4460 (NTS-KE). На стенде есть только `systemd-timesync`; chrony с NTS
    не проверялся; что показывает `xgw diag` — п. 97.
75. **fail-closed.** При остановленном Xray выражение `tproxy` не находит
    сокета и правило не срабатывает: пакет из LAN уходит в forward и
    отбрасывается политикой, пакет самой машины остаётся без ответа. Запрос
    завершается таймаутом, наружу ничего не выходит.
76. **Режимы перехвата.** Выбор `enable`/`disable` хранится в
    `/var/lib/xgw/capture.json` и запоминается, только когда правила
    действительно загружены. Временное снятие при `fail_mode = "open"` — метка
    `/run/xgw/capture-open`: после перезагрузки её нет, перехват включён.
77. **`net.ipv4.ip_forward`** включается записью в `/proc/sys`, только когда
    есть LAN; прежнее значение запоминается и возвращается командой
    `xgw net down`. Постоянный файл `/etc/sysctl.d/90-xgw.conf` ставит установка (п. 93).
78. **Демон следит за правилами на каждом шаге watchdog**, а не только при
    LEAK: если загруженное в ядро не соответствует режиму, правила загружаются
    заново. Проверка утечки выполняется, только когда перехватывается трафик
    самой машины (`capture.local`): её делает обычный сокет шлюза.
79. **Запросы DNS не A/AAAA** (TXT, HTTPS) outbound `dns` у Xray 26.3.27 сам
    отклоняет ответом REFUSED и напрямую не пересылает — проверено счётчиком
    nftables на стенде. Поле `nonIPQuery` в конфиг не добавляется.
80. **Сниффинг подставляет домен вместо адреса**, поэтому имя разрешает
    VPN-сервер. На стенде у серверов для этого прописана DNS-заглушка.
81. **Xray закрывает соединение на пару секунд позже сервера** (ответ с
    `Connection: close` через TPROXY). Клиент стенда, как браузер, читает тело
    по `Content-Length` и конца потока не ждёт.
82. **Клиент стенда вместо curl и dig** — `tests/stand/lan_client.py` на
    обычных сокетах: тот же TCP и UDP от «устройства», но без внешних
    программ. Его DHCP-клиент проходит DISCOVER → ACK и адрес интерфейсу не
    назначает.
83. **Команды сверх таблицы ТЗ**: `xgw net up` (для службы `xgw-net`), `xgw net
    down` (для удаления) и `xgw net show` (посмотреть правила, ничего не меняя).
84. **Режим `router`**: dnsmasq выдаёт один адрес — начало `dhcp_range` — по
    `router_mac` (`dhcp-range=…,static`). Конфиг проверен `dnsmasq --test`, на
    стенде режим не запускался.
85. **Не проверено на этапе 3**: штатное ядро Ubuntu (проверено ядро стенда), ограничение
    MSS на PPPoE, соседство с правилами ufw и Docker, chrony с NTS, загрузка
    правил до сети. Что из этого закрыл этап 4 — п. 87, 95, 97, 106.

## Этап 4: установка на машину

Проверено на «одноразовой машине» — Ubuntu 26.04.1, загруженная в контейнере
systemd-nspawn (systemd 259.5, NetworkManager 1.54.3, ufw 0.36.2, dnsmasq 2.92,
ядро 6.18.40). Ручной чек-лист раздела 9 на настоящей машине не выполнялся.

86. **Определение готовности этапа — ручной чек-лист, выполнить его может только
    владелец машины.** Вместо него сделано максимально близкое: установка,
    работа, перезагрузка и удаление на загруженной системе в контейнере
    (`tests/stand/test_machine.py`). Корень контейнера — оверлей поверх корня
    хоста, сеть — своя; сеть хоста не менялась.
87. **ufw: двух правил из раздела 6.3 недостаточно.** Найдено на машине: с
    `ufw allow in on <lan>` и `ufw route allow in on <lan> out on <wan>`
    устройства в LAN в интернет не выходят. Перехваченный пакет проходит цепочку
    INPUT с чужим адресом назначения, и ufw отбрасывает его в `ufw-not-local`
    (`fib daddr type local` не совпадает) — раньше, чем доходит до правил
    пользователя. Командой `ufw` правило туда не добавить. С подтверждения
    владельца (вопрос задан, ответ — «вносить с подтверждения») установка
    добавляет в `/etc/ufw/before.rules` перед переходом в `ufw-not-local` строку
    `-A ufw-before-input -i <lan> -m mark --mark <mark_proxy> -j ACCEPT` и
    выполняет `ufw reload`; копия файла — в `/var/lib/xgw/backup`, удаление строку
    убирает. Разрешает она не больше, чем `ufw allow in on <lan>`. Это
    отступление от раздела 12 («не трогать правила ufw, кроме описанных»).
88. **dnsmasq: `bind-dynamic` вместо `bind-interfaces`.** С `bind-interfaces`
    dnsmasq 2.92 завершается с ошибкой «unknown interface», если при старте у
    карты нет адреса (роутер выключен, кабель не вставлен), а у службы
    дистрибутива нет `Restart=`: устройства остались бы без адресов до ручного
    перезапуска. С `bind-dynamic` он стартует и ждёт интерфейс. Проверено.
89. **Конфиг dnsmasq пишется до установки пакета.** С конфигом по умолчанию
    `dnsmasq.service` пытается занять порт 53, на котором слушает
    systemd-resolved, и не запускается (проверено). С `port=0` из
    `/etc/dnsmasq.d/xgw.conf` конфликта нет. Если dnsmasq уже стоял и работал,
    `port=0` выключит DNS и в нём — другой службе dnsmasq на той же машине XGW
    помешает.
90. **NetworkManager в Ubuntu 26.04** хранит профили, созданные `nmcli`, через
    netplan (`/etc/netplan/90-NM-<uuid>.yaml`) и сам создаёт в памяти профили
    «Wired connection N» с повторяющимися именами — поэтому к профилям XGW
    обращается только по UUID. В пакете есть
    `/usr/lib/NetworkManager/conf.d/10-globally-managed-devices.conf`, из-за
    которого проводные карты не управляются (unmanaged), пока его не
    перекрывает netplan с `renderer: NetworkManager`, как в Desktop. `xgw diag`
    это видит и даёт FAIL.
91. **«Другие профили этого интерфейса»** — те, у кого `connection.interface-name`
    равен `lan_if`. Они не удаляются: запоминаются UUID, имя, автоподключение и
    был ли профиль активен, копия файла кладётся в `backup/nm`, автоподключение
    выключается. Профили без привязки к интерфейсу не трогаются: у `xgw-lan`
    приоритет автоподключения 100, карта достаётся ему.
92. **IPv6 на WAN** отключается в профиле, активном на WAN-интерфейсе (из
    `wan_if` или маршрута по умолчанию), затем `nmcli device reapply`. Если WAN
    не управляется NetworkManager или профиль изменить нельзя — предупреждение
    при установке и FAIL в `xgw diag` после неё (есть глобальный IPv6-адрес).
93. **sysctl.** `/etc/sysctl.d/90-xgw.conf` ставится, только когда есть LAN: в
    режиме «только эта машина» форвардинг не нужен. Прежние значения
    возвращаются при удалении; если форвардинг после установки включил ещё
    кто-то (Docker), удаление его выключит — до перезапуска той программы.
94. **Перехват включается, только если Xray отвечает.** Иначе fail-closed оставил
    бы машину без интернета сразу после установки; в этом случае сохраняется
    выбор «перехват снят» и печатается, что делать. При повторной установке
    выбор пользователя (`enable`/`disable`) не меняется.
95. **Службы.** `xgw-net.service`: `DefaultDependencies=no`,
    `Before=network-pre.target`, `After=nftables.service` (её конфиг начинается
    с `flush ruleset`), без `ExecStop` — остановка службы и выключение машины
    правил не снимают. Проверено после перезагрузки: служба активна раньше
    `network-pre.target` и NetworkManager. `xgw.service`: набор возможностей —
    `CAP_NET_ADMIN` (nft, ip, sysctl сети, `SO_MARK`), `CAP_SETUID` и
    `CAP_SETGID` (runuser для уведомления). С ним и с `ProtectSystem=strict`
    проверены `systemctl restart`, `runuser`, `nft`, запись в `/proc/sys/net`.
    Сверх ТЗ у обеих служб — `NoNewPrivileges`, `PrivateTmp`, у Xray ещё
    `ProtectSystem=strict` и `ProtectHome`.
96. **Права на конфиг Xray.** Каталог `/etc/xgw/xray` — `2750 root:xray`
    (setgid): файлы, которые XGW создаёт в нём атомарной записью, наследуют
    группу `xray` — демону не нужен `CAP_CHOWN`.
97. **Служба времени в Ubuntu 26.04.1** — chrony от пользователя `_chrony`,
    источники по умолчанию с ключом `nts`. Правила пропускают его UDP 123 и
    TCP 4460 мимо перехвата (п. 74); `xgw diag` показывает оба факта.
    Синхронизация времени с включённым перехватом на настоящей машине не
    проверялась: в контейнере chrony не запускается.
98. **Проверка ядра в `xgw diag`**: правила загружаются по-настоящему в отдельное
    пространство имён (`unshare -n nft -f -`). `nft -c` для этого не годится —
    он проверяет только синтаксис и в ядро ничего не отправляет.
99. **Демон перечитывает `config.toml` сам** (по времени изменения файла, на
    каждом шаге watchdog), не перезапуская процесс. Без этого он при следующем
    обновлении подписки вернул бы ядро к настройкам, с которыми был запущен, —
    в том числе убрал бы сервер, добавленный в `[manual]` и применённый
    командой `xgw apply`. С ошибкой в файле работает на прежних настройках.
100. **Токен страницы статуса** в `config.toml` не вписывается (файл пользователя
     XGW не правит): если `status.token` пуст, токен создаётся в
     `/var/lib/xgw/status-token` (0600). В cookie хранится не сам токен, а
     HMAC от него. Страница привязана к адресу шлюза в LAN с `IP_FREEBIND` —
     демон может стартовать раньше, чем карта получит адрес.
101. **Уведомление на рабочий стол**: сессия — из `loginctl list-sessions
     --json=short`, берётся графическая (wayland, x11), не удалённая, с шиной
     `/run/user/<uid>/bus`, активная — в первую очередь. Проверено до вызова
     `notify-send` из службы с урезанными правами; настоящей графической сессии
     в контейнере не было. Telegram — POST на `api.telegram.org`; доставка не
     проверялась (нужен настоящий бот).
102. **Удаление** оставляет `/etc/xgw/config.toml` (в нём подписка) и пакеты,
     поставленные при установке; службу dnsmasq, если её поставил XGW,
     выключает. `--purge` удаляет и `/etc/xgw`.
103. **Запуск.** `/usr/local/bin/xgw` — сценарий Python с ключом `-I`;
     `packaging/install.sh` — три строки без GNU-специфичных флагов, вся логика
     в `xgw install`. Установка читает только `/etc/xgw/config.toml`: ключ
     `--config` для неё запрещён, иначе службы работали бы с другим файлом.
104. **`xgw update-xray`**: новая версия скачивается в соседний каталог,
     проверяется (версия, поле `httpMethod` в бинарнике, `xray run -test`
     рабочим конфигом) и только потом подменяет прежнюю; если Xray после этого
     не отвечает 15 с — возвращается прежняя. Поле `httpMethod` ищется строкой в
     бинарнике: Xray молча игнорирует незнакомые поля (п. 67).
105. **Команды сверх таблицы ТЗ** у этапа 4 нет; добавлены ключи `--yes`,
     `--force`, `--purge`, `--no-net`, `--json`, `-n`, `-f`, `--out`.
106. **Не проверено на этапе 4**: настоящая машина (ядро Ubuntu, две сетевые
     карты, роутер, телефон), PPPoE, соседство с Docker (есть только проверка в
     `diag`), GNOME и его настройка сна, доставка в Telegram, `xgw install` с
     загрузкой Xray с GitHub (загрузка и сверка SHA-256 выполнялись отдельно),
     arm64.

## Сверх ТЗ: панель управления

В ТЗ графического интерфейса нет; он сделан по просьбе владельца («по аналогии с
Happ»), затем дополнен редактированием списка серверов подписок. Ограничения
раздела 12 при этом соблюдены: ничего нового наружу не слушает, зависимостей нет.

107. **Панель — страница в браузере, а не отдельное приложение.** Её отдаёт
     демон на `127.0.0.1:8781` (`[panel]`). Причины: стандартной библиотеки
     достаточно (у отдельного окна — GTK и привязки к нему); правило «слушать
     только 127.0.0.1» выполняется; страницу можно проверить на любой системе.
     Управления из домашней сети нет: страница статуса для LAN (п. 100) осталась
     только для чтения.
108. **Вход и защита запросов.** Токен (24 случайных байта) — в
     `/var/lib/xgw/panel-token` (0600), в cookie — HMAC от него (`HttpOnly`,
     `SameSite=Strict`). Запрос с заголовком `Host`, отличным от
     `127.0.0.1:<порт>` и `localhost:<порт>`, отклоняется (подмена DNS). Менять
     что-либо можно только запросом POST с заголовком `X-XGW-Panel`; `Origin` и
     `Sec-Fetch-Site`, если они есть, должны указывать на саму панель. CSP — без
     встроенных сценариев и стилей, со страницы ничего не загружается со
     стороны. Тело запроса дочитывается до отказа: иначе соединение рвётся
     раньше, чем клиент получит ответ (замечено в тестах). Известное
     ограничение: cookie привязана к имени `127.0.0.1`, а не к порту, поэтому
     её получит и любая другая программа на этой же машине, если открыть в том
     же браузере её страницу на `127.0.0.1` с другим портом. От сайтов в
     интернете и от устройств в сети это не зависит.
109. **`/etc/xgw/panel.json` рядом с `config.toml`.** `config.toml` программа не
     переписывает: в стандартной библиотеке нет записи TOML, а в файле —
     комментарии и порядок владельца (тот же принцип, что в п. 100). В
     `panel.json` (0600) — подписки и ссылки, добавленные в панели, и отпечатки
     отключённых и убранных серверов. При чтении конфига списки складываются;
     при совпадении имён подписка из `config.toml` главнее. Битый `panel.json` —
     предупреждение, а не отказ работать.
110. **Из панели — только подписки `http://` и `https://`.** `file://`
     заставил бы демон читать файлы машины от root. Подписка по `http://`
     принимается, но помечается «без шифрования».
111. **Отключённый или убранный сервер в конфиг Xray не попадает** — ни
     участником, ни запасным: ядро его не использует, сканы не проверяют. Оба
     действия хранятся по отпечатку (протокол, адрес, порт, ключ, транспорт) и
     потому переживают обновление подписки и смену имени; смена адреса или
     ключа делает сервер новым. Разница между действиями — только в том, виден
     ли сервер в списке. Последний включённый сервер отключить нельзя, а
     «Отключить все» оставляет один: без серверов конфиг не собрать, и ядро
     осталось бы работать на прежнем — то есть на тех самых серверах, которые
     просили отключить.
112. **Список серверов для панели** — `/var/lib/xgw/inventory.json`: всё, что
     дали подписки, включая то, чего в ядре нет (отключённое, отсеянное
     фильтрами). В нём имя, протокол, источник и отпечаток — без адресов и
     ключей. В `status.json` у участников и запасных появились поля
     `fingerprint` и `source`, в корне — `sub_errors` (почему подписка не
     обновилась).
113. **После перечитывания настроек подписки заново не запрашиваются, если
     источники серверов не изменились** — конфиг пересобирается из уже
     полученного списка. Раньше (п. 99) любая правка `config.toml` вела к
     новому опросу; с панелью каждое нажатие выключателя стоило бы запроса ко
     всем подпискам. Если изменился сам список подписок или ссылок — опрос
     сразу, как прежде.
114. **Кнопки панели и команды — один и тот же код** (`xgw/actions.py`): включение
     и снятие перехвата, закрепление. Отличие одно: панель не включает
     перехват, пока Xray не отвечает (команда `xgw enable` включает и
     предупреждает) — человеку с одной кнопкой fail-closed без работающего
     ядра выглядел бы как «интернет пропал».
115. **Запросы панели выполняет шаг watchdog.** Панель работает в потоках
     демона, но менять конфиг ядра продолжает один поток: «обновить» и
     «проверить запасные» — отметки, по которым просыпается пауза между шагами.
     Включение перехвата и закрепление идут сразу, как из терминала: они и там
     выполняются рядом с работающим демоном, под теми же файловыми блокировками.
116. **Установка без подписки.** Раньше отсутствие подписки было отказом; теперь,
     если панель включена, установка проходит, перехват не включается, интернет
     остаётся прямым, а итог установки ведёт в панель. Демон в таком состоянии
     ничего не сообщает: «подписок ещё нет» — не сбой. Подписка в
     `config.example.toml` закомментирована; раскомментированная без правки
     по-прежнему останавливает установку.
117. **Вопрос о сетевой карте.** При первом запуске из терминала установка
     показывает проводные карты, кроме той, через которую идёт интернет, и
     вписывает выбранную в только что созданный `config.toml` — заменой
     единственной строки `lan_if = ""`. Существующий конфиг установка не
     правит никогда. С ключом `--yes` или без терминала вопросов нет: поведение
     прежнее (создать файл и остановиться).
118. **Ярлык** — `/usr/local/share/applications/xgw-panel.desktop`
     (`Exec=xdg-open http://127.0.0.1:8781/`, значок — файл из `/opt/xgw`).
     Токена в ярлыке нет: первый вход — по ссылке, которую печатают установка
     и `sudo xgw panel`, дальше браузер помнит вход год. Каталог, если его
     создала установка, при удалении убирается пустым.
119. **Закрыто: через маршрут `direct` устройство из LAN доставало до служб на
     127.0.0.1 шлюза.** Подозрение, записанное при чтении конфига, на стенде
     подтвердилось (netns, Xray 26.3.27): сниффинг в `tproxy-in` подменяет адрес
     назначения именем из запроса, а outbound `direct` разрешает это имя сам; если
     имя входит в `routing.direct_domains` и указывает на 127.0.0.1, Xray
     соединялся с собственным loopback шлюза. Были достижимы HTTP-служба на
     loopback, метрики Xray (сведения о серверах) и `http-in`; прежняя запись «API
     так не используется» оказалась неверной — проверка показала, что путь к
     служебным портам Xray открыт тоже. Это свойство конфига этапов 1–3, панели
     оно не касалось (Host + токен, п. 108). Исправление — п. 121.
120. **Не проверено для панели**: Ubuntu Desktop с настоящим рабочим столом —
     появление ярлыка в меню GNOME, `xdg-open`, Firefox (в Ubuntu это snap) и
     чтение им буфера обмена. Страница проверялась в браузере на основе
     Chromium на выдуманных данных (`tests/panel_demo.py`); сервер панели и все
     её действия — юнит-тестами и на «одноразовой машине» запросами с самого
     шлюза.
121. **`loopback_guard`: помеченным пакетам вход в 127.0.0.0/8 закрыт.** В таблице
     `ip xgw` при любом включённом перехвате есть цепочка `output` (hook output,
     priority filter): `meta mark <mark_bypass> ip daddr 127.0.0.0/8 counter
     reject`. Метку `mark_bypass` несут сокеты `direct` и других outbounds Xray,
     к loopback им ходить незачем: адреса серверов с 127.0.0.0/8 отбрасываются
     ещё при разборе (ТЗ, 6.5), DNS обслуживает сам Xray. Проверено: у `freedom` в
     Xray 26.3.27 нет поля запрета по IP (в бинарнике нет `finalRules` и
     `ipsBlocked`), а правило маршрутизации по `ip` не срабатывает на имени,
     уже совпавшем с `direct_domains`; `routeOnly` изменил бы поведение для
     проксируемых соединений (п. 6.4 ТЗ). Поэтому запрет стоит в nftables.
     Отказ — `reject`, а не `drop`: Xray сразу получает «в соединении отказано» и
     не держит сокет до таймаута. Побочные следствия:
     - Свои запросы XGW к loopback (подписка на `127.0.0.1`, прокси `http-in`,
       probe-inbounds) идут без метки: `marknet.connect_marked` её для loopback не
       ставит, потому что loopback не перехватывается, — они правилу не мешают.
     - Программа на самом шлюзе, которая ходит через `socks-in`/`http-in` к
       службе на `127.0.0.1`, теперь получает отказ: Xray отправил бы такое
       соединение в `direct` с меткой. Ограничение принято сознательно.
     - Службы, слушающие адрес шлюза в LAN или `0.0.0.0`, из LAN доступны и
       раньше (они не перехватываются: `fib daddr type local`); правило их не
       затрагивает. Чему они открыты — решает их собственная настройка.
     - Со снятым перехватом (`xgw disable`, fail_mode = open) цепочки нет: Xray
       трафик устройств не обслуживает.
     Стенд (`test_lan_device_cannot_reach_gateway_loopback_through_direct`):
     с цепочкой службы шлюза недостижимы и счётчик правила растёт; после
     `flush chain` те же запросы проходят (контроль, что тест видит проблему);
     `xgw net up` возвращает правило. Обычное имя из `direct_domains` идёт
     напрямую, как раньше.
122. **Этап 5, правила для отдельных устройств — в панели, а не на странице
     статуса.** В ТЗ они названы «правилами на странице статуса», но страница статуса
     для LAN только читает (п. 100, 107): пустить себя мимо VPN с телефона в Wi-Fi
     не должно быть можно. Панель слушает только 127.0.0.1 и защищена токеном
     (п. 108), поэтому переключатель там. Правило одно — «мимо VPN»; других
     (принудительно через VPN, блокировка, расписание) ТЗ не требует.
123. **Устройство мимо VPN = запись в `panel.json` и статическая аренда.** Шлюз
     узнаёт устройство по адресу (набор `bypass4`), а адрес из динамической аренды
     может достаться другому, поэтому панель закрепляет за MAC текущий адрес
     (имя из аренды — если оно годится для `dhcp-host`). При чтении конфига запись
     превращается в `network.static_leases` и `network.bypass_hosts`; `config.toml`
     главнее: уже заданное там не дублируется, а конфликтующий MAC или адрес
     пропускается с предупреждением. Устройство вне сети шлюза и сам шлюз закрепить
     нельзя. Устройства, пущенные мимо VPN в `config.toml`, панель не меняет и
     отмечает «config.toml».
124. **Изменение применяется сразу и с откатом.** Панель вызывает тот же код, что
     `xgw apply` (`actions.apply_network`): правила nft проверяются `nft -c` и
     заменяются одной транзакцией, затем при изменении `xgw.conf` перезапускается
     dnsmasq. Если любой шаг не удался, запись в `panel.json` возвращается, а сеть
     приводится к прежнему состоянию; пользователь видит причину. Демон при
     перечитывании настроек загружает правила заново сам (cli.py, `_cmd_run`).
     Проверено на «машине» (настоящие systemd, nftables, dnsmasq): устройство уходит
     мимо VPN, остальные остаются за VPN, после потери таблицы демон загружает
     её заново уже с этим устройством, возврат убирает адрес из `bypass4` и
     аренду из `xgw.conf`. Тест нашёл то, чего не видели юнит-тесты: служба
     `xgw.service` работает с `ProtectSystem=strict` и не могла писать
     `/etc/dnsmasq.d` — каталог добавлен в `ReadWritePaths` (с «-»: пока dnsmasq
     не установлен, каталога нет, а служба обязана стартовать). Перезапуск dnsmasq
     на секунды прерывает выдачу адресов — уже выданные аренды не страдают.
125. **Бот Telegram (этап 5): опрос, а не вебхук.** Бот вызывает `getUpdates` (long
     polling, 25 с): входящих соединений и открытых портов нет, внешний адрес шлюзу
     не нужен (раздел 12 ТЗ запрещает слушать внешние адреса). Выход в Telegram —
     как у уведомлений: через http-in Xray, а если он не отвечает — напрямую с
     меткой мимо перехвата. Это значит, что при остановленном Xray бот отвечает в
     обход VPN; закрытый Telegram в таком режиме бот не откроет. Используются
     только методы из публичной документации Bot API: `getMe`, `getUpdates`
     (offset, timeout, allowed_updates=["message"]), `sendMessage` (chat_id, text,
     disable_web_page_preview) и форма ответа `{ok, result}` либо `{ok: false,
     error_code, description}`; HTTP 401 — неверный токен, 409 — второй опрашивающий.
     **Не проверено на настоящем Telegram**: настоящий токен ТЗ использовать
     запрещает (раздел 12). Тесты идут на локальном поддельном Bot API
     (`tests/fake_telegram.py`), который отвечает по тем же правилам; на стенде и
     «машине» он работает отдельным процессом на стороне «интернета». Первый
     настоящий запуск — ручная проверка по README.
126. **Кому бот верит.** Только чату `notify.telegram_chat_id`; остальные сообщения
     не обрабатываются и ответа не получают (так бот не подтверждает, что он
     существует). Управляющие команды — только из личного чата (`chat.type ==
     "private"`): в группе их мог бы отправить любой участник, а id группы — это
     тот же `telegram_chat_id`. Команда старше 120 с игнорируется, потому что
     Telegram хранит неполученные сообщения до суток, а `/disable` трёхчасовой
     давности после перезагрузки не должна срабатывать. Идентификатор чата
     проверяется как целое число, не строка.
127. **Подключение чата кодом.** Чтобы не просить человека искать свой chat id,
     панель показывает шестизначный код (`secrets.randbelow`), а бот запоминает чат,
     из которого пришло `/start КОД`. Код действует 15 минут, одну попытку подбора
     из пяти сжигает каждый неверный ответ, подключить можно только из личной
     переписки и только токен из панели (если бот задан в `config.toml`, подключения
     нет: чат вписывают туда же). Код живёт в памяти демона и в `panel.json` не
     пишется; токен и chat_id — пишутся (0600), токен в панель, логи и статус не
     возвращается. Пока код не запрошен кнопкой, подключиться нельзя вовсе.
     Настройки могут перечитаться посреди опроса (он ждёт до 25 с), поэтому код
     привязан к токену, сообщения разбираются по актуальным настройкам, а
     подключённый чат запоминается отдельно, пока перечитанные настройки его не
     принесут. Без этого «машина» один раз осталась без ответов бота после
     подключения (чат лежал в старом объекте настроек); теперь это закрыто
     тестами `test_reload_during_the_poll_…` и `test_stale_reload_…`.
128. **Команды совпадают с кнопками.** `/enable` и `/disable` — тот же код, что
     кнопка панели и `xgw enable`/`disable` (`actions`); как у кнопки, `/enable`
     отказывает, пока Xray не отвечает (`actions.enable_checked`) — человек, который
     управляет шлюзом из чата, остался бы без интернета и без возможности вернуть
     его. `/pin` берёт номер из `/servers` (позиция в списке участников), срок по
     умолчанию 1h, предельный — 24h, как у `xgw pin`. Управление устройствами
     (мимо VPN) из Telegram не сделано: это решение о защите трафика, и в чате его
     легко принять по ошибке; оно остаётся в панели. Каждая управляющая команда
     пишется в журнал событий («Telegram: команда …»).
129. **Параметры.** `notify.commands` (по умолчанию `true`) включает ответы на
     команды; `false` — только уведомления, и тогда бот вообще не опрашивает
     Telegram. `notify.telegram_api` — адрес Bot API (по умолчанию
     `https://api.telegram.org`; нужен для собственного сервера Bot API и для
     стенда), принимается только `http(s)://адрес`.
130. **IPv6 (этап 5): проксируется только IPv6 самой машины.** `network.ipv6 =
     "proxy"` перехватывает IPv6 приложений на шлюзе; устройствам в Wi-Fi IPv6 не
     выдаётся (нет ни RA, ни DHCPv6, профиль `xgw-lan` остаётся с `ipv6.method
     disabled`) и форвардинг IPv6 из LAN и в LAN по-прежнему запрещён. Выдача IPv6
     клиентам — это префикс (ULA или делегированный), RA через dnsmasq, согласование
     с роутером в режиме точки доступа и ещё один набор исключений для обхода; оно
     отложено, пока не понадобится. Любое значение, кроме `proxy`, считается `off`
     (с предупреждением): неизвестное слово не должно молча пускать IPv6 мимо
     перехвата. При `capture.local = false` режим ничего не делает (предупреждение).
131. **Как устроен перехват IPv6.** Копия схемы IPv4: метки `mark_proxy` и
     `mark_bypass`, таблица маршрутизации `route_table` (для `ip -6` она своя, номер
     тот же), цепочки `prerouting` (только `lo`), `output` и `loopback_guard` в
     `ip6 xgw6`, набор `reserved6` (`::/127`, `fc00::/7`, `fe80::/10`, `ff00::/8` и
     IPv6-сети из `exclude_cidrs`; порт 53 перехватывается всегда). TPROXY — на
     `[::1]:tproxy_port` через второй inbound `tproxy-in6` (`listen: ::1`, те же
     настройки, что у `tproxy-in`; тег добавлен в правило порта 53 → `dns-out`).
     В выводе `nft list` правило печатается как `tproxy to [::1]:порт`. Служба
     времени идёт мимо перехвата, как в IPv4. **Проверено**: стенд в netns (ядро
     6.6, nftables 1.1.6, Xray 26.3.27: TCP, UDP-DNS и TCP-DNS по IPv6,
     fail-closed, `enable`/`disable`/`net down`, возврат пропавшей таблицы,
     `loopback_guard` для `::1` с контрольным опытом без него) и «одноразовая
     машина» (systemd, NetworkManager: установка, inbound на `::1` под песочницей,
     демон возвращает таблицу, удаление). **Не проверено**: настоящая сеть с IPv6
     (двойной стек, только IPv6, NAT64), PMTU и фрагментация, влияние на IPv6
     через VPN-сервер без IPv6-выхода — там соединение по IPv6 просто не
     установится, приложения вернутся к IPv4 сами.
132. **DNS и direct при IPv6.** Только в режиме `proxy`: `dns.queryStrategy` и
     `domainStrategy` outbound `direct` — `UseIP` (иначе приложения не получали бы
     AAAA, а имя из `direct_domains` без A-записи не открывалось бы). Серверы
     подписки по имени по-прежнему разрешаются по IPv4 (`UseIPv4` в `sockopt`):
     при `UseIP` Xray выбирал бы между A и AAAA, а сломанный IPv6 у провайдера
     ронял бы часть соединений; узлы, записанные IPv6-адресом, работают. Выбор
     между A и AAAA при `UseIP` делает Xray; предпочтение семейства не проверялось.
133. **Если IPv6 в ядре нет.** Каталога `/proc/sys/net/ipv6` нет (`ipv6.disable=1`)
     или `disable_ipv6 = 1` на `all`/`lo` (нет `::1`) — режим `proxy` отключается
     с предупреждением: ни `ip -6`, ни таблица `ip6`, ни inbound на `::1` (Xray на
     нём не запустился бы) не используются. Если IPv6 есть, но правила IPv6 не
     загрузились — это ошибка загрузки, а не предупреждение: иначе IPv6 ушёл бы
     мимо перехвата. Смена `off` ↔ `proxy` повторной установкой: `proxy` возвращает
     IPv6 в профиле WAN из журнала, `off` отключает его снова (исходное значение
     профиля запоминается один раз и не теряется); профиль, которого XGW не менял,
     не трогается. Правка одного config.toml (без повторной установки) загружает
     правила сразу, а конфиг Xray с новым inbound применяется только в
     `restart_window` либо по `xgw apply --now`: до тех пор IPv6 машины блокируется
     (TPROXY без слушателя), но не уходит мимо; повторная установка применяет всё
     сразу (`force_now`). Если `off` вернули правкой config.toml без повторной установки,
     IPv6 на WAN остаётся включённым и идёт мимо перехвата — `xgw diag` показывает
     это как FAIL с готовой командой.
134. **TUN (этап 5): inbound `tun` уже есть в Xray 26.3.27, маршруты ведёт XGW.** ТЗ
     связывает TUN с v26.4.13 — в ней появились автоматические маршруты. Но сам inbound
     `tun` (Linux) в 26.3.27 есть: `proxy/tun` создаёт интерфейс и поднимает его.
     **Проверено опытом** на 26.3.27: поля `gateway` и `autoSystemRoutingTable` Xray
     молча игнорирует (адресов и маршрутов не появляется — как было с `allowedNetwork`
     у tunnel). Они из документации и в XGW **не используются**: XGW ведёт интерфейс,
     адрес, правила и маршруты сам, с проверкой и откатом (раздел 12 ТЗ), поэтому новый
     бинарник не нужен. Поля `autoOutboundsInterface` и `userLevel` тоже не заданы.
     Что делает режим на более новом Xray (в том числе не меняет ли он по умолчанию
     маршруты сам) — не проверено; перед обновлением Xray выше 26.3.27 режим TUN стоит
     пройти стендом (`tests/stand/test_stand_tun.py`).
135. **Постоянный интерфейс, который создаёт XGW.** Xray подключается к готовому
     интерфейсу и при остановке оставляет его (проверено: состояние NO-CARRIER, и он
     переживает перезапуски). Поэтому маршрут в него не пропадает вместе с Xray, и
     пока ядро не работает, пакеты отбрасываются — fail-closed, как у TPROXY. Если
     интерфейс всё же исчез, остаётся запасной маршрут `blackhole default metric 4096`
     в той же таблице. Интерфейс создаётся при включении перехвата (`xgw net up`,
     загрузка раньше Xray) и перед каждым запуском Xray (`Applier`); созданный самим
     Xray, он исчезал бы с ним. `xgw disable`, `fail_mode = open` и `xgw net down` его
     оставляют (Xray держит его открытым, удалённый из-под него интерфейс требовал бы
     перезапуска Xray); убирает его `xgw uninstall`, уже после остановки служб.
     Интерфейс после перезагрузки пропадает сам. Владельца интерфейсу не задаём: Xray
     (пользователь `xray`, CAP_NET_ADMIN) подключается к нему под песочницей systemd —
     проверено на «машине».
136. **Две таблицы и выбор по `iif lo`.** Метка у пакета одна, а маршрут нужен разный:
     помеченные пакеты сети Wi-Fi должны доставляться локально (TPROXY), а пакеты самой
     машины — уходить в TUN. Поэтому правило для TUN (`fwmark M iif lo lookup
     tun_route_table`, pref 90) выбирает только пакеты, созданные на самой машине, и
     стоит раньше правила TPROXY (pref 100, `route_table`). Новое поле
     `capture.tun_route_table` (101, не 253–255 и не `route_table`). Без сети Wi-Fi
     правила и таблицы TPROXY нет вовсе. Цепочка `prerouting` теперь только для сети
     Wi-Fi (при `method = tun`) либо ещё и для `lo` (при `tproxy`); `loaded()` видит и
     недостающее, и лишнее от другого режима.
137. **Адрес на интерфейсе и rp_filter.** Без IPv4-адреса на интерфейсе ядро
     отбрасывает ответы Xray даже при «мягком» `rp_filter = 2` (судя по коду ядра,
     `fib_validate_source`, интерфейс без адреса идёт в ветку отказа); на стенде это
     видно по растущему
     `TcpExtIPReversePathFilter`, соединения не устанавливаются. Поэтому на интерфейсе
     один адрес `169.254.10.1/32` (link-local, как Xray берёт по умолчанию на macOS;
     `/32` не создаёт маршрута). На самом интерфейсе XGW пишет `rp_filter = 0`.
     **Строгий `rp_filter = 1` в `all` не поддержан**: ответы приходят с интерфейса, до
     отправителя через который маршрута нет; `xgw diag` предупреждает с готовой
     командой. Умолчание Ubuntu — 2.
138. **Что режим TUN не меняет и что не проверено.** Сеть Wi-Fi остаётся на TPROXY: у
     TUN нет аналога `fib daddr type local th dport 53` для DNS к самому шлюзу, а
     пересылаемый через TUN трафик потребовал бы своих правил `forward`. ICMP машины
     идёт напрямую, как и раньше (метятся только TCP и UDP). `xray run -test` создаёт
     интерфейс из inbound `tun`, и рабочий Xray держит его открытым — поэтому проверка
     конфига идёт с одноразовым именем интерфейса (`xgwchkNNN`), а без root inbound из
     проверки убирается (его принимает службный запуск от `xray`); контрольный опыт на
     стенде подтверждает конфликт без подмены. **Не проверено**: Xray новее 26.3.27,
     производительность на скоростях порядка гигабита (нагрузка стенда — 3 МБ),
     настоящие приложения (браузер, торренты), пользовательские настройки `ufw` для
     интерфейса `xgwtun0` (на «машине» ufw включён, и трафик проходил).
139. **Вывод для пользователя.** TUN-режим не быстрее и не надёжнее TPROXY для самой
     машины — он добавлен как запасной вариант (например, если TPROXY на lo не
     устраивает); по умолчанию остаётся `tproxy`. Он ничего не даёт сети Wi-Fi.
140. **Сон маскируется только шлюзу с сетью за ним.** Раздел 6.2 ТЗ объясняет
     `disable_sleep` тем, что уснувший шлюз оставляет без интернета весь дом. В режиме
     «только эта машина» (`network.lan_if` пуст) оставлять некого, а ноутбук, который
     перестал засыпать, — заметный вред. Поэтому `disable_sleep = true` действует
     только при заданном `lan_if` (`sleep.wanted`); без роутера установка сон не
     трогает и пишет об этом в плане, `xgw diag` замечания не делает. Повторная
     установка уже без роутера (или с `disable_sleep = false`) снимает маску,
     поставленную прошлой установкой, — раньше это делало только `xgw uninstall`;
     цели, замаскированные до XGW, остаются как были. Остальное от прежней установки с
     роутером (профиль `xgw-lan`, sysctl, конфиг dnsmasq) такая повторная установка
     по-прежнему не убирает — это делает `xgw uninstall`.
141–147. Сняты в 0.1.4 (п. 175).
148. **Xray ещё не запускался — не сбой.** Пока рабочего конфига Xray нет (до первой
     подписки), `xgw diag` пишет WARN «ещё не запускался… добавьте подписку в панели», а
     `xgw status` и бот Telegram — «ещё не запускался», а не «НЕ ОТВЕЧАЕТ».
149. Снят в 0.1.4 (п. 175).

## После проверки на настоящей машине (октябрь 2026)

Отчёт — `docs/TEST-REPORT-2026-10-14.md`: Ubuntu 24.04.5, две сетевые карты, две
настоящие подписки. Ниже — что из него сделано и на чём основано каждое решение.

150. **Предохранитель перехвата распространён на TUN — и исправлен для TPROXY.** Правка
     из отчёта (D1) не загружала перехват, пока в применённом конфиге Xray нет inbound'а
     на `capture.tproxy_port`. Для `capture.method = "tun"` без сети за шлюзом
     (`capture.lan = false`) генератор `tproxy-in` не пишет вовсе, и с такой проверкой
     перехват не включился бы никогда. Теперь проверяется ровно то, на что ссылаются
     правила: нужен TPROXY (сеть LAN либо сама машина без TUN) — должен быть `tproxy-in`
     на этом порту; нужен TUN — inbound `tun` с тем же именем интерфейса, что в
     `capture.tun_name`, и сам интерфейс в системе (его создаёт XGW; проверяется после
     создания). `tproxy-in6` не проверяется намеренно: без него закрыт только IPv6, и
     программы переходят на IPv4, а снять из-за этого весь перехват было бы хуже.
     Состояние вычисляется из файлов, а не помнится в объекте: `xgw status`, панель и
     демон — разные процессы и экземпляры. `loaded()` сверяет ядро с тем режимом,
     который на самом деле загружается; иначе демон на каждом шаге «возвращал» бы
     правила и писал об этом событие.
151. **Сначала конфиг, потом правила.** Если настройки изменились так, что правилам
     нужен inbound, которого у работающего Xray ещё нет (сменили способ перехвата, порт,
     имя TUN), демон сначала применяет конфиг и только потом трогает правила, а
     перечитывание настроек их не перезагружает. Прежние правила и прежний Xray
     согласованы и трафик через VPN носят; загрузи XGW «новые» правила сразу, трафик
     ушёл бы в никуда (так было до отчёта) либо — с предохранителем — пошёл бы мимо VPN
     на те секунды, что перезапускается Xray. Остаётся одно окно без интернета: между
     перезапуском Xray и загрузкой новых правил в том же шаге (доли секунды — секунды).
152. **Inbound перехвата не ждёт окна перезапуска.** Сравниваются inbound'ы `tproxy-in`,
     `tproxy-in6`, `tun-in` (и любой inbound протокола `tun`) целиком, как JSON:
     появился, исчез, изменился любой параметр — перезапуск сразу, и для уже отложенного
     конфига тоже. Прочие inbound'ы (`socks-in`, `http-in`) по-прежнему ждут
     `apply.restart_window`.
153. **Пересечение подсетей — отказ, а не предупреждение.** Занятыми считаются сети
     адресов IPv4 всех интерфейсов, кроме самой карты LAN, сети маршрутов через них и
     адрес шлюза по умолчанию (`ip -j -4 addr show`, `ip -j -4 route show`); loopback и
     link-local не в счёт (иначе мешал бы адрес TUN-интерфейса XGW). Маршруты нужны для
     PPPoE: у интерфейса адрес /32, а шлюз провайдера может оказаться внутри нашей
     подсети. Установка с пересечением не начинается и с `--force`: в отличие от
     остальных FAIL здесь сеть машины ломается наверняка, а не «возможно». Проверка
     повторяется перед созданием профиля `xgw-lan` — за время установки пакетов мог
     подняться другой интерфейс. Умолчание `192.168.50.1/24` оставлено: менять его
     значит менять документацию и чужие установки; совет в сообщении называет первую
     свободную подсеть из 192.168.60–250.0/24. **Не проверено на настоящей машине** —
     только на подставных выводах `ip` и на «одноразовой машине» (там пересечения нет).
154. **Чем на самом деле ходит проба Xray.** Отчёт называет причиной D3 User-Agent
     `Go-http-client/1.1`. Проверено на Xray 26.3.27 локальным сервером, печатающим
     заголовки: burstObservatory отправляет полный набор заголовков Chrome
     (`User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) … Chrome/151.0.0.0 …`,
     `Sec-CH-UA`, `Sec-Fetch-*`) и `Accept-Encoding: gzip`. Небраузерный User-Agent был
     только у собственных проверок XGW (`xgw/0.1`) — они и получали 403. С этой машины
     `speed.cloudflare.com/__down?bytes=65536` отдаёт 200 при любом User-Agent: отказ
     зависит от адреса клиента, воспроизвести его здесь не удалось.
155. **Почему `probe.url` по умолчанию — не тот, что в задании на доработку.** Кандидат
     из задания, `cdn.jsdelivr.net/npm/moment@2.29.4/min/moment.min.js`, без сжатия
     весит 58 103 байта, а с `Accept-Encoding: gzip` — 18 514 (измерено). Проба Xray
     сжатие просит всегда, значит, качала бы 18,5 КБ — меньше порога «заморозки» из
     отчёта (19 451 байт у одного из узлов): детектор молча ослаб бы. Выбран файл с того
     же CDN, который не сжимается: `material-design-icons@3.0.1/iconfont/
     MaterialIcons-Regular.woff` — 57 620 байт и с gzip, и без (WOFF уже сжат внутри),
     `Content-Length` в ответе есть, версия пакета неизменяема (`immutable`), SHA-256
     одинаков при разных User-Agent. Требованиям задания он отвечает: 50–65 КБ, без
     проверки браузерного User-Agent, 5 × 57 620 × 2880 ≈ 830 МБ в сутки. **Не
     проверено**: доступность jsDelivr у конкретного провайдера и через конкретные
     VPN-серверы — это показывает `xgw diag` (строки `probe.url`).
156. **`probe.user_agent`.** Относится только к собственным запросам XGW (скан,
     сквозная проверка, `xgw probe`, `xgw diag`, проверка утечки, контрольные запросы):
     у pingConfig в Xray 26.3.27 поля для заголовков нет, и выдумывать его нельзя.
     Пустое значение и значение с управляющими символами заменяются умолчанием — перевод
     строки в заголовке позволил бы дописать в запрос что угодно. Сжатия собственные
     пробы не просят: тело нужно целиком, по нему считается расход.
157. **`PROBE_TARGET_UNREACHABLE`: что считается доказательством.** Повод — сквозная
     проверка не проходит `fail_threshold` шагов подряд либо ядро уже объявило мёртвыми
     всех участников (второе добавлено после теста: иначе шаг успевал уйти в `ALL_DEAD`,
     и скан затирал вердикты запасных). Опрашиваются все участники и до трёх запасных
     (сначала прошедшие последний скан), одновременно, результаты никуда не
     записываются. Одна ошибка у всех — ещё не вывод: одинаковые таймауты дают и мёртвые
     серверы. Решает контрольный запрос: для кода HTTP — тот же код при запросе напрямую
     либо прошедший базовый запрос через VPN (`probe.trace_url` через http-in); для
     таймаутов и обрывов — только базовый запрос через VPN, потому что `probe.url`
     напрямую может быть просто закрыт провайдером. «Заморозка» (часть тела пришла)
     доказательством не бывает никогда. Перепроверка — раз в 5 минут; прошла сквозная
     проверка — состояние снимается сразу. `probe.url_fallback` из ТЗ по-прежнему не
     используется: переключение проб ядра на другой адрес требует перезапуска Xray и
     отдельного решения, когда возвращаться.
158. **Расход трафика считается от измеренной пробы.** Размер тела `probe.url`
     запоминает сквозная проверка (вместе с адресом: после смены `probe.url` старая
     запись не годится); до первого измерения берётся размер из URL (`…?bytes=`), для
     файла по умолчанию — известные 57 620 байт, для незнакомого адреса — 64 КиБ. Лимит
     `max_daily_probe_mb` по-прежнему сравнивается с суммой «пробы ядра + сканы»
     (формула раздела 6.8 ТЗ), а в «всего» и в месячную цифру входит ещё сквозная
     проверка: из квоты подписки уходит именно всё. Месяц — 30 суток. Доля квоты — от
     полной квоты подписки (`total` из `subscription-userinfo`). Для сжимаемого
     `probe.url` оценка проб ядра завышена: Xray получает сжатое тело.
159. **Домены без адреса: карантин на 6 часов.** `resolve_domain` отличает
     определённый ответ (RCODE 3 NXDOMAIN либо пустой ответ хотя бы от одного резолвера
     при отсутствии адресов у остальных) от сбоя резолвера (таймаут, SERVFAIL, отказ).
     Только первое отправляет домен в карантин; иначе при отключении интернета из
     конфига пропали бы все серверы с доменными именами. Карантин — память процесса
     демона: `xgw apply` из терминала проверяет имена заново, кнопка «Обновить» в панели
     сбрасывает его. Звено цепочки (`dialerProxy`) с таким доменом не выбрасывается —
     вместе с ним пришлось бы выбросить серверы, которые на него ссылаются.
     Тесты в настоящий DNS больше не ходят (`conftest.py`): раньше сборка конфига в
     юнит-тестах спрашивала у 1.1.1.1 имена вида `de.example.com`, и результат зависел
     бы от наличия сети.
160. **Первая проверка участников.** Каждый участник один раз проверяется собственной
     пробой шлюза (в начале очереди сканов); `CONNECT_FAIL` или `FROZEN` — замена сразу
     на запасной, прошедший скан, без `rotate_after_min`. `TIMEOUT` и
     `STALL_BEFORE_BODY` идут обычным путём: они бывают разовыми. Отметка о провале
     снимается, если ядро сообщает, что участник жив, и когда установлено, что не
     отвечал сам `probe.url`. Проверенные участники запоминаются до перезапуска демона
     (перечитывание настроек их не сбрасывает). Цена — одна проба на участника.
161. **Предупреждения Xray об устаревании: что убирается, а что нет.** Проверено
     запуском Xray 26.3.27 на образцах outbound'ов (в режиме `-test` предупреждений нет,
     они печатаются при обычном запуске):
     - `This feature "host" in "headers" is deprecated, will be removed soon…` — запись
       `wsSettings.headers.Host`. Ссылки XGW и раньше разбирал в отдельное поле `host`,
       а JSON-подписки приносили `headers.Host` как есть. Теперь генератор переносит его
       в `host` (явный `host` главнее). У HTTPUpgrade та же запись уже ошибка
       (`"headers" can't contain "host"`) — такие серверы раньше выпадали из конфига как
       не принятые Xray, теперь работают;
     - `The feature Shadowsocks (with no Forward Secrecy, etc.) is deprecated…` (то же
       для VMess, Trojan, `WebSocket transport` и `HTTPUpgrade transport`) — это о
       протоколе сервера, а не о записи: проверены обе записи Shadowsocks (`servers` и плоская) и шифр 2022 —
       предупреждение одно и то же. Убрать его генератор не может: протокол выбирает
       владелец подписки. Строка печатается один раз на запуск Xray.
     Итог проверен на выходе генератора: конфиг с серверами WebSocket и HTTPUpgrade,
     пришедшими с `headers.Host`, Xray принимает и запускается с ним без строки про
     `"host" in "headers"`; остаются только две строки о самих транспортах.

165. **Профиль WAN из netplan не меняется.** На ВМ после `xgw install` и `xgw uninstall`
     шлюз после перезагрузки остался без интернета: профиль WAN `netplan-eth0` встал
     на карту роутера. Причина: на Ubuntu 24.04 NetworkManager 1.46 хранит профили в
     netplan, и `nmcli connection modify` профиля, описанного в YAML (`match` по MAC и
     `set-name`), переписывает его в `/etc/netplan/90-NM-<uuid>.yaml` с `match: {}` —
     без привязки к карте; пока XGW установлен, это маскирует профиль `xgw-lan`
     (приоритет 100), после удаления — нет. Теперь профиль, файл которого
     `netplan-<имя>.nmconnection` (не `netplan-NM-…`), XGW не правит: при
     `ipv6.method ignore` IPv6 выключает `net/ipv6/conf/<карта>/disable_ipv6 = 1` в
     `/etc/sysctl.d/90-xgw.conf` (прежнее значение — в журнале, удаление его возвращает);
     при другом методе установка только предупреждает, что делать в netplan. Совет
     `xgw diag` при глобальном IPv6 больше не предлагает `nmcli connection modify`.
     **Проверено** на той же ВМ: установка — профиль и его YAML не тронуты,
     `disable_ipv6 = 1`; перезагрузка с XGW — значение держится, WAN на своей карте,
     клиент через VPN; удаление — файл убран, `disable_ipv6 = 0`, link-local вернулся;
     перезагрузка — WAN на своей карте. Профили, созданные NetworkManager
     (`netplan-NM-…`, в YAML — `match: name`), правка не ломает — для них всё как раньше.
     Остаётся след: NetworkManager сохраняет в `/etc/netplan/90-NM-<uuid>.yaml`
     свой профиль карты роутера («Wired connection 1»), когда установка снимает с него
     автоподключение; удаление возвращает автоподключение, файл остаётся.
166. **Отказ `device reapply` при удалении больше не скрывается.** NetworkManager 1.46

169. **Вход в панель без терминала.** По просьбе пользователя: токен из консоли
     копировать не нужно. В конце `sudo xgw install` панель сама открывается в браузере
     того, кто запустил установку (SUDO_UID), а у ярлыка «XGW» появился пункт «Войти
     заново» (`Actions=login` в .desktop, `xgw panel --login`): команда от человека
     уходит в pkexec — пароль администратора спрашивает окно Ubuntu, — а от root
     открывает браузер в сеансе человека: `systemd-run --user --machine=<имя>@ -- xdg-open
     <адрес>`, только если в окружении его пользовательского менеджера systemd есть
     WAYLAND_DISPLAY или DISPLAY (графический сеанс GNOME передаёт их туда). В адресе —
     не постоянный токен, а одноразовый код (`?login=`, годен один раз и 60 с, на диске
     лишь его SHA-256 в `/run/xgw/panel-login`, 0700): адрес виден в списке процессов и
     журнале. Вписать токен в ярлык нельзя — файл ярлыка читают все пользователи.
     Постоянный токен, `sudo xgw panel` и `xgw panel --open` остались
     как были. `xgw diag` на машине с рабочим столом предупреждает, если нет `pkexec`
     (`sudo apt install pkexec`): без него «Войти заново» пароль не спросит.
     **Проверено**: юнит-тестами (коды, отказ при повторе и через минуту, переход через
     pkexec и его коды 126/127, открытие от root, отказ без графического сеанса, пункт в
     ярлыке, итог установки) и на «одноразовой машине» (настоящий systemd в контейнере):
     пользователь с запущенным менеджером systemd (`systemctl start user@UID` — так
     делает logind при входе; `loginctl enable-linger` в контейнере не работает),
     `xgw panel --login` от root с PKEXEC_UID — без
     WAYLAND_DISPLAY честный отказ, с ним заглушка xdg-open запущена от имени этого
     пользователя с одноразовой ссылкой, ссылка пускает в панель один раз, токена в
     адресе нет. **Не проверено**: окно пароля pkexec и агент polkit GNOME, настоящий
     браузер (Firefox из snap), запущенный через `systemd-run --user`, пункт ярлыка в меню
     GNOME — всё это в ручном чек-листе README. Пакет pkexec по индексу пакетов 26.04 и
     странице пакета 24.04 входит в задачу `ubuntu-desktop-minimal`, то есть на Ubuntu
     Desktop стоит сразу; на живой системе это не проверялось.
170. **Недоступный `probe.url` на живой машине (отчёт REAL, F1–F3, F7).** Три правки.
     (1) Признак «не отвечает probe.url» решает сам, а не имя состояния: сканы и замены
     ждут, пока он стоит, и во время LEAK — утечка в машине состояний выше и раньше его
     заслоняла (15 минут сканов, затем ALL_DEAD и замена живых серверов). (2) Признак —
     не «одна и та же ошибка у всех», а «файл не получил ни один из опрошенных»: на
     реальной подписке 64 обрыва и 3 таймаута из 67, и прежняя проверка при
     перепроверке снимала признак, после чего шаг уходил в ALL_DEAD. Довод остаётся тот
     же — базовый запрос через VPN проходит (он идёт через одного из участников, а его
     проба не прошла) либо у всех тот же код HTTP, что и напрямую; «заморозка» и любой
     полученный файл признак снимают. `xgw probe --all` подсказывает при одной ошибке у
     80 % и ни одном файле. (3) Пока признак стоит, ядро пробует серверы по
     `probe.url_fallback`, а без него — по `probe.trace_url` (через серверы он заведомо
     открывается — это и показал базовый запрос): иначе burstObservatory считает
     мёртвыми всех участников, и балансировщик отдаёт весь трафик fallbackTag — первому
     участнику, живой он или нет (вероятная причина пропавшего интернета в отчёте).
     Выбор хранится в `/var/lib/xgw/probe-fallback.json` вместе с самим probe.url и без
     него не действует; переключение в обе стороны — срочный перезапуск Xray. Сквозная
     проверка всегда качает сам probe.url — по ней видно, что он ожил. `url_fallback`
     так и был в конфиге без дела с самого начала (п. 157) — теперь он работает.
     F3: пока размер пробы неизвестен ничем (ни измерения, ни `?bytes=`, ни файла по
     умолчанию), оценка трафика идёт по 64 КиБ «наугад» и о превышении лимита не
     предупреждает — совет урезать проверки по такой цифре вреден; об исчерпанной
     квоте предупреждение остаётся. **Проверено**: юнит-тестами демона (утечка +
     недоступный адрес: ни сканов, ни замен, затем PROBE_TARGET_UNREACHABLE, а не
     ALL_DEAD; переключение адреса проб ядра туда и обратно) и разбора. **Не
     проверено** на живой машине; что Xray 26.3.27 при всех мёртвых участниках отдаёт
     трафик fallbackTag, взято из устройства балансировщика, а не из опыта.
171. **Контейнеры Docker через VPN (F4).** По решению заказчика — через VPN, с
     выключателем `capture.containers` (по умолчанию `true`). Трафик контейнеров —
     транзит с мостов `docker0` и `br-*`; первый вариант, TPROXY как у LAN, на стенде не
     заработал: на машине с Docker загружен br_netfilter, цепочка prerouting для пакетов
     с моста вызывается ещё на уровне моста, а позже `ip_rcv` сбрасывает сокет, который
     назначил TPROXY, — SYN доходит до правила и пропадает. С выключенным
     `bridge-nf-call-iptables` TPROXY работал, но выключать его нельзя: на него
     рассчитывает Docker. Метка в той же цепочке переживает br_netfilter, поэтому цепочка
     `containers` ставит `mark_containers` (3), а `ip rule fwmark 3 lookup
     <tun_route_table>` (pref 95) ведёт пакеты в TUN-интерфейс XGW, который читает
     inbound `tun-in`. Интерфейс и inbound появляются, только когда мост Docker уже есть
     (без Docker лишнего интерфейса нет — ср. F8); правило и чёрная дыра в таблице TUN
     стоят всегда, поэтому, пока Xray не перезапущен с inbound'ом TUN, контейнеры
     закрыты, а не идут мимо VPN. Демон замечает появившийся мост на шаге watchdog и
     срочно пересобирает конфиг. Исключения: `ct direction reply` (ответы
     опубликованных портов), адреса самой машины (маршрутом в TUN их не увести — таблица
     local главнее), частные сети, кроме DNS. Docker сам маскирует адрес контейнера на
     выходе в TUN (169.254.10.1) — Xray это не мешает. Правила ufw не нужны: трафик
     транзитный, его пропускают цепочки Docker. **Проверено**: на стенде пространств имён
     с той же сетью, что ставит Docker, и с загруженным br_netfilter — выход через VPN,
     DNS через Xray, опубликованный порт, `xgw disable`, Docker после XGW, выключатель.
     **Не проверено** на настоящем Docker и с IPv6 контейнеров (не перехватывается).
172. **Своя служба DHCP вместо штатного dnsmasq (F12).** Пакет ubuntu-fan (ставится с
     `docker.io`) кладёт в `/etc/dnsmasq.d` строку `bind-interfaces`; с XGW-овым
     `bind-dynamic` dnsmasq не запускается вовсе, а `dnsmasq --test` этого не видит.
     Подстраиваться под чужой файл нельзя (с bind-interfaces dnsmasq падает «unknown
     interface», пока у карты LAN нет адреса), и каталог этот общий у всех пакетов.
     Поэтому DHCP раздаёт своя служба `xgw-dhcp`: `/usr/sbin/dnsmasq --keep-in-foreground
     --conf-file=/etc/xgw/dnsmasq.conf` — `--conf-file` заменяет `/etc/dnsmasq.conf`, а
     каталог `/etc/dnsmasq.d` подключает только штатная обёртка (`-7` из
     `/etc/default/dnsmasq`; посмотрено в пакете 2.92). Программа — из `dnsmasq-base`:
     он есть на Ubuntu Desktop (NetworkManager), создаёт пользователя `dnsmasq`; пакет
     `dnsmasq` (universe) больше не нужен. В конфиге — `user=dnsmasq`, свой
     `pid-file` в `/run/xgw-dhcp` (не делит файл со штатной службой) и

178. **Стенды на машине с XGW и Docker (G2, G4–G6).** Юнит-тесты не смотрят на мосты Docker
     самой машины: каталог интерфейсов (`lan.SYS_NET`) в них подменён пустым, тесты
     контейнеров задают свой; пароль проб тест ищет по тегу inbound'а, а не по номеру.
     Стенд «одноразовой машины» убирает профиль `xgw-lan` хоста и в виде файла netplan
     (`/etc/netplan/90-NM-<uuid>.yaml` — так его хранит NetworkManager 1.46+ на Ubuntu 24.04,
     а `system-connections` пуст): по uuid из журнала установки и, без журнала, по имени в
     файле; что функция находит файл настоящего профиля, проверяет сам стенд после
     установки. Шлюз стенда без перехвата метит свои сокеты меткой 0x5e, а не 2: правило
     `loopback_guard` XGW хоста отбрасывало его пакеты к узлам на 127.0.0.1 (воспроизведено
     в отдельном netns с тем же правилом — те же «участники не ожили»). Пространства имён
     стенда начинают с `net.ipv4.ip_forward = 0`: при создании они наследуют значение
     хоста. Профиль с именем `xgw-lan` XGW по-прежнему считает своим (остаток прежней
     установки): имя зарезервировано, и стенд — единственный известный случай, когда такой
     профиль был чужим.

181. **Xray 26.10.10 по умолчанию (16.10.2026).** По решению заказчика XGW ставит

     26.3.27, и `xray.version = "latest"` берёт именно его. Умолчание — `XRAY_VERSION` в
     config.py и строка в config.example.toml; в конфиге, где уже записано
     `version = "latest"` (так было в примере раньше), остаётся стабильная версия —
     перейти: `version = "26.10.10"` и `sudo xgw update-xray`. `xgw diag` предупреждает
     (WARN), если установлен Xray не той версии, что в конфиге (кроме `"latest"`).
     Что в 26.10.10 иначе — **проверено опытом** (стенд в netns, исходники тега v26.10.10):
     - `freedom` за серверными inbound'ами (vless, vmess, trojan, shadowsocks, hysteria,
       wireguard) по умолчанию не пускает к частным адресам и loopback (`finalRules`;
       прежнего `ipsBlocked` нет). Шлюз XGW это не задевает: его inbound'ы — tunnel, tun,
       socks, http. Задело стенд: его VLESS-серверы в режиме loopback ходили к «интернету»
       на 127.0.0.1 — им добавлено `finalRules: [{"action": "allow"}]` (26.3.27 поле
       пропускает молча, проверено);
     - `freedom.domainStrategy` объявлен устаревшим: 26.10.10 сам переносит его в
       `sockopt.domainStrategy` и пишет предупреждение в журнал. Генератор поле не
       переносит: в 26.3.27 `freedom` разрешает домены сам по своему `domainStrategy`, в
       том числе для UDP, а с одним `sockopt.domainStrategy` UDP-домены там ушли бы в
       системный резолвер. Предупреждение безвредно; убрать поле — когда минимальной
       версией станет та, где перенос есть;
     - при остановке Xray выключает интерфейс TUN (`ip link set down`), и ядро удаляет
       маршрут через него (26.3.27 оставлял интерфейс поднятым, NO-CARRIER). Запустившись,
       Xray интерфейс поднимает, а маршрута уже нет. Отказаться от этого настройкой нельзя
       (Xray считает интерфейс своим, если не получил готовый дескриптор). Поэтому
       `xgw-xray.service` после каждого запуска вызывает `xgw net tun`
       (`ExecStartPost=-+…`: от root, сбой Xray не останавливает): интерфейс поднят, адрес
       и маршруты на месте; правила nftables команда не трогает. Пропущенное (Xray
       запущен не службой) возвращает демон: выключенный интерфейс — тот же сбой, что
       интерфейс без адреса (п. 176);
     - `xray run -test` интерфейс TUN больше не открывает: подмена имени в проверке
       конфига (generator/validate.py) для 26.10.10 не нужна, но и не мешает.
     **Проверено**: юнит-тесты и все стенды (loopback, netns, LAN, IPv6, TUN, Docker,
     «одноразовая машина» с настоящими systemd и NetworkManager) на 26.10.10 — 0 падений
     (816 passed); на 26.3.27 — то же (816 passed).
     **Не проверено** на живой машине.
182. **Приоритет серверов (высокий, средний, низкий).** По требованию заказчика: трафик
     идёт через серверы наивысшего уровня, на котором есть живые; нет живых — уровнем
     ниже. Средствами Xray это не сделать: `fallbackTag` балансировщика ведёт только на
     outbound, а не на другой балансировщик (app/router/balancing.go, 26.3.27 и
     26.10.10), а веса `costs` у стратегии leastLoad умножают разброс задержки, а не
     задержку, и строгого порядка не дают. Поэтому уровни ведёт XGW (priority.py):
     - уровень хранится в panel.json по отпечатку (`"priority": {fp: "high"|"low"}`,
       средний не хранится); ставится в панели и командой `xgw priority`;
     - участники — только серверы одного уровня (`select_nodes(tier=…)`), даже если их
       меньше max_members: вместе с уровнем ниже leastPing отдал бы трафик более быстрому
       серверу низкого уровня. Уровень при сборке — тот, на котором нынешние участники
       (обновление подписки его не меняет); меняет его только демон;
     - замена мёртвого участника — только запасным того же уровня; переход вниз — когда
       ALL_DEAD и живых запасных уровня нет: на ближайший уровень, где есть запасные,
       прошедшие скан (OK или SLOW), сразу и срочно; переход вверх — по скану OK,
       сделанному после последней смены уровня (старый результат не в счёт — иначе шлюз
       прыгал бы туда-обратно). Пока работает уровень ниже наивысшего, запасные уровней
       выше сканируются не реже раза в 5 минут (TIER_RESCAN) — этот расход в оценку
       бюджета проверок не входит: он появляется, только пока высокий уровень недоступен;
     - пока сервер закреплён (`xgw pin`), уровень не меняется.
     Цена строгости: если все серверы уровня перестали отвечать разом, до перехода вниз
     проходит шаг-два watchdog и сборка (на стенде — секунды), а не мгновенное
     переключение внутри балансировщика. **Проверено**: юнит-тесты и стенд на живом
     Xray (loopback и netns): высокий работает один, отказал — средний, ожил — снова
     высокий, низкий не трогается. **Не проверено** на живой машине.
183. **Лимиты подписок, множители и резервный выход (0.1.8).** По требованию заказчика:
     у подписок бывает лимит трафика, у серверов подписки с лимитом — множитель расхода
     в имени (x1 — обычный, x10 — максимальная скорость, x100 — обход белых списков на
     LTE). Безлимитные серверы — в первую очередь; лимитированные — только когда
     безлимитными работать нельзя. Именно ради этого просили ручной приоритет (п. 182).
     - Лимит — поле `total` заголовка `subscription-userinfo` (`engine.Inventory.quotas`);
       нет заголовка или `total = 0` — безлимитная, ручные ссылки — безлимитные.
       Множитель — `filters.multiplier_regex` по имени, без отметки — x1; в безлимитной
       подписке стоимость сервера 0 при любом множителе; дубль из двух подписок — по
       дешёвой (cost.py).
     - Класс сервера — (ранг приоритета, стоимость), приоритет главнее. Уровни 0.1.7
       обобщены до классов: участники — один класс, замена — тем же классом, вверх — по
       свежему OK-скану запасного класса лучше, вниз — только на класс той же стоимости
       (`_switch_tier`): участников ядро пробует постоянно, и переход с безлимитных на
       лимитированные тратил бы квоту на пробы.
     - Резервный выход — `fallbackTag` балансировщика на запасной (spare-*) лучшего из
       классов хуже. Его нет в `subjectSelector` observatory, ядро его не пробует. Когда
       leastPing не находит живых участников (возвращает пустой тег), Xray сам уводит
       трафик на fallbackTag и сам возвращается, как только участник ожил: шлюзу ничего
       пересобирать не нужно. Проверено опытом (16.10.2026, WSL, живой Xray, фейковые
       серверы): 26.10.10 — переход на резервный 40,6 с при пробах раз в 10 с, возврат 7 с;
       26.3.27 — 7,5 с и 4,5 с; проб резервного — ноль, TCP и UDP работают.
     - Состояние `RESERVE` — все участники мертвы, сквозная проверка через резервный
       проходит; она в это время идёт коротким запросом (`probe.trace_url`), чтобы не
       тратить квоту по 57 КБ каждые 20 с. Разовый сбой проверки RESERVE не прерывает;
       `fail_threshold` сбоев подряд — `ALL_DEAD`, и кандидаты в резервный проверяются
       сразу все. Подписка в RESERVE опрашивается внеочередно напрямую раз в 30 минут:
       через Xray запрос шёл бы через лимитированный резервный.
     - Недоступный `probe.url` при резервном выходе: ядро считает мёртвыми всех участников,
       трафик уходит на резервный, а короткая сквозная проверка проходит. Поэтому в
       RESERVE демон опрашивает участников probe.url и без сбоев сквозной проверки (раз в
       5 минут), а базовый запрос «носят ли серверы трафик» идёт через probe-inbound
       самих участников, а не через http-in — тот понёс бы его через резервный.
       Лимитированные запасные в эту выборку не входят, когда участники безлимитные.
     - Проверки лимитированных — коротким запросом и редко: резервный и три лучших
       кандидата — раз в 6 часов и сразу при ALL_DEAD; запасные того же класса, что
       участники (когда безлимитных нет), — по расписанию скана. Плановый скан
       лимитированных класса хуже не трогает. Короткий запрос «заморозку» не ловит,
       поэтому участник, пришедший из такого запасного, один раз проходит первую
       проверку probe.url. Оценка расхода: короткая проверка — до 8 КБ (ответ trace и
       рукопожатие TLS), сверху.
     - Бюджет проверок по подпискам (`status.quota_spend`): пробы и сквозная проверка
       участников, короткие сканы и проверки кандидатов — с множителями, только для
       подписок с лимитом; от него — доля квоты в месяц и предупреждение «больше 10 %
       остатка».
     - Отвергнутый вариант — цепочка уровней внутри Xray: балансировщик на уровень,
       `fallbackTag` — outbound `loopback`, правило по его `inboundTag` ведёт на
       балансировщик следующего уровня. Утверждение п. 182 «fallbackTag ведёт только на
       outbound» верно, но outbound loopback возвращает трафик в маршрутизацию, и
       балансировщики так связываются (проверено опытом). Отвергнута, потому что
       observatory постоянно пробовал бы серверы всех уровней, включая лимитированные
       (проба 57 КБ через x100 — 5,7 МБ квоты, 2880 проб в сутки — около 16 ГБ на
       сервер), а на Xray 26.3.27 TCP через loopback не закрывается: данные приходят,
       закрытие со стороны сервера — нет.
     **Проверено**: юнит-тесты; стенд на живом Xray (loopback и netns): безлимитные
     мертвы — трафик через резервный x1, у него ни одного соединения от observatory;
     резервный тоже не отвечает — резервным становится x10 через API, Xray не
     перезапускается; безлимитные ожили — Xray вернул трафик сам. **Не проверено** на
     живой машине с настоящими подписками.
184. **Уведомления — только когда нужно действие (0.1.8).** По замечанию заказчика: бот
     постоянно присылал «часть серверов недоступна», а делать с этим ничего не нужно —
     шлюз меняет такие серверы сам. Теперь уведомляют (рабочий стол, Telegram) только

     - Схема «сопроцессор»: Xray остаётся точкой входа (перехват, балансировщик, пробы,
       закрепление основного). Сервер, который ведёт sing-box, в Xray — outbound `socks` на
       `127.0.0.1:<порт моста>`, в sing-box — вход `sb-in-<отпечаток>-<вариант>` (socks, логин
       `xgw-<вариант>`) и выход `sb-out-…` с `routing_mark` = `mark_bypass`. **Проверено**
       (живые Xray 26.10.10 и sing-box 1.14.3, tests/stand/test_stand_singbox.py): TCP и UDP
       через такую связку работают; мост — **без метки**, потому что `loopback_guard`
       отклоняет пакеты с меткой к 127.0.0.0/8, а метка на сокетах sing-box к серверам
       выводит их из TPROXY (без неё UDP sing-box сам попал бы в перехват).
     - **Проверено: SIGHUP рвёт все соединения sing-box** (новые работают, процесс жив), а
       `ado`/`rmo` outbound'а в Xray идущее соединение не рвут. Поэтому для каждого сервера в
       sing-box заранее заведены варианты — обычный (`d`), с дроблением TLS (`f`), с
       мультиплексированием и паддингом (`m`), — а смена профиля сервера — это замена его
       outbound'а в Xray через API (другой порт моста). Конфиг sing-box меняется, только когда
       меняется состав серверов, и, пока через него идёт трафик (участник, резервный выход,
       выбранный вручную), новый конфиг откладывается до окна `apply.restart_window` или до
       `xgw apply --now`/аварии; Xray тем временем ссылается только на мосты работающего
       sing-box (`engine.assemble`).
     - Ядро сервера не входит в отпечаток: смена ядра не сбрасывает приоритет, статистику и
       отключение. Закрепление ядра (`xgw core`, панель) — в `panel.json` (`core`).
     **Не проверено** у настоящего провайдера: помогает ли sing-box против его фильтра и
     какой профиль окажется нужным.

200. **Профили обхода и лестница (0.1.12).** `xray:default`, `xray:fragment`,
     `singbox:default`, `singbox:tls_fragment` (`fragment` — сегменты TCP, пауза 30 мс вместо
     500 мс по умолчанию, и `record_fragment` — записи TLS), `singbox:mux_padded` (`h2mux` с
     паддингом и `record_fragment`). Профиль виден по применённому конфигу Xray (мост, дробление
     или обычный outbound), поэтому переживает перезапуск демона и обновление подписки.
     Лестница при `fragment.mode = "auto"`, только запасные; серверы с лимитом трафика на другое
     ядро в фоне не переводятся (каждая проба тратит квоту; дробление в своём ядре — как в 0.1.11):
     «заморозка» (FROZEN, STALL_BEFORE_BODY) — `xray:fragment` → `singbox:tls_fragment` →
     `singbox:mux_padded`; отказ в соединении (CONNECT_FAIL, TIMEOUT) — по одной попытке
     `xray:fragment` и `singbox:tls_fragment` (с 0.1.13 между ними — обычный sing-box,
     п. 207). Сервер на обученном профиле, который перестал отвечать, сначала пробуется на
     базовом. Первый профиль с ответом закрепляется; не помог
     ни один — возвращается прежний, следующая попытка через 6 ч; раз в сутки сервер на
     тяжёлом профиле пробуется на базовом. Серверам, которых умеет только sing-box
     (hysteria2, TUIC, WireGuard), перебирать нечего: QUIC не дробится. **Известно**:
     мультиплексирование sing-box (h2mux, smux, с паддингом и без) **не работает с серверами
     Xray** — Xray принимает его как запрос к `sp.mux.sing-box.arpa:444` и молчит
     (проверено); ступень `singbox:mux_padded` пробуется всем по решению заказчика и
     работает только с серверами, понимающими mux (sing-box, mihomo). При массовой блокировке
     (ALL_DEAD, RESERVE) запасные на другом ядре и другом транспорте проверяются первыми.

207. **Ступень «обычный sing-box» в лестнице (0.1.13).** Отчёт об испытаниях 0.1.12

     давали TIMEOUT/CONNECT_FAIL, а на sing-box — OK, и часть из них — именно на обычном
     sing-box, без дробления; в `auto` шлюз их не находил: лестница 0.1.12 у серверов обоих
     ядер шла `xray:fragment` → `singbox:tls_fragment`, а `singbox:default` в ней не было.
     Теперь у серверов с базой Xray для обоих типов вердиктов: «заморозка» — `xray:fragment` →
     `singbox:default` → `singbox:tls_fragment` → `singbox:mux_padded`; отказ в соединении — по
     одной попытке `xray:fragment`, `singbox:default`, `singbox:tls_fragment`. Обычный sing-box
     стоит раньше дробления sing-box: если хватает другой реализации TLS, лишняя пауза
     рукопожатия ни к чему. Вариант `d` заведён в sing-box заранее (как и в 0.1.12), так что
     ступень — только замена outbound'а через API. У серверов только для sing-box
     `singbox:default` — по-прежнему база. Лимитные подписки на другое ядро в фоне не
     переходят (ступень отсекается, как и `singbox:tls_fragment`). Перепроверка на базе раз в
     сутки и повтор через 6 ч после провала — как у остальных выученных.
     **Как профиль сохраняется.** Профиль читается из применённого конфига Xray (п. 205), а
     там обычный sing-box выглядит одинаково, дала ли его блокировка или настройки:
     `xgw core <сервер> sing-box` и `[core] mode = "sing-box"`. Если бы `singbox:default` просто
     добавили в выученные, после `xgw core … auto` или возврата `mode = "auto"` (так делает шаг
     5 плана 0.1.12) серверы остались бы на sing-box. Поэтому каждая применённая сборка
     (`xgw apply`, демон, установка; не `xgw generate`, у которой конфиг в отдельном файле)
     пишет в SQLite (meta `core_settings`) снимок `[core] mode` и закреплений ядра, а следующая
     сборка оставляет `singbox:default` у сервера с базой Xray, только если ядро этого сервера
     в настройках с тех пор не менялось. Снимка нет (первая сборка, обновление с 0.1.12) —
     правило 0.1.12: сервер возвращается на базу. Остальные выученные профили сохраняются,
     как в 0.1.12.

211. **Скорость в строках серверов и замер лимитированных (после 0.1.14).** Заказчик: «скорость
     серверов замеряется, но результаты замера не отображаются в строках данных о сервере».
     Три причины. (а) Скорость была только серой подписью под именем («в работе · 87 Мбит/с,
     замер 14:05») — теперь она справа рядом с задержкой, а под именем — время замера.
     (б) Запасной, которого замерили, пока он был в работе, показывал пустую строку, хотя
     замер хранится неделю (`SPEED_KEEP`) — теперь статус и панель отдают его и у запасных,
     бледнее и с пометкой «когда был в работе»; запасные по-прежнему не замеряются. (в) По
     п. 186 лимитированные участники не замерялись вовсе: когда в работе серверы подписки с
     лимитом, скорости не было ни у одного. По решению заказчика («не очень сильно экономить
     трафик») их замеряют меньшей загрузкой: квоты на замер — не больше `speed.max_mb`
     (x1 — 10 МБ, x2 — 5 МБ, x10 — 1 МБ), но загрузка не короче 1 МБ, иначе TCP не успевает
     разогнаться и скорость занижена. Серверы x100 и дороже не замеряются — по словам
     заказчика, это серверы для LTE; панель пишет у них «скорость серверов x100 не
     замеряется». Сервер неизвестной цены (подписка ещё не сопоставлена) не замеряется, как
     раньше. Участники одного класса стоят одинаково (п. 183), поэтому основной выбирается
     среди замеров одного размера. Расход на замеры входит в бюджет трафика и в расход квоты
     подписки с множителями.

212. **Замеры скорости при ручном выборе (после 0.1.14).** Пока действовал ручной выбор
     (`xgw pin`, кнопка «Выбрать», `/pin`) и выбранный отвечал, `_main_step` выходил раньше
     `_speed_step`: шлюз не замерял ни одного сервера, а панель при этом писала «Скорость
     замеряется раз в 6 ч». На машине заказчика после испытаний 0.1.13 стоял бессрочный
     выбор — строки серверов остались бы без скорости, та самая жалоба п. 211. Заказчик
     выбрал «замерять и при ручном выборе» (а не «не замерять, но сказать об этом»): раунды
     идут по расписанию и по кнопке, как без выбора, с теми же загрузками (лимитированные —
     меньшей, x100 — никогда), так что квоты уходит столько же. Замер идёт через собственный
     вход пробы сервера, а не через балансировщик: трафику выбранного не мешает, закрепление
     в ядре не трогает. Основной при выборе по-прежнему не выбирается и не закрепляется;
     раунд, кончившийся при выборе, запоминается (`_compare_due`), и на первом шаге после
     снятия выбора основной сверяется с его итогами — иначе смена на заметно более быстрый
     ждала бы следующего раунда (до `speed.every_hours`). Выбранный запасной не замеряется:
     запасные не замеряются вообще (п. 211). Панель при выборе пишет «Замеры скорости идут и
     при ручном выборе: раз в 6 ч, …».

213. **Запись файлов по итогам внешнего аудита 0.1.13 (после 0.1.14).** Аудит кода 0.1.13
     (`e043207`) нашёл места, где запись файла портила чужое или теряла своё; три из них
     перепроверены на текущем коде и исправлены. (а) HIGH-01: `xgw logs --export --out F`
     открывал F с усечением (`O_TRUNC`) и под sudo отдавал вызвавшему (`fchown`, п. 209), так
     что опечатка или символическая ссылка в `--out` молча затирала существующий файл — хоть
     `/etc/xgw/config.toml` — и делала его файлом пользователя. Под sudo `xgw` и так равносилен
     root (`--config` с любым путём), администратор у шлюза один, поэтому опасность ниже
     оценки аудита; настоящий риск — тихая порча файла опечаткой. Теперь архив пишется только
     в новый файл (`O_CREAT|O_EXCL|O_NOFOLLOW`): на существующий путь или ссылку, в том числе
     висячую, команда отвечает «архив не записан: файл … уже существует — укажите другое
     имя» с кодом 1, и тот файл не меняется. Путь проверяется и до сбора журнала и `diag` —
     чтобы не ждать их зря; окончательно его проверяет открытие файла. Недописанный архив
     удаляется: повтор с тем же именем не упрётся в отказ. Имя по умолчанию
     (`xgw-logs-ГГГГММДД-ЧЧММСС.tar.gz` в текущем каталоге) содержит время и не совпадает.
     (б) MEDIUM-01: panel.json пишут трое — панель и бот Telegram (потоки демона) и команды
     `xgw priority`, `xgw core`. Каждая правка читала файл, меняла и записывала без
     блокировки, и правка другого писателя, попавшая между чтением и записью, терялась
     (например, бот запоминает чат, пока в панели отключают сервер). Хуже, чем в аудите:
     временный файл атомарной записи назывался по номеру процесса (`.panel.json.PID.tmp`), и
     два потока демона писали в общий временный файл — запись падала (`FileNotFoundError`) или
     оставляла смесь двух. Теперь все правки panel.json идут через одну функцию
     (`managed._update`) под межпроцессной блокировкой (`flock`) на файле `.panel.json.lock`
     рядом, права 0600; сам panel.json для неё не годится — атомарная запись подменяет файл.
     Дольше 10 с блокировку не ждут: панель и команды отвечают «… настройки меняет другой
     процесс XGW — повторите». `sudo xgw uninstall` без `--purge` файл блокировки убирает —
     рядом с конфигом остаются только `config.toml` и `panel.json`. Временный файл атомарной
     записи теперь у каждого потока свой (номер процесса и потока) — для всех файлов, не
     только panel.json. (в) После `os.replace` атомарная запись делает `fsync` каталога: без
     него после сбоя питания на месте файла мог оказаться прежний (где каталог так не
     открыть, шаг пропускается). Не делались, хотя названы в аудите: сохранение таймеров
     лестницы профилей (LOW-01, уже сделано в 0.1.14, п. 210), WAL для SQLite, изменения
     одноразового кода входа в панель (`use_login`: файл кода удаляется при проверке, и
     второй вход тем же кодом не пройдёт). Проверено юнит-тестами, которые на прежнем коде
     падают: два потока по 40 правок разных ключей (`set_servers` и `set_telegram`) — целы
     обе серии (без блокировки правки теряются, с общим временным файлом запись падает);
     правка ждёт, пока блокировку держит другой; архив не пишется ни в существующий файл,
     ни по ссылке, и тот файл не меняется.
