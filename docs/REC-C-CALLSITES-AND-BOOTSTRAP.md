## 2. Lockgraph: конкретная опасность предлагаемого патча

[Applier.apply105](https://github.com/1521572-lang/xgw/blob/351fb54e074f4a7b497a8a4244fc74c6088788d7/src/xgw/apply/applier.py#L97-L106)
держит apply.lock → _restart_and_wait193 вызывает service.restart →
[SystemdService75](https://github.com/1521572-lang/xgw/blob/351fb54e074f4a7b497a8a4244fc74c6088788d7/src/xgw/xraycore/service.py#L55-L76)
делает synchronoussystemctl → [unitExecStartPost23](https://github.com/1521572-lang/xgw/blob/351fb54e074f4a7b497a8a4244fc74c6088788d7/packaging/xgw-xray.service#L18-L23)
вызывает CLI net tun → Capture.restore_tun666 берёт net.lock.

Если добавить ownershipflock вокруг Applier.apply и в начало Capture.restore_tun,
получится parentownership→waitchild→childownership. В зависимости от timeout это
задержка/ошибка hook или взаимное ожидание, не корректный общий fence. Prefix«-» в unit
игнорирует ошибку hook, но не доказывает его успешное восстановление маршрутов.
Это новый риск будущей интеграции, не обнаруженная liveавария текущего продукта.

AAрешение: parentdurableticket, registrylock отпущен до servicewait; nestedchildticket
допускается пока ownershipIDLE; recoveryотказывается при любомticket безPENDING.
Registrycriticalsection никогда не ждёт domainlock/process. Завершение может брать
registrylock уже внутри domainlock, потому что обратного registry→waitdomain нет.
Такой структурный инвариант ещё нужно проверить на реальных instrumentedcallsites.

## 3. Readonly/out-of-scope не путать с quiescence

Status/diag обычные readers не становятся активными проверками. Но public Capture.tidy
пишет, а managednoop может не писать. Usagexgw_acct и agentxgwfp нормального PrivateNetwork
unit — другие scopes. Сохранять их; проверки sourcecalls не аттестуют packetpath.
Прямые rootcalls, сторонний configeditor, systemdautostart и aliaspaths не охвачены AA.
Нельзя закрыть fullcallgraphverified без конкретных entrypointversionhandshakes и surfacechecks.

Исправление имени в раннем инвентаре: реальная функция **nft.delete**, не nft.remove
(nft.py1154). Раннее имя было ошибкой описания; метод и живые правила не переименовываются.

## 4. Bootstrap — решён порядок разработки, runtimeактивация ещё BLOCKED

1. Добавить C-REG как неиспользуемый productmodule, без import-timeI/O. До defaultsactivation
   тестировать через fakeadapters. Не устанавливать sandboxhelper как productmodule.
2. Инструментировать writerentrypoints и servicehooks в исходниках, договориться о context
   вложенных calls. Сохранить поведение работающей сети при неактивной feature. No bypassenv.
3. Составить manifestcapabilities/version каждого actor. Новый CLI + старый daemon не
   attestedfence. Отсутствующий/unversioned writer → BLOCKED_WRITER_FENCE, не forcearm.
4. Сначала независимый REC-Ddriver с fakeadapter. Ему не нужен установленный productfence,
   потому что fakejob не касается сети. Это разрывает цикл разработки: drydriver можно
   квалифицировать раньше установки C-ENTRY, **не разрешая livefault**.
5. Для установки C-ENTRY на ThinkCentre отдельно нужен bootstraprescue, способный вернуть
   исходные executables/units/config/on без нового интернета/модели. Capture-onlyYsнимка
   недостаточно для изменения кода и служб. Разрешённого готового такого rescue сейчас нет.
