# План: приложение XGW для Android — VPN телефона и пульт шлюза

Решение заказчика (20.10.2026, после испытаний Т2): вместо Mini App в Telegram — своё
приложение для Android, которое

1. **само является VPN-клиентом телефона** (Xray внутри, серверы берёт со шлюза) — вместо
   Happ и других клиентов;
2. **управляет шлюзом** — как панель: VPN шлюза, серверы, устройства;
3. связывается со шлюзом **через Tailscale Funnel**, без Tailscale на телефоне: Android
   держит только один VPN, и теперь это VPN самого приложения.

Фазы Т3–Т5 `TAILSCALE_MINIAPP_PLAN.md` (Mini App) отменяются. Т0–Т2 остаются: Tailscale
рядом с XGW, SSH через Tailscale и панель по tailnet работают и дальше. Бот Telegram убран
целиком (решение заказчика 20.10.2026, ASSUMPTIONS п. 222): его роль — у приложения.

Телефон заказчика: Samsung Galaxy S25 Ultra (Android 15/16, arm64).

## 1. Как это устроено

```
телефон: приложение XGW
  ├─ VpnService (Kotlin) ── дескриптор TUN ──► Xray для Android (официальная сборка,
  │                                             вход tun, XRAY_TUN_FD) ──► VPN-серверы
  └─ экран «Шлюз» ── HTTPS ──► https://<шлюз>.<tailnet>.ts.net/  (Funnel, порт 443)
                                   │ ретранслятор Tailscale, TLS не расшифровывает
                                   ▼
                         tailscaled на шлюзе ──► http://127.0.0.1:8782
                                                  └─ API приложения в демоне XGW
```

- **Xray на телефоне** — официальная сборка `Xray-android-arm64-v8a` той же версии, что
  на шлюзе (26.10.10). У неё есть вход `tun`: на Android он берёт готовый интерфейс
  VpnService по номеру дескриптора из переменной `XRAY_TUN_FD` (документация Xray,
  `proxy/tun`). Собирать Xray самим (gomobile, Go) не нужно, tun2socks — тоже.
- **Приложение — Kotlin и встроенный WebView** (А2, ASSUMPTIONS п. 225): экраны — страница
  HTML/JS из самого APK, сеть, подпись и Keystore — в Kotlin. Без Tauri и Rust: в сборке нет
  ничего, кроме Android SDK и сканера QR Google Play services, — ничего лишнего скачивать.
- Xray запускается **отдельным процессом** из нативного кода приложения (небольшая
  библиотека на C через NDK, А3): так дескриптор VPN наследуется процессом. Свои соединения с серверами Xray ведёт мимо VPN,
  потому что приложение исключено из собственного VPN (`addDisallowedApplication`) —
  процесс Xray работает под тем же пользователем Android. Это первое, что проверяет фаза А3.
- **Конфиг Xray для телефона собирает шлюз** (тот же генератор, что для самого шлюза):
  серверы в работе, их приоритет и профиль обхода, балансировщик, DNS. Приложение его
  только хранит и запускает. Последний полученный конфиг сохраняется: если шлюз
  недоступен, VPN телефона работает на нём.
- **Funnel** — публичный адрес шлюза `https://<шлюз>.<tailnet>.ts.net/` на порту 443.
  TLS заканчивается на самом шлюзе, ретранслятор Tailscale содержимое не видит. Порт 8443
  уже занят панелью по tailnet (Serve); Serve и Funnel на одном порту одновременно нельзя,
  поэтому API приложения — на 443. Имя шлюза в tailnet уже публично (сертификаты HTTPS
  попадают в открытые журналы Certificate Transparency с включения HTTPS в Т2), поэтому
  защита — не в тайне адреса, а во входе только с привязанного телефона. Funnel требует
  разрешения в правилах tailnet (атрибут `funnel`): если его нет, CLI даёт ссылку, и
  заказчик один раз подтверждает в консоли Tailscale — как с HTTPS в Т2.
- **Запросы к шлюзу — всегда напрямую, мимо VPN телефона.** Испытание А1 (20.10.2026,
  `docs/TEST-REPORT-REAL-MACHINE-0.1.17-android-a1-2026-10-20.md`): по мобильной сети без
  VPN публичный адрес шлюза открылся, а с включённым VPN телефона (сторонний клиент) — нет.
  Почему не открылся через VPN-сервер, не выяснено: ретранслятор Funnel может не принимать
  адреса VPN-серверов или их не пропускает провайдер VPN. Поэтому через туннель к шлюзу
  приложение не ходит: оно исключено из собственного VPN (`addDisallowedApplication`, как
  и Xray выше), и его запросы к Funnel идут напрямую и при включённом VPN. Браузер и
  другие приложения телефона при включённом VPN шлюз могут не открыть — им это не нужно:
  пульт есть только в приложении.

## 2. Вход: привязка телефона

Для заказчика — два действия и ничего не вводить: **нажать «Привязать телефон» в панели
на шлюзе и навести на экран камеру приложения** (просьба заказчика: регистрация — через QR,
который показывает работающий на машине XGW). Всё остальное делается само:

- первый запуск приложения сразу открывает камеру: «Наведите на QR-код в панели XGW на
  шлюзе»; ни адреса, ни кода, ни имени вводить не нужно;
- если Funnel ещё выключен, та же кнопка «Привязать телефон» сначала включает его (с
  пояснением: адрес доступен из интернета, войти можно только с привязанного телефона) и
  показывает QR, как только Funnel заработал;
- имя телефона в панели — модель из Android («Galaxy S25 Ultra»); переименовать — в панели;
- QR в панели гаснет сам, как только телефон привязан («Телефон привязан»), или через 10
  минут.

Как это устроено:

1. QR содержит адрес шлюза в Funnel и одноразовый код (10 минут, один раз):
   `xgw://pair?u=https://<шлюз>.<tailnet>.ts.net&c=<код>`. Ключа в QR нет: сфотографированный
   экран после привязки или через 10 минут бесполезен.
2. Приложение отправляет код шлюзу (`POST /api/pair`). Шлюз создаёт телефону
   случайный ключ (32 байта) и возвращает его один раз. Приложение сразу кладёт ключ в
   Android Keystore как ключ HMAC-SHA256: оттуда его нельзя прочитать, только подписывать.
3. Шлюз запоминает телефон (`/var/lib/xgw/phones.json`, 0600: имя, ключ, когда привязан,
   когда был последний запрос). Отвязать — кнопкой в панели; запросы с этим ключом сразу
   отклоняются.
4. Каждый запрос подписан HMAC-SHA256: телефон, метод, путь, время, случайное число, хеш
   тела. Шлюз проверяет подпись (`hmac.compare_digest`), время (±60 с) и что случайное число
   не повторялось. Украденная копия данных приложения (резервная копия, перенос) без ключа
   из Keystore бесполезна. HMAC, а не подпись с открытым ключом: у XGW нет зависимостей, а
   ECDSA пришлось бы писать вручную; ключ на шлюзе лежит рядом с подписками, которые он и
   так хранит.

Ограничения: не больше 30 запросов в минуту с телефона и 10 неудачных входов в минуту на
весь шлюз; после этого — 429. Неудачи — в журнал событий без подробностей.

## 3. Что умеет приложение

| Экран | Что | Откуда |
|---|---|---|
| VPN | включить и выключить VPN телефона; сервер в работе, задержка | Xray на телефоне |
| VPN | выбрать сервер вручную / автовыбор | конфиг со шлюза |
| Шлюз | состояние, VPN шлюза вкл/выкл (выключение — с подтверждением), основной сервер | API шлюза |
| Шлюз | серверы: выбрать, обновить подписки, проверить запасные, замер скорости | API шлюза |
| Шлюз | устройства Wi-Fi: мимо VPN / через VPN | API шлюза |
| Настройки | шлюз, привязка, обновление конфига, «VPN всегда» (Always-on Android) | — |

Чего в приложении **нет** (только в панели): подписки и ссылки серверов,
удаление серверов, установка, логи, настройки Tailscale, отвязка телефонов.

Белый список действий выполняется тем же кодом, что кнопки панели (`Panel.act`): приложение —
«панель в телефоне», поведение и проверки у них одни (ASSUMPTIONS п. 221 (г)).

Каждая фаза — отдельная ветка, свой пункт ASSUMPTIONS, README там, где поведение видно
заказчику.

**Кто проверяет.** Как и шлюз, приложение на настоящем телефоне проверяет исполнитель
GLM-5.3 (max) по ТЗ `docs/TEST-PLAN-REAL-MACHINE-…`: нумерованные шаги, копируемые команды,
«Ожидается» / «Если не так», шаблон отчёта, маскировка секретов. Исполнитель работает на
шлюзе и управляет телефоном через `adb` (отладка по USB или по Wi-Fi включается заказчиком
один раз): ставит APK (`adb install -r`), запускает приложение, читает его журнал
(`adb logcat`), снимает экран (`adb exec-out screencap`), проверяет маршруты VPN
(`adb shell dumpsys connectivity`). Что требует рук заказчика — навести камеру на QR,
подтвердить системный запрос «Разрешить VPN», выйти из дома на мобильную сеть, — ТЗ
описывает отдельными шагами «Попроси заказчика». Сборка APK и первая проверка — на
эмуляторе Android при разработке; настоящий телефон — у исполнителя.

`xgw uninstall` снимает Funnel, включённый XGW (как Serve в Т2), привязки телефонов
(`/var/lib/xgw/phones.json`) удаляются вместе с остальным состоянием XGW.

## 5. Риски и что проверить первым

- **Funnel из российской мобильной сети.** Ретрансляторы Funnel могут быть недоступны или
  медленны. Проверено в ТЗ А1 (20.10.2026): по мобильной сети напрямую адрес открывается,
  через VPN-сервер — нет; отсюда правило «к шлюзу — только напрямую» (§1). Запасного пути
  через VPN-сервер нет: если провайдер мобильной сети закроет Funnel напрямую, пульт вне
  дома перестанет работать, и решать это придётся отдельно. В А2–А3 — проверить напрямую
  вне дома в разное время и при работающем VPN самого приложения.
- **Ограничение Funnel по скорости** (Tailscale называет его, но цифр не даёт): через Funnel
  идут только команды и небольшие ответы, трафик VPN — нет.
- **Лимит устройств у провайдера подписки.** Телефон пользуется теми же серверами, что и
  шлюз, — если провайдер считает одновременные подключения, телефон может занять место.
  Проверяется на телефоне в А3; запасной путь — отдельная подписка для телефона (вопрос 2).
- **Запуск Xray процессом на Android 15/16**: исполняемый файл кладётся в APK как
  `lib…so` (каталог нативных библиотек — единственное место, откуда Android разрешает
  запуск). Дескриптор VPN передаётся из нативного кода (C, NDK), а не через Java: Java при
  запуске процесса закрывает лишние дескрипторы. Проверяется в начале А3 на эмуляторе.
- **Скачивания.** Для А2 скачан (с согласия заказчика 20.10.2026) сканер QR
  `play-services-code-scanner` 16.1.0 с зависимостями из Google Maven; заодно сборка
  докачала инструменты проверки кода Android (lint). Для А3 нужен официальный архив Xray
  для Android — с отдельного согласия заказчика.

## 6. Решения заказчика (20.10.2026)

1. Код приложения — в папке `android/` репозитория XGW.
2. Серверы для телефона — те же, что у шлюза: конфиг раздаёт шлюз.
3. Выключать VPN шлюза из приложения можно — с подтверждением «Интернет дома пойдёт
   напрямую, мимо VPN».
4. Funnel (публичный адрес шлюза на порту 443, вход — только с привязанного телефона) —
   включать.
5. Начинаем с А1: только шлюз; приложение ещё не нужно, доступность Funnel с телефона
   проверяется браузером (`GET /api/hello` без входа отвечает «XGW»).
