## 0. Вопрос, на который должен ответить отчёт

Какие методы из `Flowseal/zapret-discord-youtube` можно воспроизвести через nfqws2 внутри
XGW и какие из них дают устойчивое видео YouTube напрямую через WAN, включая **1080p**?
Для каждого результата указать точный метод, параметры, соответствие исходнику, качество,
протокол и доказательства реального пути. Отдельно оценить 1440p/2160p у лучших вариантов.

Основание — [отчёт r3](TEST-REPORT-REAL-MACHINE-0.2.0-nfqws2-youtube-live-r3-2026-11-14.md),
коммит `c4116890f52855c8cd2179a120df370016ce1ae3`. В нём штатный `hostfakesplit-md5`
дал 720p, 15 минут плюс 5 минут после перемотки; 1080p дважды остановилось после burst.
Причина 1080p не установлена. Фраза «линия дня, не движок» не доказана.
Остальная матрица не проверена. Расширение трассы до /16 не подтверждает конкретный видеопоток.

**Правила завершения r3 здесь заменены.** `SKIP_AFTER_PASS` запрещён для обязательной матрицы.
Успех страницы, curl, первых 60 секунд видео или 720p не закрывает проверку 1080p.
Отказ адаптации не доказывает отказ исходного Flowseal на Windows.
Обратные медиаданные должны приходить напрямую от CDN, но их прохождение через NFQUEUE
не обязательно: стратегия может обрабатывать только исходящий TLS/QUIC handshake.

## 1. Полномочия и порядок работы

Исполнитель сам получает исходники, читает код, готовит лабораторный адаптер, запускает
команды, управляет XGW и браузером, наблюдает воспроизведение через vision/DevTools,

Если терминал, root, браузер или GitHub недоступны — **запросить соответствующий доступ**,
сохранив checkpoint; не просить владельца выполнить команды вместо исполнителя.
Пароль и системный диалог при необходимости подтверждает владелец.

Разрешены временные настройки выбранных доменов, launcher под управлением XGW,
собственные диагностические правила, ограниченные изменения очереди/offload и QUIC ниже,
небольшой проверенный Lua-адаптер, восстановление и публикация материалов опыта.
Менять подписки, основной VPN-сервер, общую политику LAN/Tailscale не требуется.
Не отключать capture/kill switch или Xray ради получения direct; он может продолжать
маршрутизировать прямой поток через freedom. Не запускать второй worker на той же очереди.
Не устанавливать Windows winws/WinDivert и не выполнять BAT. Не обновлять всю систему,
Xray/nfqws2, не отключать проверку TLS или sandbox браузера/worker.

Основное испытание — на ThinkCentre, не в VM. Локальные синтетические проверки ограничить
синтаксисом адаптера, соответствием аргументов и его preflight. Полный pytest не нужен.
На реальной машине разрешён необходимый пакетный анализ, без публикации приватных данных.
Не сохранять в Git cookies, подписки, конфиги, полные HAR/pcap/netlog, signed videoplayback URL.

Ориентир — 6–10 часов, до 120 коротких попыток и до 6 длинных видео; это верхняя граница,
а не обязательное число. Сначала обязательные строки, затем дополнительные гипотезы.
Нельзя обходить лимит разбиением одной стратегии на бессчётные повторы.
Если времени/доступа не хватает, восстановить машину, опубликовать **PARTIAL** и точный
список оставшихся ID. Их статус NOT_RUN, а не FAIL. После каждого блока — приватный checkpoint:
ID, время, версии, конфиги/argv, собственные объекты, следующее действие, путь восстановления.

До сетевого опыта проверить:

1. Ранний пропуск `mark & 0x40000000` находится **до** capture/перезаписи mark в IPv4/IPv6;

4. Один worker под управлением XGW, свободная очередь перед его запуском, preflight работает.
5. Возврат подготовлен и проверен: root-таймер/процесс с keepalive и журналом своих изменений.
   Таймаут покрывает блок видео, продлевать заранее. Не восстанавливать старый полный ruleset
   поверх чужих новых правил; возвращать свои настройки штатным apply и удалять свои объекты.

Если фикс CODE отсутствует, перенести только нужный модуль по процедуре r3 с резервной копией,
проверкой импорта/синтаксиса и штатным apply. Не переустанавливать весь XGW.
При смене установленного кода записать точные SHA до/после; не скрывать изменения в «настройках».

## 4. Прямой маршрут и одинаковый браузерный опыт

По процедуре r3 §4 временно направить YouTube-домены в direct перед catch-all VPN:
`youtube.com`, `googlevideo.com`, `youtubei.googleapis.com`, `youtube-nocookie.com`,
`ytimg.com`, `ggpht.com`, а остальные — только при подтверждении в Network, что они нужны ролику.
Сверить реальный applied JSON: direct = freedom с bypass-mark, без proxySettings/dialerProxy
через VPN. Системный маршрут этого outbound должен вести в физический WAN, не в туннель.
В опыте direct fallback на VPN для этих потоков отключён; иначе результат CONTAMINATED_VPN.
Прочие домены сохраняют исходную маршрутизацию. Xray может оставаться включён как маршрутизатор.

Использовать обычный видимый браузер с отдельным профилем, `--no-proxy-server`.
В TCP-фазе — `--disable-quic`; проверить фактический h2/http1.1 в Network.
Выключить расширения/прокси только в этом профиле, DevTools Disable cache, без изменения
основного профиля владельца. Не использовать `--no-sandbox`/`--ignore-certificate-errors`.
Для каждого кандидата закрывать тестовый процесс и открывать чистый профиль: не переиспользовать
старые TLS/QUIC-соединения, буфер или ServiceWorker. Не чистить системный conntrack целиком.

Выбрать один публичный ролик ≥30 минут с доступным 1080p, без авторизации/возрастных ограничений,
и второй независимый ролик с 1440p/2160p для финалистов. Не брать прямую трансляцию вместо
основного сравнения: адаптивный live-буфер затруднит равные условия. Записать публичные video ID,
длительность, частоту кадров, кодек; signed media URL оставить приватно.
Если есть реклама — дождаться самого ролика и начать измерение после неё.
Качество выбирать вручную, не Auto. Смотреть Current/Optimal Res, а не только пункт меню.
Звук/картинка, продвижение currentTime и кадры проверяются самим исполнителем.

## 5. Перенос методов: обязательная проверка семантики

Flowseal запускает winws семейства zapret1 с `--dpi-desync-*`; XGW использует nfqws2 и Lua.
Одинаковое имя тактики не означает одинаковую последовательность пакетов.
Для каждого ID создать запись `translation.json`: исходные опции в порядке, effective defaults,
фильтры, Lua-цепочка, blob SHA, неизвестные/изменённые параметры, тест проверки преобразования.

Степень соответствия хранить **отдельно** от результата видео:

| Значение | Условие |
|---|---|
| PARAMETER_MATCH | Все применимые опции, defaults, данные и порядок воспроизведены и проверены; это не обещание идентичного Windows packet trace |
| ADAPTED | Метод воспроизведён с явно перечисленными отличиями/непроверенными defaults; всё равно испытывается на YouTube |
| UNSUPPORTED | Определённый механизм не удалось реализовать; остальные строки продолжаются |
| NO_MATCH | Исходный фильтр не выбирается для наблюдаемого потока; это не ошибка обхода |

Обязательные правила перевода:

- `fake → fake`, `multisplit → multisplit`, `fakedsplit → fakedsplit`,
  `hostfakesplit → hostfakesplit` — только исходные точки для сопоставления.
  Для `multidisorder` сравнить также `multidisorder_legacy` и порядок сегментов;
  выбрать реализацию, соответствующую исходному алгоритму, не по названию.
- Комбинации `fake,multisplit`, `fake,fakedsplit`, `fake,multidisorder` выполняются
  как упорядоченная цепочка в **одном** профиле; разделитель `--new` нужен между профилями,
  а не между стадиями одной тактики. Подтвердить, что verdict первой стадии не отменяет вторую.
- `split-pos` переносится через resolver, с проверкой фактических границ сегментов.
  В pinned nfqws2 строковый `pos=1` задаёт смещение один байт; Lua resolver возвращает индекс 2.
  **Не добавлять единицу к CLI-маркеру вручную** из-за 1-based индексации Lua.
  Проверить `1`, `2`, `midsld`, `sniext+1` на одном сохранённом несекретном ClientHello.
- `split-seqovl` и pattern сохраняются точно: 652, 679, 681 — разные варианты.
  Нулевой pattern и `tls_clienthello_www_google_com.bin` — разные данные.
  В multisplit overlap — число байт; у disorder проверить зависимость от позиции/порядка.
- `md5sig` сопоставить `tcp_md5` **на фейках**, `ts` — `tcp_ts` с исходным increment;
  `badseq` меняет SEQ **и ACK**, поэтому одного `tcp_seq` недостаточно.
  Справочный zapret1 задаёт ts=-600000, badseq SEQ=-10000 и ACK=-66000, repeats=1.
  Это справочные значения, пока версия bundled winws не сопоставлена с исходниками.
  Явные +2/+1000/+10000000 из BAT имеют приоритет; default ACK проверить отдельно.
  Если точный default установить не удалось, явно подставить справочный и пометить ADAPTED;
  не останавливать всю матрицу и не выдавать его за подтверждённый исходный default.
- Fooling и repeats не должны портить настоящие сегменты. Проверить, есть ли TCP timestamps
  у реального исходящего Xray-соединения; отсутствие option означает, что ts мог не действовать.
- `fake-tls-mod=rnd,dupsid,sni=...` сопоставить `tls_mod`, включая порядок и базовый blob.
  `none` не заменять рандомизацией. Не навязывать tls_mod профилю, где его не было.
- Повторные `fake-tls=0x00000000` и `fake-tls=!` сохраняют оба blob, их порядок и повторы.
  **`!` означает стандартный fake исходного winws, а не копию настоящего ClientHello.**
  Не заменять его `tls_client_hello_clone`. Совпадение с nfqws2 builtin доказать байтами/SHA,
  иначе извлечь данные из соответствующего исходника или честно пометить ADAPTED.
- `hostfakesplit-mod=host=...` не заменять другим доменом. `altorder=1` требует проверки
  точного порядка; в pinned zapret2 нет готового одноимённого аргумента. Разрешён маленький
  отдельный Lua-адаптер с проверкой порядка; без него явно ADAPTED, исходная строка не PARAMETER_MATCH.
  Не добавлять `midhost=midsld` в Flowseal-профиль только потому, что он помог штатному XGW.
- `ip-id=zero` проверяется отдельно на IPv4 и всех заменяющих пакетах; отсутствие опции
  не означает zero. Нельзя объявить IPv6-поведение проверенным по IPv4.
- repeats, cutoff, any-protocol, L3/L4/L7-фильтры, exclude и порядок профилей сохраняются.
  Hostlist суффиксы и записи с `^` имеют разные правила совпадения.

Минимальные проверки адаптера на ThinkCentre: все 22 конфигурации разобраны; ни одна опция
не потеряна молча; повторные blobs сохранены; `--new` корректен; G09/G10 имеют разные overlap;
G16 имеет два fake; H12 не подставлен вместо G12; S09 получает SYN; preflight всех цепочек.
Проверка неподдерживаемой опции должна выдавать понятную ошибку, не тихий PASS.
Для спорного порядка сравнить исходник алгоритма и короткий packet trace.
Если нужен новый Lua-код, проверить его синтаксис тем runtime, которым пользуется nfqws2.

## 6. Лабораторный запуск внутри XGW

`docs/helpers/nfq_lab.py` из r3 — образец безопасного launcher, **не переводчик Flowseal**.
Его 15 фиксированных кандидатов не заменяют эту матрицу. Исполнитель готовит отдельный
`flowseal_lab.py` и при необходимости Lua под текущий pinned bundle, сохраняет исходники
адаптера и небольшие проверки в отчётном коммите для воспроизводимости.

Контракт адаптера:

1. Приватный root-owned каталог `/run/xgw-flowseal.XXXXXXXX`, mode700, JSON mode600;
   launcher mode755. Отдельный DATA `/run/xgw-flowseal-data.XXXXXXXX`, root-owned mode755,
   файлы mode644: только несекретные Lua/hostlist/IPSet/blob для runtime.
   BIN/LUA/данные — реальные root-owned пути, без symlink и group/world write.
   Проверенные данные из пользовательского D копировать в DATA через install, не менять весь D.
   nfqws2 после сброса UID повторно читает списки/Lua: DATA должен быть доступен этому UID
   и в sandbox. Не класть их под LAB700 и не отключать droproot ради доступа.
   JSON, диагностические логи и сетевые доказательства остаются в приватном каталоге.
2. Управление worker/unit/queue остаётся у XGW. Принимаются его qnum, fwmark и пути Lua,
   сохраняется `--intercept=0` для preflight. Никаких shell/eval или argv из непроверенной строки.
   Выбор только по проверенным ID каталога/адаптаций, execv реального BIN после валидации.
3. Blob объявляются до использования, например `--blob=flow_google:@<DATA>/...bin`;
   имя затем передаётся в `blob`/`seqovl_pattern`. Не заменять файл строкой его имени.
   `%LISTS%`/`%BIN%` заменить проверенными путями DATA, GameFilterTCP/UDP — значением12
   исходного disabled-режима. Windows caret/quotes разобрать как данные, не запускать shell.
   Все требуемые списки, включая пустые user-списки, создать до preflight.
4. Профили формируются в исходном порядке и с `--new`. Сохранить исходные положительные
   и отрицательные списки. Во внешний допуск добавить только тестовые YouTube-потоки;
   это ограничение области опыта записывается отдельно, не изменяет сам приём.
5. Для S09 и прочих syndata нужен допуск **до SYN**: точные адреса нового тестового соединения,
   известные из фактического Xray DNS/предыдущего наблюдения, плюс семейство/порт/процесс.
   Hostlist/SNI на этой стадии ещё нет. Не навешивать hostlist на syndata и не ждать его срабатывания.
   При смене IP обновить конечный набор и создать новое соединение. Не расширять до /16.
6. В лаборатории `engine_offload=false`; исходный offload сохранить. Реальный ID подтверждать
   JSON, `/proc/<MainPID>/cmdline` и debug, даже если GUI показывает исходный селектор seqovl.
7. Смена ID: engine off → inactive/queue free → атомарный JSON → preflight с таймаутом 15 с →
   engine auto/штатный apply → PID/argv/queue → новый браузер. При ошибке вернуть предыдущий ID.
8. Debug только короткими окнами 20–45 с. В финальном длительном видео debug/capture выключены.
   Ошибка Lua, отсутствующий blob, неприменившийся конфиг — ERROR_SETUP, исправить и повторить.

В этом же проходе для каждой исходной конфигурации загрузить полную последовательность
применимых профилей BAT с исходными списками. Фактическое вмешательство ограничить потоками
тестового YouTube. Профиль можно исключить только при доказанном несовпадении L3/L4-фильтра
с тестовым потоком (например, GameFilter=12 или Discord UDP19294–19344); записать это в coverage.
Не исключать IPSet-профиль только потому, что позже SNI совпадёт с G: он может действовать на SYN.
Для исключённых профилей не нужны неиспользуемые ACTIVE_GAME/ACTIVE_DISCORD blobs.
Discord/игровой трафик не генерировать. Не менять общий доступ ради подобия Windows wf-фильтру.

Пример **фрагмента** перевода G09, а не самостоятельная команда запуска:

```text
--blob=flow_google:@<DATA>/tls_clienthello_www_google_com.bin
--filter-tcp=443
--payload=tls_client_hello
--lua-desync=multisplit:pos=1:seqovl=681:seqovl_pattern=flow_google:ip_id=zero
```

Launcher обязан добавить проверенные qnum/fwmark/Lua, исходный hostlist/exclude G09,
ограничение области опыта и остальные профили конфигурации. Сам blob здесь используется
как pattern overlap, а не как отдельная fake-стадия. Для S09 нельзя наследовать
`payload=tls_client_hello`: SYN не содержит ClientHello. Для UDP нужен payload QUIC.

повтор страница+60 с 1080p и сослаться на ID измерения. При другом выбранном профиле — новая 5 мин проба.

### 7.3 Общие и запасные методы

Проверить принадлежность каждого фактического hostname/IP к исходным спискам и исключениям.
В штатном list-google есть youtube/googlevideo/youtubei; в list-general их нет.
Поэтому H01–H21 и S01–S22 (кроме S09) могут не обслуживать эти TLS-потоки вообще.
Если действительно выбраны на любой стадии, включая SYN до SNI, — обязательна такая же 5 мин
проба всей цепочки, результат относится к исходному BAT. Проверять NO_MATCH только по
итоговому hostname недостаточно: нужен фактический выбор профилей с начала соединения.
Если не выбраны — NO_MATCH с указанием более раннего профиля; не записывать FAIL.

Дополнительно испытать эти методы **на выбранных YouTube-доменах** как ADAPTED_SCOPE,
сохранив их остальные параметры. Сначала H12 (ALT9: ts+MD5 и ozon.ru), затем H14–H17
(FAKE TLS AUTO), H02/H03/H04 (другие fake/blob/повторы), затем остальные уникальные H/S.
Убрать только точные дубликаты уже испытанных тактик с теми же defaults/blob/order.
Не переносить сюда Discord/игровые UDP-данные как будто это штатная YouTube-тактика.
Исходная строка сохраняет NO_MATCH; отдельная строка ADAPTED_SCOPE получает свой результат.
Это дополнительная фаза после обязательной TCP/QUIC-матрицы, пока остаётся лимит сеанса.

### 7.4 QUIC/HTTP3

Проверить Q01–Q03 и I01–I02 с исходными фильтрами. Различаются repeats6/11 и L7-фильтр EXP.
Сначала зафиксировать membership googlevideo IP в pinned ipset-all и hostname в hostlist.
GameFilter исходного service.bat по умолчанию disabled (TCP/UDP=12); user-списки пустые.
Список ipset не обновлять в ходе сравнения. Режим «все IP» — отдельная ADAPTED_SCOPE-проба,
не изменение источника. Исходные exclude сохраняются.

Открыть новый профиль без `--disable-quic`, проверить actual protocol=h3 у videoplayback.
Если текущая XGW-политика reject/noise мешает, разрешено временно применить quic_mode=proxy,
**только после** проверки, что более ранние правила выбранных доменов отправляют их UDP/443
в direct, а прочая политика остаётся исходной. Название proxy не доказывает маршрут — нужен
applied JSON и конкретный прямой UDP-сокет. Сразу после блока вернуть исходную quic-политику.
Если это невозможно без расширения общего доступа — QUIC=BLOCKED_BY_POLICY; TCP продолжить.

QUIC-hostlist и IPSet-профили применять в исходном порядке. Если YouTube не попадает в Q,
проверить I; если не попадает никуда — NO_MATCH, затем отдельный ADAPTED_SCOPE с точным
набором YouTube-доменов/IP и прежним blob. Q03 с filter-l7=quic не упрощать молча до UDP443.
У каждой реально применимой уникальной QUIC-цепочки —5 мин 1080p+seek; у лучшей —15+5 мин.
Fallback браузера на h2 означает TCP-результат, **не PASS QUIC**. Если h3 не согласован,
записать NOT_ESTABLISHED и фактическую причину, не приписывать отказ QUIC-обходу.

## 8. Доказательства конкретного видеопотока

Для каждого различающегося результата собирать компактную цепочку:

1. Network: успешный/неуспешный `videoplayback`, hostname, protocol, время, объём, video/audio.
2. Фактический **внешний** сокет Xray: destination IP:port, local port, PID, семейство и WAN.
   Browser Remote Address может быть адресом локального прокси; он не заменяет этот сокет.
3. Applied route этого hostname → direct; конкретное соединение не направлено VPN-outbound.
4. Короткая nft trace **до capture** (как r3 priority−401), затем очередь, выбранный Lua-профиль,
   копии с fake-bit и исходящий WAN. Trace только на точные адреса/порты тестового соединения.
5. Входящие байты того же TCP/UDP-кортежа и прирост медиаданных/currentTime/frames в браузере.
   Допустим редактированный публичный transcript с псевдонимами `CDN_A:443`, согласованными
   между строками. Сырые данные остаются локально; записать их SHA и приватное расположение.

Не подменять DNS Xray локальным `getent`: в r3 они различались. При смене CDN/балансировке
обновить наблюдаемый конечный набор и повторить новое соединение. Не расширять trace до /16,
не выдавать общие счётчики всей очереди/сети за NFQ_VIDEO. Для длинного видео достаточно
короткого точного доказательства в начале/при смене CDN, а не постоянного capture20 мин.

Разрыв nft trace на verdict queue сам по себе не доказывает зависание: reassembly и rawsend
могут завершаться DROP. Искать заменяющие пакеты, журнал Lua и ответы. Если SYN/ClientHello
вышли, но ответов нет — это наблюдение, а не доказанный источник сброса/блокировки.

После каждых 4–5 кандидатов повторить A0 и короткий A1, чтобы видеть изменение условий сети.
Сравнивать соседние по времени окна; изменившийся CDN записывать как различие условий.
Если on/off оба работают одинаково — PLAYBACK может пройти, BENEFIT остаётся NOT_ESTABLISHED.

## 9. Устранение падений в этом же проходе

| Наблюдение | Следующее действие исполнителя |
|---|---|
| Preflight/Lua/unknown argument | Исправить перевод/путь/права, проверить аргумент по pinned коду; ERROR_SETUP, не FAIL метода |
| Нет нужного профиля в argv/debug | Исправить learned override, `--new`, filter/order, JSON restart; повторить новое соединение |
| Нет SYN для syndata | Убрать ошибочную зависимость от SNI, подготовить точный допуск до SYN; проверить очередь |
| Нет ClientHello в очереди | Сверить реальный Xray IP, mark, ct packets, family; захватить с начала TCP |
| Ранний recapture | Проверить CODE и загруженные nft; исправление до дальнейшей матрицы |
| CH собирается не полностью | Проверить reassembly/packet budget; один повтор standard/no-reassembly и ограниченное увеличение первых 8 TCP-пакетов до 24 для тестового потока |
| Offload мешает видеть/обрабатывать сегменты | Один повтор с временно отключёнными подходящими WAN GRO/GSO/TSO, точный возврат; не объявлять checksum offload ошибкой на проводе |
| Страница работает, медиа нет | Проверить CDN direct, очередь именно CDN, hostlist/IPSet, ответ/таймаут видеозапроса |
| 1080p останавливается после 60–90 с | Сохранить буфер/requests/rate до и после; повторить новым соединением, сравнить другой метод и второй ролик, затем 720p отдельной строкой |
| Только один CDN/IP отказывает | Один повтор того же метода на другом реально выбранном адресе; не обобщать на весь метод |
| IPv6 отличается | Отдельная проба TCP/IPv6 при рабочем WAN IPv6; не выключать IPv6 всей машины ради результата |
| HTTP403/429/нет формата | Обновить страницу/истёкший URL, проверить доступность ролика; AUTH/RATE_LIMIT/FORMAT, не DPI_FAIL |

Не строить полное произведение всех настроек. Ветки меняют один фактор и только когда
наблюдение его обосновывает; не более двух одинаковых повторов. Исправление интеграции,
изменившее общий путь, требует повторить ранние отрицательные строки, затронутые дефектом.
Нельзя объявлять «линия ограничена» по одному stall. Для такой гипотезы нужны сравнения
других методов/роликов, фактической скорости, буфера и условий, иначе CAUSE_UNRESOLVED.

## 10. Длительные проверки и критерии

Выбрать до 3 лучших независимых TCP-методов после полного короткого перебора.
Каждому: чистый запуск, фиксированное 1080p, **15 минут**, seek за буфер, ещё **5 минут**.
Если только один прошёл короткий этап — проверить его и повторить в отдельном временном окне;
не выдумывать ещё два победителя. Отдельно лучший фактически работающий QUIC15+5.
У лучшего метода проверить второй ролик: 1440p и 2160p по 5 мин, если доступны; ограничения
декодирования/дисплея/формата записать отдельно. Они не отменяют обязательный 1080p.

Каждые 30 с записывать currentTime, фактическое разрешение/fps, buffer health, downloaded bytes,
network rate за интервал; dropped/total frames, waiting/stalled/error events по возможности CDP.
Vision-снимки минимум T0/T5/T10/T15/после seek/финал, фактическое движение кадров проверять
между снимками. «Connection Speed» YouTube не подменяет измеренный прирост bytes/время.

| Вердикт | Критерий |
|---|---|
| PASS_1080_LONG | 15+5 мин 1080p, без автоматического снижения качества, fatal error, пауз>2 с после старта вне намеренной перемотки; seek восстановился≤30 с; direct и NFQ_VIDEO подтверждены |
| PASS_1080_SHORT | Прошли 5+1 мин и доказан путь; длительной проверки ещё нет |
| PARTIAL_720 | 720p работает,1080p не прошло; не закрывает цель 1080p |
| FAIL_PLAYBACK | Нужный профиль реально применился, маршрут/перевод исправны, видео не выдержало критерий |
| ERROR_SETUP | Ошибка инструмента/переноса/очереди не устранена; эффективность метода неизвестна |
| CONTAMINATED_VPN | Хотя бы существенный page/API/media поток ушёл через VPN; повторить с правильным direct |
| NOT_RUN / UNSUPPORTED / NO_MATCH | Честная причина отсутствия измерения; не отрицательный сетевой результат |

Отдельные поля: TRANSLATION, DIRECT, NFQ_VIDEO, BENEFIT, PROTOCOL, RESTORE, UTILITY.
UTILITY=NATIVE только для штатного профиля XGW без launcher; LAB для адаптера. Успех LAB
доказывает работоспособность метода в экспериментальном пути XGW, но не наличие готовой
кнопки/штатного профиля. Подготовить точные выигравшие argv/данные и рекомендацию минимального
включения в продукт; массовый перенос всех BAT в интерфейс этим заданием не требуется.

## 11. Возврат

Закрыть тестовые браузеры, остановить лабораторный worker штатно. Вернуть CFG, quic mode,
offload, sysctl/accounting и исходный engine state. Удалить только свои nft-объекты,
launcher/LAB/DATA и timers после проверки восстановления. Сверить конфиги побайтно, владельца/права,
маршруты/applied JSON, отсутствие временных YouTube-исключений и диагностической очереди.
Проверить XGW/панель, обычный HTTPS, исходный VPN и отсутствие падений сервисов.
Подтверждённый capture-фикс CODE не откатывать к заведомо старому дефекту; записать его SHA.
Оставленные приватные доказательства/бэкапы перечислить, не публиковать их содержимое.
При ошибке восстановления сначала исправить её; RESTORE не объявлять PASS заранее.

Обязательно включить:

1. Машина/ОС/ISP без личных реквизитов, время, PLAN/CODE/installed SHA, BIN/Lua/blob версии;
   кто запускал — сам исполнитель, каким доступом; внесённые исправления и возврат.
2. Таблицу **22 исходных BAT**: выбранные page/API/video профили, ссылки на ID опытов,
   translation, TCP/QUIC,720p/1080p, причина NO_MATCH/NOT_RUN. Не скрывать непроверенные строки.
3. Таблицу уникальных G/H/S/Q/I и ADAPTED_SCOPE: exact argv, defaults и отличия от источника,
   SHA blob/adapter, маршрут, NFQ_VIDEO, время до первого кадра, stall, seek, quality, bytes/rate.
4. Сводку A0/A1 по времени и связь доказательств одного кортежа, а не только суммарные counters.
5. Данные длинных проб/высоких разрешений, остаточные сомнения, незавершённые ID и следующий шаг.
6. Проверенный исходник launcher/Lua/его минимальных проверок. Произвольный локальный shell
   без сохранённого кода не обеспечивает воспроизводимость. Разделить source data и измерения.

После PASS, FAIL или PARTIAL **самостоятельно commit и push в `origin/gui-light`** без нового
запроса разрешения. Публикация этих материалов ранее разрешена владельцем.
Перед staging проверить diff и отсутствие секретов, добавить только относящиеся к заданию файлы.
Не включать рабочие конфиги, бинарники, сырые network dumps и посторонние изменения.
Если удалённая ветка продвинулась, сохранить свои изменения коммитом в отдельной ветке/worktree,
перенести поверх актуального origin/gui-light, проверить конфликт; без force push/reset чужой работы.
После push сверить remote SHA, дать ссылку на отчёт и коммит. При недоступной авторизации
запросить доступ, сохранить готовый коммит; не заявлять публикацию до подтверждения GitHub.
