# XGW Free Pool: план реализации

Основа — ТЗ «XGW Free Pool» v1.1 (28.10.2026, требования R01–R56, этапы F01–F16, сценарии
FP01–FP55). Ниже — как оно ложится на нынешний код (ветка `freepool` от `tspu2`, а не `d327aa4`,
под который ТЗ написано) и решения заказчика, которые меняют ТЗ.

## Решения заказчика (28.10.2026)

1. Бесплатный режим — **альтернативный режим работы**, переключаемый, «приложение внутри
   приложения». После испытаний — замена подписки примерно на 90 %.
2. **Подписка остаётся несущим каналом управления**: списки серверов на закрытых сайтах
   (VPN Gate, VPNBook), профили и учётные данные качаются через неё. Трафик пользователей в
   бесплатном режиме идёт только через бесплатные серверы.
3. Делать всё по ТЗ, включая OpenVPN.
4. **VPNJantit убран** (по отчёту вехи М1): учётку он выдаёт только формой на сайте, на 7 дней;
   без неё ни одного рабочего сервера («фактически платный»). Вместе с ним убрано поле
   «Выданные ссылки» в панели. Источники пула — VPN Gate и VPNBook.

## Отступления от ТЗ и почему

| ТЗ | Здесь | Почему |
|---|---|---|
| R02: в free_pool подписки не скачиваются и не используются | Подписка — несущий канал управления (каталоги, профили, учётки), не выход для трафика | Решение 2: каталоги доступны только через VPN |
| R10/R43: каталог — напрямую, туннель — при восстановлении | Каталог — сначала через несущий канал, напрямую — только если источник открыт; холодный старт — сохранённый каталог | То же |
| R23 шаг 3: прямой TCP к серверу | Прямой TCP — признак «адрес закрыт» (как в tspu2); такой сервер в пул не берётся (через несущий канал его трафик съел бы квоту подписки) | Цель — заменить подписку, а не гнать трафик через неё |
| R05: пустой пул — CLOSED_DEGRADED | То же, плюс предупреждение в панели с кнопкой «Вернуть режим подписок» (сам шлюз не переключает) | Как с белыми списками: решения о стоимости — за заказчиком |
| Источники VPN Gate, VPNBook, VPNJantit | VPN Gate и VPNBook | Решение 4 |
| R45: адрес туннеля — из hook-скрипта OpenVPN | Из интерфейса управления OpenVPN (`state`, иначе `PUSH_REPLY`); скриптов нет вовсе (`script-security 1`) | Меньше кода, исполняемого от имени работника |
| Базовая ревизия d327aa4 | `tspu2` (main 4aeec24 + первый этап анти-ТСПУ) | Многие предпосылки ТЗ (§2) уже сделаны: независимая проверочная цель, отпечаток nft, точное правило маршрутизации, границы разбора, пределы HTTP |

Остальные требования — как в ТЗ: строгая изоляция OpenVPN (R44–R48), регион по фактическому
выходу (R14–R17), этапы проверки и бюджет (R23–R29), выбор и переключение (R30–R39), без
выдуманных API источников (R03, R07), отказ закрывает выход (R05).

## Архитектура

```
устройства LAN, сама машина, Docker, tailnet
  → перехват XGW (TPROXY/TUN, как сейчас)
  → Xray: балансировщик бесплатного пула (участники и запасные — бесплатные серверы)
      ├─ Shadowsocks (ключи Outline у VPNBook) — обычные outbound'ы Xray
      └─ OpenVPN (VPN Gate, VPNBook) — SOCKS-мост к изолированному работнику:
           пространство имён службы xgw-fp@<gen> ← veth → хост (NAT, ACL: только адрес:порт)
             openvpn (свой пользователь, без прав на сеть хоста) → TUN fpt0
             SOCKS-работник (Xray, свой пользователь) → только через fpt0
  Xray: серверы подписки (несущий канал) ← http-in на 127.0.0.1
      ← демон: каталоги, профили, учётки (никакой трафик пользователей сюда не маршрутизируется)
```

## Бэкенд OpenVPN (веха М2)

Веха М2 делится на два шага. **М2а** — настоящая проверка серверов OpenVPN в изолированном
пространстве имён, пока в режиме наблюдения: трафик по-прежнему идёт через подписку. ТСПУ
распознаёт и режет сам протокол OpenVPN, поэтому сначала нужно увидеть на машине заказчика,
сколько серверов вообще подключаются. **М2б** — трафик через пул по переключателю (выбор,
поколения, резерв, пустой пул — закрыто с предложением вернуть подписку).

Поведение OpenVPN здесь не проверяется: пакет openvpn не ставится ни в WSL, ни в контейнер
(решение заказчика 28.10.2026). Конфиг пишется по руководству OpenVPN 2.6, агент — с юнит-тестами
на подставных работниках. До решения о минимуме проверок у разработчика ядро Linux
(пространство имён службы, veth, TUN-устройство с владельцем, правила nftables, самопроверка
охраны) один раз проверено стендом в WSL с подставным OpenVPN; дальше всё это — в ТЗ М2а на
машине заказчика («живое поколение», см. «Как проверяется»).

```
служба xgw-fp@<gen> (root, PrivateNetwork=yes — своё пространство имён, PrivateTmp; возможности
CAP_NET_ADMIN, CAP_SETUID, CAP_SETGID, CAP_CHOWN, CAP_KILL; NoNewPrivileges; /run — только
чтение, кроме /run/xgw/fp/<gen>) — агент `xgw pool agent <gen>` (freepool/agent.py):
  1. охрана nftables (inet xgwfp): всё закрыто; на выходе — отказ со счётчиком refused_out;
  2. постоянный TUN fpt0 с владельцем xgw-ovpn; маршрута по умолчанию нет; фаза «guarded»;
  3. ждёт veth от демона: fpi<idx> 10.250.<idx>.2/30, маршрут только к адресу сервера /32;
  4. самопроверка охраны (R46): от пользователей работников — к серверу без туннеля, наружу, к
     хосту, к интерфейсу управления; закрыто = «нет маршрута» или отказ с ростом счётчика;
  5. SOCKS-работник — Xray от xgw-fps (socks 10.250.<idx>.2:1080, пароль, UDP; выход — только
     fpt0, DNS — 1.1.1.1 и 8.8.8.8 через туннель);
  6. OpenVPN от xgw-ovpn: конфиг собран заново из разобранного профиля (ifconfig-noexec,
     route-noexec, disable-dco, pull-filter для маршрутов и DNS, auth-retry none); конфиг и
     учётка — в /tmp службы (у каждого поколения свой), root:<группа работника>, 0640
     (memfd не годится: Xray читает конфиг только по пути, проверено);
  7. управление OpenVPN — 127.0.0.1 внутри своего пространства имён: CONNECTED — адрес на fpt0
     и маршрут по умолчанию в fpt0; RECONNECTING/EXITING — маршрут убран (закрыто).
демон (хост, CAP_NET_ADMIN, freepool/backend.py): задание /run/xgw/fp/<gen>/manifest.json
(0600); адрес сервера — в набор fp_peers таблицы ip xgw (адрес . протокол . порт) и в
/run/xgw/fp/peers.json; veth fpv<idx> ↔ fpi<idx> (внутренний конец — в пространство имён агента
по PID, только после фазы «guarded»: PID службы известен раньше, чем systemd создаёт
пространство имён); 10.250.<idx>.1/30. В ip xgw: из fpv* в WAN — только к fp_peers, ответы —
обратно, маскарадинг 10.250.0.0/16 (только при free_pool.mode не off).
проверка: временный Xray (http-inbound → socks к 10.250.<idx>.2:1080) — загрузка и страна выхода;
трафик — по счётчикам fpv<idx> (внешние байты вместе с рукопожатием); поколение — убрать всегда.
пределы (R26, R29): туннель — один за шаг, 12 подключений в час, 60 в сутки, 2 в час на
источник; профиль VPNBook — через несущий канал, раз в сутки.
```

Бэкенд не годится (нет OpenVPN, пользователей, службы, пересылки IPv4 — шлюз без сети LAN,
или набора fp_peers — перехват не загружен) — серверы OpenVPN проверяются как в М1, только
доступностью адреса; причина видна в карточке, `xgw pool` и `xgw diag` («Бесплатный пул»).
ufw: при включённом — правило `route allow in on fpv+ out on <wan>` (с подтверждения при
установке; «+» в имени интерфейса ufw принимает — проверено по его исходнику); точные адреса
и порты задаёт таблица XGW.

## Как проверяется

Решение заказчика: проверок у разработчика — минимум, на машине заказчика — максимум.

- **Здесь:** юнит-тесты затронутых модулей (один прогон в конце правки), ruff и извлечение
  помощника из ТЗ с подсчётом его суммы. Стендов, полных прогонов и опытов здесь нет, кроме
  проверки факта, без которого код не написать.
- **На машине — ТЗ вехи** (`docs/TEST-PLAN-REAL-MACHINE-0.2.0-freepool-*.md`) с помощником,
  который только читает: установка и повторная установка (пакет, пользователи, шаблон службы,
  ufw), правила (fp_peers, форвардинг, отпечаток), **живое поколение** (свойства службы,
  возможности и пространство имён агента и работников, интерфейсы и маршрут внутри до и после
  подъёма туннеля, права файлов в /tmp службы, секреты в состоянии, veth и элемент fp_peers на
  хосте — по `/proc` и `systemctl show`, без входа в пространство имён), самопроверка охраны,
  подключения и их пределы, коды отказов, сброс в форвардинге, трафик проверок, секреты в
  журналах, оценка `systemd-analyze security`, панель, `xgw pool`, `xgw diag`, выключение без
  следов.

**Веха М1 — режим наблюдения:** пул собирается и проверяется, панель его показывает, а трафик
ещё идёт через подписку. Сделано: `free_pool.mode = observe`, карточка «Бесплатные серверы»,
`xgw pool`; отчёт с машины пройден без дефектов —
`docs/TEST-REPORT-REAL-MACHINE-0.2.0-freepool-m1-2026-10-28.md`. **М2а** — серверы OpenVPN
настоящим туннелем, всё ещё в наблюдении: `docs/TEST-PLAN-REAL-MACHINE-0.2.0-freepool-m2a.md`.
**М2б** — трафик через бесплатный пул по переключателю. **М3** — восстановление, интерфейс
целиком, сутки наблюдения.

## Что нужно извне

- OpenVPN: на машине заказчика ставит установщик XGW (пакет Ubuntu `openvpn`) вместе с
  пользователями работников `xgw-ovpn` и `xgw-fps`. Пакет в окружение разработки не ставится
  (решение заказчика 28.10.2026): пространство имён, veth и правила проверяются здесь, сам
  OpenVPN — на машине заказчика по ТЗ.
- Настоящие образцы ответов источников (CSV VPN Gate, страницы VPNBook) — с согласия заказчика,
  очищенные: без ключей, паролей и адресов в репозитории.
