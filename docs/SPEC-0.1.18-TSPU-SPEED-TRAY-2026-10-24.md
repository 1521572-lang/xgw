# ТЗ 0.1.18: устойчивость к ТСПУ (DPI), контроль скорости участников, значок в трее

Для модели, пишущей код XGW. Источник: разбор архитектуры работающего шлюза (24.10.2026,
документ «XGW-описание-архитектуры»), отчёты испытаний веток android-a3 / cores-update,
issue #2. Реализовать в ветке `tspu-speed-tray` от актуального main, версия 0.1.18,
обновить ASSUMPTIONS.md. По итогам — программа испытаний на реальной машине
`TEST-PLAN-REAL-MACHINE-0.1.18-tspu-speed-tray.md` по принятому формату (извлекаемые скрипты,
маскировка выводов).

## Контекст

ТСПУ провайдера эволюционирует от полной блокировки к «придушиванию»: TCP-соединение
открывается, но пакеты дропаются на TLS ClientHello или после первых 16–32 КБ (в системе это
уже детектируется как STALL_BEFORE_BODY и FROZEN), либо полоса режется до 1–5 Мбит/с без
разрыва. Система имеет примитивы для ответа (два ядра, профили xray/xray+frag/singbox,
классификация ошибок, probe 57 620 Б), но использует их пассивно. Ниже — требования перевести
их в активную защиту. Числа в требованиях — дефолты, все выносатся в config.toml.

## R1. Эскалация профиля xray → xray+frag вместо браковки сервера

Сейчас комбинация обхода закреплена за сервером статически. Требуется:

1. Если проверка сервера в профиле `xray` дала STALL_BEFORE_BODY, FROZEN или CONNECT_FAIL —
   не списывать сервер в мёртвые, а автоматически переключить его профиль на `xray+frag` и
   повторить проверку. Умершим считать только после неудачи и во фрагментированном профиле.
2. Эскалация пишется в события (state.db) и видна в панели у сервера («обход: xray+frag
   после STALL_BEFORE_BODY, 24.10 21:15»).
3. Деградация обратная: если во фрагментированном профиле сервер стабильно OK N_ок подряд
   (дефолт 20 успешных проб за 12 ч) — вернуть профиль `xray` (фрагментация — расход CPU
   сервера и чуть скорости, держим её только по необходимости).
4. Профиль фрагментации для Xray 26.10.21: случайные размеры фрагментов и интервалы
   (диапазоны в конфиге), нарезка пакетов 1–3 (не только tlshello) — предсказуемые
   статические фрагменты ТСПУ собирает.
5. Лимит: не более K_эск (дефолт 2) эскалаций на сервер в M часов (дефолт 6), иначе сервер
   помечается «нестабилен по ТСПУ» и в авто-выбор не попадает до смены состояния.

## R2. Отсечение QUIC (UDP/443) клиентов

TCP-фрагментация не действует на HTTP/3. Требуется:

1. В таблицу `ip xgw` (механизм xgw-net, идемпотентно) добавить reject
   `icmpx type port-unreachable` для исходящего UDP/443 **из LAN и от машины** — клиенты
   бесшовно откатываются на TCP/443, где работает frag.
2. Исключения обязательно сохранить: tailnet-адресация и DERP/MagicDNS Tailscale, локальные
   подсети, **собственные исходящие подключения шлюза к серверам VPN** (если endpoint
   сервера — UDP/443, он не должен попасть под reject; сверять адреса endpoints), служебные
   порты XGW.
3. Флаг конфига `net.block_quic` (default on); при off — правило не ставится, diag
   показывает состояние.

## R3. Ротация проверочных хостов (probe.url)

1. `probe.urls` — массив из 3–4 независимых URL на разных зарубежных CDN (разные домены
   И ASN), размер файла ~56 КБ сохранить (порог 16–32 КБ должен пробиваться).
2. Выбор хоста: по кругу; при ошибке конкретного хоста — следующий, недоступный хост
   помечается и не используется T_пров (дефолт 30 мин).
3. Вердикт о канале (WAN_DOWN) выносить только когда недоступны **все** хосты напрямую;
   недоступность одного — событие-наблюдение, не состояние.
4. diag и панель показывают активный проверочный хост и счётчики ошибок по каждому.

## R4. Защита bootstrap-DNS и управляющего Tailscale (двумя этапами)

- R4a (обязательно): bootstrap-DNS — шифрованные апстримы по нестандартным комбинациям
  (DoH на нестандартных портах/путях, не только 443/стандартный путь), контроль их
  доступности в diag; деградация — WARN и событие, не молчание.
- R4b (спроектировать и реализовать, если не входит в 0.1.18 — обосновать в ASSUMPTIONS):
  при деградации прямого доступа к DERP (риск: отвал Funnel 8782 для пульта и exit node
  телефона) — аварийный маршрут управляющего трафика tailscaled через живой VPN-туннель,
  строго с fwmark-фильтром, исключающим петлю «VPN внутри VPN». Переключение — по явному
  признаку (DERP недоступен напрямую N раз), с событием и авто-возвратом на прямой путь.

## R5. Пассивный замер скорости через API ядра (без расхода квоты)

1. Раз в T_пасс (дефолт 60–120 с) демон снимает через API Xray счётчики байт (uplink +
   downlink) активных outbound'ов и считает фактическую скорость реального трафика на
   каждый участник.
2. Если реальный трафик участника ≥ П_пасс (дефолт 10 Мбит/с) — участник признаётся
   исправным, активный замер не запускается.
3. Активный замер (~3 МБ) запускается только при малом фоне; оценка скорости — сумма:
   скорость теста + фоновая скорость клиентов за окно теста (чтобы качающая игру машина
  не «убила» здоровый сервер).
4. История пассивных оценок видна в панели рядом с активными замерами (подпись источника:
   «замер» / «из трафика»).

## R6. Уход с «придушенного» участника: топ-кандидаты с ранней остановкой

Работает поверх глобального пула issue #2 (после его закрытия; до того — применять к
участникам текущего класса и к закреплённому серверу).

1. Триггер: N_низ (дефолт 3) последовательных суммарных оценок (R5) < П_низ
   (дефолт 10 Мбит/с) на интервале 5–10 мин.
2. Кандидаты: топ-K (дефолт 5) из глобального пула по свежим данным фоновых сканов,
   исключая x100 и исчерпанные подписки (правила issue #2), только со свежим статусом OK
   по быстрой GET-пробе (57 КБ).
3. Замер кандидатов строго по одному; как только первый показал ≥ П_перекл
   (дефолт 25 Мбит/с) — стоп, переключение на него.
4. Бюджет эпизода: не более K активных замеров и ≤15 МБ трафика (вместо полного скана
   74 серверов ≈ 10 минут и ~220 МБ). Параллельные замеры запрещены (кладут домашний канал).

## R7. Гистерезис и cooldown против «карусели»

1. Переключение выгодно только если кандидат быстрее текущего минимум на П_выг
   (дефолт +30–50%) и сам ≥ П_мин (дефолт 12–15 Мбит/с). С 8 на 9,5 Мбит/с не прыгаем.
2. Если все K кандидатов не лучше — вывод: глобальная просадка (провайдер/вечерний
   троттлинг направления). Cooldown на экстренные сканы T_кул (дефолт 30–45 мин),
   остаёмся на текущем, событие «глобальная просадка канала» в панель.
3. Суточный бюджет проверок сохранить (лимит 1024 МБ/сутки; суммарный расход с замерами
   ≈ 4,3 ГБ/сутки, ~5% квоты) — алгоритм не имеет права его превышать.

## R8. Интеграция с балансировщиком и пином (решение по вопросу разбора)

Целевая схема — **одновременная балансировка между 4–5 участниками** глобального пула
(issue #2); работа через один закреплённый сервер — ручной режим, а не основной сценарий.
Алгоритм R5–R7 действует на каждого участника отдельно: деградировавший выводится из
четвёрки тихо, с подстановкой кандидата, не рывая соединения на остальных участниках.
В режиме пина — тот же алгоритм, но переключение = перепин на лучшего кандидата
(«лучший пин»), с событием и сохранением пометки, что пин автоматический.

## R9. Значок XGW в системном трее (постоянно)

Утилита шлюза должна постоянно присутствовать в системном трее KDE (рядом с часами) на
машине-шлюзе:

1. Компонент `xgw-tray` (Python; QSystemTrayIcon/StatusNotifierItem, зависимость — только
   один GUI-фреймворк, согласованный с существующими зависимостями), автозапуск при входе
   (XDG autostart, .desktop), падение — перезапуск (системный юнит или встроенный сторож).
2. Значок отражает состояние шлюза: HEALTHY / DEGRADED / WAN_DOWN / идёт задание ядра
   (обновление/откат), краткий тултип (состояние, версия Xray/sing-box, выбранный сервер —
   страна и скорость).
3. Меню значка: «Открыть панель», «Проверить выпуски ядер», «Замерить скорость сейчас»,
   «О программе», «Выход» (выход закрывает только трей, не демон шлюза).
4. Данные — опрос локального состояния демона/панели (localhost, существующий токен-механизм,
   без новых сетевых поверхностей и без наружных подключений).
5. Ставится установщиком, включается по конфигу `tray.enabled` (default on).

## Ограничения и совместимость

- Fail-closed не ослаблять; любые новые правила nftables — только через механизм xgw-net,
  идемпотентно, с корректным удалением при `xgw disable/uninstall`.
- Исключения Tailscale (tailnet, DERP, MagicDNS) не трогать; петля «VPN внутри VPN»
  исключается конструктивно (fwmark).
- Конфиг 0.1.17 должен подниматься без ошибок: все новые ключи — с дефолтами; устаревших
  не вводить.
- Квота: суммарный суточный трафик проверок не выше текущего лимита.
- Совместимость с ядрами: Xray 26.10.21 (фрагментация — параметры его формата), sing-box —
  без изменений профиля.

## Приёмка

1. Юнит-тесты: эскалация/деградация профиля (R1), генерация QUIC-правил и исключения (R2),
   ротация и вердикты probe (R3), пассивный замер и сумма с фоном (R5), выбор кандидатов и
   early-stop (R6), гистерезис/кулдаун/бюджет (R7), поведение пина (R8), меню/состояния
   трея без демона (R9).
2. Интеграционные: применение конфига не роняет шлюз; diag отражает новые механизмы; события
   в state.db на каждое действие алгоритмов.
3. Программа испытаний на реальной машине (формат принятый): проверка эскалации на
   заведомо «придушенном» сервере, отсутствие QUIC у клиента (curl --http3 должен упасть и
   откатиться), WAN-вердикт при недоступности одного probe-хоста, уход с ограниченного
   сервера без обрыва остальных, трей у заказчика в сессии KDE.
