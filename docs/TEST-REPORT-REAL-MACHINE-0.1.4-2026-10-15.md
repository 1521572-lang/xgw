# Отчёт об испытаниях XGW 0.1.4 на реальной машине

Прогон по программе `docs/TEST-PLAN-REAL-MACHINE-0.1.4.md` (кейсы REAL-09…REAL-18),
машина та же, что в прошлом отчёте `docs/TEST-REPORT-REAL-MACHINE-2026-10-14.md`.

Проверяемая версия: **0.1.4**, коммит `3a0c1ef9192e8584b3402fccdba0c87304fe9c25`
(ветка `main`, «Исправления по испытаниям на реальной машине (F1–F12), Docker через VPN,
без Windows; версия 0.1.4»), поставлена поверх 0.1.3 повторной установкой из исходников.

Дата прогона: 14.10.2026, 23:56 — 15.10.2026, 01:40 MSK: обновление, кейсы REAL-09…REAL-18,
стенды, перезагрузка машины в 01:26 и показания после неё (§4), вход в панель без терминала
(§12, пароль администратора вводил заказчик).

**Коротко.** Правки по девяти из двенадцати дефектов прошлого отчёта работают на живой
машине. Главное — **недоступный `probe.url` больше не роняет интернет**: за 30 минут
наблюдения с заведомо нерабочим адресом пробы ни одной замены участников, ни одного
`ALL_DEAD`, состояние `PROBE_TARGET_UNREACHABLE` выставлено через 38 секунд (в прошлый раз
признак заслоняла утечка и через 17 минут интернет пропал). Контейнеры Docker теперь идут
через VPN и следуют за выключателем `xgw enable/disable` вместе с машиной, DHCP переехал
в свою службу `xgw-dhcp` и переживает возврат файла `ubuntu-fan` на место, «утечка»
сообщается один раз на проверку, а не каждые 20 секунд, `xgw status` при остановленном
демоне говорит об этом первой строкой с кодом 3, TUN-интерфейс убирается сам, когда
перестаёт быть нужен, а вход в панель без терминала (окно пароля → панель в браузере,
повтор ссылки отклоняется) работает.

Один случай требует внимания заказчика: **после обычной перезагрузки путь контейнеров Docker
через VPN ломается** — дефект G7, §13 (у TUN-интерфейса нет адреса `169.254.10.1/32`, ни одна
команда XGW это не лечит, а `xgw diag` считает состояние здоровым). На этой машине адрес
поставлен вручную (тем же `ip addr replace`, что делает код XGW), контейнеры работают; после
следующей перезагрузки потребуется повторить, пока дефект не исправлен.

Найдено **семь дефектов**: один высокий — **G7** (после обычной перезагрузки контейнеры
Docker остаются без интернета: у TUN-интерфейса нет адреса `169.254.10.1/32`, ни одна команда
XGW это не лечит, а `diag` считает состояние здоровым); G1, G2, G4 и G5 — средние (обновление
0.1.3 → 0.1.4 и прогон тестов на машине с Docker, стенд «одноразовой машины» на Ubuntu 24.04,
`[loopback]`-стенды на машине с работающим XGW); G3 и G6 — косметика и мелочь. Кроме G7,
дефекты не мешают шлюзу работать: интернет у машины и у устройств за роутером сохранялся,
перехват оставался включённым.

## 3. REAL-09. Обновление 0.1.3 → 0.1.4 и перевод DHCP на свою службу

1. `git pull` — коммит `3a0c1ef` (`src/xgw/__init__.py`: `__version__ = "0.1.4"`).
2. Установка поверх, как в программе: `sudo sh packaging/install.sh --yes`.

**Отказ без `--force` (дефект G1).** Установка не началась: предполётный `diag` поднял два
FAIL, которые невозможно устранить до установки:

```
2026-10-14 23:57:22  FAIL  Службы: не работают: xgw-dhcp.service
                     FAIL  Перехват: включён, но правила не загружены
                           → sudo xgw net up
                     Итог: OK — 17, WARN — 1, FAIL — 2
   Установка не начата. Исправьте и повторите (или --force).

```

Причина: новая версия проверяет службу `xgw-dhcp`, которой у 0.1.3 нет, и правила с
цепочкой `containers`, которые 0.1.3 не грузит, — то есть ровно то, что создаёт сама
установка. Подробности и предложение — §13, дефект G1.

3. Повтор `sudo sh packaging/install.sh --yes --force` — успешно, код возврата 0, шаги
   установки совпали с ожидаемыми в программе:

через VPN-узел. Машина оставлена в этом (рабочем) состоянии — см. §16.

Итог кейса: **пройден частично** — сеть, DHCP, перехват и сама перезагрузка работают,
но путь контейнеров после загрузки сломан (G7).

## 5. REAL-11. Контейнеры Docker через VPN (F4) — пройден

**1) Устройство перехвата.** `ip rule`: `95: from all fwmark 0x3 lookup 101`; таблица 101:
`default dev xgwtun0` + `blackhole default metric 4096`; интерфейс `xgwtun0` есть; в конфиге
Xray inbound `tun-in` (при `capture.method = "tproxy"`). В таблице `ip xgw` — цепочка
`containers`, в `prerouting` — `iifname "docker0" goto containers` и `iifname "br-*" goto
containers`:

```
chain containers {
    meta l4proto != { tcp, udp } return
    ct direction reply return
    fib daddr type local return
    ip daddr @reserved4 th dport != 53 return
    meta l4proto { tcp, udp } counter packets 0 bytes 0 meta mark set 0x00000003
}
```

`/proc/sys/net/bridge/bridge-nf-call-iptables` — **файла нет**: модуль `br_netfilter` на этой
машине не загружен (в `lsmod` только `bridge`). То есть описанная в ASSUMPTIONS причина, по
которой TPROXY с мостов Docker не работает, здесь не воспроизводится; путь через метку и TUN
работает независимо от этого.

`enp4s0` по-прежнему 192.168.60.1/24, профиль `xgw-lan` — 192.168.60.1/24, все четыре службы
`active`. После возврата `lan_address` — `diag` снова `OK — 19, WARN — 1, FAIL — 0`.

**REAL-05 — устройство в LAN: пройден.** Устройства за роутером-точкой доступа идут через
VPN: в журнале Xray за время прогона — `from 192.168.60.135/.136/.179/.200 … [tproxy-in ->

.135, .136, .179, .200; в журнале `xgw-dhcp` есть `DHCPREQUEST/DHCPACK`. Проверка
«`disable` — устройства выходят напрямую, `enable` — снова через VPN» выполнена в REAL-11 п.4
на контейнере и в REAL-01/REAL-14 на самой машине.

**REAL-06 — соседство с Docker: пройден.** Таблицы Docker (`ip nat`, `ip filter`, `ip6 nat`,
`ip6 filter`) и XGW (`ip xgw`, `ip6 xgw6`) соседствуют, `nft list ruleset` показывает обе;
`diag` — «OK Файрвол: ufw и Docker перехвату не мешают; контейнеры Docker — через VPN»;
контейнер выходит тем же узлом, что машина (REAL-11), `docker pull` работает.

## 13. Дефекты

### G1. Установка 0.1.4 поверх 0.1.3 с настроенным LAN и Docker отказывается без `--force`

**Важность: средний** (единственный сценарий обновления, описанный в программе, проходит
только со второго раза; на «чистой» машине не проявляется).

- **Как повторить:** машина с XGW 0.1.3, настроенным LAN (`lan_if = "enp4s0"`) и запущенным
  Docker; `git pull` до 0.1.4; `sudo sh packaging/install.sh --yes` (команда из REAL-09 п.2).
- **Что ожидалось:** установка идёт по плану: «DHCP … своя служба xgw-dhcp (dnsmasq,
  /etc/xgw/dnsmasq.conf)», «перехват: сеть enp4s0, эта машина и контейнеры Docker (docker0,
  br-*)», шаг «dnsmasq.service остановлен … DHCP теперь раздаёт своя служба xgw-dhcp».
- **Что получилось:** «Установка не начата. Исправьте и повторите (или --force).», код 1.
  Предполётный `diag` (уже новой версии, но на старом состоянии) даёт два FAIL:
  `Службы: не работают: xgw-dhcp.service` (службы ещё нет — её создаёт установка) и
  `Перехват: включён, но правила не загружены` (в правилах 0.1.3 нет цепочки `containers`,
  которую ждёт 0.1.4; `Capture.loaded()` сверяет набор цепочек в ядре с тем, что нужно новому
  режиму). Оба FAIL неустранимы до самой установки: `sudo xgw net up` под 0.1.3 добавит
  правила без `containers`, а `xgw-dhcp` — служба из 0.1.4.
- **Обход, применённый на испытаниях:** `sudo sh packaging/install.sh --yes --force` — прошло
  без замечаний, код 0, всё дальнейшее поведение штатное.
- **Выводы:** предполётная проверка `install` не отделяет «то, что сломано» от «того, что
  установка сейчас создаст». Для перехода 0.1.3 → 0.1.4 (и, шире, для любой версии, где
  добавляется служба или цепочка правил) это делает обязательным `--force`.
- **Предложение:** при обновлении исключать из предполётного `diag` те строки, которые
  установка исправляет сама (отсутствие `xgw-dhcp.service` и «правила не загружены» при
  наличии `inbound`-ов), либо выводить их как INFO с текстом «будет исправлено установкой»;
  `--force` оставить для настоящих конфликтов.

### G2. Юнит-тесты падают на машине с Docker

**Важность: средний** (прогон `pytest tests/` на целевой машине — часть программы
испытаний; 4 падения из 722 тестов, поведение самого XGW при этом корректное).

- **Как повторить:** на машине, где установлен и запущен Docker (мост `docker0` есть в
  `/sys/class/net`), выполнить `.venv/bin/python -m pytest tests/ --ignore=tests/stand -q`.
- **Что ожидалось:** 0 падений (REAL-16).
- **Что получилось:** `4 failed, 718 passed, 17 skipped`.
  1. `test_probe_all_saves_results` — `KeyError: 'settings'`:
     `gateway.applied()["inbounds"][3]["settings"]["accounts"][0]["pass"]` — тест берёт
     inbound **по порядковому номеру**, а на машине с Docker в конфиг добавляется первым
     `tun-in`, и на позиции 3 оказывается `http-in`. Без Docker порядок прежний
     (`tproxy-in`, `socks-in`, `http-in`, `probe-…`) и тест проходит.
  2. `test_net_up_loads_saved_choice_and_down_removes_all`,
  3. `test_status_shows_capture`,
  4. `test_enable_before_xray_has_the_capture_inbound` — все три ждут строку
     `Перехват: включён — сеть lan0 и эта машина`, а получают
     `Перехват: включён — сеть lan0, эта машина и контейнеры Docker` (текст 0.1.4 при
     найденном мосте Docker).
- **Выводы:** тесты читают состояние **хоста** (`lan.container_links(..., sys_net=Path("/sys/class/net"))`),
  поэтому результат зависит от того, есть ли на машине Docker, — а по программе испытаний он
  там как раз есть.
- **Предложение:** в фикстурах задавать `sys_net` явно (пустой каталог или каталог с
  `docker0`), искать inbound по тегу, а не по индексу, и сравнивать статус по префиксу
  («Перехват: включён — сеть lan0»), а не по всей строке.

### G3. Сообщение «интерфейс xgwtun0 убран: capture.method больше не tun» печатается не только при смене способа

**Важность: косметика.** Текст появляется в трёх разных случаях: смена
`capture.method` на `tproxy`; `capture.containers = false` (REAL-11 п.6); отсутствие Docker
или отсутствие `tun-in` в применённом конфиге (REAL-11 п.7, REAL-01). Причина во всех
случаях одна — «интерфейс больше не нужен», но формулировка называет только `capture.method`.
Программа сама цитирует этот текст как ожидаемый, поэтому дефектом это считать нельзя —
предложение: писать «интерфейс xgwtun0 убран: контейнерам и машине он больше не нужен».

### G4. Стенд «одноразовой машины» падает на Ubuntu 24.04: профиль `xgw-lan` с хоста виден в контейнере

**Важность: средний** (14 из 23 тестов `tests/stand/test_machine.py`; сам шлюз работает, но
проверить его на стенде на этой машине нельзя — а программа требует именно это).

- **Как повторить:** машина с установленным XGW 0.1.4 (Ubuntu 24.04.5, NetworkManager,
  профиль `xgw-lan`), `sudo -E XGW_XRAY_BIN=tools/xray/xray .venv/bin/python -m pytest
  tests/stand/test_machine.py -q`.
- **Что ожидалось:** 23 passed (F9–F11 исправлены).
- **Что получилось:** 14 failed / 9 passed; первое падение —
  `test_uninstall_after_the_panel_keeps_only_the_users_settings`: в снимке «до» есть
  `xgw-lan:04b60955-7254-484b-8c56-ef59ec0fa387:yes`, после `xgw uninstall` его нет.
  Остальные 13 — следствие: следующий `test_install` не находит в контейнере Xray
  (`WARN Xray: не установлен (/opt/xgw/xray/xray)`) и пробует скачать его с GitHub, чего в
  стенде (там своя заглушка вместо интернета) быть не может.
- **Причина.** Корень контейнера — оверлей поверх корня хоста, и `scrub_host_xgw()` убирает
  хостовые следы XGW по списку путей, среди которых
  `etc/NetworkManager/system-connections/xgw-lan*`. На Ubuntu 24.04 NetworkManager 1.46
  хранит профили **не там**: соединения пишутся файлами netplan
  (`/etc/netplan/90-NM-<uuid>.yaml`), а в `/run/NetworkManager/system-connections/…` попадают
  уже сгенерированные. На этой машине `/etc/NetworkManager/system-connections/` **пуст**, а
  хостовый профиль лежит в `/etc/netplan/90-NM-04b60955-7254-484b-8c56-ef59ec0fa387.yaml` —
  шаблон из списка его не находит, и в контейнере профиль остаётся виден. Дальше установка в
  контейнере находит профиль с именем `xgw-lan` и **присваивает** его себе
  (`nm.setup_lan`: `uuid = ours[0].uuid`), а `uninstall` его удаляет — сверка «до/после»
  расходится. Косвенно это касается и продукта: если у пользователя уже есть свой профиль с
  именем `xgw-lan`, XGW его присвоит и при удалении снесёт.
- **Предложение:** в `HOST_XGW_GLOBS` добавить `etc/netplan/90-NM-*.yaml`, относящиеся к
  профилю XGW (проще — удалять файлы netplan, в которых упомянут интерфейс
  `cfg.network.lan_if` и имя `xgw-lan`), либо определять путь профиля через
  `nmcli -g connection.filename` на хосте. Заодно стоит решить, что делать с чужим профилем
  с именем `xgw-lan` (сейчас он присваивается и удаляется).

### G5. `[loopback]`-стенды не работают на машине с установленным XGW: правила хоста отбрасывают их трафик

**Важность: средний** (4 теста из `tests/stand/test_stand.py`; именно этот прогон программа
называет «остальные стенды»).

- **Как повторить:** на машине с работающим XGW выполнить
  `sudo -E XGW_XRAY_BIN=tools/xray/xray .venv/bin/python -m pytest tests/stand -q
  --ignore=tests/stand/test_machine.py`.
- **Что ожидалось:** 0 падений.
- **Что получилось:** 4 падения вида «участники не ожили» — за 40 с ни один узел стенда не
  стал живым (`test_frozen_node_is_dropped_within_two_cycles[loopback]`,
  `test_head_probe_keeps_frozen_node[loopback]`,
  `test_subscription_change_applies_without_dropping_connections[loopback]`,
  `test_daemon_replaces_frozen_member_and_expires_pin[loopback]`). В режиме `netns` те же
  проверки проходят.
- **Причина.** В режиме `loopback` все процессы стенда живут на 127.0.0.1 **хоста** и метят
  свои сокеты меткой «мимо перехвата» (2) — так же, как это делает сама XGW для своего Xray.
  Правило хоста, защищающее службы шлюза, отбрасывает ровно такие пакеты к петле:

```
chain loopback_guard {
    meta mark 0x00000002 ip daddr 127.0.0.0/8 counter packets 91 bytes 5369 reject
}
```

  До прогона стендов счётчик был `packets 0 bytes 0` (снят в снимке «до»), после — 91 пакет:
  это обращения шлюза стенда к его же фиктивным узлам на 127.0.0.1, которые не доходят. В
  режиме `netns` пространство имён своё, правил хоста там нет — потому он и проходит.
- **Предложение:** либо в режиме `loopback` не использовать метку 2 для сокетов стенда (в
  стенде она не нужна: перехвата на хосте нет), либо в `tests/stand` при запуске на хосте с
  XGW проверять/обходить это правило, либо явно пропускать `[loopback]`-режим, когда на
  хосте работает перехват XGW (и печатать причину).

### G6. `test_gateway_own_traffic_is_captured` падает из-за `net.ipv4.ip_forward = 1` на хосте

**Важность: мелкий** (1 тест; та же природа, что F9–F11 — стенд не изолирован от состояния
хоста).

- **Как повторить:** там же, на машине, где XGW включил форвардинг
  (`/etc/sysctl.d/90-xgw.conf`: `net.ipv4.ip_forward=1`).
- **Что ожидалось:** `assert … "net.ipv4.ip_forward" == "0"  # как было`.
- **Что получилось:** `assert '1' == '0'` — новое сетевое пространство имён **наследует**
  значение хоста: проверено отдельно, `ip netns add` + `ip netns exec … sysctl -n
  net.ipv4.ip_forward` даёт `1`.
- **Вывод:** в стенде «одноразовой машины» это уже учтено (файл
  `etc/sysctl.d/00-xgw-stand.conf`, см. `tests/stand/machine.py`), а в стендах на
  пространствах имён — нет.
- **Предложение:** при создании пространства имён стенда выставлять
  `net.ipv4.ip_forward=0` (как это делает `00-xgw-stand.conf` для контейнера) либо сверять не

### G7. После перезагрузки контейнеры Docker остаются без интернета: у TUN-интерфейса нет адреса

**Важность: высокий** (в конфигурации по умолчанию — `capture.method = "tproxy"` и
`capture.containers = true` — правка F4 перестаёт работать после обычной перезагрузки;
`xgw diag` при этом сообщает, что всё в порядке, и ни одна команда XGW это не лечит).

- **Как повторить:** машина с XGW 0.1.4, Docker запущен, `capture.containers = true`;
  перезагрузить машину; затем
  `docker run --rm alpine wget -qO- https://api.ipify.org`.
- **Что ожидалось:** контейнер выходит адресом VPN-узла (как в REAL-11, §5).
- **Что получилось:** `wget: bad address 'api.ipify.org'` — интернета у контейнера нет;
  машина при этом работает через VPN (`144.31.86.64`). У интерфейса нет IPv4-адреса:

```
$ ip -br addr show xgwtun0
xgwtun0          UNKNOWN        fe80::2bd1:e32c:a3a:7e9d/64            ← нет 169.254.10.1/32
$ ip -s link show xgwtun0 | tail -4
    RX:  bytes packets errors dropped  missed   mcast
             0       0      0       0       0       0                   ← ответы Xray не доходят
```

  В журнале Xray видно, что запросы контейнера **входят** в TUN и уходят в Xray, а ответы
  пропадают (это ровно тот эффект, который описан в самом `src/xgw/net/tun.py`: без
  IPv4-адреса на интерфейсе ядро отбрасывает ответы Xray по обратной проверке пути,
  `rp_filter`):

```
01:32:17  from udp:192.168.50.24:47287 accepted udp:192.168.50.1:53 [tun-in -> dns-out]
```

- **Чего не хватает, чтобы починить штатно:** ни `sudo xgw apply --now`
  (`применено через API без перезапуска` — перезапуска нет, подготовки интерфейса тоже), ни
  `sudo xgw disable` + `sudo xgw enable` (`перехват включён: сеть enp4s0 и эта машина`) адрес
  не возвращают — интерфейс так и остаётся без адреса.
- **Причина.** Адрес ставит `tun.ensure()` (`ip addr replace 169.254.10.1/32 dev xgwtun0`),
  и его вызывают два места: `apply/applier._prepare_tun()` по **inbound'у `tun` в конфиге**
  (правильное условие — но только при перезапуске Xray) и `net/capture._prepare_tun()`, где
  стоит ранний выход:

```
rules = self.rules("on")
if not rules.tun:      # rules.tun — это «машина через TUN», т. е. capture.method == "tun"
    return ""
```

  В режиме `tproxy` условие ложно, поэтому захват никогда не готовит TUN-интерфейс — даже
  когда он нужен контейнерам (`Rules.containers`). После перезагрузки интерфейс создаёт сам
  Xray (inbound `tun`, `persist off`), адреса у него нет, а `diag` наличие адреса не
  проверяет. До перезагрузки адрес был — его поставил `apply` (`xgw apply --now` в REAL-11),
  поэтому в REAL-11 кейс прошёл.
- **Обход, применённый на испытаниях** (ровно та команда, что делает собственный код XGW;
  после неё контейнер сразу вышел через VPN — `144.31.86.64`, в журнале
  `from tcp:169.254.10.1:54244 … [tun-in -> proxy-nl-88d6]`, счётчики интерфейса ожили):

```
sudo ip link set dev xgwtun0 mtu 1500 up
sudo ip addr replace 169.254.10.1/32 dev xgwtun0
```

- **Предложение:** в `capture._prepare_tun()` проверять `rules.tun or rules.containers`
  (или, как в applier, наличие inbound'а `tun` в применённом конфиге) — тогда адрес
  появится при любом `xgw net up`; дополнительно стоит проверять интерфейс на шаге watchdog,
  когда мост Docker уже есть, и добавить в `xgw diag` строку «адрес TUN и `rp_filter`»,
  чтобы такое состояние не выглядело здоровым.

## 15. Отличия фактического стенда от программы испытаний

1. **Роутер работает точкой доступа и получает адрес от шлюза.** Программа (§2) исходила из
   прошлого стенда: роутер в режиме маршрутизатора, WAN со статическим 192.168.137.2, а на
   `enp4s0` — временный адрес 192.168.137.1/24. Сейчас этого адреса нет (снят 14.10, до
   начала прогона), роутер HUAWEI AX2 переведён в режим точки доступа, его DHCP выключен, а
   адрес 192.168.60.120 он получает от `xgw-dhcp` по статической аренде `huawei-ax2`
   (`10:71:00:ce:58:47`). Это **предпочтительный** вариант §2.2 программы: он закрывает
   пункт, который в прошлый раз проверить не удалось, — выдачу адреса настоящему устройству
   в LAN. Для REAL-10 DHCP-клиент в LAN тоже есть (сам роутер и устройства за ним).
2. **`probe.url_fallback` не пуст.** В конфиге заказчика он задан
   (`https://cdnjs.cloudflare.com/…/moment.js/2.29.4/moment.min.js`), поэтому в REAL-12 ядро
   переключилось на `url_fallback`, а не на `probe.trace_url`, как ожидает пункт 3 программы
   при пустом значении. Оба пути — один и тот же код, проверено, что выбран запасной адрес и
   что после восстановления `probe.url` выбор снимается. Значение заказчика не менялось.
3. **`capture.containers` в конфиге отсутствовал** (ключ появился в 0.1.4): добавлен явно во
   время REAL-11 п.6 и оставлен `true`; в файле он стоит последней строкой секции `[capture]`.
4. **`curl` на машине не установлен** — команды программы, где он упомянут, выполнены через
   `wget` и `python3` (тот же запрос, тот же результат).
5. **Перезагрузка (REAL-10 п.3–4) выполнена в конце прогона**, а не сразу после возврата
   файла `ubuntu-fan`: так отчёт и его публикация оказались бы уже сделанными, если сессия
   прервётся при перезагрузке. Показания снимает разовая служба `xgw-postboot-014.service`
   через 60 с после загрузки (после снятия показаний она выключена и удалена) — как и
   предлагает программа.
6. **REAL-01 выполнялся в режиме `capture.method = "tun"`** — иначе предохранитель не
   срабатывает (см. §11, оговорка); после кейса способ перехвата возвращён на `tproxy`.
7. **`xgw install` выполнялся с `--force`** (после отказа, описанного в G1).
8. **Статическая аренда роутера** (`static_leases = ["10:71:00:ce:58:47,192.168.60.120,huawei-ax2"]`)
   добавлена в конфиг до прогона по просьбе заказчика и пережила обновление: строка
   `dhcp-host=…` есть в новом `/etc/xgw/dnsmasq.conf`.
9. **Проверка «устройства в LAN»** (REAL-05) велась по журналу Xray (устройства за роутером
   ходят через VPN постоянно) — активных запросов «с телефона» в момент прогона никто не
   делал, а трафик посудомойки, духовки и роутера виден в журнале ежеминутно.
