# Программа испытаний XGW 0.1.5 на реальной машине

Задание для модели-тестировщика. Машина та же, что в отчёте
`docs/TEST-REPORT-REAL-MACHINE-0.1.4-2026-10-15.md` (дальше — «прошлый отчёт»): ThinkCentre,
Ubuntu 24.04.5 LTS, на ней стоит XGW 0.1.4 (коммит `3a0c1ef`), Docker запущен, роутер HUAWEI
AX2 — точка доступа с адресом от `xgw-dhcp`. Задача — поставить 0.1.5 поверх, проверить
исправления дефектов G1–G7 прошлого отчёта и коротко — что уже работавшее не сломалось. Итог —
новый отчёт в том же формате (раздел 6).

Читать до начала работы: ASSUMPTIONS пп. 176–179 (что и почему изменилось, что **не
проверено**), README — разделы «Перехват трафика» (TUN), «Контейнеры Docker», «Разработка и
тесты» (стенды).

## 0. Правила работы

Те же, что в программе 0.1.4 (`docs/TEST-PLAN-REAL-MACHINE-0.1.4.md`, раздел 0), коротко:

1. **Сеть меняется только командами XGW** (`xgw install`, `enable`, `disable`, `net up`,
   `apply`, `uninstall`) и правкой `/etc/xgw/config.toml`. Никаких `nft flush ruleset`, ручных
   правок чужих таблиц nftables, правил ufw и Docker. Исключения этой программы названы в
   кейсах явно — и только они.
2. **Аварийный выход**: `sudo xgw disable`. Интернет пропал больше чем на 2 минуты, и кейс
   этого не ждёт — `disable`, время, `sudo xgw status`, `sudo xgw diag`,
   `sudo journalctl -u xgw -u xgw-xray -u xgw-net --since -15min`, дефект в отчёт.
3. **Перед перезагрузкой (REAL-20)** — доступ к машине, не зависящий от перехвата
   (локальная консоль), либо разовая служба, снимающая показания после загрузки, как в
   прошлый раз.
4. **Секреты в отчёт не попадают** (адреса подписок, UUID, пароли, ключи, токены). Перед
   коммитом отчёта — `grep` на `vless://`, `vmess://`, `trojan://`, `ss://`, `token=`.
5. **Код XGW не чинить.** Найденное — дефект в отчёте; обход — только если без него дальше
   не пройти, и он описывается.
6. Telegram с настоящим токеном не проверяется; `xgw pin` в этой программе не нужен.

## 3. Кейсы

### REAL-19. Обновление 0.1.4 → 0.1.5 без `--force` (G1)

Переход 0.1.4 → 0.1.5 новых служб и цепочек не добавляет, поэтому состояние «прежняя
установка неполная» создаётся явно. **Разрешённое исключение:** остановить службу DHCP самого
XGW — `sudo systemctl stop xgw-dhcp` (аренды у устройств — 12 ч, они его не заметят).

1. `sudo systemctl stop xgw-dhcp`.
2. Обычный diag новой версии из репозитория: `sudo env PYTHONPATH=src python3 -P -m xgw diag`
   → ожидается `FAIL  Службы: не работают: xgw-dhcp.service` (совет `sudo systemctl status …`).
3. Установка: `sudo sh packaging/install.sh --yes` — **без `--force`**. Ожидается: в выводе
   проверок `WARN  Службы: не работают: xgw-dhcp.service → установка запустит их заново`,
   установка идёт по плану, код 0, в конце `systemctl is-active xgw-net xgw-xray xgw xgw-dhcp`
   — четыре `active`.
4. `sudo xgw diag` после установки — FAIL нет; `sudo xgw status` — `HEALTHY` (подождать до
   минуты), «Перехват: включён — сеть enp4s0, эта машина и контейнеры Docker».
5. Если установка всё же требует `--force` — дефект: какие строки FAIL, вывод целиком; затем
   повторить с `--force`, чтобы пройти остальные кейсы.

### REAL-20. Перезагрузка с Docker: интерфейс контейнеров с адресом (G7)

1. До перезагрузки: `docker run --rm alpine wget -qO- https://api.ipify.org` — адрес VPN-узла.
2. Перезагрузка (`sudo shutdown -r now`). Показания через 60–120 с после загрузки:
   - `ip -br addr show xgwtun0` — **есть `169.254.10.1/32`** (вручную его больше никто не
     ставит: интерфейс подготовил `xgw-net.service`);
   - `ip -s link show xgwtun0` — после запроса контейнера счётчики RX растут;
   - `docker run --rm alpine wget -qO- https://api.ipify.org` — **адрес VPN-узла**;
     `docker run --rm alpine nslookup example.com` — отвечает;
   - `sudo xgw diag` — строка `OK  TUN: /dev/net/tun есть; интерфейс xgwtun0 — для
     контейнеров Docker`, FAIL нет;
   - `sudo xgw status` — `HEALTHY`; `systemctl is-active` четырёх служб — `active`;
   - устройства за роутером — через VPN (журнал Xray, как в прошлый раз); аренды на месте.
3. Если контейнер без интернета: `ip -br addr show xgwtun0`, `sudo xgw diag`,
   `sudo journalctl -b -u xgw-net -u xgw-xray -u xgw`, подождать 2 минуты (демон должен
   починить сам — REAL-21) и записать, починил ли.

### REAL-21. Интерфейс без адреса: diag его видит, демон чинит (G7)

**Разрешённое исключение:** снять адрес с интерфейса XGW —
`sudo ip addr del 169.254.10.1/32 dev xgwtun0`: так выглядит интерфейс, который создал сам
Xray. Возвращает адрес XGW (шаги ниже), вручную не возвращать.

1. Без демона: `sudo systemctl stop xgw`; снять адрес; сразу:
   - `docker run --rm alpine wget -T 10 -qO- https://api.ipify.org` — ошибка/таймаут (ни
     через VPN, ни адресом провайдера — **если вышел адрес провайдера, это дефект**);
   - `sudo xgw diag` → `FAIL  TUN: у интерфейса xgwtun0 нет адреса 169.254.10.1/32 или он не
     поднят: ответы Xray ядро отбрасывает → sudo xgw net up`; рядом ожидаемы и
     `FAIL Службы: не работают: xgw.service` (демон остановлен намеренно) и
     `FAIL Перехват: включён, но правила не загружены` — та же причина;
   - `sudo xgw status --json` (код 3 — демон остановлен) → `capture.loaded = false`;
   - `sudo xgw net up` → адрес вернулся, контейнер — снова адрес VPN-узла, `diag` — OK.
2. С демоном: `sudo systemctl start xgw`, дождаться `HEALTHY`; снять адрес ещё раз, засечь
   время. Ожидается: **без единой команды** за ≤ 1 минуту адрес вернулся, в
   `sudo journalctl -u xgw` и событиях (`xgw status` / панель) — «у интерфейса xgwtun0 нет
   адреса 169.254.10.1/32 или он не поднят: … — интерфейс подготовлен заново»; контейнер
   выходит через VPN. Записать, через сколько секунд.
3. Машина и устройства LAN всё это время — через VPN (их перехват от этого интерфейса не
   зависит).

### REAL-23. Текст события об убранном интерфейсе (G3)

1. В `[capture]` поставить `containers = false`, `sudo xgw net up`, `sudo xgw apply --now`.
2. Ожидается событие «интерфейс xgwtun0 убран: он больше не нужен ни этой машине, ни
   контейнерам»; `xgwtun0` нет; контейнер — адрес провайдера, машина — VPN.
3. Вернуть `containers = true`, `sudo xgw net up`, `sudo xgw apply --now` → `xgwtun0` с
   адресом `169.254.10.1/32`, контейнер — снова VPN, `HEALTHY`.

### REAL-24. Стенды на этой машине (G4–G6)

Запуск — как в прошлый раз, под `sudo -E`, `XGW_XRAY_BIN=tools/xray/xray`:

| Прогон | Ожидание |
|---|---|
| `… pytest tests/stand/test_machine.py -q` | **0 failed** (23 passed); в прошлый раз 14 failed из-за профиля `xgw-lan` хоста в `/etc/netplan` |
| `… pytest tests/stand -q --ignore=tests/stand/test_machine.py` | **0 failed**; в прошлый раз — 4 `[loopback]` («участники не ожили») и `test_gateway_own_traffic_is_captured` (`ip_forward`) |

После прогонов: состояние машины не изменилось (`HEALTHY`, перехват включён, четыре службы
`active`), профиль `xgw-lan` хоста на месте (`nmcli connection show`), нет оставшихся
пространств имён (`ip netns`), контейнеров `machinectl` и процессов `tools/xray/xray`.

### REAL-25. Короткая регрессия

- `sudo xgw disable` → машина и контейнер — адрес провайдера; `sudo xgw enable` → оба VPN.
- Устройства за роутером — через VPN; `xgw-dhcp` выдаёт адреса (журнал `DHCPACK`).
- `sudo xgw diag` — FAIL нет; `sudo xgw status` — `HEALTHY`.

## 4. Что не нужно повторять

REAL-12 (недоступный `probe.url`), REAL-13, REAL-14, REAL-15, REAL-18 прошли в прошлый раз, и
0.1.5 их кода не меняла. Повторять — только если в кейсах выше что-то из этого сломалось.

## 5. Итоговое состояние машины

XGW 0.1.5, `capture.method = "tproxy"`, `containers = true`, перехват включён, `probe.url` и
`url_fallback` — как у заказчика, закреплений нет, четыре службы `active`/`enabled`, штатный
`dnsmasq` — как был, `/etc/dnsmasq.d/ubuntu-fan` на месте, `xgwtun0` с адресом, который
поставил XGW (ручных изменений сети не осталось), Docker без тестовых контейнеров и сетей,
`diag` без FAIL.
