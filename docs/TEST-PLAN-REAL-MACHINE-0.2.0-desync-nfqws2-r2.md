# ThinkCentre: остановка демона и продолжение живой проверки nfqws2

Дата подготовки: 2026-11-14. Ветка кода и отчёта — `gui-light`, версия 0.2.0.
CODE = `9b58725354799a6b91c7341c41a311371bdfa4d8` — исправление остановки и явное включение движка.
BASE = `eb47e83270cabe4b8dec9852eb9708d4a08f9266` — код с задержкой из отчёта `e4a791c`.
Испытывать именно этот CODE, не подменять его более новым HEAD.

Документ заменяет §§0–3/14 и уточняет §§4/13
[предыдущего плана](TEST-PLAN-REAL-MACHINE-0.2.0-desync-nfqws2.md).
Его §§4–13 выполняются на **новом CODE**, с поправками ниже. Старый CODE не устанавливать.
Цель — снять STOP по завершению демона и перейти к реальному трафику через nfqws2.
Успешные модульные тесты сами по себе не доказывают обход блокировок.

## 1. Исполнитель, доступ и границы

Модель сама читает файлы, выполняет команды, запускает проверки и осматривает окно через vision.
Не поручать владельцу запуск скрипта, копирование команд, чтение журналов или снятие скриншотов.
При недоступности терминала, браузера или root запросить нужный доступ и продолжить самостоятельно.
Ввод пароля и подтверждение системного диалога остаются владельцу. Нет доступа — NOT_RUN с причиной.

Уже полученные согласия не запрашивать повторно. Сверить их область с отчётом `e4a791c` и текущим
поручением. Новые действия, не покрытые согласиями, согласовать одним конкретным запросом.
Не менять WAN/LAN, Tailscale, подписки, пул и ручной выбор сервера. Не запускать общий unit zapret2,
`install_easy.sh`, `blockcheck`, `git reset --hard`, force push или выпуск дистрибутива.
`nft flush ruleset` в этом прогоне запрещён. В §8 прежнего плана проверять только таблицы XGW
при локальном доступе и действующем согласии. Сторонние таблицы не трогать, live flush = NOT_RUN.

Отчёт публикуется автоматически при любом исходе — PASS, PARTIAL, FAIL, STOP или NOT_RUN.
Дополнительное подтверждение commit/push **отчёта** не требуется. Код исполнитель не меняет.
Конфиги, журналы, снимки и сетевые данные сохранять приватно, под umask 077.
В GitHub не переносить адреса, имена серверов/устройств, URL подписок, SNI, ключи, pcap и сырой JSON.

## 2. Исходники и исходное состояние

Самостоятельно найти существующий checkout XGW на ThinkCentre и перейти в него. Выполнить:

```bash
set -eu
umask 077
REPO=$(git rev-parse --show-toplevel)
git fetch origin gui-light
CODE=9b58725354799a6b91c7341c41a311371bdfa4d8
BASE=eb47e83270cabe4b8dec9852eb9708d4a08f9266
git cat-file -e "$CODE^{commit}"
git merge-base --is-ancestor "$CODE" FETCH_HEAD
D=$(mktemp -d "$HOME/xgw-nfq-r2.XXXXXXXX")
TARGET="$D/new"
git worktree add --detach "$TARGET" "$CODE"
test "$(git -C "$TARGET" rev-parse HEAD)" = "$CODE"
test -z "$(git -C "$TARGET" status --porcelain)"
```

Не удалять неизвестные изменения в основном checkout и каталоги прежнего прогона.
Зафиксировать Python/ядра/nfqws2, capture/lifecycle, diag, PID демона/Xray/sing-box,
режимы zapret2/engine, NFQUEUE и offload. Сохранить приватно установленные модули, config.toml,
panel.json и список таблиц. Использовать команды §2 прежнего плана с новым каталогом D.
Команды diag под `set -e` выполнять через `if ...; then ...; else ...; fi`, чтобы WARN не прервал
сохранение итогов. Службы пока не перезапускать. Чужой NFQUEUE worker или неработающий шлюз — STOP.

В прошлый раз `/opt/zapret2` приведён к 0755; сейчас только проверить права и root-владельца.
TLS/QUIC fake-блобы уже встроены в установленный nfqws2 1.0.7, повторно их не скачивать.
Отсутствие внешнего stun.bin ограничивает STUN-fake, а не весь прогон.

## 3. Короткий входной контроль на настоящей машине

Запускать от обычного пользователя графической сессии, без sudo, в установленном окружении с pytest
(предпочтительно том же, что в отчёте). Не ставить пакеты и не менять тесты ради PASS.
Нет pytest — самостоятельно найти доступное окружение и при необходимости запросить доступ.
Если его нет — STOP tests_unavailable. Полный pytest на TARGET/BASE не повторять: прежние
65 падений уже зафиксированы. Не выдавать их за проверенные заново.

```bash
cd "$TARGET"
python3 --version
if PYTHONPATH=src:. python3 -m pytest -p no:cacheprovider -o addopts= -q \
  tests/test_nfqws2.py \
  tests/test_config.py::test_nfqws2_requires_explicit_enable \
  tests/test_daemon.py::test_stop_during_a_subscription_poll_ends_it_at_once \
  tests/test_daemon.py::test_stop_during_a_refresh_does_not_start_an_apply \
  tests/test_daemon.py::test_stop_during_scans_ends_the_step_at_once \
  --durations=5 >"$D/pytest-target.txt" 2>&1; then
  test_rc=0
else
  test_rc=$?
fi
printf 'target_rc=%s\n' "$test_rc"
```

Ожидание — 16 тестов PASS (некоторые версии pytest отдельно считают unittest subtests).
Остановка опроса проверяется с engine=off и auto, реальный бинарник в тесте не запускается.
Измеряется участок run, а не загрузка Python. Порог <2 секунд сохраняется.
При FAIL модель сама читает приватный журнал. Сообщение timing содержит `cancel_set`,
`cancel_wait_s`, `nfqws2_close_s`, `total_s`; эти флаг и числа разрешено включить в отчёт.
`cancel_set=false` означает отдельный дефект отмены, его нельзя списать на systemd.
Если close быстрый, а total медленный — зафиксировать факт, не придумывать причину и не менять порог.
Любое падение в этом наборе — STOP до установки и автоматическая публикация отчёта.

При PASS ещё дважды выполнить только параметризованный тест остановки опроса тем же пользователем.
Все четыре дополнительных случая должны пройти. Сверить, что службы и настройки не изменились.
Никаких root/systemd действий от этих тестов быть не должно.

## 4. Установка и реальная работа

Выполнить §§4–13 прежнего плана с новым TARGET/CODE и действующими согласиями.
Сохранять результаты сразу; при FAIL прекращать зависимые проверки и восстанавливать шлюз.
Обязательные поправки:

1. **Установка.** Новый дефолт engine — off. Перед установкой всё равно явно задать off
   в существующей секции, сохранив оригинал. После установки worker не запущен, `nfq_output`
   отсутствует, HTTPS на шлюзе/LAN работает. Проверить чтение приватной копии TOML без engine:
   результат off даже при установленном бинарнике; копию не применять.
2. **Завершение без движка.** После установки один раз перезапустить только xgw.service
   при engine=off через разрешённый root-канал. Измерить время, проверить журнал на таймауты,
   PID Xray до/после и возврат HEALTHY. Новый таймаут/потеря связи — FAIL с восстановлением.
3. **Явное включение.** Только в §10 задать engine=auto и старый selective mode=off.
   Проверить worker, очередь, рост счётчиков на Xray/direct/LAN и смену трёх профилей.
   off→auto запускает движок, auto→off останавливает его и возвращает offload.
   После off снова проверить HTTPS и отсутствие тестового worker/очереди.
4. **Отказы.** Выполнить §11. Занятая очередь и небезопасные файлы не должны останавливать
   чужие процессы. Неудачный старт не должен оставлять созданный XGW worker/изменённый offload.
   Настоящий комплект не повреждать — пользоваться приватными копиями из прежнего плана.
5. **Возврат настроек.** Утверждение старого §13 «нет engine — включится auto» здесь неверно.
   Вернуть исходные значения. Если engine отсутствовал, его можно снова удалить — останется off.
   Не оставлять auto включённым без соответствующего поручения владельца.
6. **Откат к установленному коду.** BASE — версия из неустановленного прошлого испытания,
   а не версия для отката. Использовать сохранённые исходные файлы/пакет машины и настройки,
   сверить фактический результат. Без проверенного способа восстановления установку не начинать.

В §8 проверять только восстановление таблиц XGW, общий flush не выполнять.
nf_conntrack_acct из §9 менять только в рамках согласованного теста, с возвратом исходного значения.
Смена PID Xray при установке допустима; при горячей смене только профиля nfqws2 — отдельный FAIL.
Автоматическую смену сервера отличать от ручного pin по журналу и причине смены.

## 5. Проверка полезного результата

Если есть уже согласованный direct-путь YouTube, модель сама открывает браузер, запускает один
и тот же ролик и наблюдает воспроизведение через vision. Сравнить engine=off и auto при неизменном
маршруте. HTTP 200 не заменяет воспроизведение. Путь подтвердить счётчиками direct и NFQUEUE,
проверить, что тестовый поток не ушёл через VPN fallback. Отдельно записать результат видео
и степень доказанности маршрута. Не выключать VPN всего дома и не добавлять маршруты без поручения.
Нет подходящего direct-пути — VIDEO_DIRECT=NOT_RUN; остальные живые проверки продолжить.
Успех соединений с VPN-серверами через nfqws2 не доказывает работу YouTube без VPN.

## 6. Завершение и автоматическая публикация

Модель сама восстанавливает настройки и проверяет capture/lifecycle, diag, HTTPS шлюз/LAN,
службы, offload, отсутствие тестовых очередей/юнитов и сохранность чужих таблиц.
Не оставлять остановленный xgw.service. Root-канал закрыть после восстановления.

Создать отчёт на одну страницу
`docs/TEST-REPORT-REAL-MACHINE-0.2.0-desync-nfqws2-r2-ДАТА.md` с фактической датой машины.
Указать CODE, исходный/конечный установленный код, версии, 16 тестов и повторы, первый FAIL/timing,
живые этапы §§4–13 (PASS/FAIL/NOT_RUN), NFQUEUE пути, профили/PID, offload, VIDEO_DIRECT,
изменения на машине и итог PASS/PARTIAL/FAIL/STOP. При NOT_RUN живых этапов обход остаётся недоказанным.

Автоматически опубликовать отчёт даже при раннем STOP. Создать чистую ветку/рабочее дерево от свежей
origin/gui-light, перенести только обезличенный отчёт, проверить `git diff --check`, сделать commit
и обычный push в gui-light. При конкурентном обновлении перечитать remote и перенести только свой
отчёт, без force и сброса чужих изменений. Не менять checkout с испытываемым CODE.
Сверить опубликованный коммит через `git ls-remote` и показать владельцу ссылку.
Если GitHub/терминал недоступен — запросить доступ; если его не предоставили, сохранить отчёт локально
и указать PUBLISH=NOT_RUN. Не объявлять публикацию без проверки.
