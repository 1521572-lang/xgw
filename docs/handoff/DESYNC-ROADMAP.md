# XGW: единый план T01–T12 и проверяемые гипотезы

Обновлено 2026-11-19. В исходный план включены гипотезы zapret2 и согласованная
интеграция Web UI Zapret-Manager в T11. Это продолжение исходного плана.
**Целевая ОС разработки и приёмки XGW — Ubuntu 24.04 LTS (Noble), amd64.**
На рабочем ThinkCentre в последнем отчёте зафиксированы Ubuntu 24.04.5 LTS
и штатный nftables 1.0.9. Новые правила, установочные пакеты и ТЗ учитывают
пакеты Ubuntu 24.04. В каждом ТЗ Flash сверяет `ID=ubuntu` и `VERSION_ID=24.04`
по `/etc/os-release` и записывает в отчёт `PRETTY_NAME`, ядро и версии
задействованных утилит. Windows и WSL используются для целевых проверок.
Совместимость с пакетами шлюза подтверждается на ThinkCentre.

## Порядок работы до конца разработки

1. **Codex** читает свежий отчёт на GitHub, сопоставляет результаты с планом и
   самостоятельно пишет код XGW, тесты и установочные скрипты. Локально выполняет
   минимум целевых проверок изменённого кода. Основной объём тестов запускается на
   реальной машине, включая Linux, службы, Qt, браузер и реальные маршруты.
2. **Codex** автоматически публикует реализацию и подробное техническое ТЗ в
   текущей ветке GitHub. В [NEXT_STEP](NEXT_STEP.md) указывает действующее ТЗ и
   закреплённый SHA. В ТЗ даёт проверяемую базу, готовые команды, критерии PASS/FAIL,
   порядок остановки, длительность фаз, установку и возврат. Уже принятые сценарии
   повторяются в объёме, необходимом для проверки изменений.
3. **Flash** на ThinkCentre сама запускает опубликованные команды и тесты,
   устанавливает закреплённый коммит при необходимости, проверяет интерфейс через
   браузер и vision, восстанавливает шлюз по ТЗ. При отсутствии терминала, sudo или
   GUI запрашивает доступ. При дефекте фиксирует наблюдение и выполняет указанный
   возврат. Её роль ограничена технической проверкой. Исходники, тесты,
   установщик и критерии остаются ответственностью Codex.
4. **Flash** автоматически публикует только обезличенный отчёт в `docs/reports/`
   даже при блокере. Указывает SHA, исходы и конечное состояние машины.
   **Codex** читает отчёт, обновляет план, устраняет дефекты и публикует
   следующую реализацию и ТЗ. Этот цикл действует для всех оставшихся этапов.

### Решения по внеочередному отчёту

По [повторному отчёту](../reports/2026-11-19T140219Z_audit-engine-close.md) 23 контракта прошли. В двух независимых сериях при выключенном учёте conntrack все 8 датаграмм дошли без очереди, при включённом у нового потока 4 из 8 попали под правило, у ранее открытого потока — 0 из 8. Лабораторная приёмка ограничения Engine в `df93784` завершена. Рабочая установка по отчёту остаётся на `3630b44`.

- **A2/A4, маршруты.** Девять проверок доставки TCP и шесть проверок выбора маршрута в отдельной сети дали ожидаемые результаты. Защищённый поток постороннего UID до приёмника не дошёл. В текущей поставке сохраняем семантику меток Selected и Engine. Произвольные составные метки требуют отдельной проверки при расширении схемы.
- **A5, закрытие TCP.** Обе OLD дали 12/12 LAST_ACK, обе NEW с `7ace100` — 12/12 TCP_CLOSE. На Ubuntu 24.04.5 и nftables 1.0.9 полные текстовые и JSON-листинги прошли во всех четырёх сериях. Отрицательный контроль дал ноль пакетов на тестовом WAN. Реальный бинарник sing-box 1.14.4 закрыл все соединения в обоих вариантах правил в этом опыте. Принято изолированное исправление TCP и совместимости nft, проверка работы после установки включена в единый пакет. [Отчёт](../reports/2026-11-19T160130Z_tcp-close-ab-r2.md)
- **T03/T05, предел пакетов Engine.** Штатный sysctl шлюза остался 0. Сохранены отдельное состояние панели и исключение профилей Engine при недоступном учёте. На живой очереди с включённым учётом и реальным воркером потребуется самостоятельное измерение при появлении такого рабочего режима.
- **A1/A8, панель и состояние off.** На трёх свежих снимках рабочая политика была standalone, очередью 200 владел MainPID `xgw-zapret2.service`. За 40 секунд прироста счётчиков не зафиксировано. Off/off остаётся NOT_OBSERVED. Новый анализатор суточного журнала различает режимы Selected/Engine и отдельно подсчитывает состояния карточки. Ранние файлы не содержат поля Engine. Миграция постоянного токена остаётся в T11.
- **A3/A6/A7.** В 180-секундном окне максимум шага watchdog составил 0,678 с (13 шагов). Задержка wake и гонка при реальном старте службы остаются неизмеренными. В лаборатории TUN восстановлен из отсутствующего и выключенного состояния за 85 и 97 мс. У установленного zapret2 позиция `2` оставляет два байта до разреза; изменение позиции на +1 исключаем. На четырёх нулевых байтах TLSMod вернул nil, на штатном TLS-шаблоне — 677 байт. Эти проверки не измеряли воспроизведение.

По отчёту основной приёмки Codex обновляет этапы T04/T09/T11/T12. Открытые
проверки из аудита объединяются со следующим подходящим проходом на машине.

## Подтверждённая исходная точка

**Новый отчёт — [3630b44 установлен и принят](../reports/2026-11-19_combined-open-blocks.md).**
199 обязательных тестов PASS, 14 прежних отказов совпали с OLD по сообщениям,
API 9 PASS. Установка 8/8, Flowseal, JOB01–05 и возврат прошли. Короткое
Standalone-воспроизведение и SIGKILL fail-closed подтверждены. Отчёт назвал
длинную фазу PASS по 59/59 и 19/20 usable; до проверки часов/пригодных секунд
900/300 её длительность остаётся NOT_CONFIRMED. Последний опубликованный снимок
суточного журнала охватывает 16,55 часа, включая интервалы off и standalone.

**Код основной приёмки — 08d31ee.** В проходе d818e80 прошли 257 обязательных
тестов. Установку остановило устаревшее сравнение цепочек output.
Регрессия проверяет два правила TCP close при наличии UID sing-box и сохраняет
точное сравнение остальных правил TUN и TPROXY. [Единое ТЗ](COMBINED-ADMISSION-2026-11-19.md) · [Отчёт о блокере](../reports/2026-11-19_admission-matrix.md)
Исправляется admission бюджета в обеих карточках/API/задании и контроллере до
старта worker. Неизвестный бюджет не разрешает запуск. Добавлен пофазный результат
каждого кандидата; локальный timeout продолжает матрицу только после off, а
ошибка возврата/конфликт/истощение останавливают её. Длинное видео проверяется
готовым анализатором по часам, пригодным секундам, качеству, новым байтам и seek.

**Исправлено условие эксперимента T09:** отрицательный TLS базового кандидата
не запрещает перебор. В предыдущем ТЗ двусмысленное «на пригодной паре» привело
к пропуску всех 18 строк. Пригодность — корректный формат/срок/область, а не
положительный исход. A/B/B/A не показал эффекта удаления подписи в этом окне;
это не результат проверки остальных восьми профилей и не доказательство
недоступности CDN из Chrome. Новые сутки off/off не назначать вместо завершения
уже запущенных. Новые Selective-сутки — только после подтверждённого активного пути.

Следующие записи — хронология предыдущих пакетов, не текущее состояние установки.

**Отчёт от 18 ноября — [BLOCKED_TEST](../reports/2026-11-18_combined-open-blocks.md).**
Установка 2b78617 не начиналась. API 9 и Qt 11 прошли; новый отказ patch4
воспроизвёл разрешение ручного выбора ALT9 при доступных ассетах. На старой базе
он проходит. Ещё 14 отказов повторены на OLD; точные причины без сообщений
не считать установленными только по именам файлов. Рабочая машина осталась
на принятом слое бюджета, off/off и с неизменными конфигами.

**Исправление 19 ноября — 3630b44.** ALT9 входит в настройки только через
отдельный импорт. Обычная форма может сохранять текущий импортированный профиль,
но не перейти на него с другого. Перед включением Standalone повторяется
проверка ассетов; их исчезновение не мешает off и правке выключенного профиля.
Регрессия воспроизводится независимо от наличия файлов на машине разработчика.
[Действующее единое ТЗ](COMBINED-ACCEPTANCE-2026-11-18.md) обновлено на новый SHA;
оно сохраняет матрицу, медиа, отказы и сутки, дополнено FLOW01–FLOW06 и готовым
JUnit-сравнением расширенного набора с OLD. Новые/изменившиеся ошибки не
оправдываются наличием других старых отказов. Новая реализация пока не установлена.

**Пакет от 18 ноября:** код `2b78617`,
[единое ТЗ](COMBINED-ACCEPTANCE-2026-11-18.md). Реализованы ограниченные фоновые
проверки девяти профилей в два круга, отмена/CAS-возврат/восстановление после
перезапуска, ручное сохранение/сброс профиля по двум HTTPS pass, преобразование
сохранённого CDN в `/generate_204` без подписи, проверенный локальный импорт
ALT9 из веба и desktop, локальный CLI, суточный монитор и его анализатор.
Новая реализация ожидает реальной приёмки. HTTPS-пробы не являются рейтингом
видеоплеера; автоматическое переключение по одному такому успеху не включено.

[Отчёт бюджета](../reports/2026-11-18_selective-budget.md) подтвердил точные
резервы 0,5/0,25/0,25 МиБ, прекращение попыток на лимите, UI/API и возврат

## Приоритеты после проверки CDN

Цель ближайшей версии — дать пользователю выбор между двумя рабочими режимами.

ролик идёт через zapret2, обычный сайт одновременно открывается через выбранный
VPN, а после отказа новое соединение возвращается на VPN. Второй сценарий должен
работать и после того, как истечёт адрес CDN, однажды введённый пользователем.

### Решение по отчёту Flash

Сначала проверить исход возврата, VPN и обычный сайт. При регрессии маршрутизации,
ошибке восстановления или утечке адреса пробы Codex исправляет этот дефект первым.
Затем выбрать работу из таблицы. Исход повтора и доказательство пути видео независимы.
Таблица задаёт работу Codex **после** действующего ТЗ.

| Наблюдение | Следующая доработка или решение | Когда переходить дальше |
|---|---|---|
| Установка или клик блокируют сетевую фазу | Исправить конкретный блокер в установщике или управлении. Сохранить уже принятые проверки формы. | Flash запускает режим штатной кнопкой, видит применённую ревизию и начало проб. |
| `RETRY_LIVE=FAILED` либо устойчивый отказ до повтора | Сопоставить служебную пробу и контроль по тому же URL и IP. Измерить приём и ретрансляции в окне TLS. Если TCP принимает данные, исследовать передачу ответа до TLS-клиента. При нулевом приёме уточнить участок маршрута, на котором теряются данные. | Есть сопоставимая пара либо указана конкретная недостающая привязка. Увеличение числа повторов требует отдельного замера пользы и задержки fallback. |
| Режим active, но `MEDIA_PATH=PARTIAL` | Flash запускает сбор коротких пар до клика. После принятой фоновой пары начинает новый сеанс плеера, сопоставляет время CDP и сокет с общим окном. Пара сохраняет ограничение по конфигурации Xray и владельцу очереди. | Есть свежая передача CDN, рост downlink zapret2 и NFQUEUE сверх фона и параллельный VPN-контроль. [ТЗ](T12-SELECTIVE-MEDIA-PAIRS.md). |
| `RETRY_LIVE=RECOVERED` или `NOT_OBSERVED`, путь подтверждён | Засчитать уже пройденные фазы. Закрыть недостающую часть длинного просмотра и перейти к работе без ручной замены URL. При `NOT_OBSERVED` эффект повтора остаётся открытым до естественного таймаута. | Две перепроверки на одной ревизии, 15 минут пригодного просмотра, перемотка и ещё 5 минут с подтверждением маршрута в обеих фазах. |
| Маршрут подтверждён, но плеер останавливается или снижает качество | По записи отличить истощение буфера от паузы интерфейса и пропусков кадров при полном буфере. Для сетевого голода сравнить один кандидат с базовой стратегией на том же ролике и протоколе. | Отчёт показывает качество и остановки по фазам и какое изменение воспроизводимо помогает. |

### Пригодность для повседневной работы

1. **Срок жизни CDN и бюджет, T04/T12.** Backend показывает срок из `expire`,
   блокирует запуск с истёкшим адресом и ограничивает срок прямого правила.
   [Действующее единое ТЗ](COMBINED-ADMISSION-2026-11-19.md) проверяет это вместе с TLS и медиамаршрутом.
   В 2b78617 добавлен экспериментальный переход на `/generate_204` того же CDN
   без подписи. Сравнить A/B/B/A с подписанным адресом и реальной передачей видео
   при доступном и недоступном CDN. Он не исправляет TLS-таймаут сам по себе. Запасной VPN
   проверять новым соединением. Остаток резервов и время последнего успеха HTTPS
   добавлены в обе панели и приняты в [отчёте бюджета](../reports/2026-11-18_selective-budget.md).
2. **Расход работающего шлюза.** Контроллер резервирует 256 КиБ на запрос. При
   двух адресах каждые 120 с расчёт на непрерывные сутки даёт 720 × 0,5 = 360 МиБ
   при бюджете по умолчанию 256 МиБ. При штатных 180 с получается 240 МиБ,
   запас 16 МиБ делят дополнительные запросы. Это расчёт списаний при заданной
   частоте, фактические интервалы и сетевые байты измеряются отдельно. Для короткого
   опыта ранее использовали 120 с. Действующее ТЗ использует 180 с, оставляет
   256 КиБ для одной контрольной VPN-пробы и проверяет остановку прямых проб при
   исчерпании. На ThinkCentre сверить границу бюджета и свежий VPN-сеанс.
   [Учёт контроллера](../../src/xgw/zapret2.py) · [Значения по умолчанию](../../src/xgw/desync/schema.py).
3. **Суточное наблюдение, T12.** В единое ТЗ включён готовый CLI-сборщик с
   эксклюзивным файлом 0600, пределом 16 МиБ/90 000 с и агрегатным анализатором.
   После длинного прохода выполнить наблюдение с
   обычными настройками и ограниченным журналом. Охватить смену срока CDN и границу
   учётных суток, проверить новый сеанс просмотра после каждой границы. Фиксировать
   число успешных первых проб, повторов и восстановлений, причины и длительность
   fallback, остаток бюджета и случаи ручного вмешательства. Критерий повседневной
   готовности — повторный просмотр и штатный VPN доступны после обеих границ без
   действий владельца, бюджет соблюдён. Для ненаблюдавшихся событий указать пробел.
4. **Экономия ресурсов и выбор профиля, T07–T11.** Начать с повторной обработки
   уже собранной записи. Для сетевого сравнения использовать контроль–кандидат–
   кандидат–контроль при сопоставимых условиях. До автоприменения проверить отмену
   задания, расход и возврат к прежней политике. Команды добавить в обе UI через
   общий контроллер. H07 (несколько воркеров) возвращать в работу при измеренном
   ограничении CPU или потерях очереди. H11/H12 остаются отдельными опытами со
   своими сетевыми предпосылками.

В следующих ТЗ для сравнения указывать числитель, знаменатель и длительность
наблюдения. Из телеметрии плеера брать пригодные секунды, долю 720p, время остановок,
прогресс и паузы. Для оценки кандидатов использовать существующий анализатор
(доля целевого разрешения от 95 %, прогресс от 98 % пригодного времени, контроль
сетевого голода и пропусков записи). Для шлюза сопоставлять время от первого отказа
до успешного **нового** сеанса VPN, число переключений, списанный бюджет, прирост
CPU и памяти процессов и потери очереди относительно фона. Кандидат с тем же качеством
предпочтителен при воспроизводимом снижении расхода или времени восстановления.
Если условия отличаются, сохранить результаты по отдельным окнам. [Анализатор воспроизведения](../helpers/desync_playback_observation.py) · [Сравнение снимков Xray](../../src/xgw/desync/route_evidence.py).

Нельзя просто нарезать зашифрованный UDP и считать это CRYPTO fragmentation. ECH остаётся отдельным ограничением видимости hostname |
| H12 | obfs требует внешнего узла, ключей и двусторонней настройки; это уже резерв через сервер | Расширение T04/T06: сначала существующий VPN fallback, затем отдельно предоставленный remote endpoint. Тесты отказа/восстановления/ключей/циклов/MTU. Без узла BLOCKED_DEPENDENCY. «95% напрямую» — число без измерений, исключено из требований |

## Правила вывода

- `PASS_IMPLEMENTATION` означает проверенную реализацию, не доказанный выигрыш на ТСПУ.
- `SUPPORTED_ON_THIS_LINK` — повторяемый полезный эффект в обозначенных условиях;
  `NO_BENEFIT_OBSERVED` — корректный опыт без улучшения; `REGRESSION` — ухудшение.
- `INCONCLUSIVE` — смена условий/мало данных/некорректный контроль;
  `NOT_IMPLEMENTED` / `NOT_RUN` / `BLOCKED_DEPENDENCY` не смешивать с сетевым FAIL.
- Не объяснять отказ «адаптацией ТСПУ», если не исключены URL, маршрут, CDN, клиент и worker.
  Отсутствие эффекта не опровергает все варианты идеи; отсутствие реализации не проверка идеи.
- Процент ускорения считать из сырых парных измерений. Полные конфиги, URL с подписью,
  токены, адреса подписок и pcap остаются приватными; в Git только обезличенные метрики.
