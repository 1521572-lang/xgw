# ThinkCentre. Длинное видео YouTube напрямую с zapret2

Ветка `gui-light`. Модуль nfqws2 из `c7500f6f40bdfbc9d16b1b23056063813a71a839` принят на
ThinkCentre. Этот прогон использует установленный XGW и nfqws2. Проверяется универсальный
движок `engine=auto` из r5, профиль `seqovl`. Режим `mode` остаётся `off`.
[Отчёт r5](TEST-REPORT-REAL-MACHINE-0.2.0-desync-nfqws2-r5-2026-11-14.md).

## 1. Доступ и исходное состояние

Исполнитель сам запускает команды и браузер, работает с DevTools через vision, сверяет
маршрут и публикует отчёт. При недоступности терминала, root или окна браузера запрашивает
доступ. Владелец только подтверждает системный диалог или вводит пароль.

Использовать действующие согласия на запуск nfqws2 и изменение счётчиков conntrack.
В фазе B универсальный движок обрабатывает также подходящие соединения других клиентов.
Если нужен временный прямой маршрут, согласовать окно и указать, что `direct_domains`
затрагивает эти домены у всех клиентов XGW на время прогона. Диагностическая nft-таблица
только ставит отметку трассировки для выбранного CDN. При непокрытом согласии запросить
его вместе с разрешением маршрута. Остальные настройки шлюза и VPN сохраняются.

Создать приватный каталог, записать текущие PID демона и Xray, режим перехвата, статус
шлюза, конфигурацию, `panel.json`, текущее значение `net.netfilter.nf_conntrack_acct`,
список nft-таблиц и наличие NFQUEUE/worker. Взять образцы HTTPS и статуса обычного VPN
в качестве контроля здоровья. При уже работающем движке или посторонней очереди выяснить
исходное состояние. Чужие процессы, правила и очереди не трогать.

```bash
umask 077
D=$(mktemp -d "$HOME/xgw-nfq-youtube.XXXXXXXX")
git fetch origin gui-light
PLAN=$(git log -1 --format=%H FETCH_HEAD -- docs/TEST-PLAN-REAL-MACHINE-0.2.0-nfqws2-youtube-live.md)
test -n "$PLAN"
git worktree add --detach "$D/source" "$PLAN"
cd "$D/source"
printf '%s  %s\n' d157e31a79ad96fccf69ff9e66866b8b0d724202a504f8d3ef738e6f40dab4a2 docs/helpers/nfq_video_trace.py | sha256sum -c -
PYTHONPATH=src:. python3 -m pytest -p no:cacheprovider -o addopts= -q tests/test_nfq_video_trace.py
```

Брать из ветки этот план, помощник и его тест из одного коммита. Ожидается 8 PASS. При отсутствии pytest
записать NOT_RUN для модульных тестов и продолжить живую проверку. Если тесты упали,
разобрать причину до использования помощника. Проверить наличие `nft`, `ss`, `timeout`
и рабочего браузера. Новая сборка XGW, выключение перехвата и перезапуск Xray не нужны.

## 2. Один прямой маршрут для обоих сеансов

На самом ThinkCentre использовать уже установленный Chromium-совместимый браузер
и новый временный профиль для каждой фазы. Запустить браузер от пользователя графической
сессии с `--user-data-dir="$D/browser-A"` (отдельный каталог B для фазы B),
`--no-proxy-server --disable-quic`. Проверить в DevTools, что медиа использует HTTP/2
или HTTP/1.1 и виден адрес CDN. Не отключать sandbox, проверку TLS или системный VPN.
Открыть Network, включить Disable cache, оставить DevTools открытыми и держать окно видимым.

В штатном XGW убедиться, что перехват локального трафика включён. Использовать существующий
прямой маршрут YouTube либо временно добавить в имеющийся `[routing].direct_domains`:

```toml
# Добавить к имеющемуся списку, не заменять его.
"domain:youtube.com", "domain:googlevideo.com", "domain:youtubei.googleapis.com",
"domain:youtube-nocookie.com",
```

Перед изменением сохранить файл побайтно с правами. Дождаться перечитывания настроек
демоном и проверить **применённый** Xray JSON приватно. Правила для страницы и видеосети
должны вести в `direct` (`freedom` с меткой `capture.mark_bypass`) до правила VPN.
Существующие частные правила маршрутизации сверить по порядку. Проверить, что
`routing.kernel_direct` или внешнее правило не уводит тестовый поток мимо Xray.
Если маршрут не применился штатно, зафиксировать причину, восстановить конфиг и завершить
с NOT_RUN для сравнения. Страница и медиасегменты должны использовать тот же прямой путь
во всех фазах. Смена профиля в фоне или непроверяемый VPN fallback нарушают сравнимость.

Выбрать один доступный публичный ролик длительностью ≥30 минут, с 1080p, без входа в аккаунт,
возрастного ограничения и прямого эфира. Сохранить URL приватно. В обоих сеансах выбрать
одинаковое качество (1080p или 720p, если 1080p недоступно в обоих). Время рекламы не считать.
Посмотреть положение ролика, разрешение и буфер в «Статистике для сисадминов» либо DevTools.

## 3. Живой сценарий

| Фаза | Движок | Что сделать |
|---|---|---|
| A | `off`, worker и очередь отсутствуют | Открыть ролик с нуля в чистом профиле. Записать время первого кадра, ошибки, остановки буферизации. Если за 90 с нет воспроизведения и видеосегментов, зафиксировать первый сбой и завершить фазу. |
| B | `auto`, `seqovl`, `mode=off` | Дождаться активного worker, правильного профиля и штатной очереди. Запустить тот же ролик в свежем профиле. |
| A2 | `off` | Выполнить только если A не прошла, а B прошла. После остановки worker открыть тот же ролик в новом профиле, чтобы проверить, возвращается ли отказ. Прежний прямой маршрут сохранить до конца фазы. |

Перед первой фазой временно включить `nf_conntrack_acct=1`, чтобы условие подсчёта пакетов
было одинаковым. Провести короткую разведку CDN до засчитываемого старта B (§4). Данные
разведочного сеанса пометить отдельно. Засчитываемый B запускать с нуля в свежем профиле.

В каждой фазе с рабочим видео смотреть **15 минут от начала и ещё 5 минут после перемотки**
в незагруженную часть (ориентир 20:00, дальше границы текущего буфера). Записать позиции
и факт движения кадров на 0, 5, 10 и 15 минутах, после перемотки и в конце. Отмечать
остановки буферизации длиннее 2 с и измерить время восстановления после перемотки.
Для PASS по воспроизведению в B требуются первые кадры ≤90 с, заданное время просмотра,
продвижение позиции, новые видеосегменты после перемотки, возобновление ≤30 с и отсутствие
фатальной ошибки либо непрерывной остановки дольше 30 с. HTTP 200 страницы и звук отдельно
засчитываются только как наблюдения. Во время ожидания модель продолжает сбор данных.

## 4. Доказательство пути в фазе B

1. В Network отфильтровать `videoplayback`. Найти успешный запрос с видеоданными
   (`video/*` по заголовку или идентификация видеотрека в DevTools), переданными из сети.
   Записать приватно время, CDN и Remote Address. Сделать это при начале и после перемотки.
2. Найти локальный TCP-сокет Xray к тому же CDN в это время через `ss -ntip` от root.
   Сверить полный кортеж WAN, исходящий интерфейс и рост `bytes_received` в `ss` либо
   ответные байты из `conntrack -L`, если команда доступна. Если Xray разрешил имя в другой
   адрес, связать его с CDN по одному и тому же имени TLS и времени открытия сокета,
   используя разрешённое узкое наблюдение WAN. При нескольких неразличимых сокетах
   повторить короткий старт. При неоднозначности результат пути остаётся неполным.
3. Для точного подтверждения очереди заранее включить диагностическую трассировку на 1–2
   наблюдаемых адресах CDN. Затем открыть новый чистый сеанс или зафиксировать новое
   соединение после перемотки. Старый сокет мог уже пройти первые 8 пакетов. Временно
   создать свою таблицу со случайным именем. Цепочка `output` с приоритетом 89 наблюдает
   пакеты до штатной `nfq_output` с приоритетом 90. Пример для IPv4, переменные заполняет
   исполнитель из наблюдений. Для IPv6 заменить `ip daddr` на `ip6 daddr`.

```bash
# Запустить в одном root-канале. D находится в приватном каталоге.
(
set -eu
umask 077
T=xgw_video_$$
nft create table inet "$T"
trap 'nft delete table inet "$T"' EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
nft -f - <<EOF
add chain inet $T output { type filter hook output priority 89; policy accept; }
add rule inet $T output oifname "$WAN" meta mark $MARK ip daddr $CDN tcp dport 443 ct direction original ct packets <= 8 meta nftrace set 1
EOF
timeout 45s stdbuf -oL nft -a -nn monitor trace >"$D/trace-b.txt" || test "$?" -eq 124
)
```

В коротком окне модель сама запускает браузер и фиксирует новый медиасокет.
Проверить удаление своей таблицы после выхода и при прерывании работы. Сверить worker
и владельца очереди до и после окна. Если CDN сменился, допустимо одно повторное окно
на актуальном IP. Не считать общую дельту NFQUEUE доказательством для ролика.

```bash
python3 docs/helpers/nfq_video_trace.py "$D/trace-b.txt" "$SRC" "$SPORT" "$CDN" 443 "$QUEUE"
```

Помощник читает только файл, ищет кортеж и решение очереди с тем же trace ID. Для
`NFQ_TRACE=MATCH` требуется штатная `inet xgw_guard nfq_output` и нужный номер очереди.
Сверить результат с сырым следом. При несовместимом формате можно проверить эти же
признаки вручную. Если совпадения нет, `NFQ_VIDEO=UNCONFIRMED`, даже когда видео играет.
Данные браузера, WAN и NFQUEUE должны относиться к одному новому видеосоединению.
После перемотки подтвердить свежие данные на том же прямом TCP-соединении либо повторить
привязку для нового, если маршрут изменился.

## 5. Возврат, вердикт и публикация

Закрыть временные профили. Вернуть исходные конфиги и `nf_conntrack_acct`, дождаться
применения, сверить отсутствие своего worker, очереди, диагностической таблицы
и временных direct-доменов. Проверить HTTPS, PID Xray и здоровье VPN, затем закрыть root-канал.
Если нужно применить правила, использовать штатный `xgw enable` после восстановления конфигурации.

- `PLAYBACK=PASS` и `DIRECT=PASS` и `NFQ_VIDEO=PASS` дают PASS живого пути в B.
- `BENEFIT=OBSERVED` — при PASS B и воспроизведённом отказе в A и A2 на том же прямом маршруте.
  Если A тоже прошла или контроль дал разные результаты, `BENEFIT=UNCONFIRMED`.
- Воспроизведение при неполных доказательствах маршрута/очереди — PARTIAL. Ошибка видео
  в подтверждённом сеансе B — FAIL. При недоступности необходимых условий — NOT_RUN с причиной.
  Если есть сбой восстановления, записать его отдельно и вернуть настройки до публикации.

Автоматически опубликовать `docs/TEST-REPORT-REAL-MACHINE-0.2.0-nfqws2-youtube-live-ДАТА.md`
в `gui-light` при любом исходе. Записать CODE/PLAN, профиль, длительность ролика, качество
и протокол, времена прогонов и перемотки, остановки, четыре вердикта и восстановление.
Ролик, ссылки, адреса, имена, кортежи, конфиги, HAR и сырые следы оставить приватно.
В чистом дереве от свежей ветки добавить только отчёт, проверить diff, сделать обычный
commit и push и сверить опубликованный коммит. Отдельное подтверждение публикации не требуется.
