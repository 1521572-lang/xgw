## §2 Диагностика: измерение окна зависания (воспроизведение)

Метод: `systemctl restart xgw.service` (штатное действие испытания) →
опрос `GET /api/state` анонимно и с cookie (`xgw_panel=<hmac token>`)
каждые 1–3с с таймаутом 3с.

| Окно после рестарта | Анонимный GET | GET с cookie |
| --- | --- | --- |
| 0–1с | connection refused | connection refused |
| ~1–5с | **401 мгновенно** | **висит** (3с-таймауты подряд) |
| 5–23с | 401 | **висит** (каждые 3с) |
| **~23с** | 401 | **200** — восстановление |

- Точные шаги verify(): `failed: existing_session` — первый запрос
  (анонимный, ожидание 401) проходит, второй (с cookie, ожидание 200)
  ловит TimeoutError. Чекер в r3 корректно дождался готовности листенера
  и получил 401, но аутентифицированный запрос на 9–10с после рестарта
  висел.
- **Воспроизводится и на восстановленной старой панели (`08d31ee`
  panel.py)** — поведение не зависит от кандидата: это свойство
  установленной панели. Ранее (после нескольких минут) те же запросы
  отвечают 200 мгновенно — окно закрывается само.
- Характер наблюдения: одиночный запрос блокируется ~23с и затем
  отвечает 200 (не отваливается). Похоже на ожидание ресурса, который
  инициализируется ~20с после рестарта демона (порядок START_WAIT
  воркера), при этом анонимная ветка ответа этого ресурса не касается.

## Наблюдения для Codex

1. **Главный результат — воспроизводимый измеряемый баг установленной
   панели: ~23с зависания аутентифицированного GET /api/state после
   каждого рестарта xgw.service** (анонимный 401 работает). Кандидат
   тут ни при чём (панель `08d31ee` воспроизводит); после ~23с
   восстанавливается само. Это же окно объясняет r2 (request_or_config
   на обеих фазах). Требуется исправление панели: аутентифицированная
   ветка state не должна блокироваться на инициализирующемся ресурсе
   (вероятно, статус движка/lock старта) — либо отвечать деградированно,
   либо 503.
2. Для испытания: readiness чекера стоит ждать **200 с cookie** (с
   повторами до ~30с), а не только анонимный 401 — тогда candidate-auth
   начнёт выполняться после закрытия окна и одноразовый вход на
   установленной панели будет наконец проверен живьём (новый CLI +
   303/403-цепочка всё ещё не исполнены в испытаниях).
3. Структура r3 (cancel-timer до auth) доказала работоспособность —
   таймер снят штатно, хвостов нет; readiness-тесты чекера (4/4) —
   полезное дополнение.
4. Мой рестарт для диагностики выполнен вне окна испытания (off/off,
   воркеры inactive, кратковременно); состояние шлюза подтверждено
   off/off fresh/matched.
