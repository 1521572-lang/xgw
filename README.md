# XGW — шлюз Ubuntu 26.04 на Xray-core с автопереключением VPN-серверов

XGW превращает машину с Ubuntu 26.04 в шлюз для всей Wi-Fi-сети: nftables
(TPROXY) перехватывает трафик устройств и самой машины и отдаёт его Xray-core,
а Xray сам выбирает живой сервер.

С 0.1.12 у шлюза **два ядра, как у Happ**: Xray ведёт перехват и выбор сервера, а
[sing-box](#два-ядра-xray-и-sing-box) подключён к нему как вторая «сеть» — он умеет то,
чего нет в Xray (hysteria2, TUIC, AnyTLS, WireGuard, Shadowsocks с плагинами, подписки в
формате sing-box), и даёт запасной путь, когда провайдер глушит соединения Xray.

Управлять им можно из [панели в браузере](#панель-управления) — кнопка включения
VPN, подписки, список серверов — или командами `xgw …` в терминале: и то и
другое делает одно и то же.

## Зачем

Провайдер (ТСПУ) не рвёт соединение с VPN-сервером, а «замораживает» его: после
15–20 КБ данных в одной TCP-сессии пакеты перестают приходить. ICMP-пинг,
TCP-рукопожатие и HTTP HEAD проходят, поэтому клиенты считают сервер живым и не
переключаются. Счётчик байтов работает на каждое соединение отдельно — находит
«заморозку» только скачивание тела больше порога.

Поэтому проверка в Xray — `burstObservatory` с `httpMethod: "GET"` (ядро
скачивает тело целиком; поле и дочитывание тела появились в v25.7.23). Проба
падает по таймауту на «замороженном» сервере, и балансировщик исключает узел —
новые соединения уходят через рабочий не позже чем за 1–2 цикла
`interval × sampling`. У sing-box (urltest) и mihomo (url-test) проверка —
зашитый в код HEAD-запрос, они «заморозку» не видят.

```
Устройства Wi-Fi ──► Wi-Fi-роутер (точка доступа) ──► LAN Ubuntu-шлюза
                                                          │
   Приложения Ubuntu ──► nftables output ─┐              │
                                           ▼              ▼
                              nftables prerouting (TPROXY, метка 1)
                                           │
                                     Xray (tunnel-in)
                              DNS→dns-out, RU→direct,
                прочее → балансировщик auto (основной сервер XGW / leastPing)
                     GET-пробы burstObservatory ──► VPN-серверы
                                           │
                              сокеты Xray и прямые запросы XGW
                              уходят в WAN с меткой 2 (мимо перехвата)
```

Серверы проверяет само ядро Xray. XGW работает рядом: тянет подписки, генерирует
конфиг, применяет изменения на лету через API (`xray api ado/rmo/adrules` — Xray не
умеет перечитывать конфиг), следит за состоянием (watchdog, скан запасных, утечки),
уведомляет и показывает статус. С 0.1.9 он же выбирает **основной сервер** — самый
быстрый по замеру скорости — и закрепляет его в ядре: весь трафик идёт через него, а не
скачет между серверами каждые полминуты; при отказе основного трафик сразу получает
другой живой сервер (раздел «Основной сервер и замер скорости»).

Что проверено на стенде (раздел 9 ТЗ, проверки этапа 2):

- `freeze_after=16384` на выбранном узле → `xray api bi` показывает другой узел
  за 6–16 с при `interval = 10s`, `sampling = 1` (предел по ТЗ — 2 цикла, 25 с),
  в netns — за 7–16 с; `xgw probe` такого узла отвечает `FROZEN`;
- контроль: с `httpMethod: HEAD` тот же «замороженный» узел остаётся выбранным;
- добавление и удаление сервера в подписке применяются через API, загрузка
  длиной 12 с через неизменившийся узел не прерывается, Xray не перезапускается;
- «замороженного» участника демон меняет на проверенный запасной; ручной выбор
  `xgw pin` на срок снимается по истечении срока;
- перед сервером VLESS+TLS — модель DPI: соединение сбрасывается, если в первой записи
  TLS целиком ClientHello с именем сервера. Скан без дробления — `CONNECT_FAIL`; демон
  сам включает серверу дробление ClientHello через API (Xray не перезапускается), скан
  проходит, и выбранный вручную сервер несёт трафик сквозь «DPI».

Проверки из LAN (этап 3; шлюз с двумя картами, «интернет» и устройство — три
пространства имён):

- устройство в LAN выходит через VPN-сервер; DNS-запрос к любому серверу —
  `8.8.8.8` по UDP и TCP, адрес шлюза — обслуживает Xray; сайт по имени открывается;
- трафик самой машины тоже идёт через Xray, а сокеты с меткой `mark_bypass` — напрямую;
- остановленный Xray → ни устройство, ни сама машина никуда не выходят
  (fail-closed); после `xgw disable` интернет работает напрямую меньше чем через
  5 с, включая DNS; `xgw enable` возвращает перехват;
- устройство из `bypass_hosts` ходит мимо VPN и при остановленном Xray;
- при «заморозке» выбранного сервера новые соединения устройства идут через
  другой сервер не позже чем через 25 с;
- `fail_mode = "open"`: Xray недоступен дольше минуты — перехват снимается,
  Xray вернулся — возвращается;
- демон возвращает правила, если их таблицу удалили; dnsmasq выдаёт адрес из
  диапазона и статическую аренду, шлюз и DNS-сервер в аренде — адрес шлюза;
- контейнер Docker за мостом `docker0` (стенд повторяет сеть Docker, br_netfilter
  включён) выходит через VPN, его DNS отвечает Xray, опубликованный порт работает;
  Docker, поставленный уже после XGW, демон подхватывает сам (`test_stand_docker.py`).

Установка на машину (этап 4) проверена на «одноразовой машине»: это загруженная
Ubuntu 26.04.1 в контейнере systemd-nspawn — настоящие systemd, NetworkManager,
dnsmasq и ufw, своя сеть, «интернет» и устройство в LAN по бокам:

- первый запуск без конфига создаёт `/etc/xgw/config.toml` из примера и больше
  ничего не меняет; с подпиской-примером установка не начинается;
- `xgw diag` до установки: FAIL нет, включённый ufw и отсутствие профиля LAN видны;
- `xgw install` при включённом ufw: своя служба DHCP `xgw-dhcp`, пользователь `xray`,
  профиль `xgw-lan`, прежние профили карты без автоподключения, IPv6 на WAN
  выключен, сон замаскирован, три службы работают, Xray — от пользователя `xray`
  с двумя возможностями, права на файлы — как в разделе «Безопасность»;
- повторная установка ничего не ломает и не затирает запомненное исходное состояние;
- устройство в LAN получает адрес от службы `xgw-dhcp` и выходит через VPN, сама
  машина — тоже; устройство из `bypass_hosts` — напрямую; строка `bind-interfaces` в
  `/etc/dnsmasq.d` (её кладёт пакет ubuntu-fan, который приезжает с Docker) после
  перезагрузки DHCP не ломает;
- `xgw disable` — прямой интернет меньше чем за 5 с, `xgw enable` — обратно;
- страница статуса: без токена 403, со стороны провайдера не видна;
- правка `config.toml` подхватывается демоном без перезапуска и применяется через
  API (Xray не перезапускается); `xgw apply` обновляет и настройки DHCP;
- остановленный Xray → демон (служба с урезанными правами) вызывает `notify-send`
  от имени пользователя графической сессии и сам запускает Xray;
- `xgw logs --export` — в архиве нет ни UUID, ни токена;
- после перезагрузки всё поднимается само, правила загружены раньше
  `network-pre.target` и запуска NetworkManager;
- `xgw uninstall` — правила nftables (включая правила ufw), `ip rule`, профили
  NetworkManager, IPv6 на WAN, sysctl, сон, службы, пользователь и файлы
  совпадают с тем, что было до установки.

**Чего эта проверка не заменяет.** Настоящей машины с двумя сетевыми картами,
роутером и телефоном в Wi-Fi в ней нет, поэтому не проверены: штатное ядро Ubuntu
(у контейнера — ядро хоста стенда), настоящий рабочий стол (уведомление проверено до вызова
`notify-send`, сессию изображала заглушка), загрузка Xray с
GitHub во время установки (в контейнере нет интернета — Xray лежал заранее; сама
загрузка со сверкой SHA-256 выполнялась отдельно, командой `xgw update-xray` в
пустой каталог), PPPoE, соседство с Docker. Первый запуск на своей машине —
это и есть ручной чек-лист ниже; держите под рукой `sudo xgw disable`.

## Требования

- Ubuntu 26.04 x86_64 (arm64 — желательно), Python 3.11+ (в 26.04 — 3.14).
  Ubuntu 24.04 LTS тоже подходит: на ней XGW прошёл проверку на настоящей машине
  (Python 3.12, nftables 1.0.9, NetworkManager 1.46, systemd 255 —
  `docs/TEST-REPORT-2026-10-14.md`) и в виртуальной машине с двумя картами и
  клиентом за шлюзом (Ubuntu 24.04.5, ядро 6.8; ASSUMPTIONS, п. 164); `xgw diag` там
  пишет WARN «проверялся только на Ubuntu 26.04», установке это не мешает.
- Только стандартная библиотека Python; внешние программы: `nft`, `ip`,
  `nmcli`, `systemctl`, `dnsmasq`, `xray`.
- Xray-core **только 26.10.21** (официальный бинарник; SHA-256 сверяется с `.dgst`) —
  предварительный выпуск. Прежний 26.10.10 разработчики Xray отозвали: в нём корневые
  сертификаты, ключи которых взломаны; шлюз с ним `xgw diag` отмечает FAIL — обновите
  Xray командой `sudo xgw update-xray`. Другие версии XGW не ставит и
  не использует: установка и `sudo xgw update-xray` берут 26.10.21, другое значение
  `[xray] version` не учитывается (с предупреждением; `"latest"` прежнего примера
  конфига — молча, «последний» на GitHub — старый стабильный 26.3.27). Установлена
  другая версия — `xgw diag` показывает FAIL с советом `sudo xgw update-xray`.
- sing-box **только 1.14.3** (официальный бинарник с GitHub; SHA-256 сверяется, для
  linux/amd64 хеш зашит в код). Его ставит установка или `sudo xgw update-singbox`; не
  загрузился — установка идёт дальше, а серверы, которые умеет только sing-box, пропускаются.
  Выключить второе ядро совсем: `[core] mode = "xray"`.

## Установка

Нужна Ubuntu 26.04 Desktop: сетью управляет NetworkManager. Вторая сетевая
карта — для Wi-Fi-роутера; без неё XGW защищает только саму машину.

```bash
git clone https://github.com/1521572-lang/xgw.git && cd xgw   # или распакуйте архив проекта
sudo sh packaging/install.sh
```

Править файлы не нужно. Установка:

1. создаёт `/etc/xgw/config.toml` из примера;
2. спрашивает, к какой сетевой карте подключён Wi-Fi-роутер (Enter — роутера
   нет, защищать только эту машину);
3. показывает проверки и план и спрашивает «Продолжить?»;
4. в конце сама открывает панель управления в браузере — вход уже выполнен.

В панели вставьте адрес подписки и нажмите большую кнопку — VPN включён. Пока
подписки нет, VPN выключен, а интернет работает напрямую.

Ничего из терминала копировать не нужно. Ссылка на панель с токеном
(`http://127.0.0.1:8781/?token=…`) всё равно печатается в конце — на случай, если
браузер не открылся (установку запустили по SSH, графического сеанса нет). Дальше
панель открывается ярлыком «XGW» в меню приложений. Если браузер забудет вход
(очистили cookie, другой браузер), щёлкните по ярлыку правой кнопкой и выберите
«Войти заново»: Ubuntu спросит пароль администратора своим окном и откроет панель.

Кто хочет — вписывает подписку и карту в `config.toml` сам: при запуске с
ключом `--yes` или не из терминала установка вопросов не задаёт, после создания
файла останавливается и ждёт второго запуска.

После первой установки команда `xgw` уже есть в системе, дальше — `sudo xgw …`.
Посмотреть проверки, ничего не устанавливая:
`sudo env PYTHONPATH=src python3 -P -m xgw diag` (из каталога репозитория).

Что делает установка, по порядку:

1. Запускает проверки `xgw diag`. Любой FAIL останавливает её (обойти — `--force`).
   Состояние прежней установки — неработающие службы, незагруженные правила, интерфейс
   TUN без адреса — здесь не FAIL, а WARN: его установка и исправит, поэтому обновление
   поверх прежней версии идёт без `--force`. Одно исключение: если подсеть `lan_address` пересекается с сетью, из которой машина
   выходит в интернет (или с любой другой её сетью), установка не начинается и с
   `--force` — профиль `xgw-lan` дал бы второй карте адрес из чужой сети, и интернет
   пропал бы и у шлюза, и у устройств. В сообщении названы интерфейс, его сеть и
   свободная подсеть для `lan_address` и `dhcp_range`.
2. Печатает план и спрашивает подтверждение (`--yes` — не спрашивать). До
   ответа «да» в системе ничего не меняется.
3. Ставит то, что сеть не трогает: пакеты `dnsmasq-base` (программа dnsmasq; на Ubuntu
   Desktop он обычно уже стоит) и `nftables`, если их нет, пользователя
   `xray`, код в `/opt/xgw`, команду `/usr/local/bin/xgw`, Xray-core с GitHub — версию
   из `[xray] version` (SHA-256 сверяется с `.dgst` релиза; уже лежащий Xray другой
   версии заменяется), ярлык панели «XGW» в меню приложений.
4. Настраивает сеть: отключает IPv6 на WAN (раздел «IPv6»); с роутером — ещё
   `/etc/sysctl.d/90-xgw.conf`, профиль NetworkManager `xgw-lan`, свою службу DHCP
   `xgw-dhcp` и
   маскирует сон (уснувший шлюз оставил бы дом без Wi-Fi). Без роутера сон не
   трогается: ноутбук засыпает как раньше. Если включён ufw — отдельно
   спрашивает про его правила.
5. Ставит службы, собирает первый конфиг и запускает Xray.
6. Включает перехват — только если Xray отвечает. Иначе (в том числе когда
   подписок ещё нет) интернет остаётся прямым, а установка говорит, что сделать.

Всё, что установка меняет, и то, что было до неё, записывается в журнал
`/var/lib/xgw/backup/install.json`: по нему работает `xgw uninstall`. Если
настройка сети не удалась при первой установке, установка сама возвращает сеть в исходное
состояние. Поверх работающего шлюза сеть не откатывается — откат оставил бы устройства без
интернета: профиль LAN, DHCP и правила остаются как есть, а установка говорит, что
случилось и что делать. Если не запустился только демон `xgw` (сеть, DHCP и перехват к
этому времени уже работают), это предупреждение, а не сбой: systemd запустит его сам.

**Обновление с 0.1.3 и раньше.** Прежние версии раздавали адреса штатной службой
`dnsmasq.service` по файлу `/etc/dnsmasq.d/xgw.conf`. Этот каталог читают все пакеты, и
пакет ubuntu-fan (он приезжает вместе с `docker.io`) кладёт туда `bind-interfaces`, с
которым настройка XGW несовместима: после перезагрузки dnsmasq не запускался вовсе, и
устройства в Wi-Fi оставались без адресов. Теперь у XGW своя служба `xgw-dhcp` со своим
конфигом `/etc/xgw/dnsmasq.conf`. Повторный `sudo xgw install` переводит старую установку
сам: убирает файл из `/etc/dnsmasq.d`, возвращает `dnsmasq.service` в состояние до XGW
(выключает, если его ставил XGW) и переносит аренды устройств. Пакет `dnsmasq`, если его
поставила прежняя установка, остаётся — убрать: `sudo apt remove dnsmasq`.
Установку можно запускать повторно — так применяются изменения `lan_if`,
`lan_address`, `ipv6` и `disable_sleep`.

После правки `config.toml` и после любого действия в панели: подписки, серверы
и правила перехвата демон подхватывает сам за один шаг watchdog; настройки DHCP
(`dhcp_range`, `static_leases`) применяет `sudo xgw apply`.

**Если что-то пошло не так:** `sudo xgw disable` снимает перехват и возвращает
прямой интернет, `sudo xgw diag` показывает, что не в порядке,
`sudo xgw uninstall` возвращает всё как было.

### Ручной чек-лист на машине

Это определение готовности этапа 4 — его выполняете вы, на своей машине:

- [ ] `sudo xgw diag` — OK или понятные WARN, FAIL нет.
- [ ] Подсеть `lan_address` не пересекается с сетью провайдера: `ip -4 addr` и
      `ip route` показывают, из какой сети машина выходит в интернет (часто это
      192.168.0.x, 192.168.1.x или 192.168.50.x). Если она совпала с `lan_address` —
      смените `lan_address` и `dhcp_range` в `/etc/xgw/config.toml`, например на
      192.168.60.1/24; `xgw diag` показывает это строкой «Подсеть LAN».
- [ ] `sudo xgw install` прошёл; роутер переведён в режим точки доступа.
- [ ] Телефон в Wi-Fi получил адрес 192.168.50.x; заблокированный сайт
      открывается через VPN, российский — напрямую.
- [ ] `sudo xgw status` показывает участников, задержки и трафик проверок.
- [ ] Переключение: добавить в `[manual] links` ссылку на адрес из
      203.0.113.0/24 и поднять `filters.max_members` на один, чтобы она стала
      участником — через 1–2 цикла она `мёртв`, трафик идёт через живой узел.
- [ ] `sudo xgw disable` — интернет работает напрямую; `sudo xgw enable` —
      снова через VPN.
- [ ] После перезагрузки всё поднимается само, `sudo xgw status` — `HEALTHY`, телефон в
      Wi-Fi снова получает адрес (и тогда, когда на машине стоит Docker).
- [ ] Если на машине есть Docker: `docker run --rm alpine wget -qO- https://ifconfig.me`
      показывает адрес VPN-сервера, а не провайдера; опубликованный порт контейнера
      (`docker run -p …`) открывается с другого устройства (на настоящем Docker не
      проверялось — только на стенде, ASSUMPTIONS, п. 171).
- [ ] `sudo xgw logs --export` — в архиве нет UUID, паролей и токенов.
- [ ] `sudo xgw uninstall` возвращает исходную сеть.

### Подготовка Wi-Fi-роутера (режим точки доступа, рекомендуется)

1. Переведите роутер в режим точки доступа (Access Point): DHCP на нём выключить.
2. Кабель из LAN-карты шлюза — в **LAN-порт** роутера.
3. Устройства Wi-Fi получают адреса от dnsmasq шлюза (192.168.50.x) и видны
   шлюзу по отдельности (bypass_hosts, статика).

Альтернатива — режим `router_mode = "router"`: кабель в WAN-порт роутера,
dnsmasq выдаёт один адрес самому роутеру (двойной NAT, обход VPN только для
роутера целиком).

## Панель управления

`http://127.0.0.1:8781/` — графический интерфейс XGW. Его отдаёт сам демон;
отдельной программы нет, нужен только браузер. Открывается ярлыком «XGW» из
меню приложений либо по ссылке, которую печатает `sudo xgw panel`.

![Панель XGW: кнопка включения, подписки и серверы по подпискам](docs/panel.jpg)

На снимке — выдуманные данные (`tests/panel_demo.py`).

- **Большая кнопка** включает и выключает VPN — то же, что `xgw enable` и
  `xgw disable`. Включить нельзя, пока Xray не отвечает: с fail-closed машина
  осталась бы без интернета, и панель объясняет, чего не хватает. Под ней — строка
  «Перехват: …», что сейчас с трафиком по итогам последнего шага демона: «работает»
  (через VPN), «подключается» (Xray ещё не проверил ни одного сервера, мимо VPN ничего
  не уходит), «заблокирован» (Xray не отвечает или ждёт новых настроек — мимо VPN
  ничего), «временно напрямую» (`fail_mode = "open"`, `hold = "direct"`, правила не
  загрузились) или «снят». То же показывает `xgw status` строкой «Сейчас: перехват …».
- **Подписки**: вставьте адрес (`https://…`) и нажмите «Добавить» — подписок
  может быть сколько угодно. Туда же вставляются отдельные ссылки серверов
  (`vless://`, `vmess://`, `trojan://`, `ss://`). Видны квота и срок действия,
  когда подписка обновлялась и почему не обновилась. «Обновить» запрашивает все
  подписки сейчас. В «Изменить подписку» задаются User-Agent и заголовки — они
  нужны провайдерам, которые отдают серверы только «своим» клиентам, например по
  заголовку `X-HWID` с идентификатором устройства (`docs/HWID-SUBSCRIPTIONS.md`).
- **Серверы** сгруппированы по подпискам: кто в работе и с какой задержкой, кто
  запасной и чем закончилась его проверка. У каждого сервера:
  - выключатель — **отключить**: сервер остаётся в списке, но шлюз к нему больше
    не обращается — не использует и не проверяет;
  - крестик — **убрать из списка**: то же самое, и из списка он пропадает. При
    обновлении подписки не возвращается; вернуть можно в разделе «Убранные»;
  - **«Выбрать»** — весь трафик через этот сервер, как в Happ и других клиентах VPN.
    Выбрать можно любой сервер — и тот, что в работе, и запасной. Выбор держится, пока
    не нажмёте «Автовыбор» в верхнем блоке, и переживает перезапуск. Если выбранный
    перестанет отвечать, шлюз временно уведёт трафик на автовыбор, чтобы интернет не
    пропал, и вернётся к выбранному, когда тот снова ответит; об этом придёт
    уведомление. Выбранный убрали из подписки или отключили — выбор снимается, тоже с
    уведомлением (как `xgw pin <тег> --ttl forever`);
  - **приоритет** — высокий, средний (по умолчанию) или низкий (как `xgw priority`):
    шлюз работает на серверах самого высокого уровня, на котором есть живые
    (раздел «Приоритет серверов»). Над списком тогда написано, какой уровень сейчас
    в работе;
  - у серверов подписки с лимитом трафика — множитель расхода («x10»), у резервного
    выхода — метка «резервный»: через него трафик идёт, только когда все серверы в
    работе не отвечают (раздел «Приоритет серверов»);
  - у основного сервера — метка «основной»; справа рядом с задержкой — скорость по
    последнему замеру («87 Мбит/с»), под именем — его время («замер скорости 14:05») или
    «замер скорости не удался». Запасной показывает замер, сделанный, пока он был в
    работе (бледнее, «… когда был в работе»).

  Над списком — переключатель **«Один основной сервер»** и кнопка **«Замерить
  скорость»** (раздел «Основной сервер и замер скорости»). Переключатель хранится в
  `panel.json`; выключенный — ядро само выбирает сервер с наименьшей задержкой, как до
  0.1.9. В шапке под кнопкой VPN — «Основной сервер: … · 87 Мбит/с · 84 мс».

  «Отключить все» в подписке оставляет включённым один сервер — без единого
  сервера собрать конфиг нельзя; включите нужные и отключите его отдельно.
  Изменения применяются через API, Xray не перезапускается, подписки заново не
  запрашиваются.

  Над списком — сводка разбора подписок: «Узлов: 5 активных, 65 запасных (отброшено
  4 недоступных/служебных, схлопнуто 12 дублей)». Под списком — сколько трафика
  уходит на проверки серверов: в сутки и в месяц, из чего складывается и какая это
  доля трафика подписки; при превышении суточного лимита (`probe.max_daily_probe_mb`)
  строка подсвечена и говорит, что уменьшить. Если перестал отвечать сам адрес
  проверки (`probe.url`), над списком появляется предупреждение, а отметка в шапке
  меняется на «Адрес проверки недоступен» — серверы при этом работают (раздел
  «Проверки серверов»).
- **Устройства** в Wi-Fi: у каждого выключатель «VPN для устройства». Выключите
  его — устройство пойдёт в интернет напрямую (телевизор, банковское
  приложение), остальные останутся за VPN. Шлюз узнаёт устройство по адресу,
  поэтому панель закрепляет за ним текущий адрес статической арендой DHCP;
  правила nftables и dnsmasq обновляются сразу, а если сеть изменение не приняла,
  всё возвращается как было. Устройство, пущенное мимо VPN в `config.toml`
  (`bypass_hosts`), помечено «config.toml» и меняется только там. Трафик такого
  устройства не защищён: при остановленном Xray оно по-прежнему выходит напрямую.
  **Запись трафика** — красная точка в строке устройства: шлюз 5 минут (остановить можно
  раньше) пишет все пакеты устройства в сети дома в файл `.pcap` для Wireshark — куда и
  сколько устройство отправляет (содержимое сайтов обычно зашифровано HTTPS). Пока идёт
  запись, в строке — время и размер; файл не больше 100 МБ, одна запись за раз. Готовые
  записи — внизу карточки «Устройства»: скачать или удалить; на шлюзе хранятся последние
  три (`/var/lib/xgw/records/`, 0600). Внешних программ не нужно: шлюз пишет сам
  (право `CAP_NET_RAW` у службы `xgw`, появляется после установки этой версии).
- **Tailscale**: вход шлюза в tailnet (кнопка и QR-код), SSH через Tailscale, панель по
  tailnet, маршрут самого Tailscale и исправления двух ловушек провайдера и tailnet —
  каждая кнопкой (раздел «Tailscale»).
- **Телефоны**: «Привязать телефон» — QR-код для приложения XGW на телефоне; список
  привязанных телефонов, переименование и отвязка (раздел «Приложение на телефоне»).
- **События** — как в `xgw status`.

Подписки и ссылки, добавленные в панели, отключённые и убранные серверы и
устройства мимо VPN лежат в `/etc/xgw/panel.json` (0600) и дополняют
`config.toml`; сам `config.toml` панель не меняет. То, что вписано в `config.toml`, в панели
помечено «из config.toml» и убирается только правкой файла.

Сервер опознаётся по отпечатку — протокол, адрес, порт, ключ и транспорт.
Переименование его не затрагивает; если владелец подписки сменит серверу адрес
или ключ, это будет уже новый сервер, и он появится включённым.

Защита: панель слушает только `127.0.0.1` (из Wi-Fi и со стороны провайдера её
не открыть), без токена отдаёт одну страницу входа, запросы с чужим заголовком
`Host` отклоняет, а менять что-либо разрешает только собственной странице. С устройств
tailnet её открывает Tailscale Serve (`https://<шлюз>.<tailnet>.ts.net:8443/`), и только
если «Панель по tailnet» включена в самой панели (раздел «Tailscale»).
Адреса подписок и ссылки серверов панель наружу не отдаёт — только домен и имя.
Выключить панель: `[panel] enabled = false`.

Страница статуса для домашней сети (`status.lan_page`) — отдельная и по-прежнему
только для чтения: с телефона VPN не выключить, а себя из VPN не вывести. Правила
для устройств поэтому живут в панели, а не на странице статуса.

Панель на настоящем рабочем столе Ubuntu не открывалась — проверьте на своей
машине:

- [ ] ярлык «XGW» есть в меню приложений и открывает панель в браузере;
- [ ] в конце установки панель открылась в браузере сама, вход уже выполнен
      (проверено только с подставным браузером в контейнере, ASSUMPTIONS, п. 169);
- [ ] после очистки cookie панель просит вход; правая кнопка по ярлыку «XGW» →
      «Войти заново» показывает окно пароля Ubuntu, и после пароля панель
      открывается с выполненным входом (окно пароля и Firefox не проверены);
- [ ] ссылка из установки (или `sudo xgw panel`) пускает в панель, а после
      закрытия браузера ярлык открывает её уже без токена;
- [ ] подписка добавляется вставкой адреса, через минуту появляются серверы;
- [ ] большая кнопка включает VPN: заблокированный сайт открывается, а после
      выключения — нет;
- [ ] отключённый сервер пропадает из `sudo xgw servers`, включённый —
      возвращается; убранный находится в разделе «Убранные».

## Разработка и тесты

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e ".[dev]"
.venv/bin/python -m pytest tests/             # юнит-тесты (без root)
.venv/bin/python -m ruff check src tests      # линтер
```

- Тесты и стенды — только для Ubuntu 24.04 и 26.04, как и сама программа: на другой
  системе pytest сразу останавливается.

- Golden-файлы пересоздаются `XGW_REGEN_GOLDEN=1 pytest tests/`
  (используйте только после осознанного изменения генератора).
- Скачивание Xray для локальной проверки: см. `xgw.xraycore.binary`
  (`download_release`), кладётся в `tools/xray` (gitignored).
- Тесты на живом Xray — синтаксис `xray api` (`tests/test_api_integration.py`) и
  применение конфига генератор → Applier → ядро (`tests/test_apply_live.py`):
  `XGW_XRAY_BIN=<путь к xray> pytest tests/`; без переменной они пропускаются.
- Тесты https-проб через CONNECT выпускают временный самоподписанный сертификат
  командой `openssl`; без неё пропускаются.
- Панель на выдуманных данных, без шлюза и без root:
  `python tests/panel_demo.py` — и откройте напечатанную ссылку. Сеть при этом
  не трогается; `--scene empty` показывает панель сразу после установки,
  `--scene probe` — не отвечает
  адрес проверки серверов, `--scene budget` — проверки расходуют больше суточного
  лимита, `--scene waiting` — VPN включён, а Xray ещё не перезапущен с новыми
  настройками.

### Стенд

Стенд (`tests/stand/`) поднимает «интернет» с замораживающим провайдером и шлюз
на настоящем Xray: origin с DNS-заглушкой, три VLESS-сервера, перед каждым —
реле с режимами `pass`, `freeze_after=N`, `drop`, `blackhole`.

```bash
XGW_XRAY_BIN=/opt/xgw/xray/xray .venv/bin/python -m pytest tests/stand   # ~2,5 минуты
```

- Режим **loopback** — все процессы на 127.0.0.1, root не нужен. Его хватает для
  проверок этапа 2. XGW, работающий на той же машине, ему не
  мешает: метка «мимо перехвата» у шлюза стенда своя (0x5e), иначе правило
  `loopback_guard` XGW хоста отбрасывало бы его пакеты к узлам на 127.0.0.1.
- Режим **netns** — пространства имён `inet`/`gw`/`lan`, связанные veth-парами;
  включается сам на Linux под root (`sudo -E …`), и тогда каждая проверка этапа 2
  идёт дважды — в loopback и в netns. Сеть хоста при этом не затрагивается:
  интерфейсы создаются сразу внутри пространств имён. Форвардинг в них выключен с
  самого начала, как в только что поставленной системе: новое пространство имён
  наследует его от хоста, а на машине с XGW или Docker он включён.
- Проверки из LAN (`tests/stand/test_stand_lan.py`, этап 3) идут только в netns:
  нужны root и `nft`, для выдачи адресов — `dnsmasq` (`apt install nftables
  dnsmasq-base`). Правила nftables и `ip rule` создаются внутри пространства
  имён шлюза. Весь стенд под root — около 8 минут.
- Проверки TUN (`tests/stand/test_stand_tun.py`, этап 5) — тоже только netns, на
  настоящем ядре и Xray: трафик машины через интерфейс, fail-closed и возвращение Xray,
  переключение способа в обе стороны, IPv6 через TUN, строгий rp_filter.
- Проверки второго ядра (`tests/stand/test_stand_singbox.py`, 0.1.12) идут в loopback и netns
  и требуют оба ядра и root:
  `sudo -E XGW_XRAY_BIN=<xray> XGW_SINGBOX_BIN=<sing-box> pytest tests/stand/test_stand_singbox.py`.
  Серверы hysteria2, TUIC и AnyTLS (sing-box) и VLESS+TLS (оба ядра) несут трафик через мост;
  заблокированный AnyTLS-сервер перед «ТСПУ» (режим реле `sni_freeze=ИМЯ`) сам уходит на
  профиль `singbox:tls_fragment` без перезапуска ядер и без изменения конфига sing-box; сервер
  VLESS+TLS обоих ядер за «строгим ТСПУ» (`sni_freeze_strict=ИМЯ`: узнаёт и целый
  ClientHello, и мелкие записи Xray) сам проходит лестницу «обычное соединение → дробление
  Xray → обычный sing-box → дробление sing-box» и остаётся на sing-box; сервер VLESS+TLS, к
  которому пробивается только sing-box (в ссылке хеш прежнего сертификата `pcs` при верном
  `pks`), сам уходит на обычный sing-box `[sb]` и остаётся на нём после `xgw apply`; убитый
  sing-box демон поднимает заново; новый конфиг sing-box ждёт, пока через него идёт трафик;
  при включённом перехвате устройство в LAN выходит через сервер hysteria2. Живые проверки
  перевода серверов Xray → sing-box и поведения SIGHUP — `tests/test_singbox_live.py`.
- Проверки контейнеров Docker (`tests/stand/test_stand_docker.py`) — тоже только netns:
  мост `docker0`, «контейнер» в своём пространстве имён, маскарадинг и опубликованный
  порт — как их ставит Docker. Сам Docker не нужен; если на машине загружен
  br_netfilter (его включает Docker), проверка идёт и с ним.
- Проверки IPv6 (`tests/stand/test_stand_ipv6.py`, этап 5) — тоже только netns: на
  стыке шлюза и «интернета» есть IPv6 (`2001:db8:5::/64`), origin слушает и по
  IPv6, а DNS-заглушка отвечает на AAAA. Нужны root и `nft`.
- Проверка установки (`tests/stand/test_machine.py`, этап 4) — «одноразовая
  машина»: контейнер `systemd-nspawn`, корень которого — оверлей поверх корня
  хоста (в нём та же Ubuntu, а все изменения остаются в tmpfs и исчезают вместе
  с контейнером), сеть — своя. В нём `xgw install` и `xgw uninstall` выполняются
  целиком, на настоящих systemd и NetworkManager. Нужны root, пакет
  `systemd-container` и NetworkManager с ufw: либо в системе, либо .deb-файлами
  в каталоге `XGW_MACHINE_DEBS` (по умолчанию `/root/xgw-debs`) — тогда они
  ставятся только внутри контейнера:
  `apt-get download network-manager libnm0 libndp0 libteamdctl0 libmm-glib0
  libbluetooth3 ufw iptables libip4tc2 libip6tc2 dnsmasq`. Около 4 минут.
  Там же проверяется путь без терминала: установка без подписки, подписка и
  включение VPN из панели, отключение и удаление серверов.

  Что нужно, чтобы этот стенд запустился:

  - Linux с systemd под root (`sudo -E …`), пакет `systemd-container`, `nft`,
    `XGW_XRAY_BIN` — путь к Xray (рядом с ним должны лежать `geoip.dat` и
    `geosite.dat`: в контейнере нет интернета, и установка берёт Xray из этого каталога);
  - NetworkManager и ufw — в системе либо .deb-файлами в `XGW_MACHINE_DEBS`;
  - программа dnsmasq — из пакета `dnsmasq-base` на хосте (на Ubuntu Desktop он стоит
    всегда: его использует NetworkManager). Пакет `dnsmasq` со штатной службой XGW не
    нужен; его .deb в `XGW_MACHINE_DEBS` пригодится только для
    `XGW_MACHINE_PREINSTALL_DNSMASQ=1` — проверки, что своя служба DHCP уживается со
    штатной, если та уже стоит;
  - Docker на хосте не мешает: в контейнере стенда его службы замаскированы;
  - 2 ГБ свободной памяти под tmpfs в `/var/lib/xgw-machine`.

  XGW, установленный на самом хосте, не мешает: стенд убирает его из корня
  контейнера (конфиг, код, службы, профиль `xgw-lan` — и keyfile, и файл netplan
  `90-NM-<uuid>.yaml`, которым его хранит NetworkManager на Ubuntu 24.04, — правила ufw,
  маски сна — только в верхнем слое оверлея, хост не меняется). Форвардинг в контейнере стенд сбрасывает сам: сетевое
  пространство имён наследует его от хоста, а на хосте с Docker он включён.
- Без `XGW_XRAY_BIN` стенд пропускается; части стенда (реле, origin, DNS) проверяются
  и без Xray — `tests/stand/test_stand_parts.py`.
### Проверка конфига вручную

```bash
xgw generate --config config.example.toml --out /tmp/config.json
xray run -test -c /tmp/config.json
```

Без `--out` результат пишется в `/etc/xgw/xray/config.generated.json` — рядом с
рабочим `config.json`, но не поверх него: рабочий конфиг меняет только
применение (`xgw apply`), с проверкой, last-good и откатом.

Что делает `generate` помимо сборки:

- подписку запрашивает через http-in работающего Xray, а если он не отвечает —
  напрямую, сокетом с меткой `mark_bypass` и собственным резолвером (`dns.bootstrap`);
- ответ без серверов (страница ошибки, пустое тело) считает сбоем и берёт
  последнюю удачную версию из `/var/lib/xgw/cache`;
- сохраняет состав участников, порты и пароль probe-inbounds из применённого
  конфига — новый сервер в подписке становится запасным, а не перетасовывает балансировщик;
- сервер, конфиг которого установленный Xray не принимает (снятый транспорт,
  неизвестный шифр), отбрасывает с предупреждением и собирает конфиг без него.

Демон раз в `watchdog.interval_s` (±20 %) собирает три сигнала — метрики
observatory, сквозную загрузку через http-in и доступность провайдера — и ведёт
машину состояний:

| Состояние | Когда | Что делает демон |
|---|---|---|
| `HEALTHY` | все сигналы в норме | ничего |
| `DEGRADED` | часть участников мертва | меняет мёртвых дольше `rotate_after_min` на запасные, прошедшие последний скан |
| `ALL_DEAD` | живых нет или сквозная проверка падает `fail_threshold` раз подряд | обновляет подписку напрямую, сканирует запасные, меняет участников сразу |
| `WAN_DOWN` | не отвечает `wan_check` | ждёт, проверки раз в 60 с; вернулся WAN — проверяет сразу (см. ниже) |
| `XRAY_DOWN` | не отвечают ни метрики, ни API | после двух неудачных проверок откатывает конфиг на last-good |
| `LEAK` | выход в `home_country` при включённом перехвате | раз на проверку утечки (раз в 5 минут) выясняет причину: если в эту страну выходит сам сервер, выбранный балансировщиком, — меняет его на запасной и больше не берёт; если трафик идёт мимо Xray — загружает правила перехвата заново. Событие — одно на причину, а не на каждый шаг |
| `PROBE_TARGET_UNREACHABLE` | не отвечает сам адрес проверки (`probe.url`), а не серверы | серверы не трогает, сканы и замены приостанавливает, ядро на это время пробует серверы по запасному адресу; раз в 5 минут перепроверяет; см. «Проверки серверов» |

Утечка стоит в машине состояний выше, чем `PROBE_TARGET_UNREACHABLE`, но признак «не
отвечает probe.url» действует и во время утечки: сканы и замены ждут по нему самому, а не
по имени состояния (на живой машине утечка заслоняла его, и XGW начинал менять живые
серверы). `xgw status` показывает оба: состояние в первой строке и предупреждение о
`probe.url` — отдельной. Если служба `xgw` остановлена, `xgw status` говорит это первой
строкой («СЛУЖБА xgw НЕ РАБОТАЕТ») и отвечает кодом 3.

Между шагами демон не просто спит: он слушает события ядра и просыпается раньше
(`ip monitor`, `nft monitor` и сигнал сна systemd-logind; сами программы есть в любой
установке):

- **из таблиц XGW что-то убрали** (чужой `nft flush ruleset`, `flush table ip xgw`,
  `delete chain`) — правила сверяются и возвращаются сразу, за доли секунды, без
  остального шага. Свои загрузки правил XGW демон по событиям не будит;
- **WAN пропал или вернулся, сменился маршрут по умолчанию** — шаг начинается сразу
  (не чаще раза в 2 с): после обрыва связь и VPN проверяются, как только провайдер
  ответил, а не через 60 с. Серверы, которые ядро сочло мёртвыми, пока связи не было,
  на этом шаге не меняются: их пробы ещё не повторились;
- **машина проснулась после сна** — правила и маршруты загружаются заново, запасные
  проверяются сразу, а подписки обновляются, если их срок прошёл во сне.

**Проверка с учётом трафика.** Когда устройства качают на всю ширину канала, сквозная
проба может опоздать в очереди. Если через выбранный сейчас сервер за
`watchdog.busy_window_s` (10 с) пришло не меньше `watchdog.busy_bytes` (1 МиБ), провал
пробы не засчитывается, а сервер, которого ядро сочло мёртвым, считается живым: трафик
через туннель идёт, значит, он работает.

На установленном шлюзе Xray — служба `xgw-xray.service`. Без systemd его можно
держать обычным процессом: `XGW_XRAY_SERVICE=process` — так работает стенд.

## Перехват трафика

Все правила лежат в собственной таблице nftables `ip xgw` (и `ip6 xgw6`); чужие
таблицы XGW не трогает, `flush ruleset` не использует. Таблица заменяется
целиком одной транзакцией, поэтому повторное применение безопасно. Посмотреть,
что будет загружено: `xgw net show`.

| Что | Куда идёт |
|---|---|
| TCP и UDP устройств в LAN | в Xray (TPROXY на `127.0.0.1:tproxy_port`, метка `mark_proxy`) |
| TCP и UDP самой машины (`capture.local`) | туда же: цепочка output ставит метку, пакет возвращается через `lo` (с `capture.method = "tun"` — уходит в TUN-интерфейс, см. ниже) |
| TCP и UDP контейнеров Docker (мосты `docker0`, `br-*`; `capture.containers`) | в Xray: метка `mark_containers` и маршрут в TUN-интерфейс (раздел «Контейнеры Docker») |
| DNS — порт 53 к любому адресу, включая сам шлюз | в Xray: устройство с вручную прописанным DNS VPN не обойдёт |
| Сокеты Xray и прямые запросы XGW (метка `mark_bypass`) | напрямую в WAN |
| Частные сети, сам шлюз, `exclude_cidrs` | мимо Xray |
| DHCP-клиент WAN и служба времени | мимо Xray: без точного времени не поднимется Reality |
| Устройства из `bypass_hosts`, ICMP | обычный форвардинг с маскарадингом |
| Входящие из интернета | в Xray не попадают: перехват только с LAN, `lo` и мостов Docker; ответы опубликованных портов контейнеров — тоже мимо |
| Пакеты Xray с меткой `mark_bypass` к `127.0.0.0/8` | отказ (цепочка `loopback_guard`): устройство не может заставить Xray ходить к службам самого шлюза |
| IPv6 через LAN | не форвардится |
| IPv6 самой машины при `network.ipv6 = "proxy"` | в Xray (раздел «IPv6» ниже); при `off` наружу не выходит: установка отключает его на WAN, а цепочка `v6_guard` таблицы `ip6 xgw6` отбивает всё, кроме link-local, multicast, служебного ICMPv6 и сокетов Xray, — даже если WAN не под NetworkManager |

- **Xray остановлен** (`fail_mode = "closed"`, по умолчанию) — перехваченный
  трафик никуда не уходит, утечки нет. Устройства из `bypass_hosts` работают.
- **`fail_mode = "open"`** — если Xray недоступен дольше 60 с, демон снимает
  перехват (трафик идёт напрямую, мимо VPN), а после восстановления возвращает.
- **При включении машины** порядок такой: правила перехвата (`xgw-net`, ещё до сети)
  → Xray → демон. Пока Xray не поднялся, перехваченный трафик никуда не уходит — при
  любом `fail_mode`: это несколько секунд без интернета после загрузки, зато ни один
  пакет не уйдёт мимо VPN. Разница — в том, что будет, если Xray так и не запустится
  (недоступны все серверы, испорчен конфиг): с `closed` интернета нет, пока вы не
  разберётесь или не выполните `sudo xgw disable`; с `open` демон через минуту снимет
  перехват сам. Для шлюза, за которым стоит домашняя сеть, оставьте `closed`. Для
  настольной рабочей машины без роутера, где важнее не остаться без связи, чем
  исключить выход напрямую, разумнее `open`.
- **Перехват и конфиг Xray расходятся** — правила ведут трафик на порт TPROXY или в
  интерфейс TUN, а принимает его только тот Xray, в конфиге которого есть
  соответствующий inbound (`tproxy-in`, `tun-in`). Поэтому: (1) любое изменение
  такого inbound'а применяется перезапуском Xray сразу, не дожидаясь
  `apply.restart_window`; (2) пока нужного inbound'а в применённом конфиге нет,
  перехват не загружается — `xgw status` пишет «Перехват: НЕ ВКЛЮЧЁН (ожидание
  применения inbound в Xray)», а демон включает его сам, как только Xray перезапущен.
  Что в это время с трафиком, решает `[capture] hold`: `"block"` (по умолчанию) —
  мимо VPN не уходит ничего, кроме устройств из `bypass_hosts`, связи с самим шлюзом и
  в LAN, DHCP и службы времени; соединения отбиваются сразу, без таймаутов. `"direct"` —
  сеть работает напрямую, как было раньше. При `fail_mode = "open"` всегда `"direct"`.
  Если рабочего конфига Xray нет вовсе (первая установка без подписки), сеть идёт
  напрямую при любом `hold`: VPN ещё нечем включать; (3) при смене способа перехвата прежние правила
  остаются до перезапуска Xray — трафик всё это время идёт через VPN. До этой правки
  изменение inbound'ов ждало окна перезапуска, и машина оставалась без интернета
  (`docs/TEST-REPORT-2026-10-14.md`, дефект D1).
- **Аварийное отключение** — `sudo xgw disable`: перехват снят, интернет
  работает напрямую, DNS-запросы к шлюзу уходят на первый из `dns.direct_servers`.
  Вернуть — `sudo xgw enable`.
- **Правила пропали** (чужой `flush ruleset` или `flush table ip xgw`, перезапуск
  nftables) — демон замечает это сразу по событию `nft monitor` и загружает их заново,
  обычно меньше чем за секунду; опустевшие цепочки (после `flush table`) — тоже пропажа.

### TUN

`capture.method = "tun"` меняет только путь **трафика самой машины** в Xray: вместо
возврата через `lo` и TPROXY пакеты уходят в TUN-интерфейс, который читает Xray (inbound
`tun`). Сеть Wi-Fi всегда идёт через TPROXY — с TUN или без. Метит пакеты, как и раньше,
цепочка `output`, поэтому исключения те же (частные сети, служба времени, DHCP, DNS
через порт 53, сокеты Xray с меткой `mark_bypass`).

Как это устроено:

- интерфейс (`capture.tun_name`, по умолчанию `xgwtun0`) **создаёт XGW**, а не Xray, и он
  постоянный: Xray при запуске подключается к готовому, а при остановке оставляет его.
  Поэтому пока Xray не работает, пакеты уходят в интерфейс без читателя или в запасную
  чёрную дыру и пропадают — fail-closed, как и с TPROXY, а не мимо VPN. Создаёт его
  `xgw net up` при загрузке (раньше Xray) и перед запуском Xray, который делает
  `xgw apply`. Xray 26.10.10 при остановке интерфейс выключает, и ядро удаляет маршрут
  через него, — поэтому после каждого запуска Xray служба `xgw-xray` вызывает
  `xgw net tun`: интерфейс снова поднят, маршрут на месте;
- пакеты с меткой `mark_proxy`, созданные на самой машине (`iif lo`), идут по таблице
  `capture.tun_route_table` (101): `default dev xgwtun0` и запасная чёрная дыра
  `blackhole default metric 4096` — если интерфейса не станет, помеченные пакеты не уйдут
  мимо VPN. Остальные помеченные пакеты (сеть Wi-Fi) по-прежнему доставляются локально
  по `route_table` (100);
- на интерфейсе один адрес `169.254.10.1/32`: без адреса ядро отбрасывает ответы Xray
  из-за обратной проверки пути (rp_filter), и соединения не устанавливаются. Маршрутов
  этот адрес не создаёт. Интерфейс без адреса (его создал сам Xray, раньше XGW)
  `xgw diag` показывает как FAIL, а демон на ближайшем шаге готовит его заново;
- IPv6 машины (`network.ipv6 = "proxy"`) идёт через тот же интерфейс: отдельный
  inbound на `::1` не нужен;
- `xgw disable` и `fail_mode = "open"` убирают правило и маршруты, но интерфейс
  оставляют (его держит Xray); `xgw net down` тоже, о чём печатает. Удаляет его
  `xgw uninstall`, после остановки служб, а ещё сам XGW — когда способ вернули на
  `tproxy` и Xray перезапущен без inbound'а TUN (если интерфейс не нужен контейнерам
  Docker).

Ограничения:

- **строгий `rp_filter = 1`** (`net.ipv4.conf.all.rp_filter`) отбросит ответы Xray, и
  трафик машины зависнет; умолчание Ubuntu — 2, его адрес на интерфейсе устраивает.
  `xgw diag` предупреждает и об этом, и об отсутствии `/dev/net/tun`;
- ICMP (ping) машины по-прежнему идёт напрямую: правила метят только TCP и UDP;
- проверен на Xray 26.10.10 (ASSUMPTIONS, пп. 138 и 181); в 26.10.21 у входа TUN свой
  сетевой стек вместо gVisor (п. 226).

Переключить способ: впишите `method = "tun"` (или `"tproxy"`) в `[capture]` и запустите
`sudo xgw install` или `sudo xgw net up` и `sudo xgw apply --now`. Правила меняются сразу,
inbound — при перезапуске Xray. С включённой сетью Wi-Fi `tproxy-in` есть у Xray в обоих
режимах, поэтому возврат на `tproxy` бесшовный; в обратную сторону трафик машины до
перезапуска Xray блокируется (интерфейс есть, читателя нет), а не идёт мимо VPN.
`xgw status` показывает «эта машина через TUN».

### Контейнеры Docker

Контейнеры Docker выходят в интернет транзитом через саму машину — с мостов `docker0` и
`br-*` (сети `docker network create`), и ни перехват самой машины, ни перехват LAN этот
трафик не видят: на живой машине контейнер показывал адрес провайдера, пока сама машина
шла через VPN. С `capture.containers = true` (по умолчанию) он тоже идёт через Xray:

- через TPROXY это сделать нельзя: Docker включает br_netfilter, и для пакетов с моста
  ядро сбрасывает сокет, который назначил TPROXY, — соединения не устанавливаются
  (проверено на стенде). Поэтому цепочка `containers` только ставит метку
  `capture.mark_containers` (3), а маршрут по ней ведёт пакеты в TUN-интерфейс
  `capture.tun_name` — тот же, что в режиме TUN, его читает inbound `tun-in` Xray;
- интерфейс и inbound появляются, только когда Docker на машине есть (его мост уже
  создан). Если Docker поставили после XGW, демон замечает мост на ближайшем шаге
  watchdog и перезапускает Xray с inbound'ом TUN; до этого маршрут контейнеров ведёт в
  чёрную дыру — они без интернета, но не мимо VPN;
- интерфейс готовит XGW, как и в режиме TUN: при загрузке — `xgw net up`
  (xgw-net.service, раньше Xray), перед перезапуском Xray — `xgw apply`. Созданный самим
  Xray интерфейс адреса не имеет, и контейнеры оставались бы без интернета (так было в
  0.1.4 после перезагрузки); демон это замечает и чинит, `xgw diag` показывает строкой
  «TUN … — для контейнеров Docker»;
- DNS контейнеров (порт 53, в том числе к частным резолверам) обслуживает Xray, как у
  устройств в Wi-Fi; частные сети, сама машина и ответы опубликованных портов
  (`docker run -p …`) идут мимо Xray;
- IPv6 контейнеров не перехватывается (при `network.ipv6 = "off"` его нет и на WAN);
- оставить контейнеры мимо VPN: `containers = false` в `[capture]`, затем
  `sudo xgw net up`. `xgw status` пишет «… и контейнеры Docker», когда Docker есть.

### IPv6

По умолчанию (`network.ipv6 = "off"`) IPv6 не используется: установка отключает его
в профиле WAN (`ipv6.method disabled`), а устройствам в Wi-Fi шлюз IPv6 не выдаёт и
не пропускает (`ip6 xgw6` запрещает форвардинг из LAN и в LAN). Иначе приложения
пошли бы в интернет по IPv6 мимо перехвата.

Исключение — профиль WAN, описанный в `/etc/netplan/*.yaml` вручную или cloud-init
(в `nmcli -f NAME,FILENAME connection show` его файл — `netplan-<имя>.nmconnection`, а
не `netplan-NM-…`). Такой профиль XGW не меняет: в Ubuntu 24.04 (NetworkManager 1.46)
любая его правка через NetworkManager переписывает его в
`/etc/netplan/90-NM-<uuid>.yaml` уже без привязки к карте, и после перезагрузки профиль
WAN может встать на карту роутера — шлюз остаётся без интернета (так было на проверке
в виртуальной машине). Если в таком профиле IPv6 не настроен (`ipv6.method ignore`),
установка выключает IPv6 на карте через `disable_ipv6` в `/etc/sysctl.d/90-xgw.conf`,
удаление возвращает прежнее значение. Если настроен — установка только предупреждает:
выключите IPv6 для этой карты в netplan (`dhcp6: false`, `accept-ra: false`,
`link-local: []`) и запустите установку ещё раз.

`network.ipv6 = "proxy"` — IPv6 **самой машины** идёт через Xray так же, как IPv4:

- на WAN IPv6 остаётся включённым (`xgw install` ничего в профиле не отключает, а
  если прошлая установка с `off` его отключила — возвращает как было);
- в `ip6 xgw6` появляются те же цепочки, что и в `ip xgw`: `output` метит
  TCP и UDP (кроме частных сетей, `fe80::/10`, multicast, самой машины, службы
  времени и DHCPv6), `prerouting` на `lo` отдаёт их Xray через TPROXY на
  `[::1]:tproxy_port`, `loopback_guard` не пускает Xray к службам шлюза через `::1`;
- Xray получает второй inbound `tproxy-in6` на `::1`; порт 53 по IPv6 тоже
  отвечает Xray, а приложения получают и A-, и AAAA-записи;
- для пакетов с меткой `mark_proxy` свой `ip -6 rule` и `local ::/0 dev lo` в той
  же таблице маршрутизации (`route_table`);
- серверы подписки с IPv6-адресом перестают отбрасываться;
- `capture.exclude_cidrs` может содержать и сети IPv6.

IPv6 устройств в Wi-Fi шлюз по-прежнему не выдаёт (ни RA, ни DHCPv6) и не
форвардит: проксируется только сама машина. Если в ядре IPv6 нет или он выключен
(`ipv6.disable=1`, `disable_ipv6=1`), режим `proxy` превращается в предупреждение
«проксировать нечего», и IPv4 работает как обычно.

Включить: впишите `ipv6 = "proxy"` в `[network]` и запустите `sudo xgw install`
ещё раз — установка вернёт IPv6 в профиле WAN и сразу применит конфиг Xray (второй
inbound требует его перезапуска). Одна правка config.toml без установки тоже
сработает, но конфиг Xray применится только в `apply.restart_window` (или по
`sudo xgw apply --now`), а до тех пор IPv6 машины блокируется, а не идёт мимо:
правила уже загружены, слушателя на `[::1]` ещё нет. Вернуть `off` так же через
`xgw install`: он снова отключит IPv6 в WAN. `xgw diag` показывает, идёт ли IPv6
через Xray; `xgw status` — «эта машина с IPv6».
- **Устройства в обход VPN** задаются адресом или MAC; MAC работает только со
  статической арендой (`static_leases`): шлюз узнаёт устройство по адресу.

`xgw status` показывает режим перехвата и предупреждает, если он включён в
настройках, а правила в ядро не загружены.

### Tailscale

Если на машине стоит и запущен Tailscale (`tailscaled`), XGW с ним уживается сам:
Tailscale работает во всех режимах — когда VPN включён, когда трафик заблокирован
(`blocked`), при остановленном Xray и по IPv6. XGW Tailscale не ставит и не удаляет:
поставить его — по инструкции с tailscale.com. Войти в tailnet и включить нужное — кнопками
в панели, карточка «Tailscale» (ниже); настройки Tailscale XGW меняет только по нажатию.

- Адреса tailnet (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`), MagicDNS (`100.100.100.100`,
  имена `*.ts.net`) и всё, что идёт через интерфейс `tailscale0`, — мимо Xray и
  блокировок. SSH к шлюзу по адресу в tailnet (в том числе Tailscale SSH) не рвётся и в
  режиме `blocked`.
- Соединения самого Tailscale (WireGuard, ретрансляторы DERP, вход) задаёт `[tailscale]
  route`: `"direct"` (по умолчанию) — напрямую, мимо Xray, так быстрее и работают прямые
  соединения; провайдер видит, что на машине Tailscale, но не видит, что внутри.
  `"vpn"` — через Xray, пока он отвечает (если провайдер Tailscale режет); когда Xray не
  отвечает или трафик заблокирован — напрямую, чтобы удалённый доступ не пропал вместе
  с VPN. Переключение — событие в журнале (`xgw status`, «Последние события»).
- Исключения появляются в правилах, только пока `tailscaled` работает: запустился он
  позже XGW — демон загружает правила заново за секунды.
- Устройства в Wi-Fi шлюза в tailnet через шлюз не попадают (шлюз не работает как subnet
  router Tailscale): чтобы телефон или ноутбук был в tailnet, Tailscale ставится на нём.

`sudo xgw diag`, раздел «Tailscale»: служба (нужен ли вход — со ссылкой), исключения в
правилах (FAIL, если Tailscale работает, а их нет — тогда `sudo xgw net up`), прямой UDP и
ближайший DERP (`tailscale netcheck`) и две ловушки, которые XGW сам не трогает:

- провайдер выдаёт адрес, шлюз или DNS из `100.64.0.0/10` (CGNAT) — фаервол Tailscale
  отбрасывает такие пакеты, и у машины пропадает сеть провайдера. Выход: кнопка
  «Выключить фаервол Tailscale» в карточке (`tailscale set --netfilter-mode=off`, фаервол
  держит XGW);
- в консоли tailnet включено «Override local DNS» — все DNS-запросы машины идут через
  Tailscale мимо VPN. Выход: выключить его в консоли tailnet или кнопка «Не принимать DNS
  из tailnet» в карточке (`tailscale set --accept-dns=false`; имена `*.ts.net` на самом
  шлюзе тогда не разрешаются, на остальных устройствах всё по-прежнему).

#### Карточка «Tailscale» в панели

Всё нужное для удалённого доступа к шлюзу — без терминала. Каждая кнопка выполняет одну
команду `tailscale` на шлюзе и только по нажатию:

- **состояние**: не установлен, служба не запущена, нужен вход или «в tailnet» — с именем
  шлюза в tailnet и адресом `100.x`;
- **«Войти в Tailscale»** — шлюз входит в tailnet: появляются кнопка «Открыть ссылку входа»
  и QR-код той же ссылки (наведите камеру телефона). Войдите в свою учётную запись
  Tailscale — карточка обновится сама;
- **«SSH через Tailscale»** — Tailscale SSH: заходить на шлюз можно только с устройств
  вашего tailnet, вход — по учётной записи tailnet (кто и под каким пользователем — правила
  в консоли tailnet), порт SSH в интернет не открывается. При выключении открытые сеансы
  Tailscale SSH обрываются. Если на шлюзе уже работает OpenSSH, он доступен по адресу
  `100.x` и так; XGW его не трогает;
- **«Панель по tailnet»** — Tailscale Serve: панель открывается с телефона и ноутбука по
  `https://<шлюз>.<tailnet>.ts.net:8443/`, только на устройствах с включённым Tailscale
  (из интернета этот адрес недоступен, сертификат выдаёт Tailscale). Вход — как обычно: по
  токену или одноразовой ссылке. Если в tailnet не разрешены сертификаты HTTPS, появится
  кнопка «Разрешить HTTPS в tailnet» — подтвердите в консоли Tailscale, панель заработает
  сама. На телефоне одновременно работает один VPN: пока включён Tailscale, другой
  VPN-клиент выключен;
- **«Выход в интернет через шлюз»** — шлюз становится выходным узлом tailnet (exit node):
  телефон или ноутбук с Tailscale выбирает в Tailscale «Exit node → шлюз», и его интернет
  идёт домой и дальше через Xray шлюза — VPN на телефоне без второго VPN-приложения (Android
  держит один VPN, и это Tailscale; пульт XGW в приложении при этом работает всегда). После
  включения шлюз один раз одобряют в консоли Tailscale (Machines → шлюз → Edit route
  settings → Use as exit node) — карточка подскажет. Ниже — **«Устройства tailnet»**: у
  каждого переключатель «через VPN» (по умолчанию) или «напрямую» (мимо Xray, адресом
  шлюза). IPv6 через выходной узел закрыт, чтобы не уйти мимо VPN; когда перехват снят
  («VPN выключен»), устройства tailnet выходят напрямую, как и устройства дома, а в режиме
  «заблокирован» — только те, что «напрямую». Скорость упирается в домашний интернет
  (отдача) — для быстрого VPN вне дома есть VPN XGW в самом приложении;
- **«Маршрут Tailscale»** — «Напрямую» или «Через VPN» (то же, что `[tailscale] route`;
  выбор в панели главнее `config.toml`);
- предупреждения о CGNAT провайдера и «Override local DNS» — с кнопкой исправления.

`sudo xgw uninstall` снимает Serve и Funnel, которые включил XGW; сам Tailscale, вход в
tailnet и настройку SSH не трогает.

#### Приложение на телефоне

Приложение XGW для Android (`ANDROID_APP_PLAN.md`) — VPN самого телефона и пульт шлюза.
Файл установки — `android/apk/XGW-0.1.17-a3.apk` (Android 11 и новее, телефоны arm64;
ставится поверх прежней версии, привязка сохраняется).

**Поставить.** Скопируйте файл на телефон и откройте его; Android спросит разрешение ставить
приложения из этого источника — разрешите. Либо с компьютера, к которому телефон подключён
кабелем с включённой «Отладкой по USB»: `adb install -r XGW-0.1.17-a3.apk`.

**Привязать телефон** — два действия, ничего вводить не нужно: в панели на шлюзе, карточка
«Телефоны», нажмите **«Привязать телефон»**, в приложении — **«Сканировать QR-код»** и наведите
камеру на экран. Сканер даёт Google Play services: в первый раз он может полминуты
загружаться — приложение так и скажет. QR-код читает и обычная камера телефона: ссылка
`xgw://pair…` откроет XGW. Приложение спросит «Привязать телефон?» и назовёт шлюз. Если адрес
для приложения ещё не включён, кнопка включает его сама; если в правилах tailnet Funnel ещё
не разрешён, появится кнопка «Разрешить Funnel в tailnet» — подтвердите один раз в консоли
Tailscale, QR-код появится сам. Код в QR действует 10 минут и подходит один раз; телефон
появляется в списке под своей моделью («Galaxy S25 Ultra»), переименовать и отвязать — там же.

**Как приложение достаёт до шлюза.** Карточка «Tailscale» → «Приложение на телефоне
(Funnel)»: адрес шлюза `https://<шлюз>.<tailnet>.ts.net/` (порт 443) открыт в интернет через
Tailscale Funnel, поэтому Tailscale на телефоне не нужен — на Android работает только один
VPN, и это будет VPN самого приложения. TLS заканчивается на самом шлюзе, ретранслятор
Tailscale содержимое не видит. Войти может только привязанный телефон: каждый его запрос
подписан ключом, который лежит в защищённом хранилище телефона (Android Keystore) и оттуда не
извлекается. Без привязки по адресу отвечает только проверка `https://…ts.net/api/hello`
(«XGW») — ей удобно убедиться, что адрес доступен с телефона.

Что приложение может на шлюзе — то же, что панель, по вкладкам внизу экрана:

- **«Главная»** — VPN телефона, VPN шлюза (включить; выключить — с подтверждением «Интернет
  дома пойдёт напрямую, мимо VPN»), строка «Перехват: …», сервер, через который идёт трафик,
  и «Автовыбор»;
- **«Серверы»** — все серверы по подпискам, как в панели: задержка, скорость, метки
  «основной», «резервный», ядро, множитель; у каждого — «Выбрать», ядро (Авто / Xray /
  sing-box), приоритет, выключатель и «Убрать»; «Включить все» / «Отключить все» в подписке,
  «Убранные» с кнопкой «Вернуть»; «Один основной сервер», «Обновить подписки», «Проверить
  запасные», «Замерить скорость» (с прогрессом «N из M»); сводка узлов и расход трафика на
  проверки;
- **«Подписки»** — добавить адрес подписки или ссылки серверов (поле, «Вставить» из буфера
  обмена, «QR-код» — камерой), остаток трафика и срок, изменить User-Agent и заголовки,
  убрать подписку или ссылку;
- **«Устройства»** — устройства дома: мимо VPN и обратно, запись трафика (красная точка),
  записи — «Скачать» в «Загрузки/XGW» на телефоне и «Удалить»; Tailscale: «Выход в интернет
  через шлюз», устройства tailnet «через VPN / напрямую», маршрут Tailscale;
- **«События»** — журнал шлюза.

Только в панели на шлюзе — то, что открывает доступ к самому шлюзу: вход в Tailscale, SSH,
панель по tailnet, адрес для приложения (Funnel: выключив его, телефон отрезал бы себя),
правила Tailscale на шлюзе и привязка телефонов. Экран обновляется раз в 6 секунд, пока
приложение открыто (по мобильной сети состояние идёт сжатым); каждое действие с телефона —
событие в журнале шлюза («с телефона «Galaxy S25 Ultra»: …»). Приложение и шлюз нужно
обновлять вместе: со старым шлюзом новое приложение умеет только то, что на «Главной».

**VPN телефона.** Карточка «VPN телефона» вверху экрана: **«Включить VPN телефона»** —
Android один раз спросит разрешение («Запрос на подключение» → «ОК») и разрешение на
уведомление; дальше весь интернет телефона идёт через Xray в приложении, в строке состояния —
значок ключа, в уведомлениях — «VPN XGW: Включён» с кнопкой «Выключить». Серверы — те же, что
работают на шлюзе: шлюз отдаёт их готовым конфигом Xray (той же версии, 26.10.21), приложение
проверяет его самим Xray и хранит. Список обновляется сам при открытии приложения, если ему
больше часа, и кнопкой **«Обновить серверы»** (VPN при этом не выключается). Шлюз
недоступен — VPN включается и работает на последнем списке. Xray упал — приложение
перезапускает его; четыре падения подряд — VPN выключается с объяснением, чтобы телефон не
остался без интернета. **«VPN всегда»** открывает настройки VPN Android: там у XGW можно
включить «Постоянная VPN» (телефон сам включит VPN после перезагрузки) и «Блокировать
соединения без VPN». Samsung может останавливать фоновые приложения: если VPN сам
выключается, в настройках батареи для XGW выберите «Без ограничений».

**VPN XGW или Tailscale.** Android держит один VPN: пока включён VPN XGW, Tailscale на
телефоне не работает (карточка так и пишет), а с «Постоянной VPN» для XGW Android будет сам
возвращать VPN XGW — если пользуетесь Tailscale, её не включайте. Если VPN забрал Tailscale
(он сам переподключается при смене сети), приложение скажет «Android отдал VPN другому
приложению» и покажет уведомление. Вместо VPN XGW можно оставить на телефоне один Tailscale
и выходить в интернет через шлюз (карточка «Tailscale» → «Выход в интернет через шлюз»).

**Приложение ходит к шлюзу напрямую**, мимо VPN телефона: через VPN-сервер адрес Funnel
не открывается (испытание А1). Дома такой запрос шёл бы через VPN шлюза — поэтому шлюз ведёт
адреса `*.ts.net` напрямую. Если напрямую Funnel не открылся, а VPN XGW включён, пульт
пробует ещё и через VPN телефона (карточка напишет «Пульт ходит к шлюзу через VPN
телефона»). Если на телефоне включён другой VPN (Happ и т. п.), пульт
скажет «Нет связи со шлюзом» и предложит его выключить. Телефон отвязали в панели —
приложение скажет «Шлюз не принял запрос» и предложит «Привязать заново»; опрашивать шлюз
с отвязанным ключом оно перестаёт, чтобы не закрыть вход неудачными попытками. Ключ телефона
в резервные копии и при переносе на новый телефон не попадает — там приложение нужно
привязать заново. Подписки, ссылки серверов, удаление
серверов, Tailscale, установка и логи — только в панели. Серверы через sing-box на телефон
не попадают: sing-box в приложении нет. Само приложение и его Xray исключены из VPN телефона,
поэтому запросы к шлюзу работают и при включённом VPN.

## Проверки серверов

Сервер считается живым, только если через него скачивается целиком файл `probe.url` —
так ловится «заморозка», при которой соединение замирает после 8–20 КБ. Проверяют двое:
ядро Xray (burstObservatory, раз в `probe.interval` по каждому серверу в работе) и сам
XGW (сквозная загрузка через балансировщик на каждом шаге watchdog и скан запасных раз в
`scan_spares_minutes`).

- **`probe.url`** по умолчанию — файл 57 620 байт на CDN jsDelivr (неизменяемая версия
  пакета). Это шрифт, а не текст, намеренно: проба Xray просит у сервера сжатие, и
  текстовый файл такого же размера пришёл бы сжатым до 18 КБ — меньше порога
  «заморозки». Свой адрес выбирайте так же: 50–65 КБ, отдаётся без входа, несжимаемый
  (шрифт, картинка, архив). Прежний адрес по умолчанию отвечал 403 запросам без
  браузерного User-Agent.
- **`probe.user_agent`** — заголовок собственных проверок XGW (скан, сквозная проверка,
  `xgw probe`, `xgw diag`); по умолчанию браузерный. Пробы самого Xray всегда идут с
  заголовками Chrome, эта настройка на них не влияет.
- **Не отвечает сам `probe.url`.** Тогда пробы падают у всех серверов сразу, и без
  отдельной проверки шлюз считал бы их мёртвыми и без конца менял. Если сквозная
  проверка не проходит, XGW опрашивает всех участников и несколько запасных; когда файл
  не получил ни один из них (ошибки при этом могут быть разными — на живой машине было
  64 обрыва и 3 таймаута) и контрольный запрос подтверждает, что дело в адресе —
  напрямую тот же код HTTP либо через VPN открывается другой адрес (`probe.trace_url`), —
  состояние становится `PROBE_TARGET_UNREACHABLE`. Серверы остаются как есть, сканы и
  замены ждут; в журнале, `xgw status`, панели и уведомлении — «Внимание: пробы всех
  серверов падают — вероятно, недоступен сам probe.url». «Заморозка» сюда не относится
  никогда: часть тела пришла — значит, адрес отвечает. Ту же проверку делает
  `sudo xgw diag`, а `xgw probe --all` о ней напоминает, если одна ошибка у 80 %
  серверов и ни один файл не получил.
- **Запасной адрес проб ядра.** Пока `probe.url` не отвечает, ядро Xray пробует серверы
  по `probe.url_fallback`, а если он пуст — по `probe.trace_url`: иначе ядро считало бы
  мёртвыми всех участников, и выбирать между ними балансировщику было бы не из чего.
  Сквозная проверка XGW по-прежнему качает сам `probe.url`; как только
  он ответил, ядро возвращается к нему. Каждое переключение — перезапуск Xray (на
  секунду), без ожидания окна перезапуска. Запасной адрес — только для живости серверов:
  «заморозку» на нём не видно, поэтому для `url_fallback` годится и маленький файл.
- **Первая проверка участников.** Первый состав балансировщика берётся из подписки
  наугад. Каждого участника XGW один раз проверяет собственной пробой; с вердиктом
  `CONNECT_FAIL` или `FROZEN` он меняется на проверенный запасной сразу, без ожидания
  `rotate_after_min`. Дальше за участниками следит ядро.
- **Домены, которых нет в DNS.** Сервер, чьё имя резолверы определённо не знают
  (NXDOMAIN), в конфиг не попадает и пробы не тратит; имя проверяется снова через
  6 часов или по кнопке «Обновить». Сбой самих резолверов никого не отбрасывает.
- **Сводка.** `xgw status` и панель показывают: «Узлов: N активных, K запасных
  (отброшено X недоступных/служебных, схлопнуто Y дублей)».
- **Цена.** Пять серверов в работе с пробой раз в 30 с — около 830 МБ в сутки, скан
  запасных и сквозная проверка — ещё 250–350 МБ: около 35 ГБ в месяц трафика. `xgw
  status`, `xgw diag` и панель показывают расход в сутки и в месяц (от измеренного
  размера пробы) и долю квоты каждой подписки с лимитом — с множителями её серверов:
  пробы безлимитных серверов квоту не тратят, проба через сервер x10 тратит вдесятеро
  больше. При превышении `probe.max_daily_probe_mb` строка в панели подсвечивается.
  Уменьшить расход: `filters.max_members` или `probe.interval`. Замер скорости
  основного сервера считается отдельно (раздел ниже).

## Обход блокировок провайдера

Провайдер может блокировать VPN-серверы по-разному. XGW отвечает на то, что видно с его
стороны, — то есть со стороны клиента; что задаёт сервер, задаёт VPN-сервис.

- **«Заморозка»** (соединение замирает после 8–20 КБ) — ловят проверки серверов (раздел
  выше), такой сервер меняется на проверенный запасной.
- **Блокировка по имени сайта (SNI).** Имя сайта клиент передаёт открытым текстом в
  ClientHello — первой записи TLS. Фильтр, который ищет его в одной записи, не узнаёт
  ClientHello, разрезанный на куски. Это и есть **дробление ClientHello**
  (`[fragment]`): Xray отправляет первую запись TLS частями по `length` байт с паузой
  `interval` мс (по умолчанию 100–200 байт и 10–20 мс: ClientHello уходит примерно 12
  частями, рукопожатие дольше примерно на 0,2 с). Дробятся только TLS и REALITY поверх
  TCP.
  - `mode = "auto"` (по умолчанию): запасной не отвечает так, как не отвечают при
    блокировке (`CONNECT_FAIL`, `TIMEOUT`, `STALL_BEFORE_BODY`, `FROZEN`), — шлюз
    проверяет его с дроблением. Помогло — дробление у сервера остаётся, в том числе когда
    он станет сервером в работе; нет — выключается, следующая попытка для этого сервера —
    через 6 часов. Раз в сутки сервер с дроблением пробуется без него: если провайдер
    перестал блокировать, лишняя задержка ни к чему. Переключение — через API, без
    перезапуска Xray и без уведомлений (событие «дробление ClientHello» в журнале
    событий). У такого сервера в панели — метка «дробление», в `xgw servers` —
    «[дробление]». Серверы в работе шлюз в другом режиме не пробует: не ответивший
    участник меняется на запасной, а потом дойдёт очередь и до него.
  - `mode = "always"` — дробление у всех серверов с TLS и REALITY; `"off"` — ни у кого.
    После `always` режим `auto` оставляет дробление тем, у кого оно было (запасные
    пробуются без него раз в сутки); начать с чистого листа — `off`, затем `auto`.
- **Блокировка по адресу сервера** (соединение не устанавливается вовсе) — дробление не
  поможет: такой сервер шлюз просто не берёт в работу, пока есть другие.
- **Отпечаток TLS.** Без `fp` в ссылке Xray 26.10.10 отправляет ClientHello как Chrome
  (GREASE, ECH, ALPS — проверено); `fp` из ссылки соблюдается.
- **Сертификат сервера.** Xray 26.10.10 убрал `allowInsecure`: конфиг с ним он не
  принимает. XGW это поле в конфиг не переносит (сертификат сервера проверяется), а
  поддерживает замены: `pcs` в ссылке — SHA-256 сертификата сервера (закрепить свой,
  например самоподписанный), `vcn` — сверять сертификат с другим именем.
- **BBR** (`network.tcp_bbr = true`, по умолчанию) — алгоритм управления перегрузкой TCP
  для соединений самой машины, в том числе с серверами VPN: на канале с потерями и
  большой задержкой он держит скорость лучше прежнего. Ставит его `xgw-net`, прежний
  алгоритм возвращают `xgw net down` и удаление; ядро без BBR — не ошибка.

Что XGW намеренно не делает: Reality (`dest`, shortId, ключи), транспорт и защиту от
активного зондирования настраивает VPN-сервис на своём сервере — клиент на них не влияет.
Mux поверх XTLS Vision не нужен (Vision его не использует для TCP). TCP Fast Open
требует поддержки на сервере, а пакеты SYN с данными часть сетей отбрасывает. WARP
требует регистрации учётной записи Cloudflare. DNS устройств и самой машины и так идёт
через туннель.

## Два ядра: Xray и sing-box

**Зачем.** Xray не умеет часть того, что отдают провайдеры: hysteria2, TUIC, AnyTLS,
WireGuard, Shadowsocks с плагинами, подписки в формате sing-box. А когда провайдер глушит
соединения Xray, у sing-box другая реализация TLS и транспорта, и они могут пройти. Поэтому, как
в Happ, у шлюза два ядра.

**Как устроено.** Xray остаётся единственной точкой входа: перехват (TPROXY, TUN), DNS,
балансировщик, проверки, основной сервер и закрепление работают как раньше. Сервер, который
ведёт sing-box, в Xray выглядит обычным участником или запасным, но ведёт к локальному входу
sing-box на `127.0.0.1`:

```
Xray (proxy-… / spare-…) ──socks──► 127.0.0.1:22001+ ──► sing-box ──► сервер (метка mark_bypass)
```

Поэтому участниками (до `filters.max_members`) могут одновременно быть серверы на разных ядрах —
например, VLESS+REALITY через Xray и hysteria2 через sing-box, — а проверки и замер скорости
выбирают из них самый быстрый. TCP и UDP через такой мост идут одинаково (проверено).

**Какое ядро умеет сервер.** В `xgw servers` и в панели у каждого сервера метка:

| Метка | Профиль | Что это |
|---|---|---|
| `[xray]` | `xray:default` | Xray, обычное соединение |
| `[xray+frag]` | `xray:fragment` | Xray, ClientHello режется на части (раздел «Обход блокировок») |
| `[sb]` | `singbox:default` | sing-box, обычное соединение (сервер только для sing-box — или сервер обоих ядер, который шлюз перевёл сюда сам) |
| `[sb+frag]` | `singbox:tls_fragment` | sing-box режет ClientHello на сегменты TCP и записи TLS |
| `[sb+mux]` | `singbox:mux_padded` | sing-box, мультиплексирование h2mux с паддингом |

Серверы бывают трёх видов: **оба ядра** (vless, vmess, trojan, shadowsocks, socks поверх tcp, ws,
grpc, httpupgrade с tls или REALITY — обычные ссылки), **только Xray** (xhttp, mKCP, цепочки
`dialerProxy`, REALITY со `spiderX` и `flow`, закреплённый сертификат `pcs`) и **только
sing-box** (hysteria2 и hy2, TUIC, AnyTLS, WireGuard, Shadowsocks с плагином obfs-local,
v2ray-plugin или shadow-tls). Ядро в отпечаток сервера не входит: смена ядра не сбрасывает его
приоритет, замеры и отключение.

**Ссылки и подписки.** Поддержаны `hysteria2://` и `hy2://` (obfs salamander, смена портов
`mport` и «443,20000-30000», `upmbps`/`downmbps`), `tuic://`, `anytls://`, `wireguard://` и
`wg://` (параметры AmneziaWG sing-box не знает — такая ссылка пропускается с пояснением),
`ss://` с плагином, а также подписки в формате sing-box (JSON с `outbounds` и `endpoints`):
из них берутся прокси-серверы, служебные выходы отбрасываются, цепочки `detour` переносятся
только для shadowtls. Серверы по адресам вроде 0.0.0.0 отбрасываются, как и раньше; имена
серверов разрешаются своими резолверами шлюза и записываются в конфиг sing-box готовыми
адресами (DNS-утечек нет).

**Проверка сертификата не отключается.** `insecure`, `allowInsecure`, `skip-cert-verify` из
ссылок и подписок не переносятся (с предупреждением). Закрепить самоподписанный сертификат
можно параметром ссылки `pks` — SHA-256 **открытого ключа** сервера в base64 или hex
(`openssl x509 -in c.pem -pubkey -noout | openssl pkey -pubin -outform DER | openssl dgst
-sha256 -binary | base64`). `pcs` — хеш всего сертификата, для Xray; ссылка с `pcs` и `pks`
годится обоим ядрам. `pinSHA256` из ссылок hysteria2 перевести нельзя (это другой хеш).

**Профили заведены заранее.** Для каждого сервера в конфиге sing-box сразу есть входы всех
подходящих вариантов (обычный, с дроблением, с мультиплексированием). Поэтому смена профиля —
это замена одного выхода в Xray через API: ни Xray, ни sing-box не перезапускаются и
соединения не рвутся. Это важно: **перечитывание конфига sing-box (SIGHUP) рвёт все его
соединения** (проверено). Конфиг sing-box меняется, только когда меняется состав серверов;
если в этот момент через него идёт трафик (участник, резервный выход или сервер, выбранный
вручную), шлюз откладывает конфиг до окна `apply.restart_window` — `xgw apply` пишет «перечитывание
отложено», `xgw apply --now` применяет сразу, а при аварии (все серверы недоступны) шлюз
не ждёт. Пока конфиг ждёт, Xray ссылается только на то, что sing-box уже ведёт.

**Лестница при блокировке.** При `fragment.mode = "auto"` запасной сервер без лимита трафика,
который не отвечает так, как не отвечают при блокировке, проверяется в других профилях (сервер
в работе не трогается: его заменит запасной, и до него дойдёт очередь):

- **«заморозка»** (`FROZEN`, `STALL_BEFORE_BODY`): `xray:fragment` → `singbox:default` →
  `singbox:tls_fragment` → `singbox:mux_padded`; ждать 6 часов не нужно;
- **отказ в соединении** (`CONNECT_FAIL`, `TIMEOUT`): по одной попытке `xray:fragment`,
  `singbox:default` и `singbox:tls_fragment`;
- обычный sing-box (`[sb]`, с 0.1.13) стоит раньше дробления sing-box: на испытаниях 0.1.12
  часть серверов, глухих на Xray, ответила на sing-box без всякого дробления, а лишняя пауза
  рукопожатия им ни к чему;
- первый профиль, на котором сервер ответил, закрепляется (событие «отвечает на профиле …»);
  не помог ни один — возвращается прежний, следующая попытка через 6 часов;
- проба, которую прервал перезапуск демона (`systemctl restart xgw`, обновление XGW),
  продолжается с той же ступени (с 0.1.14): пробный профиль не считается закреплённым, а
  отсчёт 6 часов и суток не начинается заново;
- закреплённый профиль переживает обновление подписки и перезапуск шлюза. Обычный sing-box у
  сервера, который умеют оба ядра, сохраняется, пока ядро этого сервера не меняли в настройках:
  после `xgw core <сервер> auto` или возврата `[core] mode = "auto"` сервер возвращается на
  Xray, а не остаётся на sing-box, на который его перевело закрепление;
- раз в сутки сервер на тяжёлом профиле пробуется на базовом — вдруг блокировку сняли;
- серверам только для sing-box перебирать нечего, кроме AnyTLS и Shadowsocks через shadow-tls
  (у них есть TLS поверх TCP): QUIC (hysteria2, TUIC) и WireGuard не дробятся;
- серверы подписок **с лимитом трафика** на другое ядро в фоне не переводятся: каждая проба
  тратит квоту (дробление в своём ядре, как в 0.1.11, остаётся);
- при массовой блокировке (`ALL_DEAD`, `RESERVE`) запасные на другом ядре и другом
  транспорте (QUIC против TCP) проверяются первыми: блокировка, срезавшая TCP через Xray,
  может пропустить QUIC через sing-box, и наоборот.

Серверам Xray профиль `singbox:mux_padded` не помогает: они мультиплексирование sing-box не
понимают (проверено) — ступень работает только с серверами sing-box. Она остаётся в лестнице
по решению заказчика; отключить: `core.mux_padding = false`.

**Закрепить ядро.** В панели у сервера (оба ядра) — выбор «Авто» / «Xray» / «sing-box» (два
последних — только это ядро), в терминале — `sudo xgw core <сервер> auto|xray|sing-box` (тег,
отпечаток или имя).
Закрепление хранится в `panel.json`. `[core] mode = "sing-box"` ведёт через sing-box все
серверы, которые он умеет; `"xray"` выключает второе ядро.

**Если sing-box отказал.** Каждый шаг watchdog проверяются его служба и Clash API
(`127.0.0.1:10087`, с паролем). Нет ответа — перезапуск; не помогло дважды — откат конфига на
последний рабочий; всё ещё не поднимается — серверы, которые умеет и Xray, переводятся на него
(интернет остаётся), серверы только для sing-box выпадают из конфига, приходит уведомление;
раз в 30 минут шлюз пробует снова и возвращает серверы, когда sing-box заработает.

**Проверки.** `sudo xgw diag` показывает версию sing-box, принимает ли он рабочий конфиг
(`sing-box check`), работает ли служба и нет ли ошибок в её журнале.

## Основной сервер и замер скорости

**Зачем.** Ядро Xray (стратегия `leastPing`) отправляет новые соединения через сервер с
наименьшей задержкой и пересматривает выбор после каждой пробы — раз в `probe.interval`
(30 с). Когда задержки близки (80 и 85 мс), выбор скачет туда-обратно: открытые
соединения не рвутся, но новые выходят то через Нидерланды, то через Германию. Сайты,
YouTube и CDN каждый раз заново подбирают узел, просят капчу, разлогинивают — интернет
кажется медленным. А задержка — ещё не скорость: проба 57 КБ скачивается за несколько
обменов с сервером и о ширине канала почти ничего не говорит.

**Как теперь.** XGW держит один **основной** сервер среди серверов в работе и
закрепляет его в ядре (`xray api bo` — тот же механизм, что ручное закрепление). Весь
трафик идёт через него; остальные участники остаются наготове — ядро пробует их как
раньше. Скорость замеряется у **всех живых серверов**, и у запасных тоже: ТСПУ может
отрезать любой из нескольких серверов в работе, и самый живой сервер часто лежит в
запасных (0.1.18, issue #1).

- **Выбор** — самый быстрый по замеру скорости. Пока замеров нет (сразу после запуска) —
  с наименьшей задержкой; как только серверы замерены — самый быстрый.
- **Удержание.** Основной меняется только если:
  - он **перестал отвечать** — ядро сочло его мёртвым или через него не прошла сквозная
    загрузка (проверка раз в `watchdog.interval_s`, 20 с). Тогда сразу, на том же шаге,
    основным становится лучший из живых — **той же страны**, если такой есть (сначала из
    другой подписки: подписку целиком могли заблокировать), чтобы адрес выхода не прыгал
    по странам; прежний полчаса основным не берётся. Ожил — назад шлюз не скачет;
  - **другой стабильно быстрее**: по свежему замеру быстрее хотя бы на `speed.gain_pct`
    (30 %), а основной продержался не меньше `speed.hold_minutes` (60 минут). Не каждые
    полминуты, как ядро само по задержке, но и не мёртвой хваткой. Если быстрее
    **запасной**, он сначала встаёт в работу вместо слабейшего участника (не основного:
    сначала мёртвого, потом самого медленного по замеру), а когда ядро его проверит —
    становится основным. Событие: «запасной … быстрее основного … — встаёт в работу
    вместо …».
- **Замер скорости** — загрузка `speed.url` (по умолчанию тестовый адрес Cloudflare, 10 МБ)
  через сервер, не больше `speed.max_mb` (запасные — не больше `speed.spare_mb`, 3 МБ: их
  десятки) и не дольше `speed.max_seconds` (8 с); скорость считается по телу ответа, без
  рукопожатий. Если адрес ответил выходу сервера ошибкой (403), берётся
  `speed.url_fallback` (большой файл на jsDelivr).
- **Кого и как часто.** Все живые серверы: участники, которые отвечают ядру, и запасные,
  прошедшие последнюю проверку. Безлимитные — раз в `speed.unlimited_hours` (1 ч),
  лимитированные — раз в `speed.limited_hours` (6 ч). Участники — первыми; фоновый замер —
  один сервер за шаг watchdog (шаг не затягивается — по нему замечают отказы), не в шаге
  со сканом запасных: круг по 70 серверам — около получаса. Пока не замерены все живые
  участники, выбор основного предварительный: следующий замер может его сменить сразу.
- **Занятый канал.** Пока через серверы идёт заметный трафик (больше ~2 Мбит/с — кто-то
  смотрит видео или качает), фоновый замер ждёт: он и исказился бы, и мешал. Но не дольше
  часа — на домашнем шлюзе фоновый трафик идёт почти всегда, и иначе замеров не было бы
  вовсе. Такой замер панель показывает бледнее: «канал был занят, цифра может быть
  занижена».
- **Кнопка «Замерить скорость»** в панели (и в приложении на телефоне) замеряет все живые
  серверы — в работе и запасные — подряд, до 10 секунд за шаг, занятый канал не ждёт; на
  кнопке — «Замер скорости 12 из 74».
- **Лимитированные серверы замеряются меньшей загрузкой**: квоты на замер уходит не больше
  `speed.max_mb` (у запасных — `speed.spare_mb`). Сервер x1 качает 10 МБ, x2 — 5 МБ, x10 —
  1 МБ (10 МБ квоты); меньше 1 МБ загрузка не бывает — на ней скорость занижена. Серверы
  x100 и дороже (серверы для LTE) не замеряются. Пока подписка не получена и цена сервера
  неизвестна, его тоже не замеряют.
- **Пустое место — с причиной.** У сервера без цифры панель пишет почему: «в очереди
  замера», «замер отложен: канал занят», «замер не удался: …», «сервер не отвечает»,
  «запасной не прошёл последнюю проверку», «скорость серверов x100 не замеряется: они для
  LTE», «замер выключен: speed.unlimited_hours = 0».
- **Результаты хранятся неделю**, у каждого сервера — со временем замера.
- **Трафик.** Безлимитные: `speed.max_mb` × участники × 24 / `unlimited_hours` плюс
  `speed.spare_mb` × запасные × 24 / `unlimited_hours` в сутки; лимитированные — меньшей
  загрузкой и раз в `limited_hours`. При 4 участниках и 70 запасных — около 6 ГБ в сутки
  (это трафик домашнего интернета, квоту безлимитных подписок он не тратит); расход квоты
  лимитированных подписок с множителями входит в строку о квоте. `xgw status`, `xgw diag`
  и панель показывают это отдельной строкой.
- **Прежний ключ `speed.every_hours`** (до 0.1.18 — один срок для серверов в работе):
  `every_hours = 0` по-прежнему выключает замеры; другое значение больше не действует, и
  `xgw` об этом предупреждает — строку можно удалить.
- **Когда основного нет.** В `ALL_DEAD`, `RESERVE`, `XRAY_DOWN`, `WAN_DOWN`, `LEAK` и
  `PROBE_TARGET_UNREACHABLE` закрепление снимается: закреплённый сервер ядро не
  проверяет на здоровье, и без живых участников трафик стоял бы на мёртвом сервере
  вместо резервного выхода. Если загрузка не прошла и через новый основной (не позже
  2 минут после смены), дело, видимо, не в серверах — закрепление тоже снимается, и до
  первой удачной загрузки сервер выбирает ядро.
- **Ручной выбор** (`xgw pin`, кнопка «Выбрать» в панели, `/pin`) главнее: пока трафик
  идёт через выбранный, основной не выбирается; выбор снят или выбранный не отвечает —
  шлюз сам закрепит основной. Замеры скорости при ручном выборе идут, как обычно (по
  расписанию и по кнопке, лимитированные — меньшей загрузкой, x100 — никогда): скорость
  видна в строках серверов. Итоги замеров, прошедших за время выбора, шлюз сверит сразу,
  как выбор снимут: основной сменится, если другой быстрее по правилам удержания (выше).
- **Перезапуск** демона основной не меняет: он хранится в базе вместе с результатами
  замеров; свежие замеры не повторяются до своего срока.
- **Где видно.** `xgw status`: «Основной сервер: proxy-nl-… «Нидерланды» — 87 Мбит/с,
  с 14:05», у серверов — скорость и «← основной». Панель — см. выше. События «основной сервер — …», «основной сервер сменён: …», «… не отвечает пробам ядра
  — выбираю другой» — в журнале, без уведомлений.
- **Выключить** — переключатель в панели или `[speed] sticky = false`: тогда сервер, как до
  0.1.9, выбирает ядро по задержке.

## Приоритет серверов

Какие серверы шлюз берёт в работу первыми, решают две вещи: стоимость трафика через
сервер и ручной приоритет.

**Стоимость.** Подписка с лимитом трафика сообщает его в заголовке
`subscription-userinfo` (поле `total`); подписка без такого заголовка или с `total = 0`
— безлимитная, ручные ссылки — тоже. У серверов подписки с лимитом бывает множитель
расхода в имени: через «x10 🛜 Германия» каждый байт трафика уносит 10 байт квоты.
Множитель ищется шаблоном `filters.multiplier_regex` — по умолчанию латинская `x`,
кириллическая `х` или `×` перед числом, допустимы дроби (`x0.5`, `x1,5`); без отметки —
x1, пустой шаблон — множители не ищутся. У сервера безлимитной подписки стоимость 0 при
любом множителе.

**Порядок:** безлимитные → лимитированные x1 → x10 → x100. Ручной **приоритет** —
главнее стоимости: сервер высокого уровня идёт первым, какой бы ни была его стоимость, а
при равном уровне решает стоимость. Уровень — **высокий**, **средний** (по умолчанию) или
**низкий** — ставится в панели (список у сервера) или командой
`sudo xgw priority <сервер> <уровень>`; он хранится в `/etc/xgw/panel.json` по отпечатку
сервера и переживает обновление подписки и смену имени сервера.

- **В работе — один класс** (уровень и стоимость): лучший из тех, где есть живые
  серверы. Участники балансировщика берутся только из него, даже если их меньше
  `filters.max_members`: иначе Xray отдал бы трафик более быстрому серверу класса хуже —
  например, лимитированному, пока жив безлимитный. Среди серверов класса трафик несёт
  основной — самый быстрый по замеру (раздел «Основной сервер и замер скорости»); с
  выключенным основным — сервер с наименьшей задержкой, его выбирает Xray.
- **Резервный выход.** Один сервер класса хуже — лимитированный с наименьшим
  множителем — становится резервным выходом балансировщика (`fallbackTag` в конфиге
  Xray). Ядро его не пробует (его нет в `burstObservatory.subjectSelector`), поэтому квоту
  он не тратит, пока безлимитные живы. Когда ядро сочтёт мёртвыми всех участников, Xray
  сам, без пересборки конфига, отправит трафик через резервный, а как только хоть один
  участник снова ответит на пробу — вернёт трафик на него. Состояние шлюза в это время —
  `RESERVE`, без уведомления (интернет работает): событие «серверы в работе не отвечают —
  трафик идёт через резервный сервер «x1 Финляндия» (x1)»; возврат — событие «серверы в
  работе снова отвечают». Мёртвых участников шлюз сразу, без `rotate_after_min`, меняет
  на живых запасных того же класса, а подписку внеочередно опрашивает напрямую — раз в 30
  минут. Живых в классе не осталось — в работу идут лимитированные (ниже, «Вниз»).
- **Проверки лимитированных** — редко и коротким запросом (`probe.trace_url`: сотни байт
  вместо 57 КБ). Резервный и три лучших кандидата на его место проверяются раз в 6 часов;
  резервным становится лучший ответивший (событие «резервный сервер — «x10 Германия»
  (x10)»). Если трафик не идёт и через резервный (`ALL_DEAD`), кандидаты проверяются
  сразу и все. Плановый скан запасных (`scan_spares_minutes`) лимитированных класса хуже
  не трогает; их проверяют и перед переходом на них («Вниз»). Безлимитных нет вовсе — в
  работе лимитированные x1, как раньше, резервный — x10; их запасные сканируются по
  расписанию, но тоже коротким запросом, а сервер, ставший участником после такой
  проверки, один раз проходит полную проверку `probe.url`: «заморозку» короткий запрос не
  ловит.
- **Вниз.** Участник перестал отвечать — его меняет запасной того же класса, как
  обычно. Если живых в классе не осталось и запасных этого класса, прошедших скан, тоже
  нет, шлюз сразу и без уведомления переходит на ближайший класс ниже, где они есть: «на
  уровне «высокий» живых серверов нет — в работе серверы уровня «средний»», «живых
  серверов нет — в работе лимитированные серверы x1 (были — безлимитные серверы)».
  Безлимитные в приоритете, но лимитированные не запрещены: когда безлимитные мертвы,
  работают лимитированные, сначала самые дешёвые. На них шлюз переходит не сразу, а после
  2 минут работы через резервный: после короткого сбоя (моргнул провайдер) ядро само
  вернёт трафик безлимитным, а с лимитированных назад — только после перепроверки. Если
  трафик не идёт и через резервный (`ALL_DEAD`), — сразу. Запасные такого класса без
  свежей проверки шлюз сначала проверяет коротким запросом — по старым результатам в
  класс дороже он не уходит. Участниками не становятся серверы дороже x1 (x10, x100):
  участников ядро пробует каждые `probe.interval`, и проба 57 КБ раз в 30 секунд через
  x100 съедала бы ~16 ГБ квоты в сутки на сервер. Через такие трафик несёт резервный
  выход — без постоянных проб. Оценка трафика проверок в панели и `xgw status` учитывает
  и лимитированных участников; если пробы тратят в сутки больше 10 % остатка квоты,
  шлюз уведомит.
- **Вверх.** Пока работают серверы класса хуже лучшего, запасные классов лучше
  проверяются не реже раза в 5 минут. Как только сервер класса лучше проходит скан
  (`OK`), сделанный после последней смены класса, шлюз возвращается к его классу:
  «сервер уровня «высокий» снова отвечает», «снова отвечают серверы лучшего класса — в
  работе безлимитные серверы (были — лимитированные серверы x1)». Старый результат,
  полученный до отказа, не в счёт — поэтому шлюз не прыгает туда-обратно.
- **Ручной выбор** (`xgw pin`, «Выбрать» в панели) важнее приоритета: пока трафик идёт
  через выбранный, класс не меняется; выбранный не отвечает — меняется, как обычно.
- **Где видно.** `xgw servers` и `xgw status`: множитель у серверов подписок с лимитом
  («[x10]»), отметка «← резервный выход» и строка «Резервный выход: …», уровень
  приоритета (у средних — без отметки); у подписки — остаток квоты или «безлимитная».
  Панель: метки «x10» и «резервный» у сервера, у подписки — «осталось N ГБ» или
  «Безлимитная», в состоянии `RESERVE` — «Работает резервный сервер». Страница статуса
  называет резервный сервер. Расход трафика на проверки считается с
  множителями: проба 57 КБ через сервер x100 уносит 5,7 МБ квоты.
- Без приоритетов и без лимитов все серверы одного класса, и шлюз работает, как раньше.

## Службы и файлы

| Служба | Что делает |
|---|---|
| `xgw-net.service` | Загружает правила nftables и `ip rule` раньше, чем поднимается сеть (`Before=network-pre.target`). Остановка службы правил не снимает — для этого `xgw disable` и `xgw net down`. Root в песочнице: файловая система только для чтения, кроме `/var/lib/xgw` и `/run/xgw`; возможности — `CAP_NET_ADMIN`, `CAP_NET_RAW` |
| `xgw-xray.service` | Xray от пользователя `xray` с `CAP_NET_ADMIN` и `CAP_NET_BIND_SERVICE`; перед запуском — `xray run -test`, после запуска — `xgw net tun` от root (интерфейс TUN и маршруты в него, если они нужны); `Restart=always` |
| `xgw-singbox.service` | sing-box — второе ядро, от пользователя `xray` с `CAP_NET_ADMIN`; запускается, только когда есть его конфиг (`ConditionPathExists`), перед запуском и перечитыванием — `sing-box check`; перечитывание (`systemctl reload`) рвёт соединения через него, поэтому XGW делает его редко (раздел «Два ядра») |
| `xgw.service` | Демон XGW и панель управления: root с `ProtectSystem=strict`, запись только в `/etc/xgw`, `/var/lib/xgw`, `/run/xgw`; возможности — `CAP_NET_ADMIN`, `CAP_SETUID`, `CAP_SETGID` |
| `xgw-dhcp.service` | DHCP для сети Wi-Fi: свой экземпляр dnsmasq (программа из `dnsmasq-base`) со своим конфигом `/etc/xgw/dnsmasq.conf` — только DHCP, `port=0`. Файлы `/etc/dnsmasq.d` и штатную службу `dnsmasq.service` XGW не трогает. Работает, только когда настроен LAN. В песочнице: запись только в `/var/lib/xgw` (аренды), только сетевые возможности и переход на пользователя `dnsmasq` |

## Уведомления и страница статуса

- **Рабочий стол** (`notify.desktop = true`): демон находит графическую сессию
  через `loginctl` и вызывает `notify-send` от имени её пользователя. Нужен пакет
  `libnotify-bin`. Если никто не вошёл в систему, уведомление остаётся записью
  в журнале.
- Telegram в XGW больше нет (ASSUMPTIONS п. 222): шлюзом управляют панель и
  приложение на телефоне. Строки `telegram_bot_token`, `telegram_chat_id`, `commands` и
  `telegram_api` в `[notify]` прежнего `config.toml` ничего не значат — `xgw` об этом
  предупредит, их можно удалить. Бот из панели демон при запуске стирает из
  `panel.json`; самого бота можно удалить у @BotFather (`/deletebot`).
- **Уведомляет шлюз, только когда нужно ваше действие** или трафик идёт не так, как
  вы ждёте: все серверы недоступны (`ALL_DEAD`), Xray не отвечает или не
  перезапускается, нет связи с провайдером, утечка, не отвечает адрес проверки серверов
  (`probe.url`) и потом — что он снова отвечает, откат или отказ конфига, перехват снят
  (`fail_mode = open`) или его правила не загружаются, превышен бюджет проверок,
  подписки не обновляются дольше часа, выбранный вручную сервер перестал отвечать (и
  потом — что снова отвечает) или пропал из списка. То, что шлюз чинит сам, — «часть серверов
  недоступна», замена сервера, смена уровня приоритета и класса (в том числе переход на
  лимитированные серверы), работа через резервный сервер и смена резервного, возврат
  правил перехвата, дробление ClientHello — только события в журнале: их видно в панели,
  и в `xgw status`. Один тип уведомления — не чаще
  `min_interval_min`. В журнале systemd уведомления записаны с уровнем warning:
  `sudo journalctl -u xgw -p warning` покажет только их и ошибки. Так ли это у
  работающей службы, показывает строка «Журнал» в `sudo xgw diag`: она считает
  предупреждения, записанные с уровнем info, и показывает, подключён ли вывод демона к
  журналу (`JOURNAL_STREAM`).
- **Страница статуса** (`status.lan_page = true`): `http://<адрес шлюза>:8780/`,
  только чтение и только по токену. Слушает один адрес — шлюза в LAN. Токен —
  `status.token`, а если он пуст — создаётся при установке:
  `sudo cat /var/lib/xgw/status-token`. Первый раз страницу открывают как
  `http://192.168.50.1:8780/?token=…`; дальше браузер помнит вход сам.

## Безопасность

- Конфиг `/etc/xgw/config.toml` — 0600; конфиг Xray — 0640 root:xray. Поэтому
  `xgw status` и другие команды запускаются через `sudo`.
- Xray работает от пользователя `xray`, демон XGW — от root, но с урезанными
  возможностями и файловой системой только на чтение (кроме своих каталогов). Так же
  урезаны службы правил и DHCP: `systemd-analyze security xgw-net.service
  xgw-dhcp.service` — около 3 (было 9.4; меньше — лучше).
- Код в `/opt/xgw` принадлежит root и никому больше не доступен на запись;
  команда `xgw` запускает Python в режиме `-I`: текущий каталог и переменные
  `PYTHON*` на поиск модулей не влияют.
- Ни один секрет (UUID, пароли, ключи, токены) не попадает в логи, статус и
  экспорт: всё проходит через `xgw.masking` (UUID → последние 4 символа,
  секреты → `***`, URL подписок → только домен).
- Служебные порты слушают только 127.0.0.1 (кроме DHCP на LAN и, по желанию,
  страницы статуса); мосты к sing-box (22001+) и его Clash API (10087) — тоже, вход в
  мост — с логином и паролем. Телеметрии нет; внешние запросы — только к URL из
  конфигурации и к GitHub за Xray.
- Панель управления слушает только 127.0.0.1 и пускает по токену
  (`/var/lib/xgw/panel-token`, 0600; в браузере хранится не он, а производная
  от него cookie). Когда браузер открывает сам XGW (конец установки, «Войти
  заново»), в адресе не токен, а одноразовый код: он годится один раз и одну
  минуту, на диске лежит только его SHA-256 (`/run/xgw/panel-login`, 0700) — адрес
  виден в списке процессов, и постоянный токен туда попадать не должен. По tailnet панель отвечает только на имя шлюза в tailnet с портом
  8443 и только пока «Панель по tailnet» включена в самой панели; cookie там — с флагом
  `Secure`. Токен даёт право включать и выключать VPN и менять подписки —
  храните ссылку с ним как пароль. Страница не загружает ничего со стороны:
  стили, сценарий и значок лежат рядом и отдаются самим шлюзом.
- API приложения на телефоне слушает только 127.0.0.1:8782; из интернета до него доходит
  только Tailscale Funnel и только пока он включён из панели (иначе 421). Всё, кроме
  проверки `/api/hello` и привязки, — с подписью HMAC-SHA256 ключом телефона (время ±60 с,
  каждый запрос один раз). Неудачные входы — общий ответ, не больше 10 в минуту на весь шлюз
  (дальше вход закрыт на минуту), не больше 30 запросов в минуту с телефона. Ключи телефонов
  — в `/var/lib/xgw/phones.json` (0600); серверы с ключами уходят только привязанному
  телефону — ему они и нужны для VPN.
- Временные JSON для API-вызовов — 0600, удаляются сразу после вызова.

## Частые проблемы

- **Устройства в сети без интернета, а шлюз «в порядке»** — до 0.1.18 так бывало, когда
  на машине включён `net.ipv4.conf.all.src_valid_mark = 1` (его ставит, например,
  tailscaled): ядро молча отбрасывало пакеты устройств сети до Xray, а машина и
  контейнеры работали. Теперь XGW держит в своей таблице маршрутизации маршрут `throw` для
  подсети LAN, и пакеты доходят при любом значении флага. Демон каждые 20 секунд
  проверяет путь пакета устройства сети (`ip route get … iif <LAN> mark …`): если пакеты
  не доходят, он загружает правила заново, а не помогло — панель показывает «Нет
  интернета в сети» с причиной, приходит уведомление, `xgw status` пишет «НЕТ ИНТЕРНЕТА У
  УСТРОЙСТВ СЕТИ», `sudo xgw diag` — строку «Путь LAN» с FAIL и советом.
- **Tailscale на шлюзе не подключается или не разрешает имена `*.ts.net`** —
  `sudo xgw diag`, раздел «Tailscale»: если «Tailscale: правила» — FAIL, исключения для
  него не загружены, выполните `sudo xgw net up`. Остальные строки раздела говорят, что
  ещё не так и что сделать.
- **После `xgw enable` пропал интернет** — Xray не запущен или не отвечает, а
  при `fail_mode = "closed"` перехваченный трафик без него никуда не уходит.
  Посмотреть: `xgw status`; вернуть прямой интернет: `sudo xgw disable`.
- **`xgw status`: «Перехват: НЕ ВКЛЮЧЁН (ожидание применения inbound в Xray)»** — VPN
  включён, но Xray ещё работает с конфигом, в котором нет нужного inbound'а; правила не
  загружены, чтобы трафик не ушёл в никуда. Обычно это секунды после смены настроек.
  Если не проходит — `sudo xgw apply --now`, причина отказа будет в `sudo xgw logs`.
- **«Внимание: пробы всех серверов падают — вероятно, недоступен сам probe.url»** —
  адрес, которым шлюз проверяет серверы, перестал отвечать (в скобках — как именно).
  Серверы при этом работают, VPN тоже: ядро на это время пробует серверы по запасному
  адресу. Задайте в `config.toml` другой `probe.url`; подробности — `sudo xgw diag`.
- **`xgw status`: «СЛУЖБА xgw НЕ РАБОТАЕТ»** — демон остановлен: серверы не меняются,
  событий и уведомлений нет, ниже — разовые данные. Запустить: `sudo systemctl start xgw`;
  почему остановился — `sudo xgw logs`.
- **«Конфликт подсетей: lan_address … пересекается с интерфейсом …»** — сеть для
  устройств совпала с сетью, из которой машина выходит в интернет. Смените
  `lan_address` и `dhcp_range` на предложенную подсеть и запустите установку снова.
- **После включения машины несколько секунд нет интернета** — правила перехвата
  загружаются раньше Xray, чтобы ничего не ушло мимо VPN; см. «Перехват трафика» про
  `fail_mode`.
- **В журнале Xray строки «is deprecated»** — «The feature Shadowsocks (VMess, Trojan,
  WebSocket transport, HTTPUpgrade transport) … is deprecated» Xray пишет о протоколе серверов из вашей
  подписки: серверы работают, а убрать предупреждение может только провайдер, сменив
  протокол. Запись `"host" in "headers"`, которую Xray тоже называл устаревшей, XGW
  исправляет сам.
- **Устройство из `bypass_hosts` всё равно идёт через VPN** — оно задано MAC, а
  статической аренды для него нет (`network.static_leases`); об этом есть
  предупреждение в журнале.
- **Включён ufw, устройства в Wi-Fi без интернета** — ufw отбрасывает
  перехваченные пакеты в своей цепочке `ufw-not-local`: у них чужой адрес
  назначения. Двух правил `ufw allow in on <lan>` и `ufw route allow …` для
  этого мало, нужна ещё строка в `/etc/ufw/before.rules`. Установка добавляет
  всё это сама, если ответить «да» на её вопрос; `sudo xgw diag` показывает
  недостающее дословно.
- **`xgw diag`: NetworkManager не управляет интерфейсом (unmanaged)** — так
  бывает в Ubuntu Server, где сетью управляет networkd. XGW рассчитан на
  Desktop; либо задайте в netplan `renderer: NetworkManager`, либо оставьте
  `network.lan_if` пустым (режим «только эта машина»).
- **Устройства не получают адрес** — на роутере не выключен DHCP либо кабель
  вставлен в его WAN-порт; `sudo systemctl status xgw-dhcp`. На версиях до 0.1.4 — ещё
  и после установки Docker: см. «Обновление с 0.1.3 и раньше»; `sudo xgw install`.
- **Docker на той же машине** — он ставит политику drop в FORWARD: устройства в
  обход VPN и режим `xgw disable` перестают работать. `sudo xgw diag` покажет
  это и подскажет правила для цепочки `DOCKER-USER`. Сами контейнеры ходят через VPN
  (раздел «Контейнеры Docker»).
- **Панель просит токен** — браузер забыл вход (очищены cookie, другой
  браузер). Правая кнопка по ярлыку «XGW» в меню приложений → «Войти заново»:
  Ubuntu спросит пароль администратора и откроет панель. Из терминала то же даёт
  `sudo xgw panel` — печатает ссылку заново; токен не меняется. Если вместо окна
  пароля ничего не происходит — нет программы `pkexec` (`sudo apt install pkexec`).
- **Панель не открывается** — `sudo systemctl status xgw`: её отдаёт демон.
  Если порт 8781 занят другой программой, об этом есть строка в
  `sudo xgw logs`; порт меняется в `[panel] port`.
- **Отключённый сервер появился снова** — у него сменился адрес или ключ, и для
  шлюза это новый сервер. Отключите его ещё раз.
- **Кнопка включения неактивна** — под ней написано почему: нет подписки, Xray
  не отвечает либо перехват выключен в `config.toml`.
- **После правки `config.toml` ничего не изменилось** — демон перечитывает файл
  сам, но с ошибкой в TOML продолжает работать на прежних настройках:
  `sudo xgw logs -n 20`.
- **Подписка отдаёт не то** — панели выбирают формат по User-Agent; задайте
  `user_agent` в `[[subscriptions]]` (например, `v2rayN/6.0`). Если на месте
  списка серверов приходит «Приложение не поддерживается!» — провайдер требует
  идентификатор устройства: `docs/HWID-SUBSCRIPTIONS.md`.
- **Подписки Clash не поддерживаются** (формат sing-box — поддерживается с 0.1.12).
- **Серверы hysteria2, TUIC, AnyTLS, WireGuard и Shadowsocks с плагином не появляются** —
  их ведёт sing-box: он не установлен или выключен (`xgw diag`, строка «sing-box»;
  `sudo xgw update-singbox`; `[core] mode`). Без него такие серверы в панели помечены
  «не используется».
- **Сервер hysteria2 с самоподписанным сертификатом не подключается** — проверка сертификата
  не отключается ни в одном ядре; закрепите свой сертификат параметром `pks` (раздел «Два
  ядра»).
- **`xgw apply` пишет «перечитывание отложено»** — через sing-box идёт трафик, а перечитывание
  его конфига оборвало бы соединения. Применить сейчас: `sudo xgw apply --now`; иначе шлюз
  применит конфиг сам в окно `apply.restart_window`.
- **«установлен Xray X, нужен не ниже 25.7.23»** — старый бинарник конфиг
  примет, но проверять серверы будет HEAD-запросом и «заморозку» не увидит;
  поэтому XGW отказывается с ним работать.

## Удаление

```bash
sudo xgw uninstall          # спросит подтверждение; --yes — не спрашивать
```

Возвращает систему в состояние до установки по журналу: останавливает и удаляет
службы, убирает таблицы nftables, `ip rule` и маршрут, удаляет профиль
`xgw-lan` и возвращает прежним профилям карты автоподключение, возвращает IPv6
в профиль WAN, значения sysctl, снимает маску со сна, убирает свои правила ufw,
службу DHCP `xgw-dhcp` и её конфиг (а у установки до 0.1.4 — возвращает штатную
`dnsmasq.service` в прежнее состояние), панель по tailnet и адрес для приложения на
телефоне (Tailscale Serve и Funnel, если их включили в панели), привязки телефонов,
пользователя `xray` (если его создала установка) и файлы. Сам Tailscale, вход шлюза в
tailnet и Tailscale SSH остаются как были.
Если NetworkManager откажется сразу применить возвращённый профиль WAN к подключённой
карте (на Ubuntu 24.04 так бывает после перезагрузки), удаление скажет об этом: IPv6
на карте включится после перезагрузки.

Профили карты роутера, которые NetworkManager создаёт сам («Wired connection 1»), при
установке сохраняются в `/etc/netplan/90-NM-<uuid>.yaml` — так NetworkManager хранит
любой профиль, который изменили. После удаления этот файл остаётся с прежними
настройками профиля (автоподключение возвращено); удалять его не нужно.

Остаются ваши настройки — `/etc/xgw/config.toml` и `/etc/xgw/panel.json` с
подписками (`--purge` удаляет и их) — и пакеты, поставленные при установке:
команда подскажет, как их убрать.
Каждый шаг выполняется независимо; если какой-то не удался, остальные всё равно
выполняются, а журнал сохраняется — удаление можно повторить.
