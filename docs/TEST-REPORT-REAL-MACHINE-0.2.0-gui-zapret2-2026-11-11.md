## Дополнение для разработчика: проблемы работы режима zapret2 (после приёмки)

После приёмки владелец попросил включить режим (вне ворот ТЗ). Управление отработало целиком:
сохранение настроек с подтверждением `expected`, цикл pending→applied, смена стратегии дошла до
командной строки nfqws2 (multisplit→multidisorder), переходы состояний off→preparing→fallback,
гейт отказа закрыт, повтор сам каждые 300 с, `can_edit`/`can_off` блокируются корректно.
Итог включения: **fallback / probe_failed** — режим в работу не принял. По пунктам.

Найдено и устранено на машине:

1. **Дефолтные пути не совпадают с раскладкой бандла.** Дефолт config ожидает
   `/opt/xgw/zapret2/<версия>/…`, бандл установлен в `/opt/zapret2/…` → блокер «Файлы zapret2
   не найдены по путям из настроек шлюза» сразу после установки окна. Обойдено симлинком
   `/opt/xgw/zapret2/<версия> → /opt/zapret2` (права root, 644/755 — валидация start прошла).
   Вопрос: согласовать дефолт с бандлом (установщик бандла прописывает пути в config или дефолт
   меняется), иначе каждое обновление бандла снова ломает пути.

2. **Ответ без тела считается неудачей пробы.** Проба-кандидат на домене видеосети, отвечающий
   `204` без тела (вечный, подписи не требует), на **обоих** путях дал `ok=False` — критерий
   успеха в checks требует скачанного тела (`downloaded > 0`). Владельцу в ZAPRET2.md не сказано,
   что адрес пробы обязан отдавать тело. Вопрос: либо принять `204` как успех, либо явно
   документировать требование тела и пример постоянного адреса.

3. **Подписанные адреса видеосети протухают быстрее интервала проверки.** Сохранённый ранее
   рабочий адрес файла видеосети (~6 ч жизни, подпись с `expire`) через сутки даёт HTTP-отказ
   без тела → `probe_failed` на selective при том, что путь к нему исправен. При интервале
   проверки 180 с..3 ч режим будет падать в fallback между обновлениями адреса владельцем.
   Вопрос: кэшировать последний успешный адрес пробы или подсказывать в окне свежесть адреса.

Не решено — главный вопрос разработчику:

4. **Причина `probe_failed` в selective установлена (диагностика 12.11, второй раунд): критерий
   `min_body=16 КиБ` в `_request`.** Каждый адрес пробы обязан скачать не меньше 16 КиБ тела
   (`checks.http_get_via_proxy(min_body=16*1024)`), иначе `ok=False`. Проверено сравнением:
   - страница (домен страниц): `path=vpn ok=1 http=200 bytes=66 569`;
     `path=zapret2 ok=1 http=200 bytes=66 274` — **прямой путь с обфускацией работает**;
   - постоянный адрес на домене видеосети без подписи (`robots`, 25 байт):
     `ok=0 http=200 bytes=25` на **обоих** путях — отвергнут размером, не сетью;
   - вечный `204`-эндпоинт домена видеосети: `ok=0 http=204 bytes=0` на обоих путях;
   - протухший подписанный адрес видеофайла (сутки, `expire` прошёл): HTTP-отказ без тела.
   На домене видеосети **всё, что не требует подписи, меньше 16 КиБ**, поэтому пара
   «страница + видеосеть» в selective не собирается никогда, кроме живого подписанного адреса
   файла (жизнь ~6 ч против интервала проверки до 3 ч — см. п. 3). Сами ручные пробы вне
   lease-окна демона висят по другой причине: nft-гейт пропускает отмеченные пакеты только
   пока метка в LIVE-наборе (`gate(45/240)`), вне окна — дроп; к отказу selective это
   отношения не имело.

Просьбы к разработчику (итог):

- задокументировать в ZAPRET2.md критерий пробы: каждый адрес обязан отдавать ≥16 КиБ тела
  по порту 443 домена из списка, редиректы не следуются (см. строки compare позавчерашнего
  отчёта: `http=302 ok=0`);
- рассмотреть приём `204`/HEAD или понижение `min_body` для служебных адресов — иначе пара
  «страница + видеосеть» без живой подписи неосуществима;
- кэш последнего успешного видеопроба или подсказка свежести в диалоге «Настроить»;
- публикация строк selective-пробы в снимок при `probe_failed` (как в compare) — этот раунд
  диагностики занял часы именно потому, что selective не сообщает, какой адрес и почему
  отвергнут.
