# Отчёт об испытаниях XGW 0.1.5 на реальной машине

Прогон по программе `docs/TEST-PLAN-REAL-MACHINE-0.1.5.md` (кейсы REAL-19…REAL-25),
машина та же, что в прошлом отчёте `docs/TEST-REPORT-REAL-MACHINE-0.1.4-2026-10-15.md`.

Проверяемая версия: **0.1.5**, коммит `0567d3f2b3fea201ace15cd9b5602a4e99efcf3e`
(ветка `main`, «Исправления по испытаниям 0.1.4 (G1–G7); версия 0.1.5»),
поставлена поверх 0.1.4 обычной установкой из исходников, **без `--force`**.

Дата прогона: 15.10.2026, 19:42 — 20:40 MSK.

Прогон был прерван сразу после перезагрузки (REAL-20): сессия тестировщика оборвалась, и
отчёт остался с незаполненным разделом §4. Показания после загрузки к тому моменту уже сняла
разовая служба (20:29:55), они сохранены в `/var/log/xgw-015-after-boot.txt` и внесены в §4
при завершении отчёта — без правок, вместе с проверкой состояния машины через 12 минут после
загрузки (20:40). Всё остальное в отчёте — записи того же прогона.

**Коротко.** Все семь дефектов прошлого отчёта (G1–G7) исправлены и проверены на живой
машине. Главное — **после обычной перезагрузки контейнеры Docker снова выходят через VPN**:
интерфейс `xgwtun0` готовит `xgw net up`, и адрес `169.254.10.1/32` на нём есть без
вмешательства человека (§4). Установка 0.1.5 поверх 0.1.4 проходит **обычной командой, без
`--force`** (§3): неработающие службы, незагруженные правила и интерфейс без адреса стали
предупреждениями «установка исправит», а не отказами. Если адрес с интерфейса всё же снять,
`diag` это видит (`FAIL TUN`), а демон возвращает адрес сам — на этой машине за **2 секунды**

по-человечески: «он больше не нужен ни этой машине, ни контейнерам» вместо прежнего
«capture.method больше не tun» (§7).

Юнит-тесты на машине с Docker: **726 passed, 17 skipped, 0 failed** (§6) — те четыре теста,

## 3. REAL-19. Обновление 0.1.4 → 0.1.5 без `--force` (G1)

1. `systemctl stop xgw-dhcp` — разрешённое исключение программы (аренды у устройств 12 ч,
   остановку они не замечают).
2. Обычный `diag` новой версии из репозитория (`env PYTHONPATH=src python3 -P -m xgw diag`),
   код возврата 1. Ожидаемый FAIL есть:
   ```
   FAIL  Службы: не работают: xgw-dhcp.service
         → sudo systemctl status xgw-dhcp.service
   ```
   Рядом — ещё два FAIL, которых в 0.1.4 не было:
   ```
   FAIL  TUN: у интерфейса xgwtun0 нет адреса 169.254.10.1/32 или он не поднят: ответы Xray ядро отбрасывает
   FAIL  Перехват: включён, но правила не загружены
   ```
   Это то самое новое поведение из §1 программы: причина у обоих одна — интерфейс без адреса.
   Перехват при этом действительно работал (правила nftables совпадают со снимком «до»,
   машина выходила адресом VPN-узла), то есть FAIL описывает не «сети нет», а
   «контейнеры обслужить нельзя». Формулировка совпадает с ожидаемой в REAL-21.
3. `sudo sh packaging/install.sh --yes` — **без `--force`**, код возврата **0**. Прежние отказы
   стали предупреждениями ровно с теми формулировками, что ждала программа:
   ```
   WARN  TUN: у интерфейса xgwtun0 нет адреса 169.254.10.1/32 или он не поднят: ответы Xray ядро отбрасывает
         → установка подготовит интерфейс заново
   WARN  Службы: не работают: xgw-dhcp.service
         → установка запустит их заново
   WARN  Перехват: включён, но правила не загружены
         → установка загрузит их заново
   Итог: OK — 17, WARN — 4, FAIL — 0
   ```
   Установка прошла по плану: код в `/opt/xgw/lib`, команда `/usr/local/bin/xgw`, службы
   `xgw-net`, `xgw-xray`, `xgw` с автозапуском, Xray запущен (5 участников, 56 запасных),
   правила nftables загружены, демон запущен.
4. После установки: `xgw --version` → **0.1.5**; `systemctl is-active xgw xgw-xray xgw-net
   xgw-dhcp` → четыре `active`; `xgw status` → `HEALTHY`; `xgw diag` → **OK 20, WARN 1,
   FAIL 0**. Появилась новая строка:
   ```
   OK    TUN: /dev/net/tun есть; интерфейс xgwtun0 — для контейнеров Docker
   ```
   и **`xgwtun0` получил адрес `169.254.10.1/32`** — до установки его не было. Контейнер
   сразу пошёл через VPN (адрес совпал с адресом машины).

**Вывод:** G1 исправлен. Отдельно отмечу: установка не просто «не отказывается», а заранее
называет, что именно починит, — оператору понятно, чего ждать.

## 5. REAL-21. Интерфейс без адреса: `diag` его видит, демон чинит (G7)

**Часть 1 — без демона.** Разрешённое исключение программы: адрес снят вручную
(`ip addr del 169.254.10.1/32 dev xgwtun0`).

1. `systemctl stop xgw`, затем снятие адреса. `xgwtun0` — только `fe80::`.
2. Контейнер: `wget: bad address 'api.ipify.org'` (код 1). **Адрес провайдера не вышел** —
   то есть fail-closed держит: контейнер не ушёл мимо VPN, он остался без интернета.
3. `xgw diag` — ровно три FAIL из программы, дословно:
   ```
   FAIL  TUN: у интерфейса xgwtun0 нет адреса 169.254.10.1/32 или он не поднят: ответы Xray ядро отбрасывает
   FAIL  Службы: не работают: xgw.service
   FAIL  Перехват: включён, но правила не загружены
   Итог: OK — 17, WARN — 1, FAIL — 3
   ```
4. `xgw status --json` — код возврата **3**, `capture.loaded` = **false**.
5. `xgw net up` — код 0, «правила сети загружены, режим on»; адрес `169.254.10.1/32` вернулся,
   контейнер снова выходит адресом VPN-узла, `diag` — FAIL только по намеренно остановленной
   службе `xgw.service`.

**Часть 2 — с демоном.** `systemctl start xgw`, состояние `HEALTHY` через 10 с. Адрес снят
повторно, засечено время. **Адрес вернулся сам, без единой команды, через 2.02 с** (программа
допускала до 1 минуты). В журнале — событие с ожидаемой формулировкой:

```
15.10 20:19:15 xgw.daemon: capture: у интерфейса xgwtun0 нет адреса 169.254.10.1/32
или он не поднят: ответы Xray ядро отбрасывает — интерфейс подготовлен заново
```

Контейнер снова через VPN, `diag` — OK 20 / WARN 1 / **FAIL 0**, `status` — `HEALTHY`.
Машина и устройства LAN всё это время шли через VPN: снятие адреса у `xgwtun0` их перехвата
не касается.

**Вывод:** G7 исправлен с обеих сторон — и «видит» (`diag`, `status --json`), и «чинит»
(демон). В прошлом отчёте ни одна команда XGW это состояние не лечила, а `diag` считал его
здоровым.

## 7. REAL-23. Текст события об убранном интерфейсе (G3)

1. В `[capture]` выставлено `containers = false`, затем `xgw net up` и `xgw apply --now`.
   `net up` подтвердил режим: «Перехват: включён — сеть enp4s0 и эта машина» (без контейнеров).
2. Ожидаемое событие есть, формулировка новая:
   ```
   15.10 20:20  capture: интерфейс xgwtun0 убран: он больше не нужен ни этой машине, ни контейнерам
   ```
   Прежнего «убран: capture.method больше не tun» нет. Интерфейса `xgwtun0` не осталось,
   контейнер вышел адресом провайдера `46.242.12.248`, машина — через VPN.

   `169.254.10.1/32`, контейнер снова через VPN, `status` — `HEALTHY`, `diag` — FAIL 0.

Замечание для оператора: событие попадает в **список событий XGW** (его печатает
`xgw status` и показывает панель), а не в stdout команды `apply`, — при проверке смотреть
туда.

## 10. Дефекты

**Новых дефектов в 0.1.5 не найдено.** Все семь дефектов прошлого отчёта (G1–G7) закрыты и
проверены на живой машине (§3–§8).

Одно наблюдение, не дефект: в программе испытаний команда прогона юнит-тестов записана как
`pytest tests/ --ignore=tests/stand -q`, но `-q` уже задан в `addopts` (`pyproject.toml`),
поэтому второй `-q` даёт `-qq` и **итоговая строка «N passed» не печатается**. Прогон при
этом полный; чтобы увидеть итог, второй `-q` нужно убрать (так и сделано в §6). Стоит
поправить формулировку в программе для 0.1.6, чтобы тестировщик не принял отсутствие строки
за сбой.

## 11. Что не проверено и почему

- **REAL-12…REAL-15, REAL-18 не повторялись** — так и написано в §4 программы: 0.1.5 их кода
  не меняла, а в кейсах выше ничего из этого не сломалось.
- **Утечка через сервер, выходящий в RU (REAL-13 прошлой программы)** — среди текущих
  участников такого узла нет, проверять не на чем.
- **Telegram с настоящим токеном** — по §0 п. 6 программы не проверяется; `xgw pin` в этой
  программе не нужен.
- **Внешняя проверка с другого устройства в сети провайдера** — такого устройства в сети
  192.168.50.0/24 нет; проверки шли с самой машины.
- **Настоящая сеть с IPv6** — на WAN глобальных IPv6-адресов нет, `network.ipv6 = "off"`.
