# Программа испытаний XGW 0.1.7 на реальной машине

Задание для модели-тестировщика (DeepSeek 4.1). Машина та же, что в отчёте
`docs/TEST-REPORT-REAL-MACHINE-0.1.5-2026-10-15.md` (дальше — «прошлый отчёт»): ThinkCentre,
Ubuntu 24.04.5 LTS, на ней стоит XGW 0.1.5 (коммит `0567d3f`), Docker запущен, роутер HUAWEI
AX2 — точка доступа с адресом от `xgw-dhcp`. Задача — поставить 0.1.7 поверх и проверить две
новые вещи:

- **0.1.6 — Xray 26.10.10** (предварительный выпуск) и восстановление интерфейса TUN после
  каждого запуска Xray (REAL-26…REAL-29);
- **0.1.7 — приоритет серверов**: высокий, средний, низкий (REAL-30…REAL-38).

Плюс коротко — что уже работавшее не сломалось (REAL-39). Итог — новый отчёт в том же формате,
что и прошлый (раздел 6).

Читать до начала работы: ASSUMPTIONS пп. 181 (Xray 26.10.10) и 182 (приоритет); README —
разделы «Требования» (версия Xray), «Приоритет серверов», «Перехват трафика» (TUN),
«Контейнеры Docker», «Разработка и тесты» (стенды).

## 0. Правила работы

Те же, что в программе 0.1.4 (`docs/TEST-PLAN-REAL-MACHINE-0.1.4.md`, раздел 0), коротко:

1. **Сеть меняется только командами XGW** (`xgw install`, `enable`, `disable`, `net up`,
   `apply`, `update-xray`, `uninstall`), действиями в панели и правкой `/etc/xgw/config.toml`.
   Никаких `nft flush ruleset`, ручных правок чужих таблиц nftables, правил ufw и Docker,
   ручных `ip addr`/`ip route`/`ip link`. Исключения этой программы названы в кейсах явно —
   и только они.
2. **Аварийный выход**: `sudo xgw disable`. Интернет пропал больше чем на 2 минуты (в
   REAL-34 — на 5 минут), и кейс этого не ждёт — `disable`, время, `sudo xgw status`,
   `sudo xgw diag`, `sudo journalctl -u xgw -u xgw-xray -u xgw-net --since -15min`, дефект в
   отчёт.
3. **Перед перезагрузкой (REAL-29)** — доступ к машине, не зависящий от перехвата (локальная
   консоль), либо разовая служба, снимающая показания после загрузки, как в прошлый раз.
4. **Секреты в отчёт не попадают**: адреса подписок, UUID, пароли, ключи, токены, в том числе
   токен панели. Перед коммитом отчёта — `grep` на `vless://`, `vmess://`, `trojan://`,
   `ss://`, `token=`. Исключение — ссылка ненастоящего сервера из REAL-33: она придумана для
   теста и ничего не открывает, её можно привести целиком.
5. **Код XGW не чинить.** Найденное — дефект в отчёте. Обход — только если без него дальше не
   пройти, и он описывается.
6. **Только фейковые данные в тестах.** Новых подписок не добавлять. Единственный добавляемый
   сервер — ненастоящий из REAL-33.
7. **Команды — те, что в программе.** Нужна команда, которой здесь нет, — только читающая
   (`cat`, `ls`, `ip … show`, `nft list …`, `systemctl status`, `journalctl`). Не угадывать
   ключи команд XGW: список — `xgw --help`, `xgw <команда> --help`.
8. **Записывать точно.** Для каждого шага — время (`date +%T`), команда, вывод (существенная
   часть дословно), сравнение с ожиданием. Ожидание не совпало — записать дефект и идти
   дальше, если следующий шаг от этого не зависит.
9. Telegram с настоящим токеном не проверяется.

### Как действовать в панели

Панель — `http://127.0.0.1:8781/` (ярлык «XGW» в меню приложений). Если графического сеанса
нет, то же самое можно сделать запросами к панели с самой машины. Токен в отчёт не
записывать:

```bash
J=~/xgw-0.1.7-test/panel.jar
curl -s -o /dev/null -c $J "http://127.0.0.1:8781/?token=$(sudo cat /var/lib/xgw/panel-token)"
P() { curl -s -b $J -H 'X-XGW-Panel: 1' -H 'Content-Type: application/json' -d "$2" "http://127.0.0.1:8781/api/$1"; echo; }
curl -s -b $J http://127.0.0.1:8781/api/state | python3 -m json.tool > ~/xgw-0.1.7-test/state.json
```

Действия: приоритет — `P priority '{"fingerprints":["<отпечаток>"],"level":"high"}'`
(`high`, `medium`, `low`), добавить ссылку — `P add '{"text":"<ссылка>"}'`, убрать ссылку —
`P link/remove '{"id":"<id из state.json, раздел links>"}'`, проверить запасные —
`P scan '{}'`, обновить подписки — `P refresh '{}'`. В отчёте указать, чем пользовались:
страницей в браузере или запросами.

## 3. Кейсы: Xray 26.10.10 (0.1.6)

### REAL-26. Обновление 0.1.5 → 0.1.7

1. `sudo sh packaging/install.sh --yes` — **без `--force`**. Ожидается код 0, а в конце
   `systemctl is-active xgw-net xgw-xray xgw xgw-dhcp` — четыре `active`.
2. `systemctl cat xgw-xray | grep ExecStartPost` → строка
   `ExecStartPost=-+/usr/local/bin/xgw net tun`.
3. Версия Xray:
   - в `config.toml` осталось `version = "latest"` (так было в примере до 0.1.6) →
     ожидается, что установка оставила **26.3.27**: `/opt/xgw/xray/xray version`.
     `sudo xgw diag` строку о несовпадении версии **не** пишет — для `"latest"` её нет;
   - в конфиге уже другая конкретная версия → записать, что поставила установка.
4. `sudo xgw diag` — FAIL нет. `sudo xgw status` — `HEALTHY` (подождать до минуты).
   Устройства LAN, машина и контейнер — через VPN:
   `docker run --rm alpine wget -qO- https://api.ipify.org` — адрес VPN-узла.

### REAL-27. Переход на Xray 26.10.10

Переход на 26.10.10 скачивает Xray с GitHub — это разрешённый внешний запрос.

1. В `/etc/xgw/config.toml`, раздел `[xray]`: `version = "26.10.10"`. Больше ничего не
   менять.
2. `sudo xgw diag` → `WARN  Xray: версия 26.3.27, а в конфиге xray.version = 26.10.10` с
   советом `sudo xgw update-xray`.
3. `sudo xgw update-xray`. Ожидается: загрузка, сверка SHA-256, проверка рабочего конфига
   (`xray run -test`), перезапуск. Записать вывод целиком и сколько секунд не было интернета
   (`ping -c 30 1.1.1.1` во втором терминале).
4. `/opt/xgw/xray/xray version` → `Xray 26.10.10`. `sudo xgw diag` — WARN о версии нет, FAIL
   нет. `sudo xgw status` — `HEALTHY`.
5. Журнал Xray за 5 минут: `sudo journalctl -u xgw-xray --since -5min`. Предупреждение, что
   `domainStrategy` у `freedom` устарело, — **ожидаемо, не дефект**. Любые другие
   предупреждения и ошибки выписать.
6. Трафик: машина (`curl -s https://api.ipify.org`), контейнер (как в REAL-26), устройства за
   роутером (журнал Xray, как в прошлый раз) — адреса VPN-узлов; `nslookup example.com` —
   отвечает. Через 10 минут — `HEALTHY`, `sudo xgw servers`: участники живы, задержки в норме
   (сравнить с «до»).

### REAL-28. Перезапуск Xray: интерфейс контейнеров на месте

1. До: `ip -br addr show xgwtun0` (UP, `169.254.10.1/32`) и
   `ip route show table all | grep xgwtun0` (записать маршруты).
2. `sudo systemctl restart xgw-xray`, сразу (в течение 10 с):
   - `ip -br addr show xgwtun0` — **UP, адрес `169.254.10.1/32`**;
   - `ip route show table all | grep xgwtun0` — **те же маршруты, что до**;
   - `sudo journalctl -u xgw-xray --since -1min` — запуск `xgw net tun` без ошибок;
   - `docker run --rm alpine wget -T 10 -qO- https://api.ipify.org` — адрес VPN-узла.
3. Повторить три раза подряд, с паузой 30 с. Каждый раз — то же.
4. В событиях (`sudo xgw status` или панель) за это время **не должно быть** «у интерфейса
   xgwtun0 нет адреса … — интерфейс подготовлен заново»: интерфейс чинит служба, а не демон.
   Если такое событие есть — записать, через сколько секунд после перезапуска (это не отказ,
   но значит, что `ExecStartPost` не сработал).

### REAL-29. Перезагрузка на 26.10.10

1. До перезагрузки: контейнер — адрес VPN-узла.
2. Перезагрузка (`sudo shutdown -r now`). Показания через 60–120 с после загрузки — как в
   REAL-20 прошлой программы:
   - `ip -br addr show xgwtun0` — UP, `169.254.10.1/32`; маршрут через `xgwtun0` есть;
   - `docker run --rm alpine wget -qO- https://api.ipify.org` — адрес VPN-узла;
     `docker run --rm alpine nslookup example.com` — отвечает;
   - `/opt/xgw/xray/xray version` — 26.10.10;
   - `sudo xgw diag` — FAIL нет; `sudo xgw status` — `HEALTHY`; четыре службы `active`;
   - устройства за роутером — через VPN, аренды на месте;
   - `sudo journalctl -b -u xgw-net -u xgw-xray -u xgw` — выписать ошибки, если есть.

## 4. Кейсы: приоритет серверов (0.1.7)

### Как это работает (кратко — для сверки с ожиданиями)

- Уровень хранится в `/etc/xgw/panel.json` по отпечатку сервера (`"priority"`). Средний не
  хранится.
- Участники балансировщика — только с одного уровня: самого высокого, на котором есть живые.
  Их может быть меньше `max_members`.
- Участник перестал отвечать — его меняет запасной **того же** уровня. Живых на уровне нет
  (`ALL_DEAD`) и запасных этого уровня, прошедших проверку, тоже нет — сразу переход на
  ближайший уровень ниже, где они есть. Событие и уведомление на рабочий стол:
  «на уровне «высокий» живых серверов нет — в работе серверы уровня «средний» (были —
  «высокий»)».
- Пока работает уровень ниже, запасные уровней выше проверяются не реже раза в 5 минут.
  Сервер уровня выше прошёл проверку (`OK`) уже после смены уровня — возврат: «сервер уровня
  «высокий» снова отвечает — в работе серверы уровня «высокий» (были — «средний»)».
- Пока сервер закреплён (`xgw pin`), уровень не меняется.
- `xgw servers` пишет у серверов `[высокий]`/`[низкий]` (у средних — ничего), а в заголовке —
  «Участники балансировщика (N), уровень приоритета «…»:». В панели у каждого сервера —
  список «Высокий / Средний / Низкий», над серверами — «Приоритет: в работе серверы уровня
  «…». Уровнем ниже шлюз пользуется, только когда живых выше нет.» (только если у
  кого-то уровень не средний).

### Почему отказ высокого уровня делается ненастоящим сервером

Выключить настоящий сервер подписки нельзя, а блокировать его адрес вручную запрещено (§0,
п. 1). Поэтому «мёртвый сервер высокого уровня» — это ненастоящий сервер, добавленный
ссылкой (REAL-33). Его адрес `192.0.2.10` — из сети TEST-NET-1 (RFC 5737): она для
документации и в интернете не маршрутизируется, так что сервер гарантированно не отвечает.

Обозначения дальше: **B** и **L** — два разных настоящих запасных сервера, у которых в
`sudo xgw servers` последняя проверка `OK`; **F** — ненастоящий сервер. Записать имена и
теги B и L; отпечатки — первые 8 символов.

### REAL-30. Без приоритетов всё как раньше

1. `sudo xgw servers` — ни одной отметки `[высокий]`/`[низкий]`; в заголовке нет «уровень
   приоритета».
2. Панель: у каждого сервера (кроме отсеянных фильтром) список, и в нём «Средний»; строки
   «Приоритет: в работе…» нет. На узком окне (меньше 600 px) кнопки сервера переносятся на
   вторую строку, имя видно целиком — снимок экрана, если есть графический сеанс.
3. В `state.json` (или `sudo xgw status --json`) — `"tier": "medium"`; у серверов
   `"priority": "medium"`.

### REAL-31. Подъём на высокий уровень (панель)

1. В панели B → «Высокий». Ожидается ответ «Приоритет сервера «B»: высокий» и примечание про
   уровни ниже. Засечь время.
2. В течение 5 минут (обычно — за шаг-два watchdog, если у B свежая проверка `OK`; иначе — после
   его проверки):
   - событие «сервер уровня «высокий» снова отвечает — в работе серверы уровня «высокий»
     (были — «средний»)» (в `sudo xgw status` / панели), уведомление на рабочем столе — если
     графический сеанс есть;
   - `sudo xgw servers` — участник **один**: B с `[высокий]`; заголовок «Участники
     балансировщика (1), уровень приоритета «высокий»:»;
   - панель — «Приоритет: в работе серверы уровня «высокий»…»;
   - `curl -s https://api.ipify.org` на машине — адрес выхода B (записать; сравнить с «до»);
     контейнер и устройства LAN — через VPN; `HEALTHY`.
3. Записать, через сколько секунд после выбора уровня B стал единственным участником.
4. `sudo cat /etc/xgw/panel.json | python3 -c 'import json,sys; print(json.load(sys.stdin)["priority"])'`
   → `{'<отпечаток B>': 'high'}` (отпечатки — не секрет).

### REAL-32. Низкий уровень (терминал)

1. `sudo xgw priority <тег L> low` (тег — из `sudo xgw servers`, например `spare-de-1a2b3c4d`).
   Ожидается «приоритет сервера «L»: низкий. Демон применит его на ближайшем шаге; …», код 0.
2. Повтор той же команды → «приоритет сервера «L» уже низкий», код 0.
3. `sudo xgw servers` — у L отметка `[низкий]`; L не участник. В участниках по-прежнему один B.
4. Всё дальнейшее время испытаний L **ни разу** не должен оказаться участником — проверять в
   каждом кейсе до REAL-37.

### REAL-33. Ненастоящий сервер высокого уровня рядом с живым

1. Добавить в панели (поле «Вставьте адрес подписки… или ссылку сервера») ссылку:

   ```
   vless://00000000-0000-4000-8000-0000000000f1@192.0.2.10:443?encryption=none&type=tcp#XGW-TEST-DEAD
   ```

   Ожидается ответ «Добавлено серверов: 1» и событие «ссылок серверов добавлено из
   панели: 1».
2. Подождать до минуты; `sudo xgw servers` — F (`XGW-TEST-DEAD`) в списке, **запасной** (не
   участник: в работе высокий уровень, а F пока средний).
3. `sudo xgw priority XGW-TEST-DEAD high` (по имени). Ожидается «приоритет сервера
   «XGW-TEST-DEAD»: высокий…», код 0.
4. В течение минуты: `sudo xgw servers` — участники **B и F**, оба `[высокий]`; F — не живой.
   Трафик идёт через B: машина, контейнер, устройства — через VPN, адрес выхода — B. Статус —
   `HEALTHY` или `DEGRADED` (один участник из двух не отвечает), но не `ALL_DEAD`.

### REAL-34. Высокий уровень весь мёртв — переход на средний

**Ожидаемый короткий перерыв**: после шага 1 единственным участником станет F, который не
отвечает. При `fail_mode = "closed"` интернета не будет до перехода на средний уровень.
Ожидается не больше 2 минут. Аварийный порог для этого кейса — 5 минут (§0, п. 2).

1. Во втором терминале — `ping -D 1.1.1.1 | tee ~/xgw-0.1.7-test/ping-34.txt` (для точного
   времени перерыва). В панели B → «Средний». Засечь время.
2. Ожидается, по порядку:
   - сборка с одним участником F (событие о применении конфига);
   - статус `ALL_DEAD`;
   - сразу за ним событие «на уровне «высокий» живых серверов нет — в работе серверы уровня
     «средний» (были — «высокий»)» и уведомление на рабочем столе, если сеанс есть;
   - `sudo xgw servers` — участники — средние, их до `max_members`; F — запасной `[высокий]`;
     L не участник; заголовок «…уровень приоритета «средний»:»;
   - статус `HEALTHY`, машина/контейнер/устройства — через VPN.
3. Записать: время от выбора уровня до каждого события, длительность перерыва по `ping`, был

### REAL-35. Закрепление важнее приоритета

1. `sudo xgw pin <тег одного из нынешних участников> --ttl 10m` — код 0.

### REAL-36. Приоритет переживает перезапуск и обновление подписок

2. Обновить подписки в панели («Обновить», или `P refresh '{}'`). Через 2 минуты — то же самое:

### REAL-37. Ошибки команды `xgw priority`

| Команда | Ожидание |
|---|---|
| `sudo xgw priority no-such-server high` | «ошибка: сервер «no-such-server» не найден: …», код 2 |
| `sudo xgw priority XGW-TEST-DEAD urgent` | отказ argparse (недопустимый выбор), код 2 |
| `xgw priority XGW-TEST-DEAD low` (без sudo) | отказ с сообщением «ошибка: …» (ожидается «приоритет не записан: … — запустите команду через sudo» или отказ в доступе к файлам XGW), код не 0; `panel.json` не изменился. Записать текст дословно |
| `sudo xgw priority <отпечаток F целиком> high` | «приоритет сервера «XGW-TEST-DEAD» уже высокий», код 0 |

Код — `echo $?` сразу после команды. Если у двух серверов подписок одинаковые имена — ещё
`sudo xgw priority <это имя> high` → «ошибка: «…» подходит нескольким серверам — укажите
тег или отпечаток», код 2. Нет таких — пропустить и написать об этом.
