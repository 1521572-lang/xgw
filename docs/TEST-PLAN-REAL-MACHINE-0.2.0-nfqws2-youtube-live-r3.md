# ThinkCentre. Один полный проход до работающего YouTube или установленной причины отказа

Ветка `gui-light`. CODE = `956db751d37e589879bc11f7205bdc5100b9be78`.
Предыдущий установленный модуль nfqws2 — `ad76983eadb2ebd6a8ffc32739895065d140e919`.
Основание — [отчёт r2, b729573](TEST-REPORT-REAL-MACHINE-0.2.0-nfqws2-youtube-live-r2-2026-11-14.md).
Это новое основное задание. Старые r1/r2 повторять целиком не нужно.
По прямому указанию владельца этот план расширен за прежний предел 200 строк.
Исполнитель проходит все применимые ветки сам, без отправки промежуточного FAIL разработчику.

## 0. Что требуется получить

1. Исправить обнаруженный повторный перехват пакетов nfqws2 самим XGW.
2. Найти работающий способ прямого доступа к странице и видео YouTube через zapret2.
3. Если первые стратегии не помогли, в этом же сеансе различить проблемы интеграции,
   сборки TLS, очереди, offload, конкретного адреса, клиента и собственно стратегии.
4. При успехе перенести минимальный вариант в штатный XGW, убрать диагностические средства
   и проверить 15 минут видео плюс 5 минут после перемотки.
5. При отсутствии успеха опубликовать результаты всех применимых вариантов и доказанный
   последний этап прохождения пакета. Конечный перебор не доказывает невозможность zapret2.

**Не путать результаты.** В r2 прошли все 26 модульных тестов. Отказала реальная загрузка
страницы. Теперь проверяем 28 тестов модуля и живой путь отдельно.
`verdict queue` без продолжения nft-trace не доказывает зависший элемент NFQUEUE.
nfqws2 законно возвращает NF_DROP после отправки заменяющих сегментов и при накоплении reassembly.
Размер ClientHello около 2 КБ не доказывает использование ML-KEM и меньше лимита сборки 16 КБ.
Ошибки Lua могут выводиться без debug. Debug нужен для решения по пакету и хода обработки.
Вывод r2 об отправителе разрыва соединения также остаётся гипотезой.

Порядок чтения: §§1–5 подготовка, §6 быстрый шанс на штатный успех, §§7–10 запасные ветки,
§11 видео, §12 интеграция, §§14–15 возврат и публикация. §13 — справочник ошибок самого ТЗ.

## 1. Полномочия, самостоятельность и организация сеанса

Модель сама читает код/логи, запускает команды, устанавливает подготовленные файлы,
открывает браузер, смотрит кадры через vision, использует DevTools и публикует итог.
При отсутствии терминала, root или окна браузера запросить соответствующий доступ.
Не просить владельца запускать скрипты или присылать скриншоты вместо работы исполнителя.
Владелец вводит пароль/подтверждает системный диалог, если это требуется платформой.
Использовать уже согласованный root-канал, не создавать второй при работающем первом.

Текущее задание разрешает описанные ниже временные настройки, диагностику, исправление
capture nft, штатное применение маршрута, краткое отключение offload с точным возвратом,
перебор через ограниченный launcher и минимальную интеграцию доказанного победителя.
Автопубликация ТЗ, отчёта и относящегося к этому результату небольшого исправления разрешена.
Подписки, основной VPN-сервер, LAN/Tailscale и общая политика доступа остаются исходными.
Прямые домены YouTube временно относятся ко всем клиентам шлюза. Универсальный движок
в штатной фазе обрабатывает и другие подходящие потоки. В лабораторной фазе Lua ограничена YouTube.
Не выключать перехват/kill switch, не останавливать Xray для создания «прямого интернета».
Не снимать sandbox браузера/worker, не выключать проверку сертификатов, не очищать весь conntrack.
Не обновлять дистрибутив, Xray, nfqws2 или пакеты в ходе подбора. Использовать имеющиеся инструменты.

Один проход означает одну связную работу с восстановлением и публикацией в конце.
Ориентир 2–4 часа. Успех завершает перебор, последующие ненужные строки получают SKIP_AFTER_PASS.
Лимит — 80 коротких сетевых попыток и до 3 длинных видео. Это потолок, а не обязательный объём.
Не строить полное произведение стратегий × адресов × offload × браузеров.
Один изменённый фактор за раз, максимум два одинаковых повтора при неоднозначном результате.
После каждого блока сохранять приватный checkpoint с последней строкой, текущими настройками,
PID, файлами отката и следующим действием. После смены контекста продолжать от него.
Если времени/доступа не хватило, восстановить машину, опубликовать PARTIAL/NOT_RUN с перечнем
незавершённых строк. Не отмечать их как проверенные отрицательно.

## 3. Исправление подтверждённого дефекта capture

nfqws2 добавляет к исходной метке бит `0x40000000`. При обычной метке Xray `0x2`
получается `0x40000002`. Старый capture output проверял только точное равенство `0x2`,
перезаписывал метку на mark_proxy и возвращал созданный пакет в Xray.
Защита от повторной очереди при priority 90 находилась позже capture priority −150.
CODE добавляет ранний обход capture по биту nfqws2 в IPv4/IPv6 и пропуск этих копий
через IPv6 guard. Исключения существуют только при включённом универсальном движке.

Заменить **только `src/xgw/net/nft.py`** установленного пакета файлом из CODE.
Оставить nfqws2.py из ad76983, сверить SHA с CODE (он в CODE тот же).
Если остальные установленные файлы отличаются от ожидаемых, проверить diff и совместимость.
Сохранить исходный nft.py, права root:root 0644, установить атомарно в том же файловом разделе.
Проверить импорт тем же PY, перезапустить только xgw.service, проверить HTTPS/HEALTHY.
При engine off новые исключения не должны появиться. PID Xray без необходимости не менять.

Включить engine auto на время проверки, дождаться worker/очереди и штатного обновления nft.
Если правила остались старыми, выполнить штатный `xgw enable`, поскольку capture исходно on.
Не останавливать xgw-net.service и не делать `flush ruleset`.
В загруженной цепочке `ip xgw output` должно быть до изменения mark:

```text
meta mark & 0x40000000 == 0x40000000 return
```

То же в `ip6 xgw6 output`, когда IPv6 capture включён. В v6_guard при его наличии —
соответствующий accept перед общим reject. Проверить off/blocked только по генерации,
не переводить рабочую сеть в blocked ради теста. Если условное правило не появилось,
сначала исправить установку/импорт/применение. Перебор Lua до этого бессмысленен.

## 4. Надёжное редактирование настроек и прямой маршрут

Каждую редакцию конфигурации готовить во временном файле рядом с CFG.
Сначала `tomllib.loads`, затем загрузка Config XGW из установленного пакета, просмотр warnings.
Сравнить распарсенные исходный/новый словари, разрешены только ключи текущего шага.
После этого chmod/chown как у CFG, fsync и os.replace. При ошибке исходный CFG не трогать.
Не дописывать повторную `[zapret2]` и не заменять весь `[routing]`.
Для переходов хранить одну проверенную базовую конфигурацию опыта, менять её копию,
а не накапливать sed-подстановки поверх предыдущих вариантов.
При multiline direct_domains работать с целым значением. Два синтаксических сбоя из r2
не являются причиной останавливать прогон, если кандидат проверен до замены CFG.

Добавить к существующему direct_domains четыре домена, сохранив остальные:
`domain:youtube.com`, `domain:googlevideo.com`, `domain:youtubei.googleapis.com`,
`domain:youtube-nocookie.com`. Дополнительный домен разрешён только когда Network
показал необходимый заблокированный запрос YouTube, записать причину и убрать при возврате.
Проверить applied JSON: страница и CDN идут в freedom/direct с mark_bypass перед VPN catch-all.
Убедиться, что media mode/частное правило/proxy_domains/kernel_direct не меняет этот путь.
Если правило перекрывается, временно исправить только конфликтующий YouTube маршрут,
сохранить исходное значение и отдельно записать изменение. Не выбирать другой VPN-сервер.
Если применение отложено из-за dns, разрешён `xgw apply --now`, затем снова HEALTHY/HTTPS
и applied JSON. Он может штатно перезапустить Xray — записать причину и PID.

Во всех B engine=auto, mode=off, одна свободная штатная engine_queue, временно acct=1.
До старта каждой строки подтвердить реально применённый argv, очередь и новый поток.
Профиль, выученный для VPN-сервера, может иметь приоритет над engine_profile.
Не засчитывать выбранный в TOML профиль, если argv другой. Использовать лабораторный
launcher (§7), который заменяет TLS-часть argv явно, вместо удаления истории VPN-профилей.

## 5. Короткая проба, одинаковая для всех стратегий

Один публичный ролик ≥30 минут с 1080p, без логина/возрастного ограничения/эфира.
URL выбрать и сохранить приватно. Не менять ролик только потому, что не открылась страница.
Доступность самого ролика можно проверить через обычный VPN в отдельном контрольном сеансе,
затем закрыть его. Его подписанные CDN-ссылки не переносить в прямой тест.

Браузер Chrome/Chromium от пользователя графической сессии. Каждая попытка с новым
user-data-dir, `--no-proxy-server --disable-quic`. DevTools Network, Disable cache,
видимое окно. Проверить chrome://version/процесс, что открылся именно новый экземпляр.
Не запускать root-браузер, не использовать --no-sandbox/--ignore-certificate-errors.
Cookies/вход/расширения основного профиля не нужны. После окончания закрывать только свой PID.

Одна короткая попытка:

1. Проверить worker active, effective argv, очередь, исходный контрольный HTTPS/VPN.
2. Свежий curl к странице, `--noproxy '*' --http1.1 --connect-timeout 8 --max-time 20`,
   приватный verbose с временными отметками. Не печатать его целиком в отчёт.
3. Свежий браузер, до 90 с на первые видеокадры, затем 60 с продвижения позиции при успехе.
4. Записать DNS/TCP/TLS/HTTP/страницу/первые кадры отдельно, protocol, effective strategy,
   reassembly, offload, IP-family и начальную/конечную позицию, не только exit-code curl.
5. Сверить здоровье VPN. При ухудшении вернуть последний рабочий набор до следующей строки.

curl и браузер имеют разный ClientHello. Ошибка curl не отменяет браузерную пробу.
HTTP 200/consent/капча/LOGIN_REQUIRED не равны воспроизведению. Ошибки UI и TLS различать.
Для отказа после загрузки страницы смотреть Network на googlevideo, а не повторять страницу.

## 7. Лабораторный launcher под управлением того же XGW

Использовать только если B1–B3 не дали полного успеха либо нужен debug.
Помощник `docs/helpers/nfq_lab.py`, SHA-256 `ac4a31634dea8907d842467027065cbf3af12639aca2f478561f108feff96073`.
Он не меняет файлы настроек, маршруты, nft, offload или systemd. Только проверяет root-owned
JSON и заменяет argv перед exec установленного nfqws2. Разрешены 15 фиксированных вариантов.
Очередью и жизненным циклом продолжает управлять XGW. Второй nfqws2 не запускать.
В лабораторной фазе только TLS/TCP443 и выбранные домены. QUIC/голосовые блоки исключены.
Префлайт `--intercept=0` сохраняется. Произвольный Lua, shell и незнакомые опции не допускаются.

В root-канале, после engine off и подтверждённой остановки worker/освобождения очереди:

```bash
# SOURCE — каталог source из §2, BIN/LUA определены по установленному bundle.
LAB=$(mktemp -d /run/xgw-nfq-lab.XXXXXXXX)
chmod 700 "$LAB"
install -o root -g root -m 755 "$SOURCE/docs/helpers/nfq_lab.py" "$LAB/nfqws2"
python3 - "$LAB/nfqws2.json" "$BIN" <<'PY'
import json, os, sys
from pathlib import Path
value = {"binary": str(Path(sys.argv[2]).resolve(strict=True)),
         "strategy": "pass", "reassembly": "standard", "debug": True,
         "domains": ["youtube.com", "googlevideo.com", "youtubei.googleapis.com",
                     "youtube-nocookie.com"]}
with open(sys.argv[1], "x", encoding="utf-8") as stream:
    os.chmod(sys.argv[1], 0o600)
    json.dump(value, stream)
    stream.flush()
    os.fsync(stream.fileno())
PY
```

BIN в JSON — настоящий бинарник, не launcher. Все его родители должны быть root-owned,
без group/world write и без symlink. Resolve выше делает реальный путь явным.
Проверить shebang /usr/bin/python3, import json доступен. Пакет XGW помощнику не требуется.
В CFG временно задать `zapret2.binary=<LAB>/nfqws2`, `lua_dir=<реальный LUA>`, engine_profile=seqovl.
Для лабораторной фазы явно задать `engine_offload=false` после остановки worker и возврата
его offload. Обученный disorder-badseq может иметь приоритет даже при engine_profile=seqovl:
Runtime меняет offload до exec launcher. Этот флаг исключает смешение факторов.
Начальные флаги сверить с исходным ethtool. Offload затем меняется только в ветви §10.4.
Существующий blob_dir сохранить. Сначала вручную вызвать префлайт с аргументами из
`xgw.nfqws2.arguments`, добавив `--intercept=0`, таймаут 15 с, приватный вывод.
Затем auto и штатное обновление правил. Runtime._check_files и sandbox не ослаблять.
Статус XGW может показывать seqovl как исходный селектор, **истинный вариант — JSON + argv worker**.
В `/proc/<MainPID>/cmdline` после exec должен быть BIN, нужный Lua-вызов, hostlist и debug.

Каждая смена JSON:

1. engine off, дождаться inactive и свободной очереди, сохранить предыдущий JSON.
2. Сформировать новый JSON во временном файле того же LAB, проверить через settings_check
   помощника, chmod600/chown root, fsync/os.replace. Редактировать только strategy/reassembly/debug.
3. engine auto, дождаться готовности, сверить cmdline. Не ожидать reload JSON в работающем процессе.
4. При ошибке вернуть предыдущий JSON и конфигурацию, не запускать ручной конкурирующий worker.

Debug включать только на окна 20–45 с, в остальном False. Вывод journald считать приватным,
не прикладывать целиком. Если debug уже большой, выгрузить только свой unit/временной диапазон,
выключить debug и продолжить. Не чистить системный journal.
При отказе helper проверить его безопасные пути/права и корректный JSON; сообщение нарочно
не содержит приватных значений. Для уточнения вызвать settings_check/build_arguments
от root с приватным stderr. Ошибка помощника не означает отказ стратегии.

## 8. Доказательство движения пакета до и после nfqws2

Старое окно priority89 не видело повторный перехват при −150. Новое начинается в OUTPUT
при −401 и захватывает исходную и составную метки. Ограничение — один IP страницы/CDN,
TCP443, время 45 с. Все наблюдения — на одном свежем потоке, время и кортеж приватны.
Найти IP свежим разрешением/Network, проверить что это публичный адрес целевого домена.
В root-канале перед запуском отдельного свежего браузера:

```bash
(
set -eu
T=xgw_trace_$$
TRACE_PID=
PCAP_PID=
cleanup_trace() {
    set +e
    if test -n "$TRACE_PID"; then kill "$TRACE_PID"; wait "$TRACE_PID"; fi
    if test -n "$PCAP_PID"; then kill "$PCAP_PID"; wait "$PCAP_PID"; fi
    nft delete table inet "$T"
}
nft create table inet "$T"
trap 'cleanup_trace' EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
nft -f - <<EOF
add chain inet $T early { type filter hook output priority -401; policy accept; }
add rule inet $T early ip daddr $DST tcp dport 443 meta nftrace set 1
EOF
timeout 45s stdbuf -oL nft -a -nn monitor trace >"$D/trace-$ID.txt" 2>"$D/trace-$ID.err" &
TRACE_PID=$!
timeout 45s tcpdump -ni any -s 0 -U -w - "host $DST and tcp port 443" >"$D/packets-$ID.pcap" 2>"$D/pcap-$ID.err" &
PCAP_PID=$!
sleep 0.3
kill -0 "$TRACE_PID" "$PCAP_PID"
printf 'TRACE_READY\n'
# Параллельно модель запускает свежий браузер в другом канале.
rc=0
wait "$TRACE_PID" || rc=$?
TRACE_PID=
test "$rc" -eq 0 || test "$rc" -eq 124
rc=0
wait "$PCAP_PID" || rc=$?
PCAP_PID=
test "$rc" -eq 0 || test "$rc" -eq 124
)
```

Для IPv6 заменить `ip daddr` на `ip6 daddr`; фильтр tcpdump принимает оба семейства.
Не подставлять имя хоста в nft. Если IP сменился — обновить цель и один повтор.
Свою таблицу удалить trap и проверить удаление, не затрагивать другие таблицы.
Файл pcap открывает root shell до запуска tcpdump. Это сохраняет umask077 и работает,
даже если tcpdump штатно сбрасывает UID, без -Z root/ослабления прав приватного каталога.
`any` нужен, чтобы отличить WAN от возвращения в lo/TUN. Если нет указания интерфейса
в доступном формате, параллельно взять узкие WAN/lo captures. Не считать отправку в lo выходом.
Если очередь ограничена первыми 8 пакетами, захват начинать до нового соединения.
При чтении исходящего pcap checksum-offload может давать видимость плохой суммы,
это само по себе не доказывает испорченный пакет на физическом канале.

Сопоставить:

- nft trace ID/кортеж → обычная mark_bypass → штатная queue;
- debug `packet id`, FULL/PARTIAL ClientHello, DELAY/REPLAYING, функция и pass/drop/modify;
- заменяющие пакеты → mark_bypass OR FAKE_MARK, ранний return capture, WAN;
- ответный поток WAN → рост bytes_received у того же сокета Xray;
- очередь `/proc/net/netfilter/nfnetlink_queue` до/после и kernel/user dropped при наличии.

ID из debug и nft trace — разные пространства, связывать временем и кортежем, не равенством чисел.
Различать verdict NF_DROP с успешной отправкой копий и реальное отсутствие обработки.
Если копии снова получили mark_proxy, вернуться к §3/§10.1. Не перебирать новые Lua.
Если есть bytes на WAN и ответы, перейти к стратегиям или уровню браузера.
Если данных нет, классифицировать по §10, а не объявлять «очередь поглотила» без debug.

## 9. Расширенная матрица стратегий

Сначала две контрольные строки. Их успех означает исправность прохождения пакетов,
а не обязательное открытие заблокированного сайта.

| ID | strategy | reassembly | Назначение |
|---|---|---|---|
| C0 | pass | standard | Без Lua-преобразований, контроль очереди и отправки |

Если C0/C1 не выпускают ClientHello, сначала §10.1–10.4. Не запускать 14 стратегий

В pass допустим обычный NF_ACCEPT без копий/fake-bit. Это контроль транспорта, не новая
стратегия обхода. No-op профиль в продукт не добавлять. При успехе off также BENEFIT=UNCONFIRMED.

## 10. Ветки устранения оставшихся причин в этом же проходе

### 10.1. Маркировка, повторный перехват, устаревшие правила

Сначала загрузить nft.py из CODE и штатно обновить правила. Проверить оба семейства,
реальный capture mode и наличие новой строки **в загруженной** цепочке до mark set.
Проверить другие ранние OUTPUT-цепочки и policy routing, которые могли менять/маскировать mark.
`ip route get <DST> mark <combined mark>` должен показывать ожидаемый WAN, не lo/TUN.
`mark_bypass` брать из CFG, не считать всегда равным 2. Бит fake брать из кода.
Не удалять чужие правила. Если виновато стороннее правило, сохранить его расположение
и ограничения. Исправлять в этом ТЗ разрешено только XGW-собственное правило.
При точной локализации другого XGW участка допускается узкая временная правка этого
участка с тем же условием engine enabled, проверкой nft -c и последующей интеграцией §12.
Глобальный accept, отключение защитной таблицы или изменение чужого VPN не являются решением.
Для проверки связи исправления с эффектом сравнить ранний trace до/после на свежих потоках,
не возвращать заведомую петлю на всю сеть ради A/B.

### 10.2. Права, реальный worker, сбой запуска, EPERM

Проверить MainPID, единичного владельца queue, argv, unit properties, доступность Lua/blob.
`unsafe_file` — восстановить root-владельца и убрать запись группы/остальных в своих файлах,
не chmod777. Ошибка поиска Lua — указать реальный lua_dir, сверить оба файла с bundle.
Таймаут/занятая очередь — дождаться остановки своего unit, проверить PID и только затем retry.
Чужой владелец очереди — выбрать свободную разрешённую очередь и применить её штатно.
Runtime + nft должны согласованно использовать один номер.
EPERM связать со временем и конкретным sendto, выводом kernel/audit при наличии и меткой.
Принятый firewall DROP может объяснять sendto EPERM; не снимать capabilities/sandbox наугад.
Если штатного CAP_NET_ADMIN/CAP_NET_RAW нет, выяснить фактический unit/launcher,
восстановить свойства из Runtime. Не запускать nfqws2 с расширенными привилегиями взамен.
Неоднократный crash — сохранить exit status/короткий traceback и перейти к C0/C1,
затем одному простому S03. Повтор того же crash без изменений не увеличивает доказательства.

### 10.3. Неполный TLS, лимит первых пакетов, очередь

Если debug показывает PARTIAL/DELAY без полного REPLAY, сопоставить seq/length продолжений
в tcpdump и количество пакетов обоих направлений. `ct packets <=8` считает весь flow,
а не только полезные исходящие данные. Проверить, не закончился ли лимит до хвоста ClientHello.
Разрешён один опыт с **узкой** дополнительной очередью для выбранного TCP-кортежа,
original direction, mark_bypass, исходящим WAN, `ct packets <=32`, priority91,
после штатного priority90. Включить source IP/port и destination IP/port,
чтобы другие клиенты того же CDN не попали в диагностический эксперимент.
Чтобы пакет не попал дважды, дополнительное правило должно содержать `ct packets >8`.
Исключить fake bit, loopback и local destination. Использовать отдельную свою nft-таблицу,
счётчик, timeout≤90 с и trap удаления. Штатные правила не заменять.
Убедиться, что это именно новые продолжения нужного потока, не массовые чужие соединения.
Если невозможно заранее получить исходящий порт Xray, использовать отдельную диагностическую
пробу через root Python socket с SO_MARK=mark_bypass: bind на WAN-адрес с port0, connect TCP,
сохранить getsockname(), поставить правило на известный кортеж, затем начать TLS с обычной
проверкой сертификата и server_hostname. Исполнитель выполняет оба этапа сам.
Это проверка транспорта с той же меткой, а не доказательство браузерного пути через Xray.
После результата всё равно нужен свежий браузер и штатная интеграция, один socket success не PASS.
Сравнить S03/S01 с теми же argv. Если улучшения нет — удалить таблицу, не увеличивать без конца.
Отдельно повторить C1 и S03 с reassembly=disabled. Если S03 помогает, проверить S01/S05
в таком же режиме. Не считать успех малого curl доказательством большого ClientHello Chrome.
При росте queue_dropped/user_dropped проверить нагрузку,debug-объём и живой worker.
Закрыть свои лишние браузеры/debug, один повтор. Размер очереди/буферы ядра глобально не менять.
Если конкретный дополнительный лимит помог, сохранить trace/точное правило для §12.

### 10.4. GSO/TSO/GRO, checksums и conntrack

Применять, когда debug/pcap показывает размер/сегментацию, способную объяснить сбой,
либо C0 исправен, а преобразованные копии не проходят после устранения recapture.
Сохранить полный текущий ethtool отдельно от исходного. Использовать имеющийся
`xgw.nfqws2.Offload` с явным WAN в отдельном root Python-сеансе и finally restore,
а его `interface`/`saved` сохранить в приватный JSON до опытов для аварийного возврата.
Offload отключает GRO/GSO/TSO/TX checksum, сверяет фактические значения и восстанавливает
зависимый tx-tcp-mangleid-segmentation. Не реализовывать неполный откат четырьмя on-командами.
Проверить fixed-флаги: on fixed — вариант неприменим, off fixed оставлять как есть.
Держать сеанс контроля открытым, таймер возврата активным. Выполнить S03/S01/S02,
при подходящей причине S06, затем вернуть весь снимок и проверить ethtool побайтно.
Если помогает только offload off, это отдельное необходимое условие, переносится через
штатный Offload lifecycle, а не через вечную команду ethtool вне XGW.

Если ранний trace показывает conntrack invalid/drop **составных копий**, разрешён
отдельный диагностический notrack только для fake-bit, одного DST, TCP443, OUTPUT priority−300
(до conntrack −200), не для всего Xray и не для исходного соединения.
Не добавлять его одновременно с offload-изменением. Свою таблицу удалить после двух проб.
Если это помогло, документировать NAT/маршрут: notrack может менять поведение NAT.
Нельзя оставлять его общим правилом без точного переноса и проверки ответного пути.
Глобальные tcp_loose/rp_filter/MTU и все conntrack-записи не трогать.

### 10.5. IPv4, IPv6, адрес, DNS, таймаут соединения

Если DNS не дал адрес — проверить действующий resolver, доступность DNS через штатный XGW,
отдельно домен страницы и реально выбранный googlevideo. Не менять DNS всей сети.
Выполнить curl -4. curl -6 — только если IPv6/WAN уже работают и разрешены текущими настройками.
Отказ -6 при network.ipv6=off не является отказом zapret2. Не включать IPv6 глобально ради строки.
Выбрать до двух актуальных публичных A/AAAA из ответа resolver, использовать curl --resolve
для того же hostname/443. URL/SNI/сертификат сохраняются. Не использовать случайные IP из интернета.
Сверить реальный удалённый адрес Xray, поскольку его DNS может отличаться от локального curl.
Фиксация --resolve клиентом за прозрачным Xray не гарантирует тот же upstream IP при sniffing.
Не засчитывать сравнение адресов, пока WAN-сокет не подтверждён.
При успехе только одного адреса повторить без фиксации на штатном браузере.
Для принятия нужна устойчивая работа с обычным DNS, временный pin обозначить ограничением.
Connect timeout до ClientHello исследовать как маршрут/адрес, Lua для TLS ещё не участвовала.

### 10.6. Отличающийся ClientHello, TLS 1.2/1.3, браузер

В том же прямом пути и с одним S выполнить дифференциальные curl-проверки:
обычный; `--tlsv1.2 --tls-max 1.2`; `--tlsv1.3 --tls-max 1.3`;
последний с `--curves X25519`, только если curl/TLS backend поддерживает.
Сначала проверить `curl -V`/`--help all`. Unsupported option — NOT_RUN этого варианта,
не изменение маршрута/стратегии. Проверку сертификата сохранить.
По debug или разбору ClientHello подтвердить actual handshake, не делать вывод из размера.
При успехе только без PQ/с малым ClientHello вернуться к §10.3–10.4.
Если имеется второй браузер, допустима одна проба в новом профиле с отключённым QUIC,
без изменения системных настроек первого. Chrome остаётся основным приёмочным клиентом.
Не придумывать флаг Chrome для отключения PQ: без проверки поддержки не использовать.
Работа только альтернативного клиента — PARTIAL, а не решение обычного YouTube в XGW.

### 10.7. Страница работает, видео/API/CDN не работает

Смотреть failed запросы Network. Различать TLS/timeout, HTTP403/429, CORS, consent,
playabilityStatus, ошибку декодирования и отсутствие сетевых видеоданных.
Подписанный CDN URL брать в том же прямом сеансе. Страница через VPN и CDN напрямую
могут дать отказ по привязке выхода, это не проверка одной стратегии.
Убедиться, что все необходимые домены страницы/API/CDN направлены одинаково, включая
наблюдённый redirect. Исправить только наблюдённый пропущенный домен, затем свежий профиль.
При 403 проверить срок URL/запрос из нового плеера. Не повторять протухшую ссылку.
При 429 ограничить запросы, один повтор после паузы, затем другой публичный ролик с отметкой.
При капче/входе не обходить проверку аккаунта, выбрать обычный публичный ролик.
Если страница и CDN требуют разных S, разрешена явная пара по hostlist в §12,
сохранить один прямой WAN-путь для обоих. Не использовать скрытый VPN fallback.
При выборе пары проверить два лучших S для googlevideo, а не все комбинации 14×14.

### 10.8. TLS проходит, но видео тормозит/останавливается

Зафиксировать quality, dropped frames, buffer, bytes, CPU и процессный memory/FD.
Если CPU занят debug/packet dump, выключить диагностику и один повтор того же качества.
Если пауза после перемотки, проверить новый CDN/соединение, первый ClientHello и маршрут.
Если сеть отдаёт данные, но кадры не движутся, проверить декодер/второй имеющийся браузер.
Понижение 1080p до 720p разрешено как отдельная характеристика, не замена критерия PASS 1080p.
Не менять основную подписку/сервер VPN, поскольку проверяем прямое видео.
Один сравнительный off-контроль отличает эффект nfqws2 от временного изменения линии.

### 10.9. HTTP/3 и QUIC

Основная приёмка по TCP, не вводить QUIC как ещё одну независимую неизвестную до успеха TCP.
После PASS TCP разрешена дополнительная проба обычного браузера без --disable-quic,
если действующая quic-политика это допускает. Лабораторный launcher QUIC не обрабатывает,
поэтому сначала вернуть штатный nfqws2 с отдельным QUIC-профилем.
При отказе HTTP/3 записать ограничение, проверить рабочий TCP fallback, не включать
новый глобальный режим QUIC/noise и не объявлять прежний TCP PASS несуществующим.
Полная независимость доступа от TCP/QUIC — отдельные вердикты, цель этого прогона TCP-видео.

## 11. Живое видео, путь туда и обратно, контроль off

Для короткого победителя выбрать свежий профиль и повторить без debug и лишних captures.
1080p при доступности, иначе 720p с явной отметкой. Посмотреть 15 минут от начала,
перемотать за границу фактического буфера (например 20:00) и смотреть ещё 5 минут.
Время рекламы не считать. На 0/5/10/15 минутах, после seek и в конце модель сама проверяет
движение кадров и currentTime, отмечает все остановки >2 с и качество.
Первые кадры≤90 с, возобновление после seek≤30 с, нет фатальной ошибки/паузы>30 с.

Привязка пути обязательна, но не требует 20 минут непрерывного pcap:

1. Network `videoplayback` с видео MIME/идентификацией трека, переданным из сети.
2. Новый TCP-кортеж Xray к тому же CDN на WAN, свежий TLS в очереди и неизменный direct.
3. Ранний trace §8 с mark fake и отправкой копий, при активном победителе.
4. Возвращающиеся медиабайты на том же WAN-сокете, рост bytes_received и новые данные после seek.
5. Если CDN сменился, повторить короткую привязку на новом соединении.

Для контрольного pass отдельная отметка NFQ_PASS, где debug показывает обычный NF_ACCEPT.
Отсутствие заменяющих пакетов там ожидаемо, такой контроль не выдавать за desync-стратегию.

Ответные байты не обязаны попадать в NFQUEUE: обработка исходящего ClientHello может
обеспечивать весь последующий TCP-поток. «Туда и обратно напрямую» доказывает WAN-сокет,
а участие zapret2 — его исходящая обработка. Не требовать fake для каждого медиасегмента.
Не использовать сумму NFQUEUE всех клиентов как доказательство одного видео.
При желании сверить очередь через прежний read-only `nfq_video_trace.py` из PLAN,
SHA `d157e31a79ad96fccf69ff9e66866b8b0d724202a504f8d3ef738e6f40dab4a2`.
Он пригоден для штатной цепочки nfq_output. Дополнительную диагностическую очередь §10.3
он не распознаёт, там вручную проверить trace ID/кортеж/реальное правило и явно указать это.

Если A0 отказала, после успешного B выполнить A2 engine off с тем же direct и свежим
профилем≤90 с. Если отказ вернулся, включить победителя и повторить короткий B2.
Если A0/A2 тоже играют, прямой путь доказан, преимущество zapret2 UNCONFIRMED.
Проверка при включённом остальном VPN доказывает отсутствие VPN **у YouTube**, но
не поведение всего XGW при остановленном Xray/VPN-сервисе. Так и записать.

## 12. Перенос победителя в штатный XGW в этом же проходе

Если победил уже имеющийся профиль без дополнительных условий, вернуть реальный BIN/LUA
в CFG, убрать launcher, engine_profile=<победитель>, выполнить короткий повтор.
Длинный 20-минутный прогон засчитывается штатному пути, если был выполнен уже без launcher.

Если победил новый вариант, не заканчивать отчётом «через помощник играет».
В отдельном чистом worktree от свежей gui-light сделать минимальную правку:

- конкретный именованный профиль в nfqws2.PROFILES/arguments с точными сработавшими Lua;
- для пары page/CDN — два явных TLS-блока hostlist с --new перед прежними UDP-блоками;
- reassembly/offload-условие только для этого профиля, без произвольного shell/Lua в config;
- при необходимом offload использовать существующий lifecycle Offload и точный откат;
- при доказанной нехватке пакетов — ограниченный, объяснимый критерий очереди,
  не глобально безлимитная обработка; сохранить original/fake/loop protection;
- если помог узкий notrack, отдельно проверить границы, NAT и отключение при engine off;
- автоматическую лестницу VPN и engine=off по умолчанию не менять.

Добавить только регрессионные тесты найденного условия, запускать затронутый набор/Ruff
на реальной машине. Не переписывать подсистему, UI или vendored zapret2 ради этого прогона.
Если минимальный перенос требует существенно более широкой архитектурной правки,
сохранить проверенный patch-кандидат и точные данные, вернуть штатный код, итог PARTIAL.
Не объявлять экспериментальную обёртку готовым режимом утилиты.

Для малого исправления: сохранить модули, установить их, один restart демона, штатное
применение правил. Проверить правильный argv без LAB-пути, здоровье, реальный WAN,
короткий старт и полный 15+5 прогон. Только это даёт UTILITY=PASS новому варианту.
Предел 3 длинных видео оставляет место сравнению и повтору после интеграции.
Публиковать этот минимальный продуктовый diff и его тесты отдельным коммитом, затем отчёт.
В отчёте точный FIX_SHA, SHA установленных модулей и диагностические условия, снятые к финалу.

## 13. Ошибки выполнения самого ТЗ — исправлять на месте

| Ошибка | Действие исполнителя в этом же проходе |
|---|---|
| Терминал/root/vision недоступны | Запросить доступ, продолжить самому, owner не запускает скрипт |
| git worktree/add конфликтует | Новый уникальный приватный каталог, не удалять чужой worktree |
| Импорт тестирует старую версию | Проверить sys.executable/__file__/PYTHONPATH/cwd, указать нужный пакет |
| У сервиса нестандартный launcher | Прочитать его, воспроизвести путь пакета тем же PY |
| Нет pytest/Ruff | Найти уже установленное окружение; иначе NOT_RUN конкретного инструмента |
| pytest subtests отличаются числом | Оценить реальные failed/error, не только итоговое количество |
| TOML синтаксис/дубли секции | Отменить candidate file, собрать от снимка, validate до замены |
| Нет nfqws2/Lua/права | Проверить реальный bundle и secure paths, не скачивать новый |
| --intercept=0 висит | Проверить, что launcher сохранил флаг, timeout15 с, engine off до исправления |
| Очередь занята своим старым worker | Дождаться штатной остановки, проверить PID/unit, затем один retry |
| Worker жив, профиль не тот | Проверить effective argv, обученный приоритет, использовать §7 |
| Rules/module не обновились | Проверить installed SHA, restart только демона, штатный enable |
| Applied JSON ждёт окна dns | xgw apply --now, записать restart/PID, проверить здоровье |
| Helper пишет invalid settings | Проверить JSON/enum/root600/realpath, не ослаблять защиту helper |
| nft неизвестный синтаксис | nft -c на отдельном файле, адаптировать синтаксис по местному man/help |
| Слишком много trace/debug | Один DST/свежий поток/45 с, выключить debug после окна |
| Нет tcpdump/tshark | Использовать имеющийся инструмент; при отсутствии trace+debug+ss, путь PARTIAL |
| Неизвестный TLS-флаг curl | Проверить backend/help, строка NOT_RUN, браузерную часть продолжить |
| Новый браузер ушёл в старый профиль | Проверить PID/user-data-dir/chrome://version, открыть заново |
| Ролик закрыт/удалён | Зафиксировать, выбрать публичный аналог и повторить контроль+опыт |
| Нет свежего CDN в capture | Сверить Network/IP, одно новое окно, не считать отсутствие пакетов отказом |
| Offload restore не совпал | Прекратить перебор, восстановить включая mangleid, сверить полное чтение |
| SSH/root-канал потерян | Использовать установленный возврат, восстановить доступ, продолжить с checkpoint |
| GitHub push non-fast-forward | Сохранить свои коммиты, fetch, перенести на свежую ветку, обычный push |
| GitHub auth/network отказал | Запросить доступ при необходимости, отчёт сохранить локально, не заявлять push |

Не считать внешнюю ошибку инструмента доказательством неработоспособности стратегии.
При восстановимом сбое исправить причину и продолжить следующую ветку, сохранив наблюдение.
При невосстановленном сетевом сбое приоритет — возврат машины, затем публикация имеющихся данных.

## 14. Возврат машины и финальные критерии

Перед возвратом закрыть только свои браузеры, выключить engine штатно, подтвердить
inactive worker и свободную очередь. Вернуть CFG/panel.json с правами, acct, offload.
Удалить только свои диагностические таблицы, правила, timers/units и LAB после остановки.
Применить исходный маршрут, если отложен — apply --now. Проверить applied JSON, не только CFG.
Сверить отсутствие временных direct-доменов/LAB-путей, ожидаемую исходную очередь/режим,
полный ethtool, обычный VPN/HTTPS/панель и HEALTHY. Записать все изменения PID.
Исправление capture из CODE оставить при отсутствии регрессии. При регрессии вернуть
резервный nft.py, restart демона, штатное обновление правил и повтор контроля.
Новый доказанный профиль из §12 можно оставить установленным, но вернуть исходное engine off,
если постоянное включение отдельно не выбрано владельцем. Не держать debug/capture в фоне.
При сравнении правил учитывать динамические счётчики/handles, а не требовать равенства чисел.
Данные и worktree сохранять приватно для разбора. Не удалять единственные доказательства перед отчётом.

| Вердикт | Условие |
|---|---|
| TRANSPORT=PASS | Конкретный ClientHello обработан, копии на WAN, ответы наблюдаются |
| PLAYBACK=PASS | Полный 15+5 прогон при заданном качестве и временных пределах |
| DIRECT=PASS | Страница/API/видео одним прямым WAN-путём, VPN outbound не использован |
| NFQ_VIDEO=PASS | Очередь/обработка связана с конкретным новым медиасоединением |
| BENEFIT=OBSERVED | Повторённый отказ off и успех on при одном direct/клиенте |
| UTILITY=PASS | Победитель принят без launcher/временных nft-таблиц, в штатном XGW |
| RESTORE=PASS | Исходная сеть/конфиг/offload восстановлены, кодовый итог явно указан |

Итог PASS требует PLAYBACK/DIRECT/NFQ_VIDEO/UTILITY/RESTORE=PASS.
Неполная доказательная привязка, только экспериментальный вариант или другой клиент — PARTIAL.
Все применимые варианты корректно исполнены и не заработали — FAIL с последним установленным этапом.
Недоступные обязательные условия — NOT_RUN, а не FAIL обхода. Сбой возврата указывать отдельно.

модульные проверки, качество/длительность/перемотку, конечные вердикты и восстановление.
Допустим подробный отчёт на несколько страниц, прежний предел одной страницы здесь снят.

При конкурентных коммитах сохранить свой результат, перенести на свежую ветку без force push.
