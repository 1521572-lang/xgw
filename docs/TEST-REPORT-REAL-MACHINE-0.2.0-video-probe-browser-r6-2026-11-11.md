Наблюдения для разработчика (факты без догадок о сервере):

1. Паттерн стабилен между прогонами: r5 — один кандидат 200/31 байт; r6 — два разных
   кандидата, оба 200/31 байт. Голый повторный GET (даже с `Range: bytes=0-16383` и UA

   Timing нужен исходный контекст запроса плеера (встроенный в URL параметр `range`,
   последовательность сегментов `rn`, или иные заголовки/токены), иначе отдаётся заглушка.
2. Просьба: в `ATTEMPT` записывать индекс кандидата и его `transferSize`/`decodedBodySize`
   из Resource Timing (числа, без URL) — сейчас отличить попытки в квитанции нельзя.
3. Предложение на r7: выбирать кандидата с наибольшим `transferSize` (реальный медиа-сегмент,
   а не служебный), и/или повторять запрос с тем заголовком Range, который использовал сам
   плеер (он виден в performance entry как часть URL либо из transferSize против
   decodedBodySize). Оба варианта не требуют изменения шлюза.
