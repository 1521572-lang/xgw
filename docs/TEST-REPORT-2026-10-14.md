## 3. Методика

1. **Модульные тесты** — как в README, дважды: без Xray и с `XGW_XRAY_BIN` (включает интеграционные тесты с живым ядром).
2. **Стенд** (`tests/stand`) — под root: loopback и netns, настоящие Xray, nftables, dnsmasq, три пространства имён; сеть хоста не затрагивается.
3. **«Одноразовая машина»** (`tests/stand/test_machine.py`) — контейнер `systemd-nspawn`, корень — оверлей поверх корня хоста, `xgw install`/`uninstall` целиком на настоящих systemd и NetworkManager.
4. **Живой шлюз** — установка на эту машину с настоящими подписками, затем: проверка выхода через VPN по внешнему IP, DNS-перехват, `disable`/`enable`, имитация перезагрузки по порядку systemd, экспорт журналов, полное удаление со сверкой «до/после».
5. **Пробы подписок** — `xgw probe --all` по всем узлам обеих подписок с классификацией OK/SLOW/FROZEN/CONNECT_FAIL/TIMEOUT.

Все проверки включения перехвата выполнялись скриптами с **автоматическим откатом**: если интернет не отвечает, скрипт сам вызывает `xgw disable`.

## 5. Дефекты

### D1 — КРИТИЧЕСКИЙ: при включении перехвата машина теряет интернет целиком

**Суть.** Правила перехвата грузятся по новому конфигу сразу, а Xray продолжает работать со старым, если изменение затрагивает inbounds: демон откладывает перезапуск до окна `apply.restart_window` (по умолчанию **04:00–05:00**). В старом конфиге нет inbound'а `tproxy-in`, поэтому все пакеты машины уходят на `127.0.0.1:12345`, где никто не слушает. При `fail_mode = "closed"` это полная потеря связи — при внешне исправном интерфейсе (адрес, маршрут, DNS-сервер на месте).

**Как воспроизвелось (дважды).**

1. Правка `[capture] lan/local = true` в `/etc/xgw/config.toml` при живом демоне:

```
00:03:57 xgw.daemon: apply: изменение настроек: применено с перезапуском…   ← после правки
22:29:40 xgw.daemon: apply: изменение настроек: нужен перезапуск Xray —
         отложен: секция burstObservatory; основные inbounds (ожидание окна 04:00-05:00)
```

`/etc/xgw/xray/config.json` при этом не менялся с момента установки (22:22:55) и **не содержал** `tproxy-in` — проверено разбором файла; при этом правила перехвата были загружены, `capture.json` хранил выбор, а `xgw-net.service` при каждом старте поднимал режим `on`:

```
22:41:02 xgw[590]: правила сети загружены, режим on
                  Перехват: включён — сеть enp4s0 и эта машина
```

Итог: после перезагрузки сеть умирала снова, пока службы не были остановлены.

2. Тот же путь достижим и из **основного сценария README**: установка без подписок (перехват не включается — «подписок пока нет»), затем добавление подписки в панели и нажатие большой кнопки. Демон применит конфиг с inbound'ом, отложит перезапуск до 04:00, а кнопка загрузит правила → та же чёрная дыра.

**Последствия.** Машина без интернета до 04:00; `xgw disable` помогает до перезагрузки, после перезагрузки состояние повторяется, потому что `xgw-net.service` грузит режим `on` раньше Xray.

**Внесённая правка (в этом репозитории):**

1. `net/capture.py` — предохранитель: режим `on` не загружается, если в **применённом** конфиге Xray нет inbound'а перехвата на `capture.tproxy_port`. Вместо перехвата грузится `off` (сеть работает напрямую), в журнал и в уведомление идёт понятная причина, `xgw status` показывает «Перехват: НЕ ВКЛЮЧЁН…».
2. `apply/applier.py` + `daemon.py` — изменение inbound'а перехвата **не откладывается**: перезапуск Xray выполняется сразу, в том числе для уже отложенного конфига (`pending`), а не «в окне».
3. `actions.enable` — если перехват не загрузился из-за отсутствия inbound'а, команда возвращает ошибку с подсказкой `sudo xgw apply --now`, а не бодрый отчёт «перехват включён».
4. Тесты: 3 новых (`test_net.py` — отказ при отсутствии/битом конфиге и включение после его появления; `test_applier.py` — немедленный перезапуск вне окна), плюс `tests/fakexray.py` — общий помощник: тестовые заглушки теперь пишут применённый конфиг Xray, как это делает `Applier` на живой машине (раньше они включали перехват вообще без конфига — из-за этого дефект и не ловился тестами).

**Проверено после правки:** перехват включается, внешний IP меняется на VPN, имитация перезагрузки проходит без вмешательства (раздел 4.5).

### D2 — ВЫСОКИЙ: не проверяется пересечение подсети LAN с подсетью WAN

`lan_address` по умолчанию — `192.168.50.1/24`, а на этой машине **WAN сам находится в 192.168.50.0/24** (шлюз провайдера — 192.168.50.1). Установка с настройками по умолчанию подняла бы `192.168.50.1/24` на `enp4s0`, то есть вторую карту в ту же подсеть с адресом, который уже занят роутером: конфликт адреса, неоднозначная маршрутизация, сломанный DNS для устройств. Ни `diag`, ни установка этого не замечают — проверок на пересечение нет ни в `install.py`, ни в `diag.py`. В отчёте тестирование велось с `192.168.60.0/24`.

### D3 — ВЫСОКИЙ: `probe.url` по умолчанию недоступен → детектор «заморозки» молча не работает

`https://speed.cloudflare.com/__down?bytes=65536` отдаёт **403 и напрямую, и через VPN**, если User-Agent не браузерный:

| Запрос | Результат |
|---|---|
| Python-urllib (без UA) | 403 |
| Chrome UA (через VPN) | 200, 65 536 байт, 0.56 с |

Xray-овский `burstObservatory` ходит как `Go-http-client/1.1` (строка есть в бинарнике, своего UA проект не задаёт), пробы самого XGW — как `xgw/0.1`. В журнале Xray это видно как `error ping … io: read/write on closed pipe` и `context deadline exceeded` **для каждого узла**. То есть на этом провайдере штатный URL проб не работает, и вся заявленная функция — переключение по «заморозке» — тихо не работает; живые узлы при этом помечаются мёртвыми, а демон бесконечно планирует замены.

Рабочие замены, проверенные и напрямую, и через VPN (без браузерного UA): `cdn.jsdelivr.net/npm/moment@2.29.4/min/moment.min.js` (58 103 Б), `cdn.jsdelivr.net/npm/jquery@3.7.1/dist/jquery.min.js` (87 533 Б), `cdnjs.cloudflare.com/...`, `proof.ovh.net/files/10Mb.dat`. В тестировании использовался `moment.min.js`: он укладывается в суточный бюджет (~850 МБ против лимита 1024 МБ), тогда как 87.5 КБ дают ~1261 МБ и предупреждение `budget`.

### D4 — СРЕДНИЙ: нет состояния «все пробы падают по одной причине»

У XGW есть `DEAD`/`ALL_DEAD` для узлов, но нет распознавания «не работает сам probe.url». На этой машине 4 участника из 5 были отброшены/мертвы, и демон каждые ~30 с выполнял «замена участника» — без подсказки человеку, что причина не в узлах. Хорошая проверка для `diag`: «все узлы падают на `probe.url` с одинаковым кодом/ошибкой — проверьте `probe.url`».

### D5 — СРЕДНИЙ: суточный бюджет проб трудно оценить заранее

`diag` считает `~944 МБ/сут при 5 участниках` для тела 64 КБ. Формула заметно чувствительна к размеру тела (58 КБ → ~850 МБ, 87.5 КБ → ~1261 МБ), а лимит в 1024 МБ — только предупреждение. При подписке с квотой (у многих тарифов 100–200 ГБ/мес) пробы съедают из неё около 1 ГБ/сутки — это стоит явно показывать в панели, а не только в `diag`.

### D6 — МЕЛКИЕ наблюдения

- Узлы с неразрешимыми доменами (`*.aib2bsas.online`) остаются в списке запасных и тратят пробы; сводки «отброшено N узлов, схлопнуто M дублей» нет ни в панели, ни в `status`.
- При `fail_mode = "closed"` окно без интернета на старте (правила грузятся до Xray) — по замыслу, но на настольной машине это заметно: стоит документировать выбор `open` как вариант для рабочей станции.
- Xray печатает предупреждения об устаревании (Shadowsocks, WebSocket, `host` в headers) — шум в журналах на стенде.
- `nmcli connection migrate` на NetworkManager 1.46 отчитывается об успехе, но профиль остаётся в `/run` — к XGW не относится, но мешает восстановлению сети руками (проверено при аварийном восстановлении).

## 6. Ограничения проверки

- **LAN-устройство не проверено на живой машине.** Попытка поднять «устройство» как macvlan поверх `enp4s0` внутри сетевого пространства имён упирается в ограничение ядра: macvlan не может общаться с родительским интерфейсом, а dnsmasq шлюза слушает именно `enp4s0` — DHCP-запрос не доходит. Для честной проверки нужен физический второй аппарат (телефон/роутер в режиме точки доступа) — это ровно тот пункт чек-листа README, который остаётся за владельцем.
- Не проверялись: Telegram с настоящим токеном, провайдер с IPv6, PPPoE, соседство с Docker, сама Ubuntu 26.04.
- Проверки «одноразовой машины» требуют, чтобы на хосте **не было установлен XGW**: контейнер — оверлей поверх корня хоста, и установленные `/etc/xgw`, `/opt/xgw`, `/var/lib/xgw` ломают проверки «первый запуск». Это стоит дописать в README (см. раздел 7).
- Правка дефекта не проверялась на `capture.method = "tun"`: там та же природа риска (правила ведут трафик в интерфейс, которого у ядра нет), но предохранитель пока смотрит только на `tproxy-in`.

## 7. Рекомендации

**По коду**

1. **Принять правку D1** (предохранитель + немедленный перезапуск при изменении inbound'а перехвата + честный ответ `xgw enable`). Это единственный найденный дефект, который оставляет машину без связи.
2. Распространить предохранитель на TUN: не включать `capture.method = "tun"`, если в применённом конфиге нет `tun-in`.
3. Добавить в `diag` проверку пересечения `lan_address` с подсетью WAN и с адресом шлюза по умолчанию (D2) — с понятным советом поменять `lan_address`/`dhcp_range`.
4. Добавить в `probe` возможность задать User-Agent и/или сменить `probe.url` по умолчанию на адрес, который отдаёт >20 КБ без браузерного UA (D3); в `diag` — проверка «все узлы падают одинаково — похоже, недоступен probe.url».
5. Распознавать состояние «все пробы падают по одной причине» (D4) и не крутить замену участников бесконечно, а один раз сказать человеку.
6. Показывать суточный расход проб в панели и учитывать его в квоте (D5).

**По документации**

7. В README: перед прогоном `tests/stand/test_machine.py` машина должна быть **без** установленного XGW (иначе оверлей видит `/etc/xgw` и проверки «первого запуска» падают) — либо стенду стоит маскировать эти пути.
8. Описать, что включение перехвата требует перезапуска Xray с inbound'ом и что до правки это откладывалось до `apply.restart_window`; для рабочей станции рекомендовать `fail_mode = "open"`, чтобы короткое окно на старте не оставляло машину без сети.
9. В чек-лист ручной проверки добавить пункт «сверить, что `lan_address` не пересекается с сетью провайдера».

**По эксплуатации (для этой машины)**

10. Подписка: участники балансировщика выбраны неудачно (3 не проходят TLS, 1 «заморожен»). Стоит либо отключить их в панели, либо поднять `filters.max_members`, чтобы балансировщик выбрал живые узлы из 50 работающих запасных.
11. `probe.url` заменить на рабочий (см. D3) — иначе переключение по «заморозке» не работает.

## 8. Приложение: как воспроизвести

```bash
# модульные тесты (в том числе с живым ядром)
python3 -m venv .venv && .venv/bin/python -m pip install -e ".[dev]"
XGW_XRAY_BIN=$PWD/tools/xray/xray .venv/bin/python -m pytest tests/ -q
.venv/bin/python -m ruff check src tests

# стенд: loopback + netns (root), сеть хоста не затрагивается
sudo -E XGW_XRAY_BIN=$PWD/tools/xray/xray .venv/bin/python -m pytest tests/stand -q

# «одноразовая машина» (нужны root, systemd-container; на хосте НЕ должно быть XGW)
sudo apt-get install -y systemd-container
sudo -E XGW_XRAY_BIN=$PWD/tools/xray/xray .venv/bin/python -m pytest tests/stand/test_machine.py -q

# живая установка
sudo xgw install          # или sudo sh packaging/install.sh
sudo xgw diag; sudo xgw status
sudo xgw enable           # перехват; sudo xgw disable вернёт прямой интернет
sudo xgw uninstall        # полный откат
```
